# Working a Metaform ticket

Report each finished step on the ticket as you go with `metaform map work op=step id=<id> said="..."`, and close with `op=done resolution="..."` only after the acceptance checks pass. Each step's `said` names what changed, why, and what was left out and why.

- Help syntax: the help command takes the module first, then the verb: `metaform help map work`, `metaform help map knowledge`. `metaform map help knowledge` fails with "Error: map has no verb help."
- Reading a node: `metaform map where <address> full=true` prints labeled lines (`provides:`, `receives:`, `work:`, `layers:`, `past_work:`), each followed by one JSON value. Split each line on its first colon before parsing. Open work on one join: `metaform map work receiver=<r> provider=<p>`. Join ids are read from the element's `provides:` line in `map where <element> full=true`; `metaform map where join:<id>` returns no output, so do not use it to read a join.
- Memory list arguments: `metaform memory open_nodes '{"names":[]}'` returned empty results with the notice "names is an array; what was sent was kept as its one member", so the object was not read as the list. Pass a bare JSON array of names. This is inferred from the notice; confirm with `metaform help memory` before relying on it.
- Named inputs may be stale: before relying on a path the ticket cites, confirm it exists (Read, or `ls`/`test -e` on the absolute path). A missing file is a stale premise: say so in the step and carry on with the files that do exist. Bash `cd` persists between calls, so use absolute paths for files under `artifacts/`.
- Yielding with the ticket open: before ending a turn while the ticket is open, including while background reader agents are still running, run `op=edit note=...` so the note says what has run, what is pending, and what has been written. Do not rely on a promise in the chat reply to carry that state.

- Shared spec records: when sibling tickets are editing the same spec record, do not fold its stacked amendments into the body. Edit only your own lines, and name the unmerged amendments in the step so the separate spec pass can settle contradictions.
- Stale memories: when your change makes a stored memory false, delete that observation with `memory delete_observations` and add the correction with `memory add_observations` in the same step. Then record the new facts at the ticket's node with `memory create_entities`. Copy the stale observation's exact text from `memory open_nodes` into the delete call; never use `delete_observations` as a probe with a guessed or shortened string, because it reports success even when it removes a still-true line. If one is removed by mistake, add it back word for word in the same step and say so.
- Read before you write memory: `metaform map where <address> full=true` prints one `key: <json>` line per field, and its `memory:` line holds the entities and their observations at that node. Check that output for an existing observation before adding one, so a node does not collect duplicates of what a sibling already recorded.
- Memory JSON from the shell: observations often contain apostrophes, which end a single-quoted argument. Put the JSON in a heredoc: `E=$(cat <<'EOF' ... EOF)`, then `metaform memory create_entities "$E" node=<node>`.
- Decisions the ticket does not own: when a step needs wording or a choice that belongs to the person (an authored prompt, a policy), ship it gated off: the authored element stays empty and an empty element turns the feature off. Keep the ticket open rather than `op=done`, and put the pending decision, with its draft and open issues, in the ticket note with `op=edit note=`.
- codebase-memory from the shell: passing a raw JSON argument to `~/.local/bin/codebase-memory-mcp cli <tool>` is deprecated and warns on every call. Use the tool's flags (`cli <tool> --help` lists them), `--args-file <path>`, or piped stdin. A ticket that quotes `'<json args>'` should be followed with flags.
- Tests: run only the filtered tests you wrote, for example `uv run pytest <file> -k <name> -q`. Report pre-existing type-checker errors as outside your change, with their line numbers.
- Running tests from a dispatched agent: the agent's runner sets `METAFORM_ROLE`, `METAFORM_SESSION`, `METAFORM_WORK` and `METAFORM_NODE`, so a worker's test that writes a ticket is refused for the wrong reason. Test homes must clear all four (the conftest home fixture does this); a test that needs a role sets it through the command's `env=`.
- Fixtures that seed tickets: assert that your ticket is in the result (membership), not that the result equals a single item, because the shared fixture already holds a ticket.
- Authority changes: when a change alters who may write or stop, test both sides with one happy path (the held role is refused and the person's or system's write goes through) and report what the page still allows, since the page is checked separately.

- Named files: a ticket that names a file without its folder is not proof of absence. Locate it with Glob or `ls -R` under the repo before calling it missing, and record the path you found in the step.
- Read the ticket back after a write: if `op=plan` (or any write) returns the ticket node without the recorded line, run `metaform map where <address> full=true` or `op=edit note=` to confirm the write landed before relying on it. Do not assume a plan was stored because the call returned without error.

## Source-pass tickets (code read against element joins)

A source pass records how code realizes each purpose join an element provides. It changes no code and never edits the map; the map's statements are the person's.

- For each join, find the realizing code with codebase-memory, then read it as a critic against the join's purpose and ef. Check coverage and read any missed range directly before relying on it.
- Record each seam with `metaform map knowledge op=add-item layer=sources node=join:<id>`, with refs only for the functions that carry the purpose. Pass `value` as a JSON object with `realized_by`, `read_with` and `on` (the date), and pass `refs` as a JSON array of `[key, value]` pairs: `["path", "src/..."]` for files and `["qn", "<full qualified name>"]` for functions, using the full name codebase-memory returns. Build both in a heredoc or a small script file, not inline quotes, because the JSON carries quotes and parentheses.
- A purpose with no code under it: open a held gap at the join with `metaform map work op=add receiver=<r> provider=<element> held=true condition=missing note=<what is absent and where you looked>`. Code that does not do what the join says: a held task at the join naming file:line. Code under the element that serves no join goes in the resolution.
- Dispatched workers cannot open held work: when `METAFORM_ROLE` is set to a worker, `map work op=add` is refused with "A worker agent writes no ticket". Then put each gap in your own ticket's note with `metaform map work op=edit id=<your work id> note="..."`, one line per gap with its file:line, and say in the step that the held tasks await the person or the orchestrator. Do not retry the add. Workers can still write sources items (`metaform map knowledge op=add-item`) and memory (`metaform memory create_entities`); only tickets are refused. Check `echo $METAFORM_ROLE` before the first gap write, so the held-work add is never attempted.
- Before writing a gap, read open work at that join (`metaform map work receiver=<r> provider=<p>`); if a sibling has already recorded it, do not duplicate it.
- Reader subagents: every brief says change no file, write no map or memory, run no tests, and report back. Their results are not yours until you have read them and recorded them; while they run, keep the ticket note current. Before you record or relay a reader's gap, re-read its cited file:line range yourself with `sed -n` and record only what you have seen there; a reader's claim that a gap exists is a lead, not a finding.
