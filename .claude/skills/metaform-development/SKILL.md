# Changing Metaform

Read the one subfile for the class of work you are in before editing. Each rule came from a real defect in this repo.

## Tickets and source passes
Reading a work record: run `uv run metaform map work id=ADDRESS#N --json` (or `id=WORK_ID`) and read the fields the record has: `done`, `held`, `resolution`, `task`, `note`, `taken`, `taken_by`, `said`, `steps`, `steps_done`, `map`, `dispatch`, `orchestration`. A `node=` list read wraps its records in `results`, and a list may hold several records. An `id=` read returns the one record itself with no `results` key, so `['results'][0]` raises KeyError on it; check the first line or the top-level keys before indexing. The record has no `state` or `column` field: reading one returns None and looks like a missing ticket, so use `done` (a timestamp when closed) and `held`. A ticket closed as a duplicate has `done` set and a `resolution` starting "Duplicate of ..."; read `resolution` before assuming the work was dropped. Pipe through `python3 -c` with `r.get(k)` for only the keys you need, so the output stays short. Do not put `2>&1` on a `--json` read before a `json.load` pipe: on 2026-10-19 `uv run metaform map work id=code.interface.graphical#150 --json 2>&1 | python3 -c "import json,sys;d=json.load(sys.stdin)..."` failed with `Expecting value: line 1 column 1 (char 0)`, and the same record read without the pipe printed plain `key: value` lines. Run the read once without the pipe, look at its first line, then parse only what the output actually is.

A launch packet or resume notice carries the ticket's note as it stood when the packet was built. After an `op=edit note=`, the packet can still show the old text, so before acting on a note from a packet, read the stored note with `map_work` and act on that. On 2026-10-19 a relaunched implementer's packet still carried a follow-up paragraph that had been removed from the stored note moments earlier. Report each step with its own `metaform map work op=step` (one note over steps 3 to 6 left the board at 5 of 8; on 2026-10-14 the notes "Steps 5-6" and "Steps 7-9" left it at 4 of 9, so count per step, never a range), and close with `op=done` only after the acceptance checks pass. `op=plan` takes only a step count and drops its `said` text, so write the numbered plan into the first `op=step` or into `op=edit note=`, then read the ticket back to confirm it landed. Plan the count you will actually reach before the first `op=step`: a step numbered past the planned count is still recorded, but the answer says `Notice: steps: Step 8 is beyond the 7 planned`, which means the plan was wrong. `op=edit note=` replaces the whole note, so send the current note text with the addition at its end, never the addition alone: read it first with `uv run metaform map work id=ID --json`. When a fix lands that closes an item a ticket's note still lists as open (a crash, a gap, a failing case), edit that note in the same pass so it says which items remain; the next reader must not chase a closed one. On 2026-10-19 the crashes once noted on code.router.assignment#13 were fixed by a follow-up to code.system.management.knowledge#39, and the note kept describing them as live until it was edited. The `map_work` tool's `fields=` takes the record's columns (`id`, `address`, `note`, `created`, `steps`, `steps_done`, `taken`, `taken_by`, `kind`, `map.agent`, `map.item`, `map.title`, `status`, as the refusal lists them); a read with `fields=["id","map.item","map.title","status"]` returned results on 2026-10-19, and an unknown name such as `column` is refused with that list. Read the full note and resolution with `--json` or `view=full`. When an orchestrator note sends you back to a ticket that is already `done`, first map each numbered item of the note's addition to code and tests already in the tree, and report that mapping with file and test names. Build only the items that are missing, as new numbered steps on the same ticket, and say which ones were already there; never rebuild a built item or reopen the ticket silently. Never edit a spec record from a ticket; the person writes specs, and a record's `Built` line is part of the record. To amend one record of a spec file through `orchestration_change`, pass `section=<record id or heading>` with `content` holding only that record; the whole-file form replaces the file, and a write that drops any heading is refused unless `removing` names each record it removes. On 2026-10-19 a 957-byte amendment sent as the whole content overwrote `specifications/11-context.md` (64 headings) until it was restored by hand. The section form was added on 2026-10-19 in `orchestration/specifications.py` and was uncommitted when this was written, so read the tool's help before relying on it. A build note or amendment line added under a spec record is an edit of that record too, so it is drafted in `artifacts/specs-draft/` like any other wording. Put the built state in the step text and the `op=done` resolution, and name the record line in the report for the person to amend. Where code and a spec record disagree, the code is the reference: never change code to match the record, since that rolls back features; report the difference and draft the record text in `artifacts/specs-draft/`. When a notice says the session stopped with the ticket open at a numbered step, resume there and do not re-plan: read the ticket's steps back with `map_work`, run `git status --short` on the files its steps name to see what is already uncommitted, then go on with the next step number and close with `op=done` whose resolution names the uncommitted files and any failures that predate the ticket. A worker agent cannot `op=add` a ticket (refused: tickets are written by the person and the agents that serve them), so a follow-up ticket goes into its own ticket's `op=edit` note for the orchestrator to file. Spec text drafted for the person goes to `artifacts/specs-draft/`, never `specifications/`, until the person approves that exact wording. Once they approve it (for example "the spec is APPROVED; build it now"), the approved wording goes into the spec file as an amendment bullet marked with the date and `approved by the owner`, the view record that cites the rule gets a matching amendment and its Relates-to line updated, and the report names both bullets so the person can review or reverse them. When a design is replaced, delete only the memory observations the new design contradicts: `open_nodes` the entity first, check each line to delete for facts that still hold (a deleted line also named a still-true eye-view fact and had to be re-added on 2026-10-15), re-add those kept facts with `add_observations`, and say which were kept. When a notice says a ticket's task has been replaced, re-read the ticket with `map_work` before more work, and do not restore the replaced behaviour. A ticket assigned to one module does not edit `src/metaform/*.py`. In a shared tree where another agent already has uncommitted edits in a file, change only your own lines and do not commit without the person's yes. Commit by name: `git add` the files you can account for and commit only those. `artifacts/specs-draft/` is git-ignored, so stage a draft there with `git add -f`. Never `git add -A`, `commit -a` or a whole-tree commit in the shared checkout by hand, because it takes other agents' half-done work with it. The one whole-tree commit is the ticket completion step, covered in Ticket dispatch below. On 2026-10-18 a whole-tree commit (`3e1e8245`) took in the orchestration edits of an agent still working, and the file was then committed in that state. Another session's commit can take your uncommitted lines with it: on 2026-10-14 commit 520c8d9 (ticket 7daa5005) swept in a first pass of edits to `server.py`, `stream.js` and `module.py`, while the later fixes stayed uncommitted on top. After each save, `git show --stat` the newest commit and `git diff -U0 -- FILE` for your lines; name in the report any of your files a commit took, and the fixes left uncommitted on top, since that commit alone can fail tests. While the `metaform` MCP server is connected and lists `map_work` and `memory_*`, write tickets and memories through those tools, not the CLI; the CLI is the labelled fallback below. Never discard a write's output (`>/dev/null 2>&1`): a refused write then looks like a success, so read the record back. On 2026-10-19 an implementer edited a ticket note through the CLI with its output discarded, while the MCP tools were listed. When the `metaform` MCP server fails to connect (on 2026-10-14 with `No module named 'yaml'`), its tools are gone for the session. Say so in the report and in the ticket's `op=edit` note, then do the ticket and memory writes through the CLI (`uv run metaform map work op=step id=ID said="..."`, `uv run metaform memory ...`), and do not present the CLI route as a fix. Reading memory: never `memory_read_graph node=element:<address>` for an element's notes. On 2026-10-15 it returned 87,660 characters, the tool refused the result and pointed at a file to chunk through. Read the named entities you need (`open_nodes`, by name) instead. Memory argument shapes through the CLI: `create_entities` takes a JSON list of `{name, entityType, observations}` with `node=NODE`, and a new entity also takes `why`, one line saying why it is worth keeping, which the MCP schema requires; to correct a stale observation, read it back with `open_nodes`, then `delete_observations` takes `[{entityName, observations:[exact old text]}]` and `add_observations` takes `[{entityName, contents:[new text]}]`, both with `node=NODE`. Memory citations (`memory_create_entities` `cite`) resolve only inside the project folder the MCP server runs in: a path in a sibling repo such as /home/rich/roundtable fails the whole entry, so cite project files or leave `cite` out and name the other repo in the text. A whole-file citation is checked against its file as it read at the citation's last write: giving it again in a write, or adding an observation to the memory, re-saves that stamp, so a memory brought up to date after its file changed is not reported stale. A line-span or symbol citation moves only when it is given again, since its line numbers may now hold other text. A citation whose file is gone stays stale. Full rules, including source passes and source_placement runs: `references/ticket-work.md`. Before reporting a deleted map element as gone, re-read it with `map_element` after a short wait, since a stale server can re-make it (see the section on fixes to running code).

## Ticket dispatch: name the agent, hold in order, tell parallel agents
- The person's system agent works like an inbox, not a feed. Worker reports, peer notes and result notices wait for it to read; none is pushed into its conversation one by one. At most a turn already going to it carries one short "N new in your inbox" line, and only something needing the person may wake it. When you change how reports or notices reach it, prove that a burst of results causes no turn of its own. The pushes came in with commit 4f2966c8 (GC-led orchestration); ticket code.dispatcher.agent#72 replaces them.
- Every ticket names the agent `agent=claude`. The person's rule is Claude agents only, and a `codex` or `gemini` row on the board shows a path nobody chose. Create a held ticket with `uv run metaform map work op=add node=ADDRESS kind=enhancement agent=claude hold=true title="..." task="..."`, and write its place in the chain in `note=` (for example "Held: runs after ADDRESS#N"). Resolve the work id from the item address with `uv run metaform map work node=ADDRESS limit=0 --json` (match `map.item`) before starting it. `dispatch start` refuses the item ref (`code.interface.graphical#148`) with "No work record has the id"; it takes only the hex work id.
- Build any text holding apostrophes, parentheses or line breaks in shell variables from a quoted heredoc (`task=$(cat <<'EOF' ... EOF)`), then pass `task="$task"`. Otherwise bash fails with `syntax error near unexpected token` and nothing is filed.
- A `task=` carries its own check: the steps to run and what should show when it works. Each boundary the person set goes in as a "leave X alone" line. The agent reads only the ticket, so anything left out of it can be changed.
- Start with `uv run metaform dispatch start WORKID claude`, then `uv run metaform dispatch wait stopped id=WORKID` in the background, since it blocks. Read `done:`, `resolution:` and `steps_done:` from `uv run metaform map work id=WORKID` before reporting. A ticket already taken by your own session resumes with `op=plan` and `op=step`, never `op=take`. An assignment the orchestration delivered is already taken for your session: go straight to `op=plan` without an `op=take` first. On 2026-10-19 an FQC on code.store.memory#24 sent `op=take` and got `Error: This task is already taken, by claude <its own session> at 2026-10-19T07:52:12Z ... Next: call map_work op=plan`.
- Slots: `dispatch_machine_agents` caps the agents on the whole machine across projects (8 on 2026-10-19; the person raises it in Settings, "Agents on this machine"). Never start a ticket's work in a subagent of your own to get past a full machine: that routes around the cap the person set, and it is the same workaround as retrying. Harness background subagents are never a way to do Metaform work, full machine or not: they never show on the map or board, the person cannot watch, steer or stop them, and their cost is out of view. On 2026-10-19 four such helpers ran unseen and the person called it a problem. When tickets cannot start, say so and get the person's go before any in-session helper; a visible helper the system role can start without a ticket is `code.dispatcher.agent#78`, and until it lands it does not exist. Once it lands, a helper is exempt from the work queue and from `dispatch_agents`: it takes no worker slot, starts at once even when every slot is full or Full Auto is off, and is not held by queue order, Backlog holds or ticket dependencies, because the system role uses it when something must be dealt with now. It is observable like any agent (a figure on the map, its brief shown, its thread readable live, its spend counted), and only the person's stop, single or stop-all, ends it. Build it through the existing launch, session, live-stream, spend and stop paths, never a second mechanism. Leave the ticket in To do, say so, and name the setting.
- Old slot text, superseded: `dispatch_agents` allowed 5 agents at once. A start that finds every slot taken fails with "Every agent slot is in use"; the ticket stays in To do and starts itself when a slot frees. Do not retry it or report it as stuck. The person's own system agent is the exception: `own_room` in `dispatch/__init__.py` lets it take one place beyond `dispatch_machine_agents`, so background work never refuses their chat. Other summons still count against the machine limit; the machine-ceiling tests in `test_dispatch.py` check both sides. Tickets that touch independent files may run side by side up to that limit. The one-agent-at-a-time rule above is the default for work the person has not released in parallel.
- Release each held ticket when the one before it lands: `uv run metaform map work op=edit id=WORKID hold=false`, then `uv run metaform dispatch start WORKID claude`.
- Shared files: when two running tickets share a map file or the store layout version, send each the other's scope with `uv run metaform dispatch note to=WORKID "what, where, who goes first"` and check for the "said:" line. A note reaches the agent after its turn in flight, so expect a reply, not an instant change. A note can arrive after the work it describes is already finished, because it was sent before the reply: read back each item it names, reply with the ids and their current state, and do not redo or undo that item on the note alone. When both tickets change the store layout version, the note says which bumps first and which files each edits. Keep the map module importable at every step: a broken map module takes down every agent's map tools and the web page. When a peer's edit lands in a test file you are verifying with repeated runs, tell that peer to hold its edit to that file until your runs finish, then send a "clear" note when you are done; a peer edit landing mid-run makes the results mean nothing.
- Notes: a note names exactly one recipient (`to=`, `at=`, `file=`, `topic=` or `reply=`), is at most 1000 characters, and is rate-limited to about six an hour. Batch what one agent needs and check `dispatch peers` before a second note. A note to a finished agent reaches no one, and a reply to an ended worker is refused: if the target is gone, put the content on the ticket. A system agent is the exception: a note to `to=system` (with `target_project=` for another project) or a reply to a system agent whose session ended waits in its last conversation and reaches its next session. A `wait=` note that times out means the agent is mid-turn; do not resend it. A peer may add tests to the same test file while you work: before reporting, grep for your own test name and read `git diff --stat` for that file, then leave the peer's lines alone rather than reverting them.
- Peers, within and across projects: every agent, whatever its role, lists the agents at work in its own project with `dispatch peers` and sends one a note; a note that cannot reach its target is reported as undelivered, never as sent. A user-facing system agent reaches a related registered project's system agent with `dispatch note target_project=PROJECT`, addressed by project rather than by session id, so a fault found in one project can be carried over as a ticket in the other. Cross-project notes (`dispatch note to=system target_project=ID`, the kept waiting thread, `dispatch_note reply=ID`) have a two-project test with fake system agents in `dispatch/tests/test_cross_project.py`. That test proves the routing in code only; a real note still needs a live check before relying on it. The routing was uncommitted on 2026-10-19 alongside `dispatch/peering.py`, so commit it together with its test. On 2026-10-19 agents could not message each other after the cross-project change (commit c4f449fc).
- Decisions: `uv run metaform dispatch message WORKID "..."` is the person's decision to the agent on that work. `dispatch note decision=true` is the only note that relays one: it is sent only by the person's own system agent, in the turn the person's message started, and each recipient takes it as the person's direction (steered into its turn in flight, else queued ahead of waiting prompts). A plain note that relays a decision is still peer information, and agents kept building for several turns after one (2026-10-18). When the person decides something about running work, send it with `dispatch message` to each working agent at once, and put it on the ticket. A message to an idle agent is not acted on: run `dispatch peers` after it, and start the agent if it is still idle.
- A spec that lands while tickets run: cite its record ids on each governed ticket (`map work op=edit` with the note extended), then `dispatch message` each running agent, naming the records and the open questions it must not build past.
- Do not change a setting the person owns to quiet a symptom. The same holds for `metaform set --dispatch-agents N`, even to put back a limit the person raised earlier: the command's own output says to ask the person in chat. `metaform set --no-dispatch-autostart` to stop tickets starting, or any other flag that stops noise, is a change to their settings: ask first, and fix the cause as a ticket. On 2026-10-19 that command was made unasked and the person rejected it.
- A stop given to every agent at once (the page's "Stop every agent on this machine?") pauses the whole machine; it is not a stop of each ticket. Turning Full Auto back on afterwards means "go again": the assignments that pause stopped resume in place through the existing resume path, within `dispatch_agents`. A stop the person gave one agent alone stays until that work is restarted. Record the two kinds of stop distinctly where the stop is written, so Full Auto lifts only the stop-all kind.
- Restart a worker with nothing resumed: `uv run metaform dispatch new WORKID` (CLI only). Never stop then start: `dispatch stop` on the system agent turns `dispatch_stay_connected` off, and a stopped worker keeps its ticket taken, so `dispatch start` refuses it.
- Tickets do not stay open for want of a yes. The system agent owns the board: a ticket that is stale, superseded, a duplicate, or whose task no longer matches the current spec and tree closes at once with `op=done`, a `resolution` naming what replaced it and a `why`, and the person gets one short list of what was closed and why. Ask first only when a close abandons work the person asked for and has not released. Before reporting the board, check each open ticket still applies; a ticket left open with no task and no owner is the defect. Run that check in the same turn as the report and close what fails it then. Do not defer the rest to "after the restart": on 2026-10-19 six tickets were closed and thirty-one were left open with that promise, and the person said tickets must close out and asked whether all of them were still relevant. Cancel with `uv run metaform map work op=done id=WORKID resolution="Cancelled: what replaced it" why="who decided, date"`. A worker cannot cancel (`dispatch cancel` refuses it, and `op=done` records completed), so the system agent closes. `op=done` ignores `said=`, so put the closing account in `resolution=` and the reason in `why=`. A `done` that sends `resolution=` without `why=` is refused ("Error: The resolution has no why. Next: add why"), so send both on the first call. A done on a record already closed keeps its first resolution, so put the full account in the first close. A ticket noted "likely fixed, not yet verified" or with "Not checked:" closes only when each named check has been run.
- A ticket a review files from its own finding is not a request. Check that the person raised the problem before starting it. When the person drops such a line, note each ticket on it, stop them, and cancel the held ones.
- A completion commits the whole shared tree under the person's git name, so it can take other tickets' uncommitted work along. Name in the resolution which other tickets' work the commit carried, and tell the person that completions commit. Before a completion runs while others are running, confirm the guard in `dispatch/merge.py` is present; it acts only on a real worktree (its `.git` is a file). This is the one whole-tree commit the system makes. The commit-by-name rule above still binds every agent's own commits.
- A detached runner that owns children (a table follower, a page server) needs its own SIGTERM handler that runs its cleanup. `dispatch stop-all` ends the runner's whole process group, so a runner ended by a signal skips its `finally`: its server keeps running, and its agent slots free while its seats still run. Stop such a runner by asking it to stop (SIGTERM), and let its slots go only after its children have closed.
- A landed fix does not reach a process started before it (the MCP server, any runner). When a change alters behaviour another open ticket relies on, send that ticket a dispatch note that names the restart, and put the restart in the resolution.
- A worker that lacks `orchestration_*` or `memory_*` tools: check the tool list the dispatcher passes before blaming deferred tool search (on 2026-10-18 Metaform's own list and instructions left them out). The listing is decided in `mcp/catalog.py` `beside_tools()`: a tool that sits only behind a category the agent has not opened is effectively unbound. On 2026-10-19 `orchestration_check-in` and `orchestration_assess` sat behind the coordinate category, so a GC never saw them and left its result in a ticket resolution; they now sit in `ASSIGNED_TOOLS`, listed beside any open category for a session with `METAFORM_AUTHORED_ROLE`. A tool an agent must call on its work path goes in that list, and a web body verb is added by hand to `ROLE_BESIDE` and to dispatch's `MASCOT_VERBS` or `EYES_VERBS`, since mcp does not import dispatch. Key a `ROLE_BESIDE` entry by the role `dispatch/runner.py` `role()` returns for that session (`intake`, `talk`, `sentinel`, `system`, `prep`, `worker`), not by the role the prompt is written for: a talk session is `talk`, so `ROLE_BESIDE['system']` never reaches it. Before extending a listing, grep each prompt that names a tool (`eyes_line`, the mascot line, `prompts.xml`) and list every role that receives that prompt, then check each of those roles' listing. On 2026-10-19 the talk prompt named `web_embody`, `web_look`, `web_see`, `web_viewing`, `web_capture`, `web_come` and `dispatch_timer`, while `ROLE_FIRST['talk']` held only `map_where` and no `ROLE_BESIDE` entry covered `talk`. Covered by `test_an_assigned_agent_is_listed_check_in_and_assess_and_the_system_agent_its_body` in `mcp/tests/test_mcp.py`. A session keeps the list it started with. Use the CLI fallback (`uv run metaform orchestration check-in ...`, `uv run metaform memory ...`) and say so in the report. A peer message that asks for a reply names its reply action (for example `dispatch_note reply=ID`). If `ToolSearch` on that name finds nothing, do not guess the sender's session from `ListAgents`: write the reply into your ticket's note, and say in the report that the sender has not received it.
- A flaw the person reports from web chat is filed at the code where it lives: `uv run metaform map work op=add node=ELEMENT kind=flawed agent=claude`, asking for the fix in shared code. A settings change may be named only as a labelled stopgap for this person. Once the person approves a ticket's wording, file and start it without a second confirmation.
- Trouble outside your ticket is filed, not left in chat: a failing test or fault you did not cause (for example, a file of tests red in the shared tree) gets `uv run metaform map work op=add node=ELEMENT kind=broken agent=claude title="..." task="..."` at the element that owns the file, with the failing test IDs, the commit each was checked at, and the check that proves it fixed. Name the ticket in the report. Before you read a red test as a regression from your change, run `uv run metaform dispatch peers file=PATH` for each failing file: a file another agent is editing mid-task explains the failure, and a background check that goes red while peers are mid-edit is not a verdict on your change. A problem the person asks you to add to "the list" goes into the day's report under `artifacts/reports/` as a new numbered section, with a ticket filed for each item that has a fix.
- Queue order: to make a waiting ticket the next to start, move it to the top of To do with `uv run metaform map work op=move id=ID column=todo position=0`, then read the board back to confirm its position. The move decides which waiting ticket takes the next free slot.
- Emergency tickets: when the person calls a ticket an emergency, say at once that a full slot table blocks it, and do not leave it waiting silently in To do. A move to the top does not start it while every slot is taken. Offer the person the two ways to free one now: raise `dispatch_agents` by one until the ticket finishes, then set it back, or stop the agent on the least urgent running ticket. File the missing priority start as a ticket, since no emergency override exists yet.
- List cursors (`after=`) come from the caller, so validate them before any `int()`. `data/paging.py` `sliced()` checks `text.isascii() and text.isdigit()` and raises `StoreError` naming the fix ("read the list again without after"). The store's `fetch` closures in `modules/map/storage.py` (`work()` and `messages()`, the `int(cursor or 0)` lines) and `reports.py` `list_reports` still call `int()` unchecked, so a malformed `after=` from an MCP call surfaces as a bare `ValueError`; `workflow/runs.py` `listed()` already wraps its `int(after)` in a `try` and raises `Stop` with the cursor's help line. When you touch a list read, route its cursor through the same check as `sliced()` (or a shared helper in `paging.py`) and give the refusal the same next-step text. Cover it with one test in the list's existing test file.
- Reads: read a running ticket when its wait starts and when its result arrives, not on every turn. Read a node once when an assignment starts. Count the board first (`map_work` with `view=count`), then read only the fields a decision needs. A full list of open tickets in the system agent's context is paid on every turn, and the person's account pays for it.
- A ticket that names a cost (a read size, a call count, a time) is checked against the current HEAD before any code changes. `git log -S` on the function it names, and a measurement on the tree as it stands, show whether an earlier commit already removed the cost. If it is gone, change no product code: add the requested check as one test in the file that already holds its neighbours, and return with the measured numbers. If the ticket's stated reason no longer holds because the data also serves other uses, keep the code, do not delete the read to satisfy the ticket, and return `returned` with the decision for the person. On 2026-10-19 (ticket 57bffbda) commit c4f449fc had already cut the open-ticket read from 485 tickets (2.4 MB) to 63 (259 KB); the remaining read fed figures, the mascot and conversation bodies, so it was kept and reported as a material decision.
- Repeated deliveries: when the orchestrator re-sends an assignment whose `assignment_id`, `work_id` and task text match one already handled, it carries no new fact. Make no memory or ticket read for it; reply in a line only if the state changed, and otherwise send nothing.
- Refs never move. A ticket that links refs says each stays at the element or join it was linked at. A property link settles at the longest common prefix of its addresses and never moves toward the leaves.
- A CI-configuration ticket closes on the config change, and its proof is a green run on a separate ticket. If GitHub refuses every job (each ends in seconds with no steps run), name that as a billing refusal in the resolution and leave the proof ticket open.

## Orchestration check-in: state word, summary, then key=value
- Call `orchestration_check-in` as an MCP tool only when this session lists it. On 2026-10-19 a direct call to `mcp__metaform__orchestration_check-in` answered `Error: No such tool available`, and the agent had not searched for it first; the CLI form below then landed and read back `state: delivered`. Read the record back with `orchestration inspect` after either route.
- Return a ticket with the state word, the quoted summary, then the keyword arguments: `uv run metaform orchestration check-in STATE "SUMMARY" assignment=ID 'candidate=JSON' 'evidence=JSON LIST'`. `assignment=` placed before the state word or the summary is refused ("assignment= comes after the required nouns"). It was missed again on graphical#136 (c781ec60, 2026-10-18), whose session had no orchestration check-in tool loaded: take the CLI check-in above before the close, not after. A `returned` check-in also closes the worker's work record: a `map work op=done` sent after it answers "done: This work record was done at ...; its resolution was kept" and changes nothing. After a `returned` check-in has queued the assessment, a further check-in for a follow-up change queues a duplicate assessment: record the follow-up with `uv run metaform map work op=edit id=WORKID note=...` on the ticket (the note sent whole, as the rule above on `op=edit note=` says), and send no second check-in.
- After a check-in that carries evidence, read the record back with `uv run metaform orchestration inspect assignment=ID` (`assignment=` only; it refuses `fields=`) and confirm `state: returned` and a non-empty `evidence:` before any close. A record that still reads `state: delivered` with `evidence: []` after the check-in means the check-in did not land, whatever the command printed, and the fix is a re-sent check-in before `op=done`, not a note on the FQC ticket. On 2026-10-19 (assignment 4a7b3bba, ticket code.dispatcher.agent#5a) the ticket was closed first and the check-in read back exactly that way.

On 2026-10-19 (ticket code.dispatcher.agent#5c) two passing browser runs showed that switching projects ended no agent, so the fix the ticket asked for had no cause to fix. Keep the test only if it is in an existing test file.
- `candidate` is one JSON object: the work's `kind` (`working-tree` for a working tree), its `branch`, and the changed `files`. `evidence` is a JSON list of the commands run and what they showed: the test counts, and the failure seen without the fix.
- Before a check-in or ticket resolution says a file is or is not packaged, shipped or gitignored, check it: `git check-ignore -v PATH` (no output means not ignored) and `git ls-files --error-unmatch PATH`. The GC acts on the evidence as written. On 2026-10-18 an FQC check-in claimed a spec file's final newline had been restored; it had not, and the error surfaced only after the ticket closed.
- The summary carries the work's own result. Name any part left to another ticket by its id.
- A spec revision an assessment publishes goes through `uv run metaform orchestration change` with `specification={"path": ...}` naming the file. A revision is the sha256 of the exact bytes, and `"$(cat FILE)"` strips trailing newlines, so after publishing compare `sha256sum FILE` with `current_revision` from `uv run metaform orchestration changes`. Once published, the file keeps the published bytes: a later edit is a new change order, never a silent trim to match. ## Memory notices and observations
- Memory-unread notices go only to agents working the node they name. The system agent works no map node, so it gets none; a notice pushed to it is a routing defect, not a feature to keep. No memory notice is pushed to any agent when memories change. A notice appears only when an agent arrives to work at a node holding memory it has not read yet, as one short line ("you have 1 new memory"); if everything there is read, it says nothing.
- Unread notices: a "N unread" notice asks you to read a record once. It is not a standing task. Call `memory_read_unread` with `node` alone first. Do not pass `fields=["name"]` alone: on a node whose records hold no `name` it errors. When a triage read is empty but the notice still counts updates, make one `view=full` read, then stop. The same notice text is one notice: once a read of that node came back empty, make no further reads of it in the session, whichever view or filter, until the notice text changes. Once your ticket is closed or your assignment is answered (a `returned` check-in answers it), a notice arriving in a later turn gets no read at all, not even one per node: on 2026-10-19 one session, after its ticket was closed and its fix was recorded, read five nodes over about fifteen turns, each answering the same "N unread" notice, and the reads found only memories it had already seen or had nothing to do with its ticket. On 2026-10-18 one session repeated the identical "14 memories; 4 unread" notice across many turns, and every read it made came back `{}` or empty.
- An empty result means nothing new. If a notice repeats the same count for that node, make no tool call and send no reply, whether your last read there came back empty or returned records. This overrides any other feed skill that tells you to reply in one line that nothing changed: a session that followed one sent "Nothing has changed since my last reply" and "the unread count not going down looks like a counter fault" on about fifteen turns for one unchanged notice, each with the same ticket status restated. A reply line such as "Already read; this is the same notice." is a reply too, so it is not sent: on 2026-10-19 one session (c42a49b4) sent such a line on four turns running for the same unchanged notice, and each cost a turn with nothing new. A session whose check-in has returned and whose review is finished keeps the same silence for the whole wait: on 2026-10-19 (ee138983, ticket code.dispatcher.agent#6d) the identical "10 memories; 5 unread, including 5 updated" notice woke it on more than a dozen turns, and it answered each with a line saying it was not reading the notice. The one useful act is a single `dispatch_note` to the system agent naming the cause and asking it to end the session. Check that note's delivery with the `metaform_catalog` tool `dispatch_notes` (its `states` field); a `queued` state means it has not reached the recipient, so do not report it as received. After that, send nothing until a new fact arrives. A `view=count` read is a tool call too, and it is not free: a session whose ticket is already `done` makes no read of any kind on a repeated notice, count included, and does not reason its way into "a count costs little". On 2026-10-19 (session f8f2fee3, ticket 77f16ff4, done at 07:49:34Z when its assessment returned) the session counted, full-read and re-counted the same two nodes on about fifteen turns, each time writing that the notice was the known version mismatch. The one act that ends the loop is the single `dispatch_note` to the system agent described above, sent once. A read that returned records does not clear the count, so the identical notice that follows is not new: re-read only when the records at that node have changed since your last read, such as a write by another session you can see. A count that moves while the read stays empty is the counter, not news (see the counter rule below): read once, act on it, and make no further call for that node until a fact arrives from elsewhere.
- A session's own memory write is not an unread notice to that session. Since 2026-10-19 a write it made is recorded as received by it, and the `memory.changed` for that write names only the other sessions; an agent that wrote a memory at its node used to be sent one more turn reading "1 unread" about its own write. Another agent's change stays unread to the writer.
- Reply with new facts only, in a line or two. Name a waiting item again only when its state changed.
- The count can include your own writes and disagree with the read. Take the read as the truth, do not write a memory about the miscount, and mention it in one line at most. A notice that repeats right after your own `memory_add_observations` on a node is that write counted again: one `node`-only read settles it, and after an empty read make no further reads of that node, even when each turn repeats the notice. The CLI `memory read_unread` refuses `view=count` ("read_unread does not take 'view=count'"); use `node` alone or `view=full`.
- A `must_contain` or `fields` read leaves the rest unread, and the notice keeps counting it: on 2026-10-18 `fields=['name','entityType']` listed 13 entities and a `view=count` read still gave total 12. When a notice repeats after a narrowed read, read the whole node once with `node` alone (or `view=full`).
- Observations: write each as one sentence stating one fact about the entity. Each observation stands alone: it must not lean on a reason, name or note given in another observation or in a note you have since deleted, because a later reader gets only that line. When you delete an observation, `open_nodes` the entity again and rewrite any remaining line that depended on the deleted text, so it states its own reason. The store refuses an observation holding two facts (a semicolon, a line break or a second sentence) and names the one it refused.
- Send the delete and the add as separate calls: in one batch a delete landed and the add was refused, leaving the entity without its new lines. Read the add's reply first, and re-send a refused add alone once it is split.
- To replace a stale line, read its exact text with `open_nodes`, delete that text, then add each corrected fact as its own observation. A delete that answers `Deleted 0 of N observations.` matched no line: another agent may already have rewritten it, so re-read with `open_nodes` before any retry and never resend the same text blind.
- Keep only facts that will still hold after the next change. Dated history of a fix belongs in the ticket note. Pruning is part of reading: when an agent reads its unread memories at a node, it deletes or merges the entries there that are outdated or repeat a sighting in that same pass, and it does not leave cleanup for a later ticket. Memory that only grows makes every arrival cost more; on 2026-10-19 one defect entity held about 40 one-off sightings.
- Working-tree state is not a memory fact: "uncommitted", "as of HH:MMZ", "still in the working tree" goes false at the next commit and nobody revisits it. Write the commit hash that holds the fact, or leave it out. Per-review lines ("the FQC on X passed it, found Y unchanged") are ticket-note history too: one memory line states the settled fact, and the review log stays on the ticket.
- A notice whose count disagrees with the reads is the counter, not new memories. On 2026-10-19 the notice read "5 memories; 6 unread" over about ten turns, then "15 unread", with no write of the session's own in between; `view=count` returned total 3, then 5. Read once, act on what that read returns, and make no further call for that notice text.
- The count in a "N unread" notice comes from `delivery.notices()` in `modules/memory/delivery.py`, and it must read memory bodies with the same check `memory_read_unread` uses (`_view(tx, key, Checker(reading))`). Without it, a memory whose cited file changed counts as unread after every read that returns nothing. A memory deleted and made again under the same name must also drop its old withdrawal at every node: `delivery.remade()` does this on writes that remove nothing, or the reads at two nodes alternate between the withdrawal and the body forever. Both causes are tested in `modules/memory/tests/test_delivery.py`.
A third cause (code.store.memory#1c, built over the uncommitted #18 fix on 2026-10-19): a stale citation's reason says "the cited text is now at line N", and the line is shown to readers. `citations.settled` replaces that clause with "is elsewhere in the file, unchanged" wherever a body's identity is taken (`delivery.component` receipted text and fingerprint), so an unrelated edit that shifts the cited line does not re-deliver the memory. A moved citation counts as changed only when its settled reason differs. Until that fix is committed, a memory that returns with a line-only change is the defect, not news. When a memory returns with the same claim, check its citation note before treating it as news. A notice whose count does not match what `read_unread` returns is the session-receipt mismatch tracked in code.system.management.knowledge#35; read once, record it in the ticket note, and make no further reads of that node.
- Before `memory_create_entities` or a new observation, `open_nodes` the node and look for an entity or line that already states the fact (`must_contain` on its key words). If one does, write no second entity: link yours to it with `memory_create_relations` (active-voice `relationType`), or add nothing. On 2026-10-19 a worker wrote an entity about leftover test runners whose two facts a peer's entity of the same name already held, and then had to delete its own copy.
- Pass `node=` on every call. Shapes: `memory_add_observations` takes `observations: [{entityName, contents: [...]}]`; `memory_delete_observations` takes `deletions: [{entityName, observations: [exact old text]}]`. A new entity also takes a `why` line and a `title` line (one line saying what the entity is): `memory_create_entities` refuses an entity with no title ("The memory '...' has no title. Next: add title"), and the refusal comes only after the call, so send both.

## Project data lives in layers
Every piece of project data is in a layer, or linked from one (LAYER-001, "Everything Metaform holds is a layer"). A body too big or too raw for a layer item (transcript, report, recording) stays where it is kept, and a layer item at its element points to it. Machinery (settings, process state, caches) is the only exception, decided with the person. Before adding or reviewing any store of project data, name its layer or its link. Known drift: work (tickets, steps, links, the board's backlog, todo, doing and done) lives in the map module's own tables (`work`, `work_links`, `work_steps`) and is no layer, though MAP-046 designed statuses as layers. ## A module that keeps what happened writes through memory.record
A module that must keep an event at a part (an Address) writes it through the memory module's `memory.record`, reached with `provided(folder, 'memory.record')`, and never through its own copy of memory's write rules. `memory.record` runs create_entities at the Address's element, so the title, why, one-fact-per-observation and project-file citation rules all apply. Text quoted whole in straight, curly or backtick quotes counts as one fact, so engine text such as a host's summary goes in as one quoted observation. A `prompt_files.required` fill slot cannot be named `name` or `folder`, since both collide with that function's own parameters. Each memory the module records names its own question and result, and cites the saved file it refers to.

## A new source file is linked to the element that owns it
When a change adds a source file to a module (for example `modules/autoticket/proof.py`), link it in the same change to the element that owns it: `dispatch_link` with `file=PATH`, `node=ADDRESS`, `ref=NAME` and a `why` line, then read back `linked: true`. A ref is a dotted lowercase name of letters, digits and underscores, such as `metaform.modules.roundtables` for the module's `__init__.py` and `metaform.modules.roundtables.follow` for `follow.py`. A title-cased name (`Roundtables Follower`) or a 32-character id is refused with "cannot be a ref_id" and nothing is linked, so a refused call leaves the file unlinked until it is retried in dotted form. Autoticket files a fault at the element whose path ref names the failing file, and otherwise falls back to a guess (the deepest shared folder, then the top node), so an unlinked file sends its faults to the wrong element. A ref name is unique across the project: `dispatch_link` refuses a name an element already holds ("... is taken: it names path=... Nothing was linked; give another name."). When that refusal names the same `path=` as your file, the file is already linked, so read the element's refs before linking again instead of inventing a second name.

## Shared generated snapshots: edit only your own entry
`tests/module_tables.snapshot.json` is shared by every module. Its write mode records every module's unrecorded table changes, not only yours. When a new module adds a table, add only that module's entry by hand, then run the snapshot test and name in the report any failures from other modules that were already there. Do not regenerate the whole snapshot to clear other modules' failures on a ticket that does not own the guard: that records someone else's pending change under your ticket.

When the guard itself is failing for several modules and your ticket owns it, regenerate the snapshot only after each module is checked: `cp` the snapshot aside, run `METAFORM_TABLES_SNAPSHOT=write uv run pytest -n 0 tests/test_module_tables.py -k snapshot`, diff the two files by module, and keep only entries whose change is intended. An intended change raised that module's `Tables(version=...)` and says why in a comment above it (`# Version 2 adds ...`); the guard checks for those comments. A change that only adds tables or columns that may be empty needs no upgrade, since the chassis adds them in place. A table changed with no version bump is fixed in the module, never recorded. Then prove the guard: the file passes, and a column retyped on the live file with no bump fails with `version NOT raised, still N`. Restore the file and confirm `git diff` on it is empty.

On 2026-10-19 a count read 4 with three real runners. ## Titles from titled()
`titled(ctx, what, title, why, ...)` in `metaform.module` only checks a write and returns None. A verb that passes its return value as the title sends None, and the ticket then shows the task's first line instead of the intended title. Build the title as a string first (`str(ctx.nouns.get('title') or ...)[:120]`) and pass that string; `titled` refuses a missing title, it does not supply one.

- A regression test for a fix in a file that live servers load (a relay, a runner, the MCP server's own module) runs against the unfixed tree before the fix lands, not against a copy of the file swapped in: the running servers watch that file, so a swap hands every live agent the buggy code. Write the test, run it to see the exact failure, then apply the fix and rerun. This does not change the /tmp mutation copy below, which never touches the tree.

## Tests that follow an event stream
- Event `seq` numbers are per table: each table restarts at 1. A "fresh events" cursor built from one `max(seq)` across all tables hides a second table's events. Key the cursor on `(table_id, seq)`. On 2026-10-19 a `max(seq)` cursor hid a second table's `end` event, and the stop test reported the table as ended by its chair when the follower had ended it.
- A stub that finishes its table before the stop arrives tests nothing. Pace the stub so each stop lands while the table is still discussing, and assert the stop's effect on that table.
- Prove each such guard with the mutation check in the `regression-test-mutation-check` skill: remove the one fix line and watch the named assertion fail. Run the mutation on a copy, never in the shared tree: copy `src conftest.py pyproject.toml` into a fresh `/tmp` folder, make the one-line edit there with a replace that asserts its match count is 1, delete `__pycache__` under the copy (a stale .pyc hides the edit), then run `PYTHONPATH=/tmp/NAME/src .venv/bin/python -m pytest -p no:cacheprovider -n 0 PATH -k NAME`. Confirm the failure is the named assertion, not a timeout or import error, and that the unmodified test passes in the tree. A cheaper route for a guard on a fix that is already in the tree: write a pytest plugin under `/tmp` that monkeypatches the fix's helper to the identity function (for example `settled(why)` returns `why`), load it with `PYTHONPATH=/tmp/NAME -p PLUGIN`, and run only the guarding test with `-k`. ## Prompts are XML: escape first, then fix the wording
- `prompts.xml` is parsed with `ET.fromstring`, so one raw `&` or `<` stops the whole file loading. Write `&amp;` in the file; never strip characters to get it to parse.
- Edit an element by its real position, never a bare string search: a regex on `<instructions>` matched the same word quoted in a comment and broke the file. Comments are product documentation and are never sent.
- After every write, run `prompt_files.text(...)` on the module and compare it with the text you meant to store. If it fails, `git checkout --` the file and redo the edit.
- A rewrite that removes numbered steps or named sections leaves cross-references behind. Grep every prompt for the old reference ("steps 5 and 6 of the memory prompt" survived the orchestration merge 4f2966c8 in dispatch's `<record>` and in memory's `<orient>`) and fix or drop each one in the same change.
- Restoring a line a test pins: take the wording from the commit before the change (`git show SHA^:path`), restore only that line, and check that the restored text's own references still resolve.
- Tags written as text inside a prompt (`<role>`, `<core_behaviors>`, any XML-looking markup from an outside prompt) must be escaped in the file: `&lt;role&gt;`. A bare `<name>` is read as a tag, and a bare `<name/>` is a fill place that renders empty unless a caller supplies it. `prompt_files.py` refuses a raw `<` with "write < as &lt; in the file". Escape the whole pasted text with `xml.sax.saxutils.escape` and check the stored text reads back the same before reporting. Put a comment above such an element saying why its tags are escaped, since comments are product documentation.
- Before a scripted multi-replace on `prompts.xml`, re-read the file: a peer agent may have reworded the target phrase since you last looked. On 2026-10-19 a seven-pair replace asserted each match count was 1 and stopped on `Apply current GC change orders` (count 0) because a peer had already changed it. Re-grep the phrase, rebuild the pair list, and only then write. Find prompt references with bounded searches (`grep -rn ... --include=*.xml --include=*.py | grep -v "/tests/\|vendor/" | cut -c1-220 | head`); an unbounded grep of `src/metaform` returned 2.8 MB on 2026-10-19.
- Do not write code that checks a prompt's structure (headers, Axiom names). Whether a prompt is complete is judged by its reader.

## Store upgrades and concurrent openers

The guard against the race is `test_three_processes_opening_a_layout_10_store_at_once_all_read_it_upgraded_once` in `tests/test_store_upgrade.py`: it failed 3 of 3 runs before the lock (one process raised `disk I/O error`) and passed 5 of 5 after. The general rule and the SQLite facts behind the guard connection are in `check-then-create-under-lock`. A table cannot change place (`metaform` or `project`) under its own name: `data/tables.py` `_upgrade` raises `moves X from the metaform store to the project store, and the rows here would be lost`, and the module's upgrade hook never runs. A move is a new table name, declared at the new place, with a carry from the old table on every read (dispatch version 14: `spending` at project place, `carry_spend` reading the per-metaform `spend`); whether a table may keep its name across a place move is a chassis decision for the person. Prove an upgrade on a scratch home (recipe and pitfalls in `verify-store-schema-change`): `git archive HEAD src | tar -x -C /tmp/<dir>`, enable the module first (a disabled module declares no tables, so the store read raises `dispatch declares no tables`), `home.ensure_base(project)`, seed rows with the HEAD code, then read the same totals with the working-tree code against a copy of that home. No schema change unless the ticket's own task needs it (AGENTS.md, "No schema change unless the task needs it"). Do not add, drop or retype any module's tables, columns or keys as a side effect of a fix. If a fix seems to need one, stop and say so in the ticket note, and the orchestrator decides. On 2026-10-14 two fixers each changed dispatch's tables and both called the result version 14, and the same-version refusal then stopped dispatch and the page. An approved change raises `Tables(version=N, ...)` once, says why in the comment above `TABLES` and in the ticket, keeps `compatible_from` at the oldest version that still reads the tables, and updates `tests/module_tables.snapshot.json` in the same commit (`METAFORM_TABLES_SNAPSHOT=write uv run pytest -n 0 tests/test_module_tables.py -k snapshot`). Two open tickets never share one version number. `test_no_module_changes_its_tables_without_the_snapshot_saying_so` fails on any unrecorded change, naming the module and whether the version was raised. Since ticket 03f869a0 (2026-10-15), `data/tables.py` `state()` and `ensure()` judge a store by its real schema (`pragma table_info`, index lists), not by the declaration text in `meta`. A missing table, optional column or index is added in place with no backup. Only a real conflict raises: a key, type or default differs, or a required column with no default is missing. Since ticket 13b34894 (2026-10-15) a CHECK, foreign key, collation, ON CONFLICT resolution, generated column, partial-index condition or a held unique index the code lacks is compared too, as SQL tokens from `sqlite_master`, and any difference conflicts; a raised version rebuilds the table for it. It raises for that module alone, and `ensure_extensions` holds each module under its own savepoint. Upgrades take "before" from the real tables, so a column the record never named is kept. A test module rewritten to the same byte size reuses stale bytecode (the mtime and size match), so a `user_module` variant must differ in size; add a comment line at the module's indent. `sqlite.file_lock` with `wait=True` no longer gives up on Windows (fixed 2026-10-14, ticket #2e). msvcrt's `LK_LOCK` gives up after ten tries a second apart, so the win32 branch now retries `LK_NBLCK` every 0.05 s with no cap until the holder lets go; `wait=False` still raises `Held` at once. Keep no timeout on `upgrade()`'s lock: a waiter must wait for the upgrade to finish. The Windows wait is guarded by `test_a_process_waiting_on_a_file_lock_held_past_ten_seconds_gets_it_when_the_holder_lets_go` in `tests/test_store_upgrade.py`; on Linux that test passes with or without the fix, so its proof on the win32 branch is in `verify-guard-test-by-mutation`.

## Testing outbound sends and intake follow-ons
Stub `metaform.module.provided`, not an attribute of a module you imported: `intake finish` publishes `intake.finished`, the loader loads modules afresh, and a stub on an old module object never reaches the code that runs. Stub `urllib.request.urlopen`, and `subprocess.Popen` for a detached run, but a plain function patched over `subprocess.Popen` breaks `import mcp` ('function' object is not subscriptable), which is how a missed stub shows up. Turn a person-only boolean on in a test with `run('set', '--jev', cwd=folder)`. A stub for a function a verb reaches through its module (for example `twilio.api`'s `_get`/`_post`, or `twilio.selfcheck.answers`) goes on the module the verb calls at run time, never on a top-level import in the test file: the loader re-imports the module, so a stub on the test file's `api` left one real GET reaching api.twilio.com. In the same test, block `urllib.request.urlopen` so a missed stub fails at once. The shared client retries 429, 503 and 529, so an HTTP-error test uses a status it does not retry, such as 402. A module whose client takes an opener (paperclip's `OPENER`, passed to every `Client`, `None` meaning urlopen) is faked in its tests by monkeypatching that module attribute to an in-memory server class; the paperclip tests in `modules/paperclip/tests/test_paperclip.py` are the model. A fresh test home has `dispatch` off, so a test that needs dispatch's cancel or stop runs `run('enable', 'dispatch', cwd=folder)` first; a bare `assert paperclip._on_surface(...)` is not an enable. A test that sets a `dispatch_*` setting (`--dispatch-prompts`) needs the same `run('enable', 'dispatch')` first: `conftest.pytest_sessionstart` imports dispatch, so the missing enable passes in a run where nothing else has loaded it, and fails with "is not a setting" once an earlier test runs a dispatch verb in-process (`loader.reset` withdraws its settings). `Store.add_work` at an Address with no current element stores the record as given and raises nothing (BASE-044), so a test that needs a store refusal injects a `StoreError` with monkeypatch.

## Intake notes and the base layer
The base holds RE, PE, OP and EF only. An intake note given without a condition, or with `ok`, is the node's one item of layer `critic` (`_beside` in `modules/intake/__init__.py`), never a base `note`. A part marked `ok` opens no work record: `_condition` closes that part's untaken `_finding` records ('Replaced by ok.') and writes one item, value `ok`, in the `checked` layer at the element or join (`_checked`, CHECKED_VARIABLE). A later MISS or BKN at the part removes that item, and `_findings` falls back to it so `intake show` reads `ok` back. Before this (ticket 9de74d83, 2026-10-15) every `ok` opened a task-less record, and the board drew an empty card for each part. The store refuses any open work record that nothing would show (no task, no trouble, broken or missing marker, and not an `unbuilt` or `under-construction` stage): `_shown()` in `map/storage.py` runs in `add_work` and `edit_work`, so a test that writes such a record must give it a `task=` or the `unbuilt` stage. A stage with no task stays allowed, since the page's state control writes one and the node draws it. `boardTickets` filters on the `is_work` flag the server sends, not on a page-side marker list. `data/writes.py` `base_only`, called by `writes.edit` and `layering.refine`, refuses a non-empty note on a base element or join; clearing one to None is allowed. Read a node's note with `map node node=element:<address>`; `map knowledge op=list` does not exist. A one-time move of notes already in a real base is held as a patch under `artifacts/critic/` until the person says apply, because the first map call from any process runs it on the real home. Verify it only on a scratch home. MAP-046 now carries an amendment dated 2026-10-15 (ticket code.graph.knowledge#d) stating the base-only rule and the move of the 34 stored notes; it was written into `specifications/01-map.md` directly, so the person must approve or reword it. Still open by design: a note sent to an element or join of a non-base layer through `map knowledge op=edit` is not refused. None holds one as of 2026-10-15; the person decides whether the same guard covers every layer.

Merged finding notes are paragraphs joined by a blank line (`intake._condition`, MAP-046). Whether a note is already held is decided by `_holds(merged, note)` in `modules/intake/__init__.py`: the note equals the whole merged note or one of its paragraphs. Never test `note in merged`: a substring test dropped a shorter new finding ('sounds' inside 'never sounds') while its notice still said it was kept. Guard it with the `never` assertion in `test_a_finding_on_an_element_and_its_purpose_record_is_written_once`.
