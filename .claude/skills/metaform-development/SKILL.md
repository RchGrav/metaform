# Changing Metaform

Read the one subfile for the class of work you are in before editing. Each rule came from a real defect in this repo.

## Tickets and source passes
Report each step with its own `metaform map work op=step` (one note over steps 3 to 6 left the board at 5 of 8; on 2026-10-14 the notes "Steps 5-6" and "Steps 7-9" left it at 4 of 9, so count per step, never a range), and close with `op=done` only after the acceptance checks pass. `op=plan` takes only a step count and drops its `said` text, so write the numbered plan into the first `op=step` or into `op=edit note=`, then read the ticket back to confirm it landed. `op=edit note=` replaces the whole note, so send the current note text with the addition at its end, never the addition alone: read it first with `uv run metaform map work id=ID --json`. The `map_work` tool's `fields=` takes only `number`, `said` and `at`, so `fields=["note"]` is refused and a read through it never shows the note, resolution or done state; use `--json` or `view=full`. When an orchestrator note sends you back to a ticket that is already `done`, first map each numbered item of the note's addition to code and tests already in the tree, and report that mapping with file and test names. Build only the items that are missing, as new numbered steps on the same ticket, and say which ones were already there; never rebuild a built item or reopen the ticket silently. Never edit a spec record from a ticket; the person writes specs, and a record's `Built` line is part of the record. A build note or amendment line added under a spec record is an edit of that record too, so it is drafted in `artifacts/specs-draft/` like any other wording. Put the built state in the step text and the `op=done` resolution, and name the record line in the report for the person to amend. Where code and a spec record disagree, the code is the reference: never change code to match the record, since that rolls back features; report the difference and draft the record text in `artifacts/specs-draft/`. When a notice says the session stopped with the ticket open at a numbered step, resume there and do not re-plan: read the ticket's steps back with `map_work`, run `git status --short` on the files its steps name to see what is already uncommitted, then go on with the next step number and close with `op=done` whose resolution names the uncommitted files and any failures that predate the ticket. A worker agent cannot `op=add` a ticket (refused: tickets are written by the person and the agents that serve them), so a follow-up ticket goes into its own ticket's `op=edit` note for the orchestrator to file. Spec text drafted for the person goes to `artifacts/specs-draft/`, never `specifications/`, until the person approves that exact wording. Once they approve it (for example "the spec is APPROVED; build it now"), the approved wording goes into the spec file as an amendment bullet marked with the date and `approved by the owner`, the view record that cites the rule gets a matching amendment and its Relates-to line updated, and the report names both bullets so the person can review or reverse them. When a design is replaced, delete only the memory observations the new design contradicts: `open_nodes` the entity first, check each line to delete for facts that still hold (a deleted line also named a still-true eye-view fact and had to be re-added on 2026-10-15), re-add those kept facts with `add_observations`, and say which were kept. When a notice says a ticket's task has been replaced, re-read the ticket with `map_work` before more work, and do not restore the replaced behaviour. A ticket assigned to one module does not edit `src/metaform/*.py`. In a shared tree where another agent already has uncommitted edits in a file, change only your own lines and do not commit without the person's yes. Commit by name: `git add` the files you can account for and commit only those. `artifacts/specs-draft/` is git-ignored, so stage a draft there with `git add -f`. Never `git add -A`, `commit -a` or a whole-tree commit in the shared checkout by hand, because it takes other agents' half-done work with it. The one whole-tree commit is the ticket completion step, covered in Ticket dispatch below. On 2026-10-18 a whole-tree commit (`3e1e8245`) took in the orchestration edits of an agent still working, and the file was then committed in that state. Another session's commit can take your uncommitted lines with it: on 2026-10-14 commit 520c8d9 (ticket 7daa5005) swept in a first pass of edits to `server.py`, `stream.js` and `module.py`, while the later fixes stayed uncommitted on top. After each save, `git show --stat` the newest commit and `git diff -U0 -- FILE` for your lines; name in the report any of your files a commit took, and the fixes left uncommitted on top, since that commit alone can fail tests. When the `metaform` MCP server fails to connect (on 2026-10-14 with `No module named 'yaml'`), its tools are gone for the session. Say so in the report and in the ticket's `op=edit` note, then do the ticket and memory writes through the CLI (`uv run metaform map work op=step id=ID said="..."`, `uv run metaform memory ...`), and do not present the CLI route as a fix. Reading memory: never `memory_read_graph node=element:<address>` for an element's notes. On 2026-10-15 it returned 87,660 characters, the tool refused the result and pointed at a file to chunk through. Read the named entities you need (`open_nodes`, by name) instead. Memory argument shapes through the CLI: `create_entities` takes a JSON list of `{name, entityType, observations}` with `node=NODE`, and a new entity also takes `why`, one line saying why it is worth keeping, which the MCP schema requires; to correct a stale observation, read it back with `open_nodes`, then `delete_observations` takes `[{entityName, observations:[exact old text]}]` and `add_observations` takes `[{entityName, contents:[new text]}]`, both with `node=NODE`. Memory citations (`memory_create_entities` `cite`) resolve only inside the project folder the MCP server runs in: a path in a sibling repo such as /home/rich/roundtable fails the whole entry, so cite project files or leave `cite` out and name the other repo in the text. Full rules, including source passes and source_placement runs: `references/ticket-work.md`. Before reporting a deleted map element as gone, re-read it with `map_element` after a short wait, since a stale server can re-make it (see the section on fixes to running code).

## Ticket dispatch: name the agent, hold in order, tell parallel agents
- Every ticket names the agent `agent=claude`. The person's rule is Claude agents only, and a `codex` or `gemini` row on the board shows a path nobody chose. Create a held ticket with `uv run metaform map work op=add node=ADDRESS kind=enhancement agent=claude hold=true title="..." task="..."`, and write its place in the chain in `note=` (for example "Held: runs after ADDRESS#N"). Resolve the work id from the item address with `uv run metaform map work node=ADDRESS limit=0 --json` (match `map.item`) before starting it. `dispatch start` refuses the item ref (`code.interface.graphical#148`) with "No work record has the id"; it takes only the hex work id.
- Build any text holding apostrophes, parentheses or line breaks in shell variables from a quoted heredoc (`task=$(cat <<'EOF' ... EOF)`), then pass `task="$task"`. Otherwise bash fails with `syntax error near unexpected token` and nothing is filed.
- A `task=` carries its own check: the steps to run and what should show when it works. Each boundary the person set goes in as a "leave X alone" line. The agent reads only the ticket, so anything left out of it can be changed.
- Start with `uv run metaform dispatch start WORKID claude`, then `uv run metaform dispatch wait stopped id=WORKID` in the background, since it blocks. Read `done:`, `resolution:` and `steps_done:` from `uv run metaform map work id=WORKID` before reporting. A ticket already taken by your own session resumes with `op=plan` and `op=step`, never `op=take`.
- Slots: `dispatch_machine_agents` caps the agents on the whole machine across projects (8 on 2026-10-19; the person raises it in Settings, "Agents on this machine"). Never start a ticket's work in a subagent of your own to get past a full machine: that routes around the cap the person set, and it is the same workaround as retrying. Leave the ticket in To do, say so, and name the setting.
- Old slot text, superseded: `dispatch_agents` allowed 5 agents at once. A start that finds every slot taken fails with "Every agent slot is in use"; the ticket stays in To do and starts itself when a slot frees. Do not retry it or report it as stuck. The person's own system agent is the exception: `own_room` in `dispatch/__init__.py` lets it take one place beyond `dispatch_machine_agents`, so background work never refuses their chat. Other summons still count against the machine limit; the machine-ceiling tests in `test_dispatch.py` check both sides. Tickets that touch independent files may run side by side up to that limit. The one-agent-at-a-time rule above is the default for work the person has not released in parallel.
- Release each held ticket when the one before it lands: `uv run metaform map work op=edit id=WORKID hold=false`, then `uv run metaform dispatch start WORKID claude`.
- Shared files: when two running tickets share a map file or the store layout version, send each the other's scope with `uv run metaform dispatch note to=WORKID "what, where, who goes first"` and check for the "said:" line. A note reaches the agent after its turn in flight, so expect a reply, not an instant change. When both tickets change the store layout version, the note says which bumps first and which files each edits. Keep the map module importable at every step: a broken map module takes down every agent's map tools and the web page.
- Notes: a note names exactly one recipient (`to=`, `at=`, `file=`, `topic=` or `reply=`), is at most 1000 characters, and is rate-limited to about six an hour. Batch what one agent needs and check `dispatch peers` before a second note. A note to a finished agent reaches no one, and a reply to an ended sender is refused: if the target is gone, put the content on the ticket. A `wait=` note that times out means the agent is mid-turn; do not resend it.
- Decisions: only `uv run metaform dispatch message WORKID "..."` counts as the person's decision to the agent on that work. A note that relays a decision is peer information, and agents kept building for several turns after one (2026-10-18). When the person decides something about running work, send it with `dispatch message` to each working agent at once, and put it on the ticket. A message to an idle agent is not acted on: run `dispatch peers` after it, and start the agent if it is still idle.
- A spec that lands while tickets run: cite its record ids on each governed ticket (`map work op=edit` with the note extended), then `dispatch message` each running agent, naming the records and the open questions it must not build past.
- Restart a worker with nothing resumed: `uv run metaform dispatch new WORKID` (CLI only). Never stop then start: `dispatch stop` on the system agent turns `dispatch_stay_connected` off, and a stopped worker keeps its ticket taken, so `dispatch start` refuses it.
- Closing is the person's call: offer, then wait for their yes before `op=done`. Cancel with `uv run metaform map work op=done id=WORKID resolution="Cancelled: what replaced it" why="who decided, date"`. A worker cannot cancel (`dispatch cancel` refuses it, and `op=done` records completed), so the system agent closes. `op=done` ignores `said=`, so put the closing account in `resolution=` and the reason in `why=`. A done on a record already closed keeps its first resolution, so put the full account in the first close. A ticket noted "likely fixed, not yet verified" or with "Not checked:" closes only when each named check has been run.
- A ticket a review files from its own finding is not a request. Check that the person raised the problem before starting it. When the person drops such a line, note each ticket on it, stop them, and cancel the held ones.
- A completion commits the whole shared tree under the person's git name, so it can take other tickets' uncommitted work along. Name in the resolution which other tickets' work the commit carried, and tell the person that completions commit. Before a completion runs while others are running, confirm the guard in `dispatch/merge.py` is present; it acts only on a real worktree (its `.git` is a file). This is the one whole-tree commit the system makes. The commit-by-name rule above still binds every agent's own commits.
- A landed fix does not reach a process started before it (the MCP server, any runner). When a change alters behaviour another open ticket relies on, send that ticket a dispatch note that names the restart, and put the restart in the resolution.
- A worker that lacks `orchestration_*` or `memory_*` tools: check the tool list the dispatcher passes before blaming deferred tool search (on 2026-10-18 Metaform's own list and instructions left them out). A session keeps the list it started with. Use the CLI fallback (`uv run metaform orchestration check-in ...`, `uv run metaform memory ...`) and say so in the report. A peer message that asks for a reply names its reply action (for example `dispatch_note reply=ID`). If `ToolSearch` on that name finds nothing, do not guess the sender's session from `ListAgents`: write the reply into your ticket's note, and say in the report that the sender has not received it.
- A flaw the person reports from web chat is filed at the code where it lives: `uv run metaform map work op=add node=ELEMENT kind=flawed agent=claude`, asking for the fix in shared code. A settings change may be named only as a labelled stopgap for this person. Once the person approves a ticket's wording, file and start it without a second confirmation.
- Trouble outside your ticket is filed, not left in chat: a failing test or fault you did not cause (for example, a file of tests red in the shared tree) gets `uv run metaform map work op=add node=ELEMENT kind=broken agent=claude title="..." task="..."` at the element that owns the file, with the failing test IDs, the commit each was checked at, and the check that proves it fixed. Name the ticket in the report. Before you read a red test as a regression from your change, run `uv run metaform dispatch peers file=PATH` for each failing file: a file another agent is editing mid-task explains the failure, and a background check that goes red while peers are mid-edit is not a verdict on your change. A problem the person asks you to add to "the list" goes into the day's report under `artifacts/reports/` as a new numbered section, with a ticket filed for each item that has a fix.
- Reads: read a running ticket when its wait starts and when its result arrives, not on every turn. Read a node once when an assignment starts.
- Repeated deliveries: when the orchestrator re-sends an assignment whose `assignment_id`, `work_id` and task text match one already handled, it carries no new fact. Make no memory or ticket read for it; reply in a line only if the state changed, and otherwise send nothing.
- Refs never move. A ticket that links refs says each stays at the element or join it was linked at. A property link settles at the longest common prefix of its addresses and never moves toward the leaves.
- A CI-configuration ticket closes on the config change, and its proof is a green run on a separate ticket. If GitHub refuses every job (each ends in seconds with no steps run), name that as a billing refusal in the resolution and leave the proof ticket open.

## Orchestration check-in: state word, summary, then key=value
- Return a ticket with the state word, the quoted summary, then the keyword arguments: `uv run metaform orchestration check-in STATE "SUMMARY" assignment=ID 'candidate=JSON' 'evidence=JSON LIST'`. `assignment=` placed before the state word or the summary is refused ("assignment= comes after the required nouns"). Quote JSON in single quotes so the shell does not split it.
- States: `running`, `waiting`, `blocked`, `returned`, `delivered`, `failed`. `completed` is refused. A finished worker with no assessment waiting checks in `delivered`, with `work_so_far` naming what the person still decides (a commit, a spec amendment), then closes with `map work op=done`.
- When an FQC assessment takes a worker's evidence, check in `returned` with `evidence` and `candidate` set before the close. A `done` before that check-in returns the assessment an empty evidence list and the old candidate; if the order was missed, put the corrected candidate and evidence in the FQC ticket's note with `map work op=edit`. Check in first on every return, never as a fallback: the order was missed on four FQC assessments on 2026-10-18 (f83d5705, fbb433cf, f3e13b67, 00deb395), each left with empty evidence or the old candidate. It was missed again on 2026-10-19 (assignment f47e0063, FQC ticket #11 on code.scheduler.task): the worker closed its record as `delivered` before any evidence check-in, and a check-in sent afterwards did not attach the evidence, so the record stayed `delivered` with `evidence: []` and only the FQC ticket's note carried it. A check-in after a close does not repair the record; put the evidence on the FQC ticket with `map work op=edit` at once, and check in first next time. It was missed again on graphical#136 (c781ec60, 2026-10-18), whose session had no orchestration check-in tool loaded: take the CLI check-in above before the close, not after. Once a record is `returned` after the assessment accepts it, a later `delivered` leaves it `returned`. A `returned` check-in also closes the worker's work record: a `map work op=done` sent after it answers "done: This work record was done at ...; its resolution was kept" and changes nothing. Do not retry that done; read the ticket back with `map_work` to confirm the summary is the recorded resolution, and put any account you still need in the check-in summary, since it is the one that lands.
- `candidate` is one JSON object: the work's `kind` (`working-tree` for a working tree), its `branch`, and the changed `files`. `evidence` is a JSON list of the commands run and what they showed: the test counts, and the failure seen without the fix.
- Re-read each evidence line against the tree before the check-in: a file's final bytes (`od -c` or `tail -c 1`), whether a probe file is really gone, a test count from the run in front of you. The GC acts on the evidence as written. On 2026-10-18 an FQC check-in claimed a spec file's final newline had been restored; it had not, and the error surfaced only after the ticket closed.
- The summary carries the work's own result. Name any part left to another ticket by its id.
- A spec revision an assessment publishes goes through `uv run metaform orchestration change` with `specification={"path": ...}` naming the file. A revision is the sha256 of the exact bytes, and `"$(cat FILE)"` strips trailing newlines, so after publishing compare `sha256sum FILE` with `current_revision` from `uv run metaform orchestration changes`. Once published, the file keeps the published bytes: a later edit is a new change order, never a silent trim to match.
- Every finding carries a `title` (one line) and a `task` (the steps and the check). Other keys such as `summary` or `remediation` make the title or task the Python repr of the whole dict. Read the new ticket's title back with `map_work` after each check-in, and if it shows a dict, `map_work op=edit` it at once. Tasks are prose, never a dict string.
- A finding is filed only when no open ticket at its node carries the same normalised signature. A repeat adds its new evidence to that ticket's note.

## Memory notices and observations
- Unread notices: a "N unread" notice asks you to read a record once. It is not a standing task. Call `memory_read_unread` with `node` alone first. Do not pass `fields=["name"]` alone: on a node whose records hold no `name` it errors. When a triage read is empty but the notice still counts updates, make one `view=full` read, then stop. The same notice text is one notice: once a read of that node came back empty, make no further reads of it in the session, whichever view or filter, until the notice text changes. On 2026-10-18 one session repeated the identical "14 memories; 4 unread" notice across many turns, and every read it made came back `{}` or empty.
- An empty result means nothing new. If a notice repeats the same count for that node, make no tool call and send no reply, whether your last read there came back empty or returned records. A read that returned records does not clear the count, so the identical notice that follows is not new: re-read only when the count or the text changes, or the records have changed since your last read.
- Reply with new facts only, in a line or two. Name a waiting item again only when its state changed.
- The count can include your own writes and disagree with the read. Take the read as the truth, do not write a memory about the miscount, and mention it in one line at most. A notice that repeats right after your own `memory_add_observations` on a node is that write counted again: one `node`-only read settles it, and after an empty read make no further reads of that node, even when each turn repeats the notice. The CLI `memory read_unread` refuses `view=count` ("read_unread does not take 'view=count'"); use `node` alone or `view=full`.
- A `must_contain` or `fields` read leaves the rest unread, and the notice keeps counting it: on 2026-10-18 `fields=['name','entityType']` listed 13 entities and a `view=count` read still gave total 12. When a notice repeats after a narrowed read, read the whole node once with `node` alone (or `view=full`).
- Observations: write each as one sentence stating one fact about the entity. The store refuses an observation holding two facts (a semicolon, a line break or a second sentence) and names the one it refused.
- Send the delete and the add as separate calls: in one batch a delete landed and the add was refused, leaving the entity without its new lines. Read the add's reply first, and re-send a refused add alone once it is split.
- To replace a stale line, read its exact text with `open_nodes`, delete that text, then add each corrected fact as its own observation.
- Keep only facts that will still hold after the next change. Dated history of a fix belongs in the ticket note.
- Pass `node=` on every call. Shapes: `memory_add_observations` takes `observations: [{entityName, contents: [...]}]`; `memory_delete_observations` takes `deletions: [{entityName, observations: [exact old text]}]`. A new entity also takes a `why` line.

## Orchestrating: write the ticket, start one agent, do not code it yourself
- Decision of 2026-10-19 (the person's): the GC role is to be removed. Tickets are taken directly by worker agents, one worker per ticket, as dispatch did before the orchestration merge 4f2966c8, and Full Auto runs as many workers as there are slots, so a swarm picks up the issue list. Until that removal lands, the GC and FQC rules below still hold. The open question is whether the reviewer (FQC) stays as one pass per ticket that fixes what it finds in the same run, rather than filing new tickets; get the person's answer before changing the check-in rules.
- A request for work becomes a ticket (`uv run metaform map work op=add`, with the node, the element's files and line numbers, the evidence and the check that proves the fix), then one agent is started on it: `uv run metaform dispatch start ID claude`. Follow it with `uv run metaform dispatch wait stopped id=ID --dispatch-wait-seconds 3000` in the background, and review what it changed before telling the person it is done. If the session stops with the ticket still open, `uv run metaform dispatch message ID "..."` names the step to resume from (the step number, not a re-plan), then wait again; read `done:`, `resolution:` and `steps_done:` from `uv run metaform map work id=ID` before reporting.
- When you are the system agent answering the person, do not edit code yourself, even for an obvious fix. A question about the system ("why aren't you orchestrating", "where is the prompt") gets an answer; the fix it exposes becomes a ticket.
- Keep one agent running at a time unless the person says go and the cost is stated. Once the person has asked for a swarm of workers over an issue list, the slot limit governs how many run, not this default. If you have said a second ticket waits because two agents would run at once, it keeps waiting until they say go. Parallel tickets that touch independent files are governed by the slot limit in Ticket dispatch below.

## Project data lives in layers
Every piece of project data is in a layer, or linked from one (LAYER-001, "Everything Metaform holds is a layer"). A body too big or too raw for a layer item (transcript, report, recording) stays where it is kept, and a layer item at its element points to it. Machinery (settings, process state, caches) is the only exception, decided with the person. Before adding or reviewing any store of project data, name its layer or its link. Known drift: work (tickets, steps, links, the board's backlog, todo, doing and done) lives in the map module's own tables (`work`, `work_links`, `work_steps`) and is no layer, though MAP-046 designed statuses as layers. Memory (`modules/memory`, `LAYER = 'memory'`) is the working example. Do not move or delete data to bring a store into layers; that migration is ticket code.graph.knowledge#a.

## Public base additions
A module reaches chassis code only through the public base (`metaform.module`, `settings`, `data`, `events`, `prompt_files`, `axiom`, `home`, `outline`, `finish_xml`). A helper a module needs from elsewhere in the chassis (`src/metaform/sqlite.py`, say) is re-exported from a public module, never imported directly: `tests/test_base.py::test_every_shipped_module_imports_only_the_public_base` fails on any other import. `metaform.skills` (the skill registry: `served`, `bound`, `libraries`) is not in that public set yet, and `mcp/server.py`, `workflow` and `dispatch` all import it, so that test already fails on it; whether it joins the public base is the person's call, so do not add a new `metaform.skills` import from a module without saying so in the report. Each addition is written into `modules/template` (code, README, `CHANGELOG.md` Unreleased) in the same change. A verb wrapper in a package `__init__.py` must not share a submodule's name: a function `a2a_peers` shadowed the `a2a_peers` submodule on the mcp package, so the submodule's own imports broke. The mcp wrappers are `list_peers`, `add_peer` and `remove_peer` for that reason.

## Titles from titled()
`titled(ctx, what, title, why, ...)` in `metaform.module` only checks a write and returns None. A verb that passes its return value as the title sends None, and the ticket then shows the task's first line instead of the intended title. Build the title as a string first (`str(ctx.nouns.get('title') or ...)[:120]`) and pass that string; `titled` refuses a missing title, it does not supply one.

## Module verbs and settings
- A new capability ships as one unit: the module's declaration, README, `CHANGELOG.md` Unreleased entry and spec bullet, with tests in its existing test file. Also keep the hand-kept tool reference `docs/reference/metaform-mcp-server.md` in step (nothing generates it): one row per tool with its effect (read, write, remove, open world), and grep the verb name in the README, CHANGELOG and that file after any change so no row keeps an old signature.
- A verb that writes or reaches the network declares its effect; the guard `test_every_verb_that_reaches_the_network_or_writes_declares_it_in_its_annotation` in `src/metaform/modules/mcp/tests/test_mcp.py` checks it. It can flag a verb you did not touch: check with `git log -S` first.
- A failed verb's answer does not ask the agent to report a failure the system already recorded. When autoticket took the fault and the pass returned its ticket, the answer says `Next: this failure is filed for a fix as ticket <id>; call metaform_feedback only for what this error does not say`. When it took the fault but returned no ticket (the group waits for a slot, or another pass merged it), the answer says `Next: this failure is recorded for a fix; call metaform_feedback only for what this error does not say` instead, because "filed" is false until a ticket exists. Any answer wording must be true in every branch it covers, and the spec line (`specifications/06-mcp-install.md`, MCP-006 build) is updated in the same change with its date and ticket. `Next: call metaform_feedback and say what you called` stays only for a fault nothing took (no project, or autoticket off). A test that files faults through an MCP or chassis test home calls `run('enable', 'autoticket')` first, since the test home does not have it on, and asserts both answers.
- A server agents start and stop gets one restart verb (`metaform web restart`), never a stop an agent must follow with a start.
- Ruff ISC004 fails a test edit that writes an implicit string concatenation inside a list without parentheses. Wrap the concatenated pieces in their own parentheses, `(f'...' '...')`, then run `uv run ruff check` on the touched test file before the pytest run.
- A module's `__init__.py` must not import a name `SUPPORTED_OS` from a helper: discovery reads it as one top-level literal and the build breaks. Name the helper's tuple differently and pass it to `Verb(supported_os=...)`.
A verb or setting lands as one unit: the module's `__init__.py` declaration, its `README.md`, its `CHANGELOG.md` Unreleased entry, and the spec bullet it cites, with tests in the module's existing test file. A module with no `CHANGELOG.md` gets no entry; its README still changes. When only a verb's `effect` or `open_world` changes, its row in `docs/reference/metaform-mcp-server.md` changes too: that file's tables are generated from the running server, so the Effect column (`write, open world`, `read`, `remove`) must match the declaration. A verb's `caution` text changes its row the same way (the server shows it as `summary Caution: text`). A caution is enforced on both surfaces: MCP stops the call without `confirm: true`, and the CLI stops it without `--confirm` (`cli.py`, `if verb.caution and not parsed.confirm`). So when a verb gains a caution, grep `tests/` and `src/` for its CLI form and add `--confirm` to each call that must still run, and add a test that asks for the confirm over MCP. Next-step texts that print the bare command (`metaform map activate <name>`) now lead to a stop; say so in the report rather than editing them silently. A fixed set is a choice setting, never free text. ## Dispatch thread lines
Every new line in a session's thread is numbered by `signals.add_line(tx, ...)` inside the write transaction, from the rows past the writer's last-known seq. Never take a seq from a process counter: a second writer on the session (another runner, a served session) then gets the same number. `Session.table(fatal=False)` logs a failed line write and carries on, so a bug on the line path stays silent; test line writes through the thread itself, as `test_a_second_writer_on_the_session_never_ends_the_runner_and_lines_keep_one_order` does. A `tx.rows(by=('session_id', 'seq'), after=...)` cursor must carry both values, `[seq, name]` (the key column is appended to the index's rest); a one-value cursor raises an SQL error. Reads of the thread right after `dispatch.start` can be empty: use `max(..., default=0)`, and wait with `eventually` for the lines a test asserts on. Spec: code.dispatcher.agent#12.

## Store upgrades and concurrent openers
When several processes open an old store at once (web server, MCP server, runners after a release), one upgrades it and the rest wait and read the new file. `upgrade()` in `src/metaform/data/upgrade.py` holds `<store>.upgrade.lock` (`sqlite.file_lock`) and re-reads the layout inside it. The guard against the race is `test_three_processes_opening_a_layout_10_store_at_once_all_read_it_upgraded_once` in `tests/test_store_upgrade.py`: it failed 3 of 3 runs before the lock (one process raised `disk I/O error`) and passed 5 of 5 after. The general rule and the SQLite facts behind the guard connection are in `check-then-create-under-lock`. A table cannot change place (`metaform` or `project`) under its own name: `data/tables.py` `_upgrade` raises `moves X from the metaform store to the project store, and the rows here would be lost`, and the module's upgrade hook never runs. A move is a new table name, declared at the new place, with a carry from the old table on every read (dispatch version 14: `spending` at project place, `carry_spend` reading the per-metaform `spend`); whether a table may keep its name across a place move is a chassis decision for the person. Prove an upgrade on a scratch home (recipe and pitfalls in `verify-store-schema-change`): `git archive HEAD src | tar -x -C /tmp/<dir>`, enable the module first (a disabled module declares no tables, so the store read raises `dispatch declares no tables`), `home.ensure_base(project)`, seed rows with the HEAD code, then read the same totals with the working-tree code against a copy of that home. No schema change unless the ticket's own task needs it (AGENTS.md, "No schema change unless the task needs it"). Do not add, drop or retype any module's tables, columns or keys as a side effect of a fix. If a fix seems to need one, stop and say so in the ticket note, and the orchestrator decides. On 2026-10-14 two fixers each changed dispatch's tables and both called the result version 14, and the same-version refusal then stopped dispatch and the page. An approved change raises `Tables(version=N, ...)` once, says why in the comment above `TABLES` and in the ticket, keeps `compatible_from` at the oldest version that still reads the tables, and updates `tests/module_tables.snapshot.json` in the same commit (`METAFORM_TABLES_SNAPSHOT=write uv run pytest -n 0 tests/test_module_tables.py -k snapshot`). Two open tickets never share one version number. `test_no_module_changes_its_tables_without_the_snapshot_saying_so` fails on any unrecorded change, naming the module and whether the version was raised. Since ticket 03f869a0 (2026-10-15), `data/tables.py` `state()` and `ensure()` judge a store by its real schema (`pragma table_info`, index lists), not by the declaration text in `meta`. A missing table, optional column or index is added in place with no backup. Only a real conflict raises: a key, type or default differs, or a required column with no default is missing. Since ticket 13b34894 (2026-10-15) a CHECK, foreign key, collation, ON CONFLICT resolution, generated column, partial-index condition or a held unique index the code lacks is compared too, as SQL tokens from `sqlite_master`, and any difference conflicts; a raised version rebuilds the table for it. It raises for that module alone, and `ensure_extensions` holds each module under its own savepoint. Upgrades take "before" from the real tables, so a column the record never named is kept. A test module rewritten to the same byte size reuses stale bytecode (the mtime and size match), so a `user_module` variant must differ in size; add a comment line at the module's indent. `sqlite.file_lock` with `wait=True` no longer gives up on Windows (fixed 2026-10-14, ticket #2e). msvcrt's `LK_LOCK` gives up after ten tries a second apart, so the win32 branch now retries `LK_NBLCK` every 0.05 s with no cap until the holder lets go; `wait=False` still raises `Held` at once. Keep no timeout on `upgrade()`'s lock: a waiter must wait for the upgrade to finish. The Windows wait is guarded by `test_a_process_waiting_on_a_file_lock_held_past_ten_seconds_gets_it_when_the_holder_lets_go` in `tests/test_store_upgrade.py`; on Linux that test passes with or without the fix, so its proof on the win32 branch is in `verify-guard-test-by-mutation`.
