# Changing Metaform

Read the one subfile for the class of work you are in before editing. Each rule came from a real defect in this repo.

## Tickets and source passes
Report each step with its own `metaform map work op=step` (one note over steps 3 to 6 left the board at 5 of 8; on 2026-10-14 the notes "Steps 5-6" and "Steps 7-9" left it at 4 of 9, so count per step, never a range), and close with `op=done` only after the acceptance checks pass. `op=plan` takes only a step count and drops its `said` text, so write the numbered plan into the first `op=step` or into `op=edit note=`, then read the ticket back to confirm it landed. When an orchestrator note sends you back to a ticket that is already `done`, first map each numbered item of the note's addition to code and tests already in the tree, and report that mapping with file and test names. Build only the items that are missing, as new numbered steps on the same ticket, and say which ones were already there; never rebuild a built item or reopen the ticket silently. Never edit a spec record from a ticket; the person writes specs, and a record's `Built` line is part of the record. Put the built state in the step text and the `op=done` resolution, and name the record line in the report for the person to amend. Where code and a spec record disagree, the code is the reference: never change code to match the record, since that rolls back features; report the difference and draft the record text in `artifacts/specs-draft/`. A worker agent cannot `op=add` a ticket (refused: tickets are written by the person and the agents that serve them), so a follow-up ticket goes into its own ticket's `op=edit` note for the orchestrator to file. Spec text drafted for the person goes to `artifacts/specs-draft/`, never `specifications/`, until the person approves that exact wording. Once they approve it (for example "the spec is APPROVED; build it now"), the approved wording goes into the spec file as an amendment bullet marked with the date and `approved by the owner`, the view record that cites the rule gets a matching amendment and its Relates-to line updated, and the report names both bullets so the person can review or reverse them. When a design is replaced, delete only the memory observations the new design contradicts: `open_nodes` the entity first, check each line to delete for facts that still hold (a deleted line also named a still-true eye-view fact and had to be re-added on 2026-10-15), re-add those kept facts with `add_observations`, and say which were kept. When a notice says a ticket's task has been replaced, re-read the ticket with `map_work` before more work, and do not restore the replaced behaviour. A ticket assigned to one module does not edit `src/metaform/*.py`. In a shared tree where another agent already has uncommitted edits in a file, change only your own lines and do not commit without the person's yes. Another session's commit can take your uncommitted lines with it: on 2026-10-14 commit 520c8d9 (ticket 7daa5005) swept in a first pass of edits to `server.py`, `stream.js` and `module.py`, while the later fixes stayed uncommitted on top. After each save, `git show --stat` the newest commit and `git diff -U0 -- FILE` for your lines; name in the report any of your files a commit took, and the fixes left uncommitted on top, since that commit alone can fail tests. When the `metaform` MCP server fails to connect (on 2026-10-14 with `No module named 'yaml'`), its tools are gone for the session. Say so in the report and in the ticket's `op=edit` note, then do the ticket and memory writes through the CLI (`uv run metaform map work op=step id=ID said="..."`, `uv run metaform memory ...`), and do not present the CLI route as a fix. Reading memory: never `memory_read_graph node=element:<address>` for an element's notes. On 2026-10-15 it returned 87,660 characters, the tool refused the result and pointed at a file to chunk through. Read the named entities you need (`open_nodes`, by name) instead. Memory argument shapes through the CLI: `create_entities` takes a JSON list of `{name, entityType, observations}` with `node=NODE`, and a new entity also takes `why`, one line saying why it is worth keeping, which the MCP schema requires; to correct a stale observation, read it back with `open_nodes`, then `delete_observations` takes `[{entityName, observations:[exact old text]}]` and `add_observations` takes `[{entityName, contents:[new text]}]`, both with `node=NODE`. Memory citations (`memory_create_entities` `cite`) resolve only inside the project folder the MCP server runs in: a path in a sibling repo such as /home/rich/roundtable fails the whole entry, so cite project files or leave `cite` out and name the other repo in the text. Full rules, including source passes and source_placement runs: `references/ticket-work.md`.

## Project data lives in layers
Every piece of project data is in a layer, or linked from one (LAYER-001, "Everything Metaform holds is a layer"). A body too big or too raw for a layer item (transcript, report, recording) stays where it is kept, and a layer item at its element points to it. Machinery (settings, process state, caches) is the only exception, decided with the person. Before adding or reviewing any store of project data, name its layer or its link. Known drift: work (tickets, steps, links, the board's backlog, todo, doing and done) lives in the map module's own tables (`work`, `work_links`, `work_steps`) and is no layer, though MAP-046 designed statuses as layers. Memory (`modules/memory`, `LAYER = 'memory'`) is the working example. Do not move or delete data to bring a store into layers; that migration is ticket code.graph.knowledge#a.

## Public base additions
A module reaches chassis code only through the public base (`metaform.module`, `settings`, `data`, `events`, `prompt_files`, `axiom`, `home`, `outline`, `finish_xml`). A helper a module needs from elsewhere in the chassis (`src/metaform/sqlite.py`, say) is re-exported from a public module, never imported directly: `tests/test_base.py::test_every_shipped_module_imports_only_the_public_base` fails on any other import. `metaform.skills` (the skill registry: `served`, `bound`, `libraries`) is not in that public set yet, and `mcp/server.py`, `workflow` and `dispatch` all import it, so that test already fails on it; whether it joins the public base is the person's call, so do not add a new `metaform.skills` import from a module without saying so in the report. Each addition is written into `modules/template` (code, README, `CHANGELOG.md` Unreleased) in the same change. A verb wrapper in a package `__init__.py` must not share a submodule's name: a function `a2a_peers` shadowed the `a2a_peers` submodule on the mcp package, so the submodule's own imports broke. The mcp wrappers are `list_peers`, `add_peer` and `remove_peer` for that reason.

## Titles from titled()
`titled(ctx, what, title, why, ...)` in `metaform.module` only checks a write and returns None. A verb that passes its return value as the title sends None, and the ticket then shows the task's first line instead of the intended title. Build the title as a string first (`str(ctx.nouns.get('title') or ...)[:120]`) and pass that string; `titled` refuses a missing title, it does not supply one.

## Module verbs and settings
A verb or setting lands as one unit: the module's `__init__.py` declaration, its `README.md`, its `CHANGELOG.md` Unreleased entry, and the spec bullet it cites, with tests in the module's existing test file. A module with no `CHANGELOG.md` gets no entry; its README still changes. When only a verb's `effect` or `open_world` changes, its row in `docs/reference/metaform-mcp-server.md` changes too: that file's tables are generated from the running server, so the Effect column (`write, open world`, `read`, `remove`) must match the declaration. A verb's `caution` text changes its row the same way (the server shows it as `summary Caution: text`). A caution is enforced on both surfaces: MCP stops the call without `confirm: true`, and the CLI stops it without `--confirm` (`cli.py`, `if verb.caution and not parsed.confirm`). So when a verb gains a caution, grep `tests/` and `src/` for its CLI form and add `--confirm` to each call that must still run, and add a test that asks for the confirm over MCP. Next-step texts that print the bare command (`metaform map activate <name>`) now lead to a stop; say so in the report rather than editing them silently. A fixed set is a choice setting, never free text. A setting's web heading is its `heading` field, never `section`: `section` nests a submenu in the terminal settings screen and broke 5 tests in `tests/test_tui.py` when first used for the web. Wording a setting's choices (`choice_help`) applies only to settings that declare words for them: wording every choice turned the project id `proj` into `Proj`, and identifiers are shown exactly as stored. Tests: a project-place test module needs `SUPPORTED_OS`, or it loads with `SUPPORTED_OS is required` and its setting 404s. When a ticket session has `METAFORM_ROLE`, `METAFORM_SESSION`, `METAFORM_WORK` or `METAFORM_NODE` set, unset them for the pytest run. Browser tests (`-m browser`) passed under `METAFORM_BUILD_VIEWS=1`. A running web server keeps its old code until restarted. A setting's choices function (`setting.options(folder)`) runs on every `tools/list`, `config --show`, help and select validation, so it does no network or other slow I/O: a remote list is kept by its own verb, which writes it (that verb's effect becomes `write`, which the MCP declaration guard checks), with a published constant as fallback. A `scope='global'` setting's list is kept in a home file, not a module table: `home.write_private(home.home() / '<module>' / '<name>.json', ...)`, read with a plain file read, with the constant as fallback. A module table has only the `metaform` and `project` places (`data/tables.py` Place), so a table-backed list is per project, and a global setting then accepts different values from each folder it is set from. A table fits only a project-scoped setting; a home-wide place is a chassis change, outside a module ticket. Update the module README's verb row with the declaration. A verb's `needs_project` and the module's `layered` flag decide what its MCP tool lists before registration and which arguments it takes: read the bodies to set them, and see `metaform-mcp-tool-listing`. A setting holds a whole number only (`settings.number`), so a dollar or other fractional limit is a whole-number setting, and the fraction is taken as the verb's argument (`spend=0.50`). A setting the person marks `person_only` binds agents too: MCP `set_schema` omits it and `refuse_person_only` refuses it; a verb's per-call switch for it is refused in `cli.run_module` under an agent `METAFORM_ROLE` by `settings.refuse_held_control`, the same check the MCP `_prepare` uses, and a limit among them: a verb that takes an agent-supplied override may only tighten the setting, and refuses a looser value saying only the person can raise it. Independent choices get one setting each: a single list setting holding many entries loses the others whenever one is saved. A list is stored member by member, never as comma text, on every web path: the settings screen draws a list without choices as a textarea, one item per line (`itemsBox` in `page/app/settings/screen.js`), and saves the array of its trimmed non-empty lines; `/api/settings` refuses a string for a list kind with 400 `<switch> is a list: send its items as an array.`, so the server never splits at commas. The CLI still splits on commas, so an item holding a comma awaits the person's form. `set_setting` sends every list array to `save_list`; nothing joins a list with commas on the web path any more. A list the running server does not declare is saved by `stored_list_there`, which runs `store_list_here` in the project's own folder so that folder's modules load there. Never load another project's modules into the server's own process: the loader keeps one process-wide cache and takes its project from the server's cwd. The child's `-c` program names the module path in full, because the server runs as `__main__`. A switch whose stored value would silently change later calls of another kind (a transport, a dry run, `--raw`, `--critic`) is `per_call=True`: given on its call, never read from storage (`settings.value` ignores a stored row), refused by `set` with the verb that takes it named, and left out of the settings screens and `config --show`. A choice that lets agents act without asking is `risky` (a tuple, or a function of a Context): `set` needs `--confirm`, the set tool `confirm: true`, the screen and the page a yes, and stepping never lands on one. A reset, unglue or clear writes only at the folder's own scope (`own_scope_of`, never `scope_of`); a value inherited from a folder above is refused, naming that folder. Changing what a stored setting means needs a one-time migration, run from the module's start hook through the public `home.save`/`home.clear` calls so caches and change notices stay right. Wire the start hook last, and first run it against a scratch `METAFORM_HOME` seeded with the old names: the moment the hook lands, every live Metaform process on a shared tree runs it on the real home (a second process racing the first left a folder move unrecorded in the marker). A scratch home is a copy, so it carries the real project paths and project ids: a copy that runs a start hook moves the real project folders (on 2026-10-14 another session's copy of `~/.metaform` moved the person's five placement runs, 448M, into `/tmp` within a minute of the hook landing). Before the hook lands, search `/tmp` for homes that register `/home/rich` paths, and never let a scratch home point at a real project folder. Give each migration step its own marker: a marker an earlier step already wrote makes the new step never run. Make each step idempotent. A read never carries a stored value: `settings.carry_once(step, carry)` runs from a module start hook only. A test of a carry deletes the `carried:STEP` meta row and clears `settings._carried` first, since the home's own first start already marked it. Prove a carry with one real CLI process start on a scratch home seeded with the old rows, then read `config --show` and the stored view afterwards; an in-process call alone does not show the start hook ran. A test home's own first start writes the migration marker, so a migration test removes that marker just before it calls the migration. Processes started before the change (the MCP server, live agent runners) still read the old declaration until restarted; say so in the report. Tab completion for a setting's choices works through `complete -C metaform metaform`, and module discovery must run inside that path too. Full rules: `references/module-changes.md`. Renaming a module is one change across its id, folder, tools, layers and settings: `git mv` the folder; rename the declaration id and tool names; rename the module's layer in every base (a layer-rename operation in the data layer, since none existed before); rewrite its members in the `modules`, `layers` and `jev_decisions` settings and in aliases; move the run folders out of each project folder's `.metaform/<old id>` into `projects/<project-id>/<new id>/` in the Metaform home, never leaving a `.metaform` tree in a project folder (intake and placement write run state only in the home, `getting-started.md` says so, and the run path must match `runs_root` and `pipeline._directory`); update prompts, README and help. Then re-record the memories under the new names and delete the ones that cite old paths. Recorded ticket text stays as written; the report names the running processes that still hold the old module.

## Changes that act on records already on the board
A change that lets autostart, a scheduler or any loop act on records already there runs them the moment it lands. Before it lands, count the live candidates from the person's real home, read-only, and say in the report how many will start, what each costs, and that the person may hold them first. On 2026-10-14 the marker change made eleven open markers that already existed into candidates for paid agents, one per node; the report named it only after the code was built. Verify such a change in a scratch home that is not a real project folder.

Legacy records left by an old behaviour are closed, never deleted. Close them with a terminal outcome (`completed`, `failed` or `cancelled`): the outcome list in `data/status.py` (TERMINAL) is shared by every module, so a new outcome value changes all of them. Put the reason at the start of the resolution, as ticket 9de74d83 did with 'Not a ticket: ...' for 71 empty intake records (2026-10-15). Run the close on a copy of the home first, per `sqlite-cleanup-dry-run-on-copy`.

## Removing a module or feature
Delete it; never switch it off (the person's rule). Before deleting, find everything only it used: grep its names, tool names, routes, setting keys, prompt ids, vendored files, `docs/reference` rows, test entries and `artifacts/specs-draft` drafts across `src`, `tests`, `docs`, `specifications`, `artifacts` and the template module. A removed setting key is grepped the same way in `tests/`, including `settings.assign('KEY', ...)` and `run('set', ...)` calls: a TUI test still assigning `report` after its removal only fails when that test runs, so the 2026-10-15 settings cleanup had to repoint it at `connect_instructions`. After deleting, run `uv run ruff check src tests conftest.py` (an import the deleted code alone used shows as F401 in a file that stays) and `uv run metaform help`. A deleted page part hands its place in the load-order chain (the `workspace.js` imports) to the part before it, or every later part loads out of order. Run `git ls-files` on any folder of artifacts before `rm`: untracked files cannot be recovered. Check removed web routes from the page's own origin: from outside the page every POST answers 403 "A write is taken only from the web GUI's own page.", so that proves nothing; from the page a removed route answers 404 "No such write". Running servers keep the old tools until restarted, so say so. Spec records and skills that still name the removed thing are the person's to edit unless the ticket names them for deletion; list them in the report.

## Demo and scripted agents
A demo or probe that writes tickets or dispatch sessions names `claude` as the agent on every row it writes (the `agent` in a ticket's `map` and `taken_by`). The person's rule is Claude agents only; a scripted agent that shows as `codex` or `gemini` on the board shows a path nobody chose. Read the agent names back with `metaform map work` in the scratch home before reporting a trial.

## Prompt fills
A fill slot in a `prompt_files.chassis` call cannot be named `folder`: the name collides with `required()`'s own parameter. Name the slot `<path/>` (or another name that is not `folder`) in `prompts.xml`, and check the rendered prompt with a call before reporting.

## Prompts on trial
Try a prompt text before it is approved, without editing `prompts.xml`: write a trial file in the same `<prompts><name>text</name></prompts>` shape and run the CLI with `METAFORM_PROMPTS=<file>`. Its non-empty prompts are read before the package's own (`prompt_files.TRIAL`). Check routing by role: no `METAFORM_ROLE` is the person's own agent, `METAFORM_ROLE=intake` gets the intake step, `METAFORM_ROLE=worker` gets neither, and with no trial file nothing is sent. Keep the drafted wording in `artifacts/specs-draft/` until the person approves that exact text, then move it into `prompts.xml`.

## Module data cleanup
A module removes its own data (run folders, launch receipts, caches) when the thing it depends on is gone. The chassis names no module folder: `home.clear_project` once removed `source_placement/` by name, and that was the wrong owner. Put the sweep in the module's start hook, keyed on current state (a run whose base the project no longer has), so one check covers every path that deletes the base: a clear, and a remove followed by registering the same source into the same home folder. Sweep only the home's own folder, never a project folder another home may share, and say what it could not remove and leave that for the next start. Before the sweep lands, count what it would delete from the person's real home, read-only, as under "Changes that act on records already on the board". Worked case: `source_placement._drop_orphaned_runs` (ticket code.analyzer.refactoring#18, 2026-10-14).

## Web page and browser tests
Make the page change surgically; a new POST route is classed in `route_class` (`web/server.py`) in the same change, or a Node member gets 403 on it (see `metaform-node-hosting`). Then make every browser test that touched the old control pass against the new one. Run `node --check` on each changed part. A key that starts a mode (listening, a menu) must not leave focus in a text box, or the next press of that key types instead. To check the page in a real browser, run a private server on a temp home and a non-default port, and stub the voice endpoints: `references/web-browser-check.md`. Launch Playwright headless with `env -u DISPLAY -u WAYLAND_DISPLAY` (under WSLg a headed window still shows on Rich's screen). A probe or test that starts `metaform web` sets `METAFORM_HOLD=` (empty) first, so it never writes the person's hold ledger; the suite's `conftest.py` does the same. It also unsets `TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN`, `TWILIO_API_KEY` and `TWILIO_API_SECRET`, because a web start with a Twilio number and credentials runs the phone check at once, and a scratch home must not reach Twilio through the person's shell. A start under the real `hold` works now: the watchdog runs through `/bin/sh` with the venv's interpreter named in the environment, and `metaform web stop` purges the call it placed, so a clean stop leaves no entry. Purge any entry your own run left behind (`hold purge metaform-web-<port>`), never another session's; general rules in `hold-supervised-processes`. Page performance work keeps its before/after harness and raw results in `artifacts/perf/<date-slug>/`: on 2026-10-15 the critic's scripts were gone because a scratchpad had been reused. Before touching the render path, read the recorded rules at `code.interface.graphical` (memory #69 to #6b): `css()` in `core/dom.js` caches root CSS variables, so any new writer of a root variable must clear that cache; the library's link particles stay off (`linkDirectionalParticles(0)`) and the page's flow reads `data.links`; a three-forcegraph purge frees only the children of an exiting object, so default spheres are freed on `childremoved` in `map3d/graph3d.js`. Method for cost numbers: `browser-idle-frame-throttling`. Take before and after screenshots into `artifacts/<ticket-slug>/`, then stop the server and delete the temp home. Headless pages fold the header at 1280px and 1600px wide (View sits behind the menu button, so `#settingsBtn` is "not visible" to Playwright) but not at 1440px: take demo screenshots at 1440px. When a layout change is blamed for a fold, measure the same page with and without the suspect element before naming it. The page's CSS has a global `header{grid-area:top}` rule, so a `<header>` inside a window lands in a phantom grid column; use a `div`. The CSS also has a global `.count{position:absolute;bottom:44px}` rule (the map's node count), so any new element with class `count` is pinned to the map's corner: grep `app.css` for a class name before using it, and name a new counter something like `stackcount`. From an agent session, unset `METAFORM_ROLE`, `METAFORM_SESSION`, `METAFORM_WORK` and `METAFORM_NODE` before starting it, and in the same shell before each `-m browser` test run, so the server or the test's CLI calls do not inherit the session's own role or node; after `metaform web stop`, confirm the port refuses connections and delete the temp folders. A picture taken from any camera other than the person's (`web look`) needs the 3D signs turned for that render, and the check must read a known label in it: same reference, section "Pictures from another camera". Full rules: `references/web-page-changes.md`. A browser check that a path filter skips in CI is not run by any other step, so a change to the chassis that the page reads (`src/metaform/data/`, `settings.py`) reaches the page with no browser test unless the filter names it; say so in the report.
A filter on what the map draws (depth, toggles) must apply in every builder, the 3D `graphData` and the 2D `build2D` alike, or the two maps diverge; a browser test asserts both maps draw the same ids. The settings screen shows one page at a time and always opens on Essentials (`openSettings` sets `CONFIG.page='essentials'`; no page is remembered, and the old `keptPage`, `.setpicker` and `page:<owner>` flyout are gone). Its side list (`#settings .setside button[data-page=<name>]`) holds Essentials, then the categories from `settings.CATEGORIES`, then Modules last under Advanced. A row on another page needs its category clicked first, e.g. `page.click('#settings .setside button[data-page="agents"]')`, or search with `#settings .search` and Enter, which focuses the first match. On Advanced each heading is a folded `details.setgroup[data-group=<Owner>]`; open it before touching a row. Without the pick the test waits on a row that is not drawn and times out at its first step. A row a setting only draws once enabled is no wait target either: `dispatch_agent` is absent until dispatch is on, so wait on an always-drawn row such as `#settings .setlist.essentials .setrow .control > *`. When a control's behaviour changes, grep its part's header comment and the module README for the old wording: `separated by commas` survived in `screen.js`'s header after the control changed. A page control that stores a `risky` choice asks through `confirmAct` and sends `confirm`; its browser test picks Cancel first and asserts the old value is kept, then confirms. Settings saved from the page are asynchronous: a browser test that reads `/api/settings` right after a key press polls until the value appears, and never asserts once. Console errors are checked too (`problems`): 3d-force-graph logs `node not found: <id>` for any link whose end is not a drawn node, so a link to a hidden parent is dropped before the graph is fed. An event handler that awaits before it reads `event.currentTarget` gets null after the await: copy the element into a `const` before the first `await`, and re-enable that same element when the write is refused, or the control stays disabled or marked `chosen` (the permission card in `session/tools.js`, Resume in `session/text.js`). A read never writes: `followView` in `views/settings.js` saved `web_graphics` on every settings read, and the load of the page was the write; a setting is saved only by the person's act (VIEW-011). A mascot or agent act that opens a box calls that box's opener (`openFor`), never the overlay stack's `opened()`, which returns quietly for an unknown box, so `web open` reports success and does nothing. The verb answers only after the page does: `open` must be in `MASCOT_ASKS` (`web/server.py`), and `openFor` returns `{error}` for a ticket not on the map, a pane not found or with the workspace off, or an unknown `what`, which the CLI and MCP exit non-zero on. The workspace has two layouts: `WS.on` is true only in the grid, while `WS.active` is true in the grid and the classic framed layout alike (the default). `openFor` must check `WS.active`; checking `WS.on` refused every real pane in the default layout. When the page answered and refused without a `next`, the CLI hint is `metaform web viewing`, since the page is open; `open the page on this project` is only for when no page answered. A verb noun named `id` never reaches the page: `mascot_request` overwrites the payload's `id` with its own request token and the page answers under that token, so send the noun under another key (`which`, as `open_on_page` does) and keep `id` for the answer. Any new mascot act with an `id` noun needs the same rename. A mode the person turns on that must survive changes of target (the agent view, `EYE.agentMode` in `page/app/figures/eyes.js`) is its own flag: never inferred from the derived state (`EYE.agent`, whether eyes are showing now). Target keys such as A read the flag and never clear it; only the mode's own key, or a swap that ends it, clears it. A tween that returns to the person's view saves the resting camera only when no save is held, because a re-entry while the camera is still easing back otherwise overwrites the return point with a midway pose. A met sign (`labels.js` `metSign`, the selected name drawn on a flat 2D layer over the scene, stretched to the rectangle its four corners project to) is right only square on, and its meeting holds the camera's near plane out at the sign. Any code that moves the camera off a meeting (agent view V or E in `figures/eyes.js`, the memory network's `into3d`, a flight) must call `meetEnds(now)` in `camera/fly3d.js` first, or the squeezed name and the cut-away scene stay on screen (ticket code.interface.graphical#63). A new camera mover follows the same rule.

## Sending project text out
A module that sends project text to a third party (a hosted model, an API) checks the person-only `jev` setting before every request and sends only through `metaform.jev`, the public base. An API key in the environment is not consent: people set `OPENROUTER_API_KEY` for other tools. Agents cannot set `jev` over MCP, so when it is off no caller can send. Every send path checks it, including a resumed run, so a run prepared while `jev` was on sends nothing after it is turned off. A verb that can send out declares `open_world=True`, never `effect='read'` with a read-only or idempotent hint, and a subscriber that can reach the network is declared on the tool that triggers it. The mcp module's `test_every_verb_that_reaches_the_network_or_writes_declares_it` (`src/metaform/modules/mcp/tests/test_mcp.py`) enables every module and walks each verb's calls from source: it fails on a network reach without `open_world`, and on a `read` verb that writes the map or settings or sends through `metaform.jev.post`. A connection to 127.0.0.1, localhost or ::1 is Metaform's own process, not open world; bookkeeping (tables made on first use, caches, the shown-once record) is not a write. ## Dispatch thread lines
Every new line in a session's thread is numbered by `signals.add_line(tx, ...)` inside the write transaction, from the rows past the writer's last-known seq. Never take a seq from a process counter: a second writer on the session (another runner, a served session) then gets the same number. `Session.table(fatal=False)` logs a failed line write and carries on, so a bug on the line path stays silent; test line writes through the thread itself, as `test_a_second_writer_on_the_session_never_ends_the_runner_and_lines_keep_one_order` does. A `tx.rows(by=('session_id', 'seq'), after=...)` cursor must carry both values, `[seq, name]` (the key column is appended to the index's rest); a one-value cursor raises an SQL error. Reads of the thread right after `dispatch.start` can be empty: use `max(..., default=0)`, and wait with `eventually` for the lines a test asserts on. Spec: code.dispatcher.agent#12.

## Home folder and file modes
The Metaform home is its owner's alone: a new home is made 0700 and every file in it 0600. Create any SQLite file through `sqlite.private` (`src/metaform/sqlite.py`) before SQLite opens it, so `-wal` and `-shm` get the same mode; `data.private_database` already does. Write run files and state through a helper that opens with `os.open(..., 0o600)` (`web.write_run` in `modules/web`; dispatch's `migrated-dispatch-agent-options` marker is written the same way, as `source_placement`'s marker is), never `write_text` or `open` at the default mode, which makes the file world-readable first. `home.make_private()`, called from `cli._command` before anything reads the home, tightens an existing home once and records `home_private` in the chassis meta, but only after a fresh `stat` of the root shows no group/other bits, so a root still open is retried at the next start. It resolves a `METAFORM_HOME` that is a symbolic link first and works on the link's target, chmodding the root before the walk, because the walk's lstat filter skips links; it keeps an executable's owner x bit by design. Test a linked home with a real 0755 folder behind the link, passed through `run(..., env=...)`. A test that loosens files to check tightening uses 0644 for files: 0755 keeps the owner x, so the test fails on that and not on the code. Windows keeps the access its parent folder gives, so skip such tests with `os.name == 'nt'`. Known gap, not a precedent: `run/looks`, `run/captures` and voice clips are still written at the default mode inside the 0700 home. So are the top-level folders the code makes with `mkdir` (`projects/` on the first `add project`, `run`, `backups`, `node`, `relay`, `models`, `modules`, `skills`, `builds`, `cloud`, `.agents`): `Path.mkdir(parents=True)` gives parents the default mode too. They are safe only while the root is 0700; a design question for the person, not yet decided.

## Store upgrades and concurrent openers
When several processes open an old store at once (web server, MCP server, runners after a release), one upgrades it and the rest wait and read the new file. `upgrade()` in `src/metaform/data/upgrade.py` holds `<store>.upgrade.lock` (`sqlite.file_lock`) and re-reads the layout inside it. The guard against the race is `test_three_processes_opening_a_layout_10_store_at_once_all_read_it_upgraded_once` in `tests/test_store_upgrade.py`: it failed 3 of 3 runs before the lock (one process raised `disk I/O error`) and passed 5 of 5 after. The general rule and the SQLite facts behind the guard connection are in `check-then-create-under-lock`. A table cannot change place (`metaform` or `project`) under its own name: `data/tables.py` `_upgrade` raises `moves X from the metaform store to the project store, and the rows here would be lost`, and the module's upgrade hook never runs. A move is a new table name, declared at the new place, with a carry from the old table on every read (dispatch version 14: `spending` at project place, `carry_spend` reading the per-metaform `spend`); whether a table may keep its name across a place move is a chassis decision for the person. Prove an upgrade on a scratch home (recipe and pitfalls in `verify-store-schema-change`): `git archive HEAD src | tar -x -C /tmp/<dir>`, enable the module first (a disabled module declares no tables, so the store read raises `dispatch declares no tables`), `home.ensure_base(project)`, seed rows with the HEAD code, then read the same totals with the working-tree code against a copy of that home. No schema change unless the ticket's own task needs it (AGENTS.md, "No schema change unless the task needs it"). Do not add, drop or retype any module's tables, columns or keys as a side effect of a fix. If a fix seems to need one, stop and say so in the ticket note, and the orchestrator decides. On 2026-10-14 two fixers each changed dispatch's tables and both called the result version 14, and the same-version refusal then stopped dispatch and the page. An approved change raises `Tables(version=N, ...)` once, says why in the comment above `TABLES` and in the ticket, keeps `compatible_from` at the oldest version that still reads the tables, and updates `tests/module_tables.snapshot.json` in the same commit (`METAFORM_TABLES_SNAPSHOT=write uv run pytest -n 0 tests/test_module_tables.py -k snapshot`). Two open tickets never share one version number. `test_no_module_changes_its_tables_without_the_snapshot_saying_so` fails on any unrecorded change, naming the module and whether the version was raised. Since ticket 03f869a0 (2026-10-15), `data/tables.py` `state()` and `ensure()` judge a store by its real schema (`pragma table_info`, index lists), not by the declaration text in `meta`. A missing table, optional column or index is added in place with no backup. Only a real conflict raises: a key, type or default differs, or a required column with no default is missing. Since ticket 13b34894 (2026-10-15) a CHECK, foreign key, collation, ON CONFLICT resolution, generated column, partial-index condition or a held unique index the code lacks is compared too, as SQL tokens from `sqlite_master`, and any difference conflicts; a raised version rebuilds the table for it. It raises for that module alone, and `ensure_extensions` holds each module under its own savepoint. Upgrades take "before" from the real tables, so a column the record never named is kept. A test module rewritten to the same byte size reuses stale bytecode (the mtime and size match), so a `user_module` variant must differ in size; add a comment line at the module's indent. `sqlite.file_lock` with `wait=True` no longer gives up on Windows (fixed 2026-10-14, ticket #2e). msvcrt's `LK_LOCK` gives up after ten tries a second apart, so the win32 branch now retries `LK_NBLCK` every 0.05 s with no cap until the holder lets go; `wait=False` still raises `Held` at once. Keep no timeout on `upgrade()`'s lock: a waiter must wait for the upgrade to finish. The Windows wait is guarded by `test_a_process_waiting_on_a_file_lock_held_past_ten_seconds_gets_it_when_the_holder_lets_go` in `tests/test_store_upgrade.py`; on Linux that test passes with or without the fix, so its proof on the win32 branch is in `verify-guard-test-by-mutation`.
