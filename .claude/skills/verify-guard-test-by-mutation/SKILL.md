# Prove a guard test can fail before trusting it green

A test that walks code to enforce a rule is only evidence once it has been seen to fail on a deliberate violation. Flip one real declaration to the wrong value in a scratch copy or with `dataclasses.replace` inside the test, run it, and confirm it reports exactly that item. If it reports nothing, the walk is blind to that kind of call: widen it, then repeat.

- Assert the reported set equals the flipped items, not just that the test fails.
- Every item the walk cannot see goes on an explicit allow-list with a reason. Silent gaps are the defect.
- Assert the count of "no sink found" items equals that allow-list, so new blind spots fail the test.
- Never leave a changed declaration in the shared tree.
- A regression test for a fix gets the same proof: copy `src`, `conftest.py`, `pyproject.toml` and `tests/fixtures` to a fresh `/tmp` folder (a test that reads a fixture fails with `FileNotFoundError` without it, a setup error that proves nothing about the defect), revert only your own fix lines there, run the test from the copy with `PYTHONPATH=<copy>/src`, and confirm it fails on the defect's own assertion (not an import or setup error). Then make that assertion name the exact output the fix must keep: a check that matched a later reply passed while the lost earlier reply was missing, so it only counts as proof once it requires the held text. Then run it on the fixed tree and confirm it passes. Delete the copy. When another agent's uncommitted work already holds the fix in the shared tree, the "before" copy must come from `git show HEAD:<file>` for each file the fix touches, plus only the test's own seam (for example a module-level hook the test sets), so a green run on the shared tree proves nothing about the fix; a failure there on the defect's assertion is the proof. Report the copy's result, not the shared tree's. For a fix that changes how many requests a cached call sends, the test's stub must refuse (raise) rather than answer: an answered call is cached for minutes and hides the second request, so the "before" run shows one request where it should show two. Measure the before and after counts from the same test, and the copy's `PYTHONPATH` must win over the editable install.

- To find which of several code paths acted (a subscription, a listing, a follower), put the probe prints only in the `/tmp` copy, never in the shared tree. Editing a shared file in place and restoring it with `cp` still races another session's writes to that file. Restore a mutant by reversing the one replaced line with exact string replacement, never by copying a saved file back: a sibling's edit made between the copy and the restore is overwritten by `cp`, and the file only kept a sibling's `answer()` changes on 2026-10-15 because they had landed before the copy. Then `git diff` the file to confirm what is left. Read probe output from the run's returned stderr, since the run fixture swaps `sys.stderr`, and confirm with `grep -c` that every probe marker is gone from each file touched.
- A new verb or declaration can trip a registry test: an allow-list of items the walk cannot see, such as `UNSEEN_OPEN_WORLD` in `src/metaform/modules/mcp/tests/test_mcp.py`. Add the entry with a one-line reason, as the sibling verb has one; do not loosen the walk. Run the registry tests by `-k` name, not the whole suite.

- Before-run in a shared tree, in one shell: copy the touched files to a `mktemp -d`, set `trap 'cp ... EXIT'` to restore them before anything else, then `git show HEAD:<file>` over each, run the test with `-k`, and restore. The trap restores even when pytest fails, and `git diff --stat` afterwards shows the fix is back.
- A race is proven by repetition, never one run: run the test 5 times before and 5 times after the fix, with enough concurrent workers that the unfixed code fails most runs (two workers failed 2 of 5 on 2026-10-14, four failed 5 of 5). Report both counts.
- Order a regression test's assertions so the defect's own check runs first. In the before run, an earlier assertion on the new fix's output (a `KeyError: 'session'` on a stop record the old code never wrote) fired before the dock-count check that proves the fix, so the before run failed for the wrong reason. Move the defect's check to the top, then rerun the before copy.
- A mutant proves a test only when it fails on the assertion the defect should trip. Read the `>` line and the `E` line of its output: an `AttributeError` or `ImportError` raised by the mutant itself is a false proof, so fix the mutant until the failure is the assertion's.
- An "is absent" check passes vacuously when the code never writes that path. Before trusting it, grep the writing function for the path it actually uses, and confirm a mutant that writes there makes the check fail.
- A guard that reads a new field (an `origin`, a flag) passes vacuously through any hand-seeded fixture row that leaves the field out, because the row takes the default branch. Set the field in every seed the test relies on, then confirm the mutant that drops the guard fails on that row's assertion. On 2026-10-14 the copied-home test passed for the wrong reason until its three dispatch seeds carried `origin`.
- When the defect's original code was never committed, no git history holds it: write a mutant that reproduces the old behaviour at the one line that differs. Copy the file aside first, and confirm `cmp` is byte-identical after restoring; never `git stash`. Restore with `cp -p` only in the same shell command as the run, and only when no other session can write that file in that window; otherwise reverse the one replaced line by exact string replacement, as the restore rule above says.
- In a shared tree where another agent is editing the same module, do not touch that file even to copy it aside. Put the mutant in a scratch `-p` plugin outside the repo on `PYTHONPATH`: it takes `inspect.getsource(module.func)`, asserts the old line is in it, and `exec`s the replaced source into `module.__dict__`. Run `-k NAME` with `-p <plugin>`, read the `>` and `E` lines to confirm the assertion fired, then delete the plugin folder.
- Read the selected count, not the tail. A `-k` expression that matches nothing still prints a line ending in `passed` or `deselected`; `| tail` also hides the exit code. A line of only `9 deselected` means the test never ran, so confirm `N selected` covers the tests you wrote before calling a run green.
- A test for a platform branch (`sys.platform == 'win32'`, `os.name == 'nt'`) passes on Linux whatever the fix, because the branch never runs there, so a green Linux run proves nothing about it. Force the branch in a spawned child: set `sys.platform` to `'win32'`, put a stand-in `msvcrt` in `sys.modules` built on `fcntl.flock` that gives up the way the real call does (`LK_LOCK`: ten tries one second apart, then `OSError`), and run the probe against a `/tmp` copy before the fix and after it. Report both numbers. Name the platform's own CI job as the one unrun check; never write "passes before and after" for a branch you did not run. Worked case 2026-10-14: the store-upgrade lock waiter raised `OSError` at 9.04 s before the fix and acquired at 12.02 s after it.

- A mutant written over a module file at the same byte size within the same second reuses the stale `.pyc` (mtime and size match), so the test runs the old code and passes for the wrong reason. Make each variant differ in byte size, for example with a comment line at the module's indent; column 0 breaks `textwrap.dedent` and the module fails to load.
- A snapshot guard of declared tables is proven by two mutants: adding a column without raising the version must fail, naming the module and saying the version was not raised; reordering the same columns must pass, since the snapshot matches columns by name.

- A browser test that gained assertions for a fix is proven the same way: copy `src` and the test file itself to a `/tmp` folder, `git show HEAD:<file>` over only the page files the fix touches, run `PYTHONPATH=<copy>/src ... -m browser -n 0 -k NAME` on the copy, and confirm the failure is the new assertion's line in the `/tmp` path. Before blaming a timing failure, run that test alone on the copy: a fade-timing assertion also failed on the unfixed copy, so it proved nothing for the change.

- A helper shared by many surfaces (the cut-text opener, the header fold) is proven by a no-op mutant of that one helper: a probe that lists every surface's items must fail on each listed item. Count the failures against the probe's list, not "some failed"; 23 of 23 cut texts failed on 2026-10-15.

- A behaviour test that waits for an async record (`eventually(...)` with a 60 s bound) is proven by a mutant that stops the record being written. The kill is the test's own timeout line (`AssertionError: not within 60 s`), and it takes the full bound, so run it with `-n 0 -k NAME` on the copy and read the `N selected` count first. Worked case 2026-10-15: a dispatch runner test failed with `not within 60 s` once the publishing of prompt versions was disabled in a `/tmp` copy.
