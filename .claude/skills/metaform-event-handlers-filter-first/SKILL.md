# Metaform event handlers filter first, then read one record

A handler decides from the event alone whether it concerns it, and does no store read for an event that does not. Idle CPU that rises with the event rate means a handler reads on every event; look there before looking for a loop.

- Writes say what they concern. `map.changed` carries `work_ids`, `session_ids` and `kinds`, each a sorted list. A field present means that dimension is fully known; absent means unknown, so the handler falls back to `tables`. An empty list is not absent: it concerns no ticket, so a waiter with no id drops that change rather than reading it as "says nothing". Design and call sites: `references/concern-fields.md`.
- Filter order: the handler's own ticket or session named, act; other tickets or sessions named and nothing else, skip; nothing named, act only when the event touches a table the handler reads.
- Read one record, not the collection. A step on your own ticket reads that ticket; a burst of changes for other sessions reads zero records.
- Never react to your own writes. Events that arrive during pending work merge into that work.
- A bookkeeping write that changes no map and that no handler listens for (a receipt, a delivery record) runs inside `events.quietly(...)`. Noted without a concern, it strips the `kinds` and `session_ids` that the same command's map writes carried, so every filter falls back to reading. The writer's own session then counts that write as received, so `memory.changed` names only the other sessions at that entry (`memory/delivery.py`, `changed` and `authored`; test `test_a_write_is_never_an_unread_notice_to_the_session_that_wrote_it`, which fails without the fix with `assert ['other', 'worker'] == ['other']`).
- Set a "something to write" flag only when the event moves the state it guards. A reader's start event that found the position already written set `dirty` anyway and cost one extra write a second after every start (autoticket watch, 2026-10-15). Compare the event's identity and offset with what is held before setting the flag, and test that a no-change start writes nothing.
- Coalesce bursts of your own ticket's changes: a check that is running takes one flag for the changes that arrive meanwhile (`checking` / `check_again`) and runs one more pass after it, never one spawned check per event. `Session.checks` in `dispatch/runner.py` does this; `workflow_answers` does the same with `workflow_reading` / `workflow_again`. A burst of 50 own changes must cost at most twice one change's reads (test it; the unfixed spawn-per-event version gave 50 reads for 50).
- Queued deliveries coalesce too: a note or message that arrives while an earlier one still waits as a queued turn joins that waiting turn, never one turn each. Memory notices are never pushed as turns (2026-10-19, code.dispatcher.agent#72): an agent hears of unread memory only when it reads its own node. The person's system agent takes notes, updates and board items into its inbox, named by one line on its next turn (`Session.inbox_add`). Before this rule, a system agent's thread took more than 100 note-turns that drained one per turn while the person's own messages went ahead of them (`runner.Session.turn()`, 2026-10-19). Test it with a burst of notes to one waiting session: the count of turns must stay near one.
- A write that names no tables and no kinds reads as "does not say" to every waiter, its own included. `Session.write` calling bare `changed()` woke the launch wait on each runner's own session-row insert. Pass `tables=` and `kinds=` on every write path; when a waiter wakes on its own writes, grep for bare `changed()`.
- Writes that change no table still name their concern: `changed(tables='dispatch', kinds=['session'])` for a session going busy or idle, the intake phase, an answered question. A `kinds`-only event tells a reader of other kinds to read nothing.
- A test that writes a module's tables directly (a seeded thread line, a fixture row) must announce the change through `events.announce`, or event-driven readers never see it. A view that used to re-read every 2 s hid this; once it stopped, the seeded lines vanished. `events.announce` raises inside a running event loop (BASE-009), and Playwright's sync API runs one, so announce from a thread of the test's own (`seed_thread` in `mcp/tests/test_mcp.py`, 2026-10-15).
- Known open reads, on the handler's own events only: `answered()` reads every question at its node because the store cannot read one message by id; `workflow_read` reads runs by state because the workflow module has no one-run read and its pause and answer events do not name the run. Fixing either is a change to the map or workflow module, not to the handler. The same gap holds for the MCP server: `map.changed` has no `task_ids`, `exchange_ids` or `addresses`, so the task owner, the A2A followers and the resource watcher decide from `kinds` and `tables` and read a few rows more than one. Adding those fields is a chassis change, named in the ticket, not a handler fix (2026-10-15). A watcher also ignores a change from another project of the home, and a change that names only dispatch's or the mcp module's own tables when it cannot hold a watched item.
- A wait with no id that must read tickets keeps the tickets its changes named since its last read and reads only those, merged between reads. A change that names no tickets (no `work_ids`) forces the next read to be full. The first read is always full.
- A pass over many rows (a check of every system session for a live runner) decides each row from its own fields first, and reads a row's runner only when the row's state can matter or a start file names it. A pass over many old conversations then costs no runner read each. `holding()` in `dispatch/__init__.py` is the model (code.dispatcher.agent#36, 2026-10-16).
- Waits are events, not sleeps: `events.listen` for a change naming the thing awaited, or an `asyncio.Event` set by the code that produces it, plus the process exit. Deadlines (silence clock, retry backoff, pacing) stay timers and are named as such.
- Sweep a folder for polling by its sites: `setInterval`, a `setTimeout` inside a check loop, `time.sleep(`, and `for (;;)` or `while` loops that await a timer. Classify each. A stream reader (`reader.read()` looping until `done`) is not polling and stays; so do real deadlines, retry backoff and pacing. Anything that only looks for a state change becomes an event. Pin the kept set in a guard test (see `verify-guard-test-by-mutation`) so a new timer fails it.
- A health or status heartbeat is replaced by asking at the events that say the thing may have gone or come back (a stream's error or open, a failed read), never by a clock.
- A "reads nothing" test opens its quiet window on a signal the code emits (a `threading.Event` set when the store-touch count reaches the point where the setup has settled), never on a fixed sleep. A 1.5 s sleep passed alone and failed in a combined run, because the lease and first write landed after it. Run the new idle tests together with their file once, since load moves timing, and confirm the window still fails on HEAD's files.
- A dirty flag is set by a change, not by an event's arrival. A watcher's start event that reports the position already written must not mark the watch dirty, or every start costs a write. Compare the new value with the recorded one, then set the flag.
- Long-lived servers: uvicorn's `Server.main_loop` wakes ten times a second even when idle. Override it to await an exit `asyncio.Event`; make `should_exit` a property whose setter sets that event (uvicorn's `handle_exit` assigns it), and set a ready event at startup. Keep one shared copy in the chassis, not one per module. When the chassis is outside the ticket's module, leave the copy where it is and name the duplicate in the ticket and the report rather than adding another silently (2026-10-16, ticket code.server.tool#14: `serving()` went into `mcp/server.py` beside the node module's copy).
- Before keeping a timer for an upstream, read how the upstream's own UI gets its updates. Paperclip's pages follow a live-events WebSocket (`/api/companies/{id}/events/ws`, `activity.logged` naming the entity id); a timed sync was the wrong design. A timed fallback is kept only for a server that answers the stream with 404.
- Waits on a Windows file lock use the blocking OS call (LockFileEx without LOCKFILE_FAIL_IMMEDIATELY), not a try-lock loop with a sleep.
- A client with no server push (an MCP Apps view: ext-apps 2.0.3 delivers only tool-input, tool-result, tool-cancelled and host-context) is woken by a held read only on a host that carries its calls concurrently. The Playwright check host (`expose_function` into a probe Session) carries one call at a time: a held read froze the view's other reads and four browser tests timed out (2026-10-15, code.server.tool#14). On such a host the view keeps its own clock (`bridge.js`, 2 s trace and 2.5 s focus), and the server answers each tick from the change marks, reading the store only when the ticket's mark moved (`views.Traces`). The server answers a read with `wait` when what it reads is unchanged since the caller's `seq` or `mark`, and holds it on an `asyncio.Event` set by the change it follows, or until a deadline on that one call (`views.WAIT_S`, 25 s, inside the host's request limit). The client asks again the moment it is answered; only a failed read waits, on a doubling backoff. A read already behind the server's counter answers at once, never holds.
- A draw added to an existing handler's path (a list redrawn from `renderAgents` or `ticketsChanged`) returns at once when its surface is hidden, and draws from state the handler already holds; it reads no record. Mutation-check it: removing the call must fail the test of the update it carries (2026-10-15, the full-size dock's agent list, where the step test failed without the `ticketsChanged` call).
- A change to a project's source files has no Metaform event: `map.changed` follows map writes only, and an editor's save writes nothing to the map. A process that must react to cited or watched files runs its own OS watcher (inotify on Linux, kqueue on macOS/BSD, none on Windows), drains each burst into one pass, and ignores its own writes. Memory's `metaform memory watch` (`src/metaform/modules/memory/watch.py`, 2026-10-16) is the model: it works out a changed file's results once and stores them, and nothing wakes on a timer. Test it with a burst of unrelated events that causes zero reads, and measure idle CPU in ticks over 60 s.
- Prove it before and after: per-process CPU from `/proc/<pid>/stat` (utime + stime) over 60 s at the live event rate, plus `voluntary_ctxt_switches` from `/proc/<pid>/status` as the wake-up count: an idle waiter should show near zero, and unrelated changes should add none. Run the "before" processes from a copy of the old source tree (`PYTHONPATH` pointing at it), with the "after" tree beside them in the same run, not a stash in the shared checkout. Also a test where a burst of unrelated events causes zero reads (count `Store._read`), and the same burst with one related change causing exactly the reads it needs. Prove the filter by mutation: make each new filter answer "concerned" for every event, confirm the burst test fails, then restore the files and compare them with copies. The four burst tests in `mcp/tests/test_mcp.py` (tasks, resource watcher, A2A followers, trace marks) each failed on the pre-fix copy and under that mutation (2026-10-15). Method: `references/concern-fields.md`.
