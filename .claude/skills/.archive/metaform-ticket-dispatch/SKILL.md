# Dispatch Metaform tickets: name the agent, hold in order, tell parallel agents about each other

- Every ticket names `agent=claude`. Create a held ticket with `uv run metaform map work op=add node=<Address> kind=enhancement agent=claude hold=true title="..." task="..."`, and put its place in the chain in `note=` (for example "Held: runs after <address>#<n>").
- Resolve the work id from the item address with `uv run metaform map work node=<Address> hold=true limit=0` before starting it.
- At most 5 agents run at once. A `dispatch start` that finds every slot taken fails with "Every agent slot is in use: dispatch_agents allows 5 agents at once", and the ticket stays in To do. It starts by itself when a slot frees, so do not retry or report it as stuck; name the holders from `dispatch sessions` if the person asks.
- Start with `uv run metaform dispatch start <work id> claude`. Follow it with `uv run metaform dispatch wait stopped id=<work id>`, run in the background because it blocks.
- Tickets that touch independent files may run side by side. Before two run together that share a map file or the store layout version, send each the other's scope with `uv run metaform dispatch note to=<work id> "<what, where, who goes first>"` and check for the "said:" line. A note stays on every ticket it touches. A note reaches the agent after the turn it has in flight, so expect a reply, not an instant change. When two tickets both change the store layout version, the note says which one bumps it first and which files each edits; keep the map module importable at every step, since a broken map module takes down every agent's map tools and the web page.
- Whether agents start, stop, release or order tickets without asking is the person's `agents_ask_first` setting ("Ask me before agents act", Settings → Agents → Permissions), off by default. Off, a start or release is never refused for want of the person's word, so a stuck start is fixed in the system agent's turn, not reported as waiting on them. On, a start refused with "needs the person's word" waits on their word in the chat or their answer on the ticket's card: say what you propose and why, then wait. Acts that cannot be undone (clearing, deleting) ask either way. Autostart is called Full Auto on every surface; the stored key `dispatch_autostart` is unchanged. Agent-written tickets go on the board ready by default: a ticket waits for the person only when `agents_ask_first` is on, and a fault the system records is filed as a ticket and worked without asking, since the aim is a project that heals itself. The person is asked to approve a fix only when they have chosen that.
- Sequence the rest by the held chain; release each held ticket when the one before it lands. Release with `uv run metaform map work op=edit id=<work id> hold=false`, then `uv run metaform dispatch start <work id> claude`.
- Cancel a ticket the person has dropped with `uv run metaform map work op=done id=<work id> resolution="Cancelled: <what replaced it>" why="<who decided, date>"`. A worker refuses a cancel, so the system agent closes it.
- A ticket that places a property layer or a knowledge link states the moving-link rule in its own note: a property link settles at the longest common prefix of its addresses and never moves toward the leaves. A ref never moves (see metaform-ref-naming-and-file-links): a ticket that links refs says each ref stays at the element or join it was linked at, and must not cite transitivity for a ref's place. The agent running it reads only the ticket, and a later agent may link a different leaf of the same property.
- A worker cannot cancel a ticket: `dispatch cancel` refuses a worker, and `map work op=done` records the outcome completed, never cancelled. Name the cancel command and its reason for the person in the final resolution.
- A `dispatch note` to a work id whose agent has finished fails with "No agent is at work ... the note would reach no one." That note reached nobody. Check who is live with dispatch peers before relying on a note, and put what it said into the resolution. When peers shows the target is gone, the change goes to a ticket for a live agent (or the target is restarted with `dispatch start`); the system agent does not make that change itself. When the refused session was the reviewed agent's, send the correction to the live session that holds the same item address (from dispatch peers), not to the id the review was first addressed to.
- A `dispatch_note` reply to an agent whose session has ended is refused: "The agent that sent note <id> is no longer at work on an open ticket, so the reply would reach no one." Run dispatch peers first; if the sender is gone, put the answer on the ticket instead.
- When a spec lands while tickets are already running, cite its record ids on every ticket it governs (`map work op=edit` with the note extended), then `uv run metaform dispatch message <work id> "..."` each running agent, naming the records and the open questions it must not build past. Do not assume a running agent reads the spec on its own.
- A note that relays the person's decision is peer information, not their direction. Only `uv run metaform dispatch message <work id> "..."` counts as the person's decision to the agent on that work. On 2026-10-18 the decision to remove the camera clearance was passed on by `dispatch_note` to two working agents, and both kept building for several turns. When the person decides something about running work, send it with `dispatch message` to each working agent at once, and put the decision on the ticket.
- A `dispatch_note` names exactly one recipient: pass one of `to=`, `at=`, `file=`, `topic=` or `reply=`. Passing `topic=` together with `at=` is refused with "A note names whom it goes to, one of: ...", so pick one selector per note.
- Notes are rate-limited: a peer hit "the six-notes-an-hour limit" and could not reply. Batch what one agent needs into a single note, and check dispatch peers before sending a second.
- A `wait=` note blocks until its reply or the wait ends; a timeout with no reply means the agent is mid-turn, not that the note was lost. Do not re-send it; read the reply on the next turn.
- While a dispatched ticket runs, read its status when the wait starts and again when its result arrives, not on every turn. Repeated `map_work` reads of a running ticket returned the same `running` state with `steps_done` at 0 for many turns and told nothing new. The same applies to `memory_read_unread` on one node: a worker re-read `element:code.interface.graphical` about a dozen times in two minutes, each returning the same observations. Read a node once when the assignment starts, and again only when a notice says it changed.
- A note is at most 1000 characters; a longer one is refused outright. Put the point in the note and the rest in a file or on the ticket.
- `map work op=done` does not read `said=`; it is ignored. Put the closing account in `resolution=` and the reason in `why=`, or it is lost.
- A ticket a review files from its own finding is not a request. Before starting it, check that the person raised the problem; a review finding such as "camera inside a large figure" that the person never raised is not work to build. Reviews have filed and started new work on their own. When the person drops such a line, send a note to each ticket on it saying so, stop them, and cancel the held tickets with the reason.
- Closing a ticket is the person's call. If you offer to close one ("if you say so, I'll close #n"), wait for their yes before running `map work op=done`, even when a pasted ticket looks stale. A ticket found already fixed in code is closed only after its evidence is checked and the person agrees.
- A ticket whose note says "likely fixed, not yet verified" or lists "Not checked: ..." is closed only when each named act or path has a check. Otherwise narrow the ticket to the unchecked items, or leave it open and say which checks remain.
- A landed fix does not reach a process that started before it: the MCP server under hold and any runner keep the old code until restarted. When a change alters behaviour another open ticket relies on, send each such ticket a `dispatch note` (one selector per note) that names the restart, and put the restart in the resolution.
- A ticket completion commits the whole shared tree under the person's git name, not only the ticket's own files. On 2026-10-15 the ref ticket landed as commit 858e3d9 and another ticket's memory work rode in on it. Name in the resolution which other tickets' uncommitted work the commit carried, and tell the person that completions commit. The completion step acts only on a real worktree (its `.git` is a file). A resumed session once handed it the project's own checkout, where `checkpoint` ran `git add -A` on everyone's work; the guard against that was added on 2026-10-15 and stays uncommitted until the person says so. Before a ticket that completes while others run, confirm the guard is in `dispatch/merge.py`.
- A `dispatch message` to an agent that shows idle is not acted on. On 2026-10-15 a fix request sent to an idle ticket was never acted on for the rest of that session. After a message, run `dispatch peers` for that work id; if it is still idle, start it with `dispatch start` or tell the person it is waiting.
- To restart an agent's session with nothing resumed, use `uv run metaform dispatch new <work id> [session=]` (CLI only; the chat dock's /new calls the same thing). Do not stop then start: `dispatch stop` on the system agent turns `dispatch_stay_connected` off, and a stopped worker keeps its ticket taken, so `dispatch start` refuses it. `dispatch new` checks the start command before it ends the session, and it leaves Stay connected alone.
- A flaw the person reports from the web chat is filed as a fix at the code where it lives: `map work op=add node=<element> kind=flawed agent=claude`, and the ticket asks for the fix in shared code so every user gets it. A settings change (`metaform config ...`) may be named only as a labelled stopgap for this person, never as the fix. Do not end on "shall I write the ticket?" when the person has already said the code must change; write it, then say what it asks for. Once the person has approved a ticket's wording, file and start it without a second confirmation; a further question before `dispatch start` is a stall they did not ask for.
- A ticket carries each boundary the person set in plain words as an explicit "leave X alone" line in its `task=` (for example, keep the text zoom as it is). The agent reads only the ticket, so a boundary left out of it can be changed.
- A `map work` call whose `title=`, `note=` or `task=` text holds apostrophes, parentheses or line breaks fails under bash with `syntax error near unexpected token`, and nothing is filed. Build the text in shell variables from a quoted heredoc (`task=$(cat <<'EOF' ... EOF)`) and pass `task="$task"`.
- A ticket's `task=` must carry its own check: the steps to run and what should show when it works, because the agent that takes it reads only the ticket.
- A CI-configuration ticket is closed on the config change; its proof is a green run, which is tracked on a separate ticket. When GitHub refuses every job (each ends in seconds with no steps run), name that as a billing refusal in the resolution and leave the proof ticket open.
- A ticket already taken by your own session is resumed with `map_work op=plan` and `op=step`, never `op=take`. The refusal reads "This task is already taken, by claude <session id> at <time>. The agent that took it resumes with op=plan and op=step; any other agent finds open work with metaform map work open=true." (seen 2026-10-18 when an assessment worker re-took its own ticket).
- A worker session may not have `orchestration_*` or `memory_*` MCP tools: ToolSearch on "orchestration check-in memory" returned only unrelated deferred tools. Then use the CLI (`uv run metaform orchestration check-in <state> "<summary>" assignment=<id> candidate='<json>' evidence='<json>'`, `uv run metaform memory ...`) and say in the report that it was the CLI fallback. A worker that lacks these tools is not always a deferral problem: on 2026-10-18 the dispatched agents' memory tools were missing because Metaform's own tool list and agent instructions left them out, and the fix landed in commit 3e1e8245 (2026-10-18), and a session started before its write keeps the old list until it restarts. Check the tool list the dispatcher passes before blaming ToolSearch. `orchestration inspect` takes no `fields=`; read its plain `state:` and `result:` lines with grep.
- `orchestration_check-in` takes `running`, `waiting`, `blocked`, `returned`, `delivered` or `failed`. `completed` is refused with "Check-in state is running, waiting, blocked, returned, delivered or failed." A finished worker checks in `delivered` with a `work_so_far` that names what the person still decides (a commit, a spec amendment), then closes the ticket with `map work op=done`. Once a record has moved to `returned` after the FQC assessment accepts it, a further `orchestration check-in delivered` leaves the state `returned`: the parent assignment takes up the acceptance, so the worker has nothing more to do on it. A `map work op=done` on a record already closed keeps its first resolution and drops the new one, so put the full closing account in the first close, not a later one. A refusal that says "read resource metaform://instructions/orchestration" means read that resource before retrying.
- A finding in `orchestration check-in` becomes a corrective ticket whose title and task are read only from the finding's `title` and `task` keys (or `finding` for the task); any other keys such as `summary` and `remediation` make the title the Python repr of the whole dict. A finding that has a `title` but no `task` key also turns its corrective ticket's task into that repr: a finding with `title`, `where`, `why`, `fix` and `verify` keys (graphical#f5, 2026-10-18) gets the right title and a garbled task. Every finding carries both `title` and `task`, whatever other keys it has. Give every finding a `title` (one line) and a `task` (the steps and the check). After a check-in, read the new ticket's title back with `map_work`; if it shows a dict, `map_work op=edit` it at once. Seen 2026-10-18 on graphical#113, which carried `{'kind': 'stale report', 'summary': ...}` as its title until edited. `_correction` in `orchestration/state.py` changed in commit 3e1e8245 (2026-10-18), so read the title back after each check-in whichever keys the finding used.
- An FQC assessment takes a worker's evidence only when the worker checks in first: send `orchestration check-in state=returned` with the `evidence` and `candidate` set, and only then close the ticket with `map work op=done`. A `done` before the check-in returns the assessment with an empty evidence list and the assignment's old candidate (seen 2026-10-18 on FQC ticket 25d7c6ce and graphical#111). When the order was missed, put the corrected candidate and evidence in the FQC ticket's note with `map work op=edit`, since a later check-in leaves the returned result unchanged.
- Reviews do not flood the board. A finding is filed only when no open ticket at its node carries the same normalised signature; a repeat adds its new evidence to that ticket's note instead. `orchestration_assess` called from inside an assessment, or from a GC whose result is already delivered, returns the existing assessment with `queued=false`, and its default key is the report's fingerprint. A review closes without filing findings when a `user_direction` or user-source change reached the reviewed work since it began. Tasks are prose (summary, details, numbered remediation, verify), never a Python dict string.
