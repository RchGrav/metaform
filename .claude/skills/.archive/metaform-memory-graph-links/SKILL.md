# Record memories and knowledge where they apply, linked into the graph

Memories and knowledge attach to the address they concern and reach every address they apply to through layers; never pin one memory to one leaf. Before creating a memory, open or search the existing entities about the same thing and add an observation to one that already exists, rather than a near-duplicate. Every observation is one atomic fact in one sentence; a paragraph gets split into one observation per fact. A semicolon or a second sentence inside one observation is refused by the store as more than one fact, so split it there too. The person has said memories that are not atomic facts get purged, and on 2026-10-16 most observations were paragraphs (median 313 characters). After creating, relate each new entity to the existing entities it concerns with `create_relations`, in active voice.

- Memory is what happened in the work. Knowledge is what is true of the project: what an element is, how it behaves, its constraints, and its properties. Every property (genre, medium, style, encoding, storage engine, protocol revision, framework) is a knowledge layer of the same kind. The property's own node (code.python, platformer.3d) is held inside a layer and is never a layer's name: no layer is named a project root (code, document, media, data, upstream, downstream; LAYER-028). The store refuses exactly those six names. A layer is named by the short name of the element it relates to: its Address reversed and cut to `name_length` segments (the glossary's Name_Length), and it belongs to a property element. So a cpp best-practices layer is named for the cpp element, not `code.cpp.best_practices`, and never `code.cpp@best_practices`, `unnamed-<time>`, or a free label such as `event-handling` or `constraints`. The map tool's `layer` noun text still tells agents to name a layer `scope@content` (src/metaform/modules/map/__init__.py:962); do not follow it until that text is changed. Rich rejected such names on 2026-10-16. The reserved `logic`/`prompt` root is not refused yet. Run `metaform map layers` before a spec or ticket names a layer. A port is a layer swap, and a property layer bound at a function is inherited by everything under it (how a game mashup works). Knowledge goes in a knowledge layer at the element it concerns. Memory goes in the memory graph and is linked from the layer it belongs to.
- Always name the layer on a knowledge write (`map knowledge` add-element, add-join, add-property, add-item, add-ref). With no layer named, the store puts the value in a new building layer called `unnamed-<timestamp>` with no variable and no provenance, and only a notice says so. Run `metaform map layers`, pick an existing layer, and pass it. Agents never create a layer. Layers come only from the person saying to add one or from the predefined layers (base, sources, the logic/prompt layer, memory). What an agent learns while working is memory. Check the response's `notices` before reporting the write as done. Pass `layer=` on the first call: the MCP `map_knowledge` tool's `add-property` sent without it on 2026-10-15 landed in `unnamed-20261015T231725Z`, and the fix was to write again into the named layer and `op=discard` the unnamed one. It recurred on 2026-10-16: a `map_knowledge op=add-property` for `code.server.tool` with no `layer=` landed in `unnamed-20261016T002901Z`, and its `on` field read false, so agents were not sent that knowledge until it was named. Read `on` and `notices` back before reporting a knowledge write as done. Creating a new layer can come back with a name notice: on 2026-10-16 `map_knowledge op=create layer=code.interface.graphical@stored_mascot` returned `'code.interface.graphical@stored_mascot' is not 1 to 128 letters, digits, ., _ and -; it was stored as given`, and an `add-property` into a layer name that did not exist returned `Error: No layer behaviour`. Read the create response's `notices`, confirm the layer exists with `map_layers`, and check its `on` field after `op=finish`, which left it false in that case. Pass `mutable=true hideable=true` on `op=create` as well: without them the layer is stored with `mutable: false` and `hideable: false`, each with a notice, and it stays off. On 2026-10-16 (ticket graphical#82) an `add-property` to an address that was not yet an element created that element inside the layer, with the notice `... was not an element; it was created in layer ...`. Add the element first with `add-element` into the named layer, then read the notices back.
- Record where you found it; do not judge the depth. A knowledge layer has its own address and one link to a base map address. Recording the same knowledge on another branch moves that link up, toward the trunk, to the longest common prefix of the two addresses, never toward the leaves. Worked example: linked at code.interface.speech.engine, then at code.interface.graphical.dock, it moves to code.interface; linked next at code.dispatcher.agent, it moves to code. Every move keeps who linked where and when. An address that does not exist yet can be created as an element inside an existing layer. Naming a new element does not make a layer; agents do not make layers at all (see the layer rule above).
- A memory linked from a layer is transitive with it: it applies at every address the layer covers, toward the leaves on every branch, so one link replaces a join per node. Hiding the layer hides its memories too.
- Read the placement records before designing where anything attaches: MAP-011, MAP-022 and specifications/02-layers.md:62-64. Placed near the trunk, an item applies to every branch below it; placed at a leaf, it spreads to nothing else.
- Context reaches an agent by address: what applies at the element it works on, inherited from addresses toward the trunk, pushed once per session as the agent starts work at that node (design, not yet built). A compaction clears what was sent; the next push waits until the agent goes to work on a node again, and nothing is pushed on compaction itself. Detecting compaction needs the ACP client capability; see acp-client-capabilities. Today `read_graph node=` (src/metaform/modules/memory/__init__.py) returns only memories joined at that node, so inherited memories are not read yet. That change is held as ticket code.graph.knowledge#b.
- Cross-node relations are the point, not an exception. A memory may relate to one held at another node.
- Before telling the person that old memories were cleared, check the store. Read the whole graph with the CLI (`uv run metaform memory read_graph --json`), since the MCP memory tools can be stale, then count entities by the date of their first observation (`memory.entities` joined to `memory.observations.at`) on a copy of `modules/memory.sqlite3`. Report the store path and the counts by day. A cleanup that was never recorded as a ticket cannot be confirmed from tickets; ask before deleting anything, and back up first. When the person says memories written before a memory-prompt change should have been cleared, that is a standing expectation: split the graph by first-observation date at the change, report the count before the change, and ask which to remove. Work the person did outside Metaform leaves no ticket, so a missing ticket does not mean the clear never happened. When memories you read earlier in the session now return "not found", stop writing: do not recreate them from your session reads. Run the store check above first, because a deliberate clear leaves the same symptom as a loss, and a recreated memory overwrites what agents recorded since the clear. Tell the person what is missing and ask whether to restore; restoring from the backup is their call.
- No tool links a memory to a knowledge layer: `memory_create_relations` relates memories only, and `map_knowledge` adds items. Until one exists, a memory goes at the same node as the knowledge item it concerns, so the two show together there. For a change made directly to the tree, put each memory at the element whose files changed, cite file:symbol or file:lines (or the spec amendment line), and give a `why`. A deleted file is described, not cited.
- A memory recorded at an element that was removed is refused ("is not a node of the map here"). Attach it to the RE that now holds the goal the removed element served, and name the removed Address in its observations so the trail stays findable. Each new entity needs a `title` (one line saying what it is) and a `why` (one line saying why it is worth keeping); the store refuses an entity with either missing.
- Known defects that block cross-node relations, with file and line references: `references/memory-link-defects.md`.
- The wording agents are sent is decided by Rich. Check the pushed texts with `metaform-prompt-store-served` before claiming agents follow this rule.
- Names, structure and classification are the model's choice; the store never judges them. Enforce only mechanics: a file is linked before it is written, the ignore list is read-only, one push per session, unique ref ids.
- The person's own note at a node (VIEW-034, person-only, one field) is where the person writes something for agents at that node without AGENTS.md. It is neither a memory nor a knowledge layer. Until pushed delivery is built, dispatch's hand-off carries it whole as the field `the person's note here: <text>` whenever it is set (memory `person_note`, read through `memory.note`); the node read shows it under `memory`. Only the page writes it.
- A base element or join holds RE, PE, OP and EF only, never a note (MAP-046 amendment, 2026-10-15). A note the intake is given with no condition goes to the node's one item of layer `critic`; `map knowledge op=edit` or `refine` with a note on a base is refused, and the refusal names `metaform map knowledge op=add-item layer=critic node=<kind>:<id> value=<note>`.
- Agents do not judge depth. They record knowledge where they found it to hold; a link recorded on a second branch settles at the common prefix by itself, and a link never moves toward the leaves. Any prompt still telling agents to place knowledge at the most general address is the superseded rule. A ticket that places properties states the moving-link rule and its worked example in its own note, because the agent that runs the ticket reads only the ticket.
- The design record is `docs/preprint/inference-metaform.md`: §5.2 (a language Encounter attaches at its element, applies to its descendants, is visible at ancestors, and leaves siblings alone), §7.1 (memory has a functional location), §7.2 (informational knowledge kept apart from imperative knowledge, which is used only when selected for that role), §7.3 (selection and hidden layers). Read the matching section before asking Rich for a spec; he has said the paper is the spec.
- When a code change makes a recorded observation false, replace it instead of adding beside it: find the entity with `memory search_nodes`, `delete_observations` the old text, and `add_observations` the new text on the same entity at its node. Dated, referenced observations ("since 2026-10-18 (graphical#b5)") let the next agent tell the current rule from history; a superseded fact left in place sends the next agent to a rule that no longer holds. Each replacement is still one fact per observation. Before adding an observation that cites code, read the cited line: a claim copied from another agent's note can be wrong (on 2026-10-18 one said `clearWatched` does not check `ROAM.held`; `figures/eyes.js:756` does), and the wrong fact must then be deleted and re-added with the line cited.
- The system agent's own working memory (Rich's proposal, 2026-10-16; not yet specified or built): at the start of each task, and when something is worth keeping, it records a memory at the RE of the element the task concerns, citing the task number and the message where the task started. When Rich refers back to earlier work, it reads its memories at that Address first and opens the cited task at that line. Writes already carry who, session and time, so this is a filter on memory reads, not a new store. It is what happened in the work, so it goes in the memory graph, not a knowledge layer.
- The "N memories; M unread ... read_unread node=..." notice repeats on every stop-hook turn while the counts stay the same. Read the node once when the counts change, and do not reply to a repeat with unchanged counts. If the same notice still returns after `read_unread` has read the node, the notice and `read_unread` disagree (held ticket code.system.management.knowledge#35, 2026-10-18): stop reading and replying, and file one held ticket with the evidence. To check, compute the notice read-only with `from metaform.module import context` and `delivery.notices(ctx)` under `METAFORM_SESSION=<the runner's session>`; `metaform.context` does not export `context`. One memory recounted as "17 updated" is still one memory; compare the node, not the count. A memory counts as read only when `memory_read_unread` returns its full contents. A names-only read (`fields=["name"]`) or a `view=count` read does not mark it read, and the notice keeps counting it. Observed 2026-10-18 (graphical#e2): after a names-only read the next notice still said "2 unread, including 2 updated"; after the full read, `view=count` returned `{"total":0}`. Notices are worked out when an event lands and can be delivered several turns later, so a notice can repeat an update that a full read already returned. A repeat with unchanged counts needs no read and no reply, whatever the count shows. Another agent's new observation on the same node raises a notice worded exactly like the empty ones, so a repeat is a defect only when a full `memory_read_unread` of that node returns nothing for it; when it returns the new observation, that notice was real and the read is the reply. Do not write a defect memory from a repeat until a full read has come back empty.
