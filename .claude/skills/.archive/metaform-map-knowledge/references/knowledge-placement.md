# Knowledge placement: details

## Layers
- Knowledge is what is true of the project: what an element is, how it behaves, its constraints and its properties. Every property (genre, medium, style, encoding, storage engine, protocol revision, framework) is a knowledge layer of the same kind. The property's own node (for example code.python) sits inside a layer and is never the layer's name.
- Naming history: the store refuses the six root names (LAYER-028). Names of the form `scope@content` (for example `base@best_practices`) were rejected by the person on 2026-10-16. The map tool's `layer` noun text still says `scope@content` (src/metaform/modules/map/__init__.py:962) until that text changes. The reserved `logic`/`prompt` root is not refused yet.
- Creating a layer can answer with a name notice, such as `... is not 1 to 128 letters, digits, ., _ and -; it was stored as given`. Read the create response's notices, confirm the layer with `map_layers`, and check its `on` field after `op=finish`. Without `mutable=true hideable=true` the layer is stored with both false and stays off.
- An `add-property` into a layer name that does not exist returns `Error: No layer behaviour`.
- An `add-property` to an address that is not yet an element creates that element inside the layer, with a notice. Add the element first with `add-element` into the named layer.
- Read `on` and `notices` back after every knowledge write. On 2026-10-15 an `add-property` without `layer=` landed in `unnamed-20261015T231725Z`; the fix was to write again into the named layer and `op=discard` the unnamed one. It recurred on 2026-10-16 (`unnamed-20261016T002901Z`), where `on` read false, so agents were not sent that knowledge.
- Record where you found the knowledge. A knowledge layer has its own address and one link to a base map address. Recording the same knowledge on another branch moves that link up to the longest common prefix of the two addresses, never toward the leaves. Worked example: linked at code.interface.speech.engine, then at code.interface.graphical.dock, it moves to code.interface; linked next at code.dispatcher.agent, it moves to code. Every move keeps who linked where and when.
- A property layer bound at a function is inherited by everything under it. Placed near the trunk, an item applies to every branch below it; placed at a leaf, it spreads to nothing else. Read MAP-011, MAP-022 and specifications/02-layers.md:62-64 before designing placement.
- A base element or join holds RE, PE, OP and EF only (MAP-046 amendment, 2026-10-15). A note with no condition goes to the node's `critic` layer item: `map knowledge op=add-item layer=critic node=<kind>:<id> value=<note>`.

## Memory
- Memory is what happened in the work. It goes in the memory graph, linked from the layer it belongs to, or at the same node as the knowledge item it concerns. `memory_create_relations` relates memories only.
- A memory linked from a layer is transitive with it: it applies at every address the layer covers, toward the leaves on every branch. Hiding the layer hides its memories too.
- Cross-node relations are the point, not an exception. Known blockers with file and line references: `references/memory-link-defects.md`.
- Context reaches an agent by address: what applies at the element it works on, inherited from addresses toward the trunk, pushed once per session as the agent starts work at that node. This is design, not yet built; today `read_graph node=` returns only memories joined at that node (held ticket code.graph.knowledge#b). A compaction clears what was sent; nothing is pushed on compaction itself.
- A memory recorded at an element that was removed is refused ("is not a node of the map here"). Attach it to the element that now holds the goal the removed one served, and name the removed Address in its observations.
- When a code change makes an observation false, find the entity with `memory search_nodes`, delete the old observation and add the new one on the same entity. Use a dated, referenced prefix, for example `since 2026-10-18 (graphical#b5)`, so the next reader can tell the current rule from history. Read the cited line before writing it: a claim copied from another agent's note can be wrong.
- The notice `N memories; M unread` repeats on each turn while its counts stay the same. Read the node once when the counts change. A names-only read does not mark a memory read; a full `memory_read_unread` does. Do not write a defect memory from a repeat until a full read of that node returns nothing for it. To compute the notice read-only, use `from metaform.module import context` and `delivery.notices(ctx)` under `METAFORM_SESSION=<the runner's session>`.
- Before saying old memories were cleared, check the store: read the whole graph with `uv run metaform memory read_graph --json` and count entities by first-observation date on a copy of the memory store. A deliberate clear and a loss look the same. When memories an earlier read returned now come back not found, stop writing, report what is missing, and ask before restoring.
- The person's own note at a node (VIEW-034, person-only) is neither a memory nor a knowledge layer. Dispatch's hand-off carries it whole as `the person's note here: <text>`.
- The wording agents are sent is the person's decision. Check the pushed texts with the metaform-prompt-store-served skill before claiming agents follow a rule.
- Design record: `docs/preprint/inference-metaform.md`, sections 5.2 (a language encounter attaches at its element and applies to its descendants), 7.1 (memory has a functional location), 7.2 (informational knowledge kept apart from imperative knowledge) and 7.3 (selection and hidden layers). Read the matching section before asking for a spec.
- System agent working memory (a proposal, not yet specified or built): at the start of a task, and when something is worth keeping, it records a memory at the element the task concerns, citing the task number and the message where the task started. It is what happened in the work, so it goes in the memory graph, not a knowledge layer.
