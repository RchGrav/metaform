# Metaform dispatch: agent choice, stops, and the sentinel

The person chooses which agent runs; the system follows that choice and never overrides it by hand.

- Route each ticket by its functional area. Front-end work (web page, 2D and 3D map, board, figures, chat dock: addresses under `code.interface.graphical`, `code.assistant.navigation`, or `src/metaform/modules/web/page/`) goes to `claude`. Everything else goes to `codex`. Why: the person judges Codex stronger on system and backend work and Claude stronger on frontend, and should not have to flip `dispatch_agent` for each ticket.
- Order of precedence: the ticket's own agent field, then the area rule, then the `dispatch_agent` setting only when the area is unknown.
- Runtime choice (`orchestration_runtime` with a `choice`): `task_type` must be exactly one of the eight keys of `TASKS` in `modules/orchestration/runtime.py`: `planning`, `needs_plan`, `frontend`, `coding`, `lookup`, `routing`, `analysis`, `writing`. A free phrase such as `data reconciliation` makes `_validated()` return None, and the answer is `needs_choice` with a `reason` naming the failed field. Check the key against `TASKS` before sending, and when `needs_choice` comes back, fix the field and resend rather than reporting the ticket blocked. Why: on 2026-10-21 (ticket 17ea54ae, #2e) the first choice failed silently and took several reads to trace. Until the Facilitator's runtime step lists these keys, that gap is a defect to route to a ticket.
- A runtime-only Facilitator commission keeps the ticket's existing role and never reassigns expertise. Before choosing the runtime of a ticket, compare its role with the node memory's routing rule (for example, lock-contention tickets route to `sqlite_concurrency_engineer`). On a mismatch, leave the role unchanged and send the system agent a one-line `dispatch_note` asking whether to reassign before start. Why: on 2026-10-21 ticket code.graph.knowledge#2a was lock contention carrying `event_store_engineer`; the commission kept it and the mismatch needed the person's decision.
- Runtime-only publication order: record the runtime of every shared in-place ticket the commission carries (`orchestration_runtime work=ID choice={...}`, reading back `state: selected`) before `orchestration_publish_role`. Publish refuses while any such target is still `needs_choice`. Pass `role` equal to the commission's own role name: a runtime-only commission keeps its assigned expertise and refuses any other name. Republishing the same role returns `source: existing` and `continued: 1`, and the ticket moves to To do, so pass `column=backlog` when it must wait. Why: on 2026-10-21 (ticket code.router.assignment#40) the runtime was recorded first, then the assigned role was republished unchanged, and the ticket continued in one call.
- When the person has set `dispatch_agent` to codex, a Facilitator runtime choice for an ordinary ticket is codex, and the decision's `reason` names that setting so the person's choice is visible in the record. Why: on 2026-10-21 (code.processor.intake#16) Jev returned `needs_choice`, and the Facilitator chose codex, gpt-6-astra at high effort for an analysis ticket, citing the person's Codex setting.
- Never stop an agent the person chose, and never switch its agent, without asking first. Why: stopping person-chosen agents as "unwanted" wasted their work and the stop had to be reversed.
- Before choosing a ticket's runtime (`orchestration_runtime`) or publishing a role that launches it, read the ticket with `map_work` and check `done`, `resolution` and `held`. A ticket the person cancelled (`done` set, resolution "Cancelled", `hold=true`) gets no runtime choice and no publication: record a `blocked` check-in that names the hold, and ask the person before anything reopens it. Why: on 2026-10-21 (ticket code.framework.plugin#1f) a runtime-only commission was created for a ticket the person had cancelled and held, and publishing its role would have reopened and launched it.
- The sentinel and its tickets take no worker slot and no helper slot. They are exempt from `dispatch_agents`, `dispatch_machine_agents` and helper capacity, like the person's own system agent. Why: "Send to the sentinel" must answer at once, even when agent counts are full.
- Helper capacity counts only live helper sessions. An ended helper that is still counted blocks new starts: on 2026-10-20 the start refused with "The project has 8 helpers active" while one helper was running. Count live sessions, and check the count against the running processes before reporting it.
- Each routed ticket also creates bookkeeping tickets ("Choose ticket runtime", and "Functional assessment of <ticket>"). After any routing change, list the tickets created since the change with `map_work`. Two or more "Functional assessment" tickets for the same ticket address are duplicate paid reviews: report each by address#n as a defect to `code.router.assignment`, and do not count them as work. Why: on 2026-10-21 three assessment tickets (code.framework.plugin#26, #2a, #2d) were created for one ticket, a64cc22b, after the duplicate-assessment fix was reported as landed.

- Facilitator runtime choice (`orchestration_runtime work=ID choice={...}`): `work` takes the hex work record id, never an item address such as `code.graph.knowledge#2c`, nor the citation form `code.interface.graphical#1ae`, which is refused with "No work record has the id". `map_work id=` accepts the same citation and returns the hex `id` field, so read that field first and pass it to `orchestration_runtime`. `task_type` must be one of `planning, needs_plan, frontend, coding, lookup, routing, analysis, writing` (the `TASKS` dict in `orchestration/runtime.py`); the catalog's `choice` description does not list them. A choice that fails validation comes back as `needs_choice` with a `reason` naming the failed field; check `task_type` and the agent/model/effort against `TASKS` before resending, and read back `state: selected`. Do not report the ticket blocked on a bare `needs_choice`. `coding` admits only codex and `frontend` only claude unless the person fixed an agent on the ticket. Use `analysis` for a hard-to-reproduce bug at high effort; `debugging` is not a task type. Call Metaform operations such as `orchestration_runtime`, `agents_confirm` and `map_work` through `mcp__metaform__metaform_catalog` with `tool=NAME` and `arguments={...}`; `ToolSearch` on the operation name finds no deferred tool. Call `orchestration_runtime work=ID` without `choice` first: it returns `needs_choice` with the catalog of agents, models and efforts, and the strengths for each.

- Set `task_type` when the ticket is commissioned, and make it match the area: front-end work (web page, board, figures, CSS, browser tests) is `task_type=frontend`, which routes to Claude. `coding` routes to Codex, so a front-end ticket filed as `coding` is sent to the wrong agent the moment the Claude choice is removed. Why: on 2026-10-21 a front-end ticket was commissioned as `coding`, and the runtime choice could not be corrected afterwards.
- Only the open Facilitator commission records the full-model runtime choice (agent, model, effort, task_type). A worker, memory curator or system session that calls `orchestration_runtime` after the commission has returned is refused with "Only the commissioned Facilitator records a full-model runtime choice." Set the choice in the commission itself, never as a later correction.
- A start refused with "Ticket <id> is not available for specialist assignment." means the ticket has no orchestration assignment and no routing role (`Orchestration.ensure` in `orchestration/state.py`). Fix it by publishing a specialist role for the ticket; retrying the start does not help. The ticket's map item may already name an agent, and that choice stays.
- Publishing a specialist role moves its ticket to To do and launches it unless `column=backlog` is passed. Pass `column=backlog` when the ticket is meant to wait, and read the board back to confirm where it landed. Why: on 2026-10-21 a role published for a set-aside held ticket put it in To do and started a launch, which the person had not asked for.
- A start refused with "Ticket ID is not available for specialist assignment." means the ticket has no bound specialist: routing found no role and no assignment exists. Do not retry the start or report the ticket stuck. Publish a specialist for it first (`orchestration_publish_role` through `metaform_catalog` with `request`, `role` and `match_reason`; an existing role returns `source: existing`), read the assignment back as `queued`, then start. Why: on 2026-10-21 (ticket code.dispatcher.agent#c9) two starts failed with that refusal before `dispatch_lifecycle_engineer` was bound; after the publish the ticket ran under that role.

- A session that holds a ticket keeps every worker off that ticket until the session ends, so a session that has finished its job must end itself. The sentinel's session ends once its issue ticket is released (`held=false hold=false`) or done: `Session.issue_done` in `dispatch/runner.py` checks that one ticket at the end of each turn and when the ticket changes, and `issue_settled` in `dispatch/__init__.py` decides it. The sentinel selects its own proposal and asks the person nothing, so an issue held for the person's choice is a defect. Sentinel sessions run as prep, so the worker end-of-turn ticket check never reads their ticket; any new session kind that holds a ticket needs its own end path. Why: a sentinel left running kept its released issue out of every worker (`not within 60 s` in `test_a_sentinel_ends_once_its_issue_is_released_or_done_so_a_worker_can_take_it` before the fix).

Reference: `dispatch/__init__.py` (`preferred()`, `_admit`, `capacity_kind`). Stop-all side effects are in the `metaform-full-auto-launch-gate` skill.
