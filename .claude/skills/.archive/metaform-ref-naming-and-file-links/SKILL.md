# Ref naming and file links in Metaform

A layer is named by its scope, then `@`, then its content (`base@best_practices`). A ref is named `{ref_id}@{address}` (CTX-066): its id first, then the Address it is linked at. The `:{join}` part is not built while what it names is open (CTX open question 25): a ref on a join is named at its receiver's Address and its record's `join` says which. Whether an element's main ref is named `main` is open (question 13); do not build it.

- A `ref_id` is a proper noun for what the referenced thing is; for code, its qualified name (`metaform.data.refs`). Underscores and periods are allowed, as in Address segments. A title with spaces or hyphens is refused by `dispatch_link` and nothing is linked: name a spec draft file as dotted segments, such as `specs_draft.store_029.runner_hand_over`, then link it before writing it. Hyphens and spaces are refused: a title such as `STORE-029 runner hand-over draft` is answered "cannot be a ref_id" and nothing is linked, so name a spec draft's ref as segments of letters, digits and underscores, such as `specs_draft.store_029.runner_hand_over`, and keep the title in the `why=`. It is unique in the base; a clash writes nothing and answers with the ref that holds it. The exception is a file already linked elsewhere: linking it at a second place gives that place a second ref with a derived name (`metaform.data.refs` at the first place, `metaform.data.refs_py` at a second, then `_py_2`), so check the name the link answers with. The 13 field names of CTX-087 (`metaform.data.RESERVED_REF_NAMES`) are refused as ref_ids; no other name is banned (question 19).
- The `ref_id` is the identity; the `@address` part says where it is linked, which never changes. A read with another address (`store.ref('x@code.b')`) answers with where `x` is linked, and a notice saying so. The same file at two places is two ref_ids: a derived second name takes `_<extension>` or `_2` (`metaform.data.views`, `metaform.data.views_py`).
- A ref is one item of the sources layer, written only as versions (src/metaform/data/refs.py, built 2026-10-15, code.graph.knowledge#c): cite its item id or its ref_id, never a row or position. Linked again at another place it is a second ref there, one per place. Refs are not properties and never move (owner ruling, 2026-10-15); the moving link of CTX-009 applies to properties only. Never justify a ref's place by transitivity or CTX-009, in code, docstrings, spec amendments or replies: a ref stays at the element or join it was linked at, and a common prefix such as `code` is not where a ref belongs. A link that moved refs to the longest common prefix made the `code` and `code.store` elements that hold about 90 refs with no joins, which is the defect this rule prevents. code.graph.knowledge#17 (2026-10-15) deleted the move from refs.py and restored every live store's refs to their pre-layout-22 places; a process started before that still moves refs until it is restarted, so check start times against the fix (see restart-processes-after-code-fix).
- Never create an element to hold refs. A role-less element at a short prefix such as `code` is drawn by the page as the parent of everything under it, so an upgrade or link that makes one is a defect, not a tidy-up.
- `dispatch_link` at an Address that does not exist creates that element, so naming a new Address is the same as making one. Run `metaform map where` on the Address first. If it is missing, link at the existing element that realizes the file, or ask in the ticket; never name a new one to hold a file. To undo a mistaken element, remove its ref from the sources layer by id first, then remove the element with `map refine` (remove true); its earlier versions are kept. Removing the element first leaves its ref orphaned.
- An agent places a file on an element by an explicit link, made while it works on that file, and before the first edit to it. A new file counts as a file: a Write to an unlinked path under `artifacts/` or anywhere else is refused, so link the path first, then retry the same write: an edit to an unlinked file is refused with "To unlock access to this file, please first link it to its functionality in the map", so run `dispatch_link` with the node first, then edit. The link is `dispatch_link file=<path> node=<Address> ref=<ref_id> why=<why>` (CLI `metaform dispatch link`); `ref` is made from the path when left out. It answers the ref's name and id. Never link through `map knowledge op=add-element` with refs: that replaces the refs last linked at that element. The `map code-*` verbs and `code_index.py` were deleted on 2026-10-15 (ticket `code.analyzer.refactoring#1a`), so there is no code-layer link to write. Do not place files by matching code structure: the automatic matcher put 44% of files in a folder fallback and was removed with them.
- A script that writes a file (sed, python, a bulk rewrite) is an edit too: link each file with `dispatch_link` before the script touches it. Editing through Bash to get past the gate, then linking afterwards, is the same breach.
- Read the ticket before assuming any part of a ref or link change is built; a status line written in a skill goes stale.
