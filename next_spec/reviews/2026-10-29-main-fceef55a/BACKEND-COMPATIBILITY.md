Target source: remote main `fceef55a2fb6bd9bf5f8a46310e1af84276fa9f9`. LadybugDB is selected. The question is which implemented behavior survives the different backend and data model, including every retained runtime category. Detailed candidate records, inspected tests and history searches are in [reviewer 5](reviewers/05-BACKEND-RECOVERY.md). Historical native integration is assessed separately in [SEPTEMBER-LADYBUG-RECOVERY.md](SEPTEMBER-LADYBUG-RECOVERY.md).

## Current model versus target

The current implementation is a SQLite operation log with cached in-memory projection. `src/metaform/data/schema.py:1` describes the log as authority, `data/log.py:20` supplies snapshots/replay, `data/session.py:214` updates a process projection and appends committed operations. `data/projection.py:47` emulates legacy row shapes. Current Cypher executes through `grandcypher.GrandCypher` over NetworkX at `data/projection.py:396`, reached by `data/reads.py:596`. It is not current LadybugDB integration.

The ECS target separates published `MapSnapshot` records from mutable runtime revisions, uses typed Namespace/Element/PurposeJoin/Layer/ContextItem/RuntimeRecord records, and publishes derived ancestry/incidence consistently with source changes. See the ECS ZIP member `03-technical-specification.md:35`, `:65`, `:137`, `:151`, `:654`, and `contracts/graph.cypher:1`. Storage keys are distinct from semantic Addresses. Global settings and other retained categories need explicit target contracts. RuntimeRecord is an available target design boundary, not a storage implementation already proven for those categories.

Consequently, replace the current storage realization and adapt domain responsibilities. A connector/import substitution, or a Ladybug-backed version of the same old log/projection model, would not complete this model change.

## IDs, rows, transactions, concurrency and projections

- **Semantic identity:** preserve meaningful Address/canonical name/RE-owned purpose semantics. `data/names.py:16` and `data/ids.py:44` have small storage-free formatting/prefix algorithms worth extracting. Their enclosing `metaform.data` package imports Store/SQLite, so approve routine bodies behind a clean import boundary, not wholesale package reuse. `tests/test_store_map.py:145` observes the formatting behavior.
- **Row/result shapes:** legacy Tx exposes sqlite3.Connection/Cursor and projection-emulated rows. Target typed graph values, null handling, native payload bytes and structured references need explicit result contracts. Retaining generic coercion or SQL-row emulation indefinitely would preserve the wrong interface.
- **Transaction ownership:** preserve scoped atomic operations, rollback and after-commit publication as invariants. ECS source/derived topology and event-head appends must join their specified target transaction. SQLite `BEGIN IMMEDIATE`, PRAGMA and SQL authorizers do not transfer unchanged.
- **Writer serialization:** physical serialization does not resolve stale intent. `Store.refine` at `data/store.py:339` accepts changes/reason/evidence/by but no observed version or operation identity. `data/layering.py:323` reads the current state in its transaction. Target submissions must preserve incompatible contributor values and expose the conflict, as ECS technical `:692` requires. Keeping older log entries alone does not satisfy that result contract.
- **Locks:** current project/file locks and historical per-query engine ownership protect particular resources. A target single-writer service/write queue must own consistent read snapshots and publication, while allowing agent reasoning concurrently. Do not copy incidental file-lock placement as a participant hierarchy.
- **Caches:** cached projections, source selection and delivery receipts have different lifetimes. Replace filesystem WAL stamps/current log sequence with explicit snapshot/runtime/provider revisions where appropriate. Cache hits are not evidence another context received or retained a body.
- **Migrations/history:** this review defines no data migration. Later preservation work must map old IDs, source/role versions, conversations and receipts explicitly. Immutable exports, parent/source digests and complete-output staging are reusable principles. A Ladybug snapshot needs its own consistent engine/export contract.

## Practical backend recommendation

Use the recovered Ladybug mechanics as reference material while completing the target service contracts. Define base graph publication, runtime records, prompt/version repository, settings scope, conversations/session history, delivery/skill observations and journal/replay behavior together at their boundaries. Keep pure parsing/rendering/lifecycle algorithms small enough to extract without importing the old storage package.

Do not restore SQLite authority, a dual-authority analysis-copy architecture, a separate settings/transcript/receipt database or a generic Record/JSON graph as a silent compatibility layer. Do not reopen LadybugDB selection. Explicit native providers can own native data where the specification says so, with source/revision references. That is an ownership contract to document, not an assumed SQL exception.

## Verification status and remaining proof

Tests were read, not executed. Legacy SQLite integrity, append-only history, NetworkX Cypher, retained module tables and fake ACP cases are positive evidence for their stated behavior. They do not establish target graph execution, stale-contribution reconciliation or real harness retention.

Future acceptance needs the selected LadybugDB version running target DDL/queries, typed results and nulls, multi-query consistent reads, rollback/failure recovery, one-writer scheduling, source/ancestry/incidence publication, prior-view reads and explicit runtime-state mappings. It must exercise settings, sessions, conversations, prompt versions and delivery/event records, including retry/conflict/unknown outcomes. A driver smoke test alone is insufficient. No such integration result is claimed by this review.
