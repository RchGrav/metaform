## Principal conclusion

Re-engineer the agent-facing command and intake interactions. Preserve functional meaning, incremental reasoning, meaningful Address references, receiver-owned OP/EF/IFD, readback, revision history and explicit unresolved correspondence. Adapt existing discovery, rendering and exact-body delivery mechanics behind that interface. A new tool name around the existing verbs would preserve the current choreography and storage assumptions.

The old one-object flow is an explicit legacy contract, not an accidental defect: `specifications/04-chassis-modules.md:501` (`BASE-039`) and `src/metaform/modules/intake/__init__.py:1556` declare it. Owner amendments A/C supersede its procedural prescription while preserving the semantics.

## Proposed semantic boundaries and journeys

These examples specify interaction meaning. They do not adopt final tool names, a JSON schema, a new workflow engine or a mandatory reviewer pipeline.

1. **Coherent intake submission.** An agent reads the AUE and source specifications. It submits `code.timer.kitchen`, `code.alarm.audible` and one receiver-owned purpose together: RE `code.timer.kitchen`, OP “Know when the countdown ends”, provider `code.alarm.audible`, EF “Signals that the countdown ended”, IFD `receives`, with the supporting source reference. The service handles namespace records, stable purpose identity and persistence. The result identifies the accepted revision and any unresolved reference. The agent continues with another coherent group when ready, without holding the whole map or calling storage operations.
2. **Readback and refinement.** The agent requests local functional readback at `code.timer.kitchen`. It receives the element, both direct incidence directions and the receiver-owned OP/EF/IFD records. It notices the EF should describe an audible signal and revises that purpose using its returned semantic reference and expected revision. Readback shows the new meaning and source identity. The older revision remains referenceable. Ambiguous selectors return candidate purpose descriptors, rather than revising whichever provider happens to match.
3. **Local functional presentation.** At a provider Address, read its own incoming requirements and the purposes it serves for other receivers. Return relationship meaning and explicit completeness. Do not append each neighboring receiver's notes, tickets, skills and memories.
4. **Global functional presentation.** Read the compact functional map for a named consistent view. Include its elements, receiving purposes and provider contributions. Omit ancillary knowledge layers. Return a snapshot-bound continuation when partial. This is requested navigation, not compulsory startup context.
5. **Local knowledge-rich presentation.** Inspect the same selected element with its attached knowledge descriptors/bodies according to the request and direct functional relationships. The neighbor's knowledge stays out. Explicit reads fetch referenced bodies/ranges with actual source/version identity and continuation.
6. **Revisit and changed knowledge.** Moving to a provider exposes its functional place and relevant discovery. Already delivered unchanged bodies are not resent within the epoch. A changed source is delivered with its actual version/delta policy. A receipt records the response observed, never comprehension. Harness retention that cannot be observed remains unknown.

Proposed result outcomes to refine next: committed coherent change, recorded provisional change with explicit unresolved correspondence, mechanically invalid/unapplied request, expected-revision conflict, and unknown submission outcome after transport failure. These are proposals for concrete schema work, not an approved implementation or permission pipeline. Define retry/idempotency and partial-application policy before extraction so the agent never guesses whether a coherent group landed.
