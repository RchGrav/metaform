Preserve the archived approximately 50% self-handoff intent and graduated warning/enforcement around 65% using real exposed capacity. Unknown capacity/retention remains unknown. ## Concrete proposed intake → readback → refinement journey

This is an illustrative functional account, not an executed transcript or a new product requirement. Pseudostructure deliberately avoids adopting final field/tool names.

1. The agent examines the module author and the module contract and loader. In one coherent submission it describes RE `downstream.cqu.author.module` (canonical name “Module author”), provider `code.system.plugin` (canonical name “Module contract and loader”), OP “Add a capability through one declared module contract”, EF “exposes the declared capability through the selected system surfaces”, IFD `receives`, and source references to `src/metaform/module.py:592` and `src/metaform/loader.py:314`. It may add another contribution separately as its reasoning develops.
2. The service returns the represented element/purpose/contribution records, the accepted revision and a stable semantic purpose reference, here denoted `returned-purpose-ref`. These are domain references. It does not require the agent to create Namespace, OWNS, PROVIDED_BY, INCIDENT or closure records. An unresolved source reference is reported explicitly rather than creating a fabricated element.
3. The agent asks for local functional readback at `code.system.plugin`. It sees both what the element receives and what it provides, with the receiver-owned OP/EF/IFD and supporting references. It does not receive every module author's conversation or memory collection.
4. The agent refines the EF using `returned-purpose-ref` and the observed revision, making clear that the operator CLI and semantic MCP have separate bindings. The response identifies the new revision and retains the earlier referenced form. A stale incompatible change returns the competing versions/finding. An ambiguous readable selector returns candidates without silently modifying one.
5. If the response is lost, retry uses the specified operation identity/outcome contract. A committed retry must not create another purpose. An uncertain runtime outcome remains explicit. Coherent-change atomicity and precise error fields are still to be specified.

No registration/browser launch, raw database query or per-edge command is inherent in this interaction. The agent is free to reconsider its initial functional account.

## Proposed context continuity journey

At epoch E1 the agent discovers specification S revision 4 and skill K digest A. Discovery records no body/skill receipt. An explicit source read establishes only its observable resource-delivery boundary. The native skill-loading path separately reports K loaded if supported. Moving away and back changes discovery while omitting unchanged automatically delivered bodies. Revising S to revision 5 produces a changed-source reference and the requested delta/body with actual version identity. Compaction starts a recorded epoch only when observed. A supported harness restores retained skill bytes/digests and records that action. An opaque harness reports retained state unknown. A handoff carries source and continuation references, and its successor loads what it needs.

This journey is a proposed acceptance demonstration. No hidden harness state, live ACP behavior, new Ladybug projection or new Python–Node integration was exercised during the review.
