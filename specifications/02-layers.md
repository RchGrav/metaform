# 02 Layers

This section defines layers: what a layer is, how it attaches to the map, its declared properties, how select and mask decide what reaches each point, how layers are read, provenance, memory, corrections, the two types of blind spot analysis, the blind-spot challenge workflow, knowledge layers built node by node, the flags their items carry, and reading a project from its roots.
The receiver, purpose and encounter structure itself, element identity and subtypes are in section 01; storage tables and indexes are in the storage section; the operations a module calls are in the common base section.

### LAYER-001 Everything Metaform holds is a layer

- Requirement: Every piece of knowledge Metaform holds belongs to exactly one layer, the intake's map included.
- What this means: A layer is a named body of inferred knowledge laid over the map. The intake produces a layer too: its layer is the one that creates most elements and joins. Every element, join, subtype and layer item records the layer that produced it. The core map is the selection of the intake layer. A new element proposed by a later pass lives in that pass's layer.
- Why: When everything is a layer, every piece of knowledge attaches, selects, hides and records its origin the same way. That uniformity lets modules compose, and it keeps the map from becoming a special case that every module has to handle separately.
- How it shows: Asking for an element's or join's origin always names one layer. Selecting only the intake layer shows the core map with nothing else on it.
- Build: The layer record holds: id, name, the module that owns it, variable (LAYER-002), mutable and hideable (LAYER-004), and created time; an intake layer also holds the intake result id (MAP-040). The project is the store the layer lives in (STORE-003), and hidden state is kept as in STORE-013. Every element, join and subtype record carries a layer id, never empty. Every layer item record carries a layer id, never empty. The intake writes its elements, joins and subtypes under one intake layer, recorded one object per call while it is building and locked when the intake finishes, STORE-032, so context reads see the map only once it is whole. A knowledge layer is built and then locked, LAYER-018. Memory is mutable and never locked against change, LAYER-012.
- Acceptance:
  - After an intake through MCP, every stored element, join and subtype names the intake layer, and reading the intake layer returns all of them.
  - An element, join, subtype or layer item sent without a layer is stored in a new building layer named `unnamed_<UTC timestamp yyyymmddthhmmssz>`, LAYER-028, and the result names that layer in a notice, BASE-044.
  - Amended, 2026-10-10: when the folder's `write_layer` setting names a layer, such a write is stored in that layer instead, with no notice, BASE-060. A project wheel's first run sets it to the working layer it opens, so what a remote agent writes travels back in one layer.
- Relates to: LAYER-002, LAYER-003, LAYER-008, MAP-040, STORE-013, STORE-014.
- Status: confirmed.

### LAYER-002 A layer carries one inferred variable

- Requirement: Each layer answers exactly one question, and every item in it is an answer to that question at the place it attaches.
- What this means: The variable is the one thing the layer infers, and for a knowledge layer it is whatever the prompt that builds the layer defines. Examples, not a closed list: a blind-spot challenge where the critic sees one, best-practice imperatives for a type, porting concerns for a move to another language, or an agent's memory. A layer never mixes two variables. Two questions make two layers.
- Why: A layer with one variable can be selected, masked, hidden, compared and trusted as a unit, because everything in it was produced the same way for the same purpose. That is what makes layers compose: a module adds its one variable without knowing about any other module, and select and mask decide which layers an agent sees together.
- How it shows: Every layer states its variable in one sentence. Reading a layer returns items that all answer that sentence.
- Build: The layer record's variable field is required text, stating the question. A layer created with an empty variable is stored as given, and the result carries a notice asking for the variable, BASE-044.
- Acceptance: Creating a layer without a variable stores the layer and returns a notice; nothing is refused.
- Relates to: LAYER-001, LAYER-003, LAYER-009.
- Status: confirmed.

### LAYER-003 A layer item attaches on an element, on a join, or on a new element and join

- Requirement: Each layer item attaches at one element or one join, a subtype join included, or it creates a new element and join and attaches there.
- What this means: Where an item attaches is where it says something. An item about what an element is attaches at the element. An item about how a provider serves a receiver attaches at their join. An item about an absorbed part attaches at the element it is, directly, and an item about how it serves within its parent's join attaches at its subtype join, MAP-030. When a layer's answer is something the map does not contain yet, the layer creates the element and its join, and those new records belong to that layer. The new element joins on either side, MAP-044: as a receiver it owns its join to an existing provider, and as a provider its join is held by the existing receiver that names it. Functions are not transitive, so a new element with a function or a purpose reaches the metaform only through its join. A property attaches only to an element, MAP-022. When a property belongs at a namespace prefix where the project has no element, the layer creates an element at that prefix and attaches the property to it; the namespace tree links that element to every element above it, so it needs no join.
- Why: Attaching where the knowledge applies means an agent reading any node receives exactly what was inferred about it. Allowing a layer to create its own element and join means a module can extend the map without special machinery, which is the same way the intake builds the map.
- How it shows: Reading an element returns the items attached there. Reading a join returns the items attached to that join. An element created by a later layer shows that layer as its origin.
- Build: A layer item record holds: id, layer id, attach kind (element or join), attach id, value, and the op, reason and evidence of a correction layer's rows, LAYER-011. The value is text or a structured document. Attach id refers to the stable id of the element or join, never to its address; an element's id belongs to its address, MAP-015, and a join's stays with it when the join is moved, MAP-003. An item cannot attach to a missing target.
- Acceptance:
  - An item attached to a join stays attached after the join is moved to another receiver or absorbed into another join.
  - An item attached at a subtype join is returned by a read of that join and not by a read of its parent join, and one attached at the element it holds by a read of that element.
- Relates to: MAP-015, MAP-031, MAP-044, LAYER-001, LAYER-008, STORE-015.
- Status: confirmed for elements, joins, subtype joins, and new elements and joins, and that properties attach only to elements. Creating an element at a prefix to hold a property there, linked by the namespace tree with no join, is recommended; it replaces attaching properties at a bare type address. Whether other items may attach at a type address that no element holds is open; see open question 10.

### LAYER-004 A layer declares its properties

- Requirement: Each layer declares whether it is mutable or immutable and whether it is hideable, and the chassis applies those rules the same way for every layer.
- What this means:
  - Mutable: its items change in place. Memory is mutable.
  - Immutable: its items never change in place. The intake layer and correction layers are immutable: the metaform, the intake map and what correction layers added, changes only through correction layers, LAYER-011. Knowledge layers are not immutable: an agent with the knowledge-layer tool can change them at any time, LAYER-018.
  - Hideable: the layer can be hidden from views and agent context while its content and history stay stored (LAYER-006).
  - Transitivity is not a layer flag. It belongs to properties, MAP-022: a property attached to an element travels along the namespace tree as described in LAYER-005, whatever layer holds it, and nothing else travels, D73.
- Why: Declaring the behavior on the layer lets the chassis apply corrections, visibility and propagation once, uniformly. No module rebuilds these rules, and no module can apply them differently.
- How it shows: A layer's properties are listed with it. Trying to edit an item in place in the intake layer or a correction layer changes nothing and returns a notice naming the correction operation, BASE-044.
- Build: Two required boolean fields on the layer record, mutable and hideable, declared by the module when it creates the layer and never changed, D12. The chassis enforces them in every write and read path.
- Acceptance:
  - An in-place edit of an item in the intake layer changes nothing, succeeds, and its notice names the correction operation.
  - A property on an element at a parent address is received at a child address; an item at the same element is not.
- Relates to: LAYER-005, LAYER-006, LAYER-011, LAYER-013.
- Status: confirmed that layers declare these properties. Chosen by the module for each layer it creates, D12; no transitive flag, D73.

### LAYER-005 Properties apply up toward the leaves and are visible down toward the trunk

- Requirement: A property, which is attached to an element, MAP-022, applies from that element's address to every address above it toward the leaves, and is visible, without applying, at every address below it toward the trunk.
- What this means: Orientation: the trunk is down and the leaves are up. From the address where an item is linked, it goes down to the trunk as visibility and up to the leaves as inheritance. Inheritance runs one way. A practice for `code` holds for every engine, every game engine and every FPS engine. A practice for `code.engine.game.fps` means nothing for code in general. Toward the trunk, the item is visible without applying: C++ attached at the engine and Bash attached at the installer both show at `code`, so `code` shows every medium in use in the project, yet the installer does not inherit C++ because C++ is visible at `code`. Where an item is placed is therefore strategic. Placed near the trunk, it applies to every branch after it. Placed further from the trunk, the branches beside it do not inherit it. An item that still holds with its leaf segment removed belongs lower in the tree, toward the trunk.
- Why: Every prefix of an address is a complete type with its own inference, and practice passes from parent to child. Visibility toward the trunk lets a broad question see everything in use above it without spreading a branch's specifics to its siblings.
- How it shows: Reading an address lists the properties that apply there, and separately the properties visible there from above, toward the leaves.
- Build: Transitive travel follows the namespace tree only, never the purpose graph, so it always terminates. For an address A, the applying set is the properties attached to the elements at A and at every prefix of A, after select and mask. The visible set is the properties attached to elements at any address that has A as a prefix, after select and mask. Storage and reads are STORE-039 and STORE-035. Reads return the two sets separately.
- Acceptance:
  - With C++ attached as a property to the element `code.engine` and Bash to the element `code.installer`: `code` shows both as visible and neither as applying; `code.installer` does not receive C++.
  - A property attached to the element `code` applies at the element `code.engine.game.fps`.
- Relates to: LAYER-003, LAYER-004, LAYER-007, MAP-011, MAP-022, STORE-035, STORE-039.
- Status: confirmed, including the orientation: down is toward the trunk, up is toward the leaves, and that properties attach only to elements.

### LAYER-006 Hiding removes a layer from view and keeps it stored

- Requirement: A hideable layer can be hidden and shown again; hiding removes it from every view and agent context and deletes nothing.
- What this means: Hidden knowledge stays stored with its history and provenance, and it can be shown again at any time. A port from C++ to Rust hides the C++ layers and selects the Rust layers; addresses and purposes stay unchanged.
- Why: Knowledge that no longer applies must stop steering agents without being lost, because it may apply again and because its history explains why things are the way they are.
- How it shows: After hiding a layer, no read, view or context assembled for an agent contains its items. Showing it restores them unchanged.
- Build: The layer's hidden state, stored as in STORE-013. Every read path and every context assembly path filters hidden layers out. Hiding a layer that is not hideable changes nothing and returns a notice saying why. Correction layers are never hideable, LAYER-011.
- Acceptance: A hidden layer's items appear in no element read, join read, layer-at-node read or MCP read, and reappear unchanged when it is shown.
- Relates to: LAYER-004, LAYER-007, STORE-013.
- Status: confirmed for hiding a layer. Hiding is of whole layers only, per D20's recommendation. Whether hiding a layer also hides the layers built from it is open.

### LAYER-007 Select and mask decide which layers reach each address

- Requirement: At each namespace address, the effective selection is (incoming & mask) | select, computed from trunk to leaf, and it applies on every path by which knowledge reaches an agent.
- What this means: Selection is a set of layers. The layers toggled on for the working context supply the starting selection at the trunk, LAYER-019. At each address, a mask can block layers coming up from the trunk, and a select can turn layers on from that address downward. An address with no select and no mask passes its incoming selection through unchanged. A mask on `code.engine` can block porting notes for everything under it, and `code.engine.renderer` can select them again for itself. The same selection governs direct element reads, property and provider context, workflow context and MCP reads. A layer excluded at an address cannot reach an agent there through a property or provider path. Correction layers take no part in select and mask: they are always applied, in order, LAYER-011.
- Why: Select and mask let one map serve many jobs, each seeing exactly the knowledge meant for it at each place, without copying knowledge or building a separate map per job. Applying the same rule on every path is what makes the selection trustworthy: an excluded layer that leaks in through a side path defeats it.
- How it shows: Two jobs with different starting selections read the same element and receive different layers. Selecting a layer at a child address makes it appear there and above it toward the leaves, and nowhere else.
- Build:
  - A selection entry holds: project, address, layer id, kind (select or mask). A mask entry names a layer blocked at that address; the mask applied is all layers except those named.
  - Resolution at address A: start with the starting selection, the layers toggled on, LAYER-019; for each prefix of A from the trunk to A itself, set selection to (selection minus the layers masked there) plus the layers selected there.
  - Resolution follows the namespace tree only, never the purpose graph.
  - An element's effective selection is the effective selection at its address. Every context assembly path calls this one resolution.
  - The starting selection is the folder's `--layers` setting, CLI-033; when it is unset, every finished layer that is not hidden starts selected.
  - Selection data that cannot be applied faithfully, a select or mask row whose layer is hidden or still building, is kept and reported as unresolved by the resolution read, STORE-035, never replaced by a broad default.
- Acceptance:
  - With layer L masked at `code.engine` and selected at `code.engine.renderer`: L reaches `code.engine.renderer`, and does not reach `code.engine` or `code.engine.physics`.
  - A layer masked at an element's address is absent from context assembled through a join whose provider carries that layer.
- Relates to: LAYER-005, LAYER-008, LAYER-009, STORE-019, MCP-003.
- Status: confirmed. Whether a join has its own select and mask, or uses its receiver's, is open; using the receiver's is recommended because the receiver owns the join.

### LAYER-008 Layers are read directly

- Requirement: A whole layer, or every layer at one element or join, is one direct indexed read.
- What this means: The store is a multilayer graph: one set of nodes with many layers over it. Two reads are basic. By layer: everything one layer holds. By node: every layer's items at one element or join, a subtype join included. A node read comes in two forms: raw, with every stored layer; and in context, filtered by the effective selection and hidden state.
- Why: Agents navigate by meaning, one question at a time. Each question must be answered by going straight to the answer, so the structure does the orienting and the agent keeps its inference for the task.
- How it shows: Reading a layer or a node returns at once regardless of how large the project is. No read scans every record to find one.
- Build: Indexes on layer item by layer id, and by attach kind and attach id; on element and join by layer id. The by-node read in context applies LAYER-007 and LAYER-006.
- Acceptance: The raw read and the in-context read of the same node differ exactly by the masked and hidden layers.
- Relates to: LAYER-007, STORE-005, STORE-025.
- Status: confirmed.

### LAYER-009 Comparing is a view, not a stored record

- Requirement: Comparing two layers means selecting both; the comparison itself is never stored.
- What this means: Two perspectives on the same nodes, such as a blind critic's blind-spot layer and a sighted critic's blind-spot layer, are two layers. Selecting both at a node puts them next to each other. Where they disagree is found by the view reading both layers, not by a record holding both answers.
- Why: Each layer stays one variable with one provenance. Storing a comparison would mix two perspectives into one record and give it no single origin.
- How it shows: Selecting two layers at a node shows both sets of items, each labeled with its layer and provenance.
- Build: No comparison record exists. A view takes a list of layer ids and returns, per node, the items of each layer grouped by layer.
- Acceptance: None beyond LAYER-008; the rule is enforced by the absence of a comparison record.
- Relates to: LAYER-002, LAYER-014, LAYER-015.
- Status: confirmed.

### LAYER-010 Provenance is one record per layer, and one per intermediary diff

- Requirement: Provenance tracks exactly two things: one record per layer, and the intermediary diffs made with git diff. Every layer except memory has exactly one provenance record, stating how the layer was created: the module and the workflow within it, the prompt, the model, the role, and whether the producer was blinded. Each intermediary diff, a variant, carries the same fields, PROJ-017.
- What this means: Everything in a layer was produced the same way, by one producer following one prompt in one role, so one record describes the origin of every item in it. Nothing else is tracked: nothing per item, per change or per read. Blinded means the producer saw the map and not the artifact.
- Why: Provenance tracks what a feature actually uses and nothing more. Knowing how a layer was made, by which perspective under which role, is what lets layers be trusted, compared and reproduced. Per-item and per-read records turn provenance into bloat, and bloat defeats a system whose purpose is to give agents only what matters.
- How it shows: Asking for any layer's origin returns one record. Two critics' blind-spot layers over the same metaform show two records, for example one blinded and one sighted, each with its role.
- Build: The provenance record holds: layer id (unique), module, workflow, prompt (the full text as delivered, empty for an intake layer, STORE-016), the exact prompt version when the prompt is a stored one, model, role, blinded. Prompts are their own versioned records; editing a prompt creates a new version for future runs and never changes the version a provenance record references, STORE-044. It is written when the layer is created, by the operation that creates it, and never changes: it is fixed as written through building and locking. A layer other than memory cannot be created without it.
- Acceptance:
  - Creating a non-memory layer without provenance stores the layer with an empty provenance record and returns a notice, BASE-044.
  - Writing a thousand items to a layer leaves exactly one provenance record for it.
- Relates to: LAYER-012, LAYER-014, LAYER-015, STORE-016, STORE-044, PROJ-010, PROJ-017, VIEW-013.
- Status: confirmed, including that provenance tracks exactly these two things and is a chassis function, PROJ-010. What the record holds for a layer written directly by a person, with no model or prompt, is open. Whether a second run adding items to an existing layer is the same layer or a new layer is open.

### LAYER-011 Correction layers are chronological, stacked, and the only way to change the metaform

- Requirement: Correction layers are applied in the order they were made, stacked on top of the intake map, and they are the only thing that can remove, move, or permanently add something to the metaform.
- What this means: The metaform an agent reads is always the intake map with every correction layer applied in order. A correction layer is a knowledge layer whose content is corrections: new versions of elements, joins, subtype joins and properties, removals, join moves, and permanent additions. A correction is relocating a join, renaming, releasing an absorbed element's subtype join from its parent join, or otherwise changing joins; a work record is never a correction, MAP-046. An element cannot be moved: it is an address in the namespace, and moving it changes its address, MAP-015. A function's join can be moved, mostly during annealing, otherwise to fix a serious misinterpretation or to follow a change in the design's structure; a moved join is the same join, with its history, and what is attached to it stays with it, MAP-003. An element is only a namespace address, so removing it does not drop what is attached: those things are orphaned, kept and not shown, and if an element is later put back at the same address, whatever was attached there shows again, because its element is back. When a functionality belongs at a better address, the correction records the element there and moves its joins to it; what was attached to the old element stays with the old element. Knowledge layers extend the metaform only while they are toggled on; only a correction layer changes the metaform itself, and an approved blind-spot entry becomes a permanent record of the metaform, LAYER-015, in the way D89 settles. Correction layers always beat knowledge layers: they sit underneath. The metaform is the intake map with the correction stack applied, and knowledge layers sit on top of that result. A correction layer never changes a knowledge layer's things. When a correction removes something so that a knowledge item, or a knowledge layer's join, has nothing left to attach to, that item is orphaned: it stays stored, but no read in context shows it, because there is nothing for it to be attached to. Items attached to a moved join stay with it; items on a join that is removed are orphaned. Correction layers cannot be toggled: they are not part of layer select or mask, `--layers`, or hiding. A correction layer in the middle of the stack cannot be deleted. To remove one, walk the stack backwards, peeling layers off the top one at a time, and rebuild the ones above it; or put another correction layer on top. Each correction layer carries its one provenance record like any layer. Knowledge built on a thing a correction layer changed is re-examined and never rewritten: layers that depend on it are marked for re-examination, and their contents stay as they were until someone re-examines them.
- Why: The metaform is the shared foundation, so every change to it must be explicit, ordered and traceable, and every agent must stand on the same foundation. A chronological stack gives one answer to what the metaform is, and each change keeps the provenance of the layer that made it. Toggling corrections would give agents different foundations, and deleting one from the middle would change what every later correction was applied to; peeling from the top keeps every remaining layer applied to exactly what it was built against. Rewriting dependents silently would put inference into them that nobody performed.
- How it shows: The correction stack lists its layers in order. After a correction layer that moves a join to another receiver is finished, every read shows the join under the new receiver, and the join's history shows the intake's version and each correction layer's version in order. Peeling a correction layer that is not on top is refused, naming the top layer. Layers built on the corrected thing show that they need re-examination.
- Build: The stack, applying a correction layer when it is finished, peeling the top layer, and the history read are STORE-017; what a correction may change and what a removal does to what depends on the removed thing are STORE-034; the dependency marking and how it is cleared are STORE-036. A correction layer is built like any knowledge layer, LAYER-018: freely edited by its builder until locked, and applied only when locked.
- Acceptance:
  - Two correction layers change the same element; reads show the later one's version, and history shows the intake's version, then each correction layer's in stack order.
  - Peeling the lower of two correction layers changes nothing and returns a notice naming the top layer; peeling the top one restores the metaform as it was before that layer was finished.
  - Selecting, masking, toggling or hiding a correction layer changes nothing and returns a notice.
  - A correction layer changes no item in any other layer.
  - A correction that removes an element orphans a knowledge item attached to it: the item is absent from every read in context, and a raw read returns it marked orphaned.
  - A later correction that puts an element back at the same address shows that item again in context, with no row of its layer rewritten.
- Relates to: LAYER-004, LAYER-006, LAYER-007, LAYER-010, LAYER-015, LAYER-018, LAYER-019, MAP-015, MAP-046, STORE-017, STORE-034, STORE-036.
- Status: confirmed, 2026-09-25, for the model: chronological, stacked, the only way to remove, move or permanently add something to the metaform, never toggled, a middle layer never deleted, removal by peeling from the top and rebuilding or by another layer on top, one provenance record each; correction layers underneath and knowledge layers on top, a correction never changing a knowledge layer's things, an item left with nothing to attach to orphaned and not shown, and an element put back at the same address showing again what was attached to it. Confirmed, 2026-09-27: the same element identity restored when an element is put back, STORE-009; an element cannot be moved and a join can; what a correction is, releasing a subtype join from its parent join included, and that a work record is never one; an approved blind-spot entry becoming a permanent record of the metaform. Open: whether correction layers stay at all, or each change to the metaform becomes a new version of the object it changes, with its provenance, D86. Whether a removed join shows again when its receiver and provider both exist again at the same places is open question 14. The storage mechanics, and raw reads listing orphans marked as orphaned, are recommended. Superseded 2026-10-01 by LAYER-025: the metaform is refined in its own `intake` layer, and there are no correction layers.
### LAYER-012 Memory shows as a layer named memory, with no provenance, that layer selection turns off

- Requirement: Memory shows at the map's nodes as a layer named `memory`, of kind memory, mutable, hideable and with no provenance, and the orchestrator turns memories off with layer selection: select, mask, hiding and the folder's `--layers`.
- What this means: The memories themselves are the memory graph of LAYER-013, kept apart from the map; the layer is how they show at a node. Memory shows at a node while the memory layer reaches the node's address, LAYER-007, so a job can include it or mask it on a branch, and with `--layers` naming other layers it is off. Memories tied to places in the metaform belong to no single agent: any agent may read them and add to them, because they exist to share knowledge. One memory at a node corrects a small wrong inference right where agents read it, so the map does not have to be perfect to be useful.
- Why: Shown as a layer, memory is turned on and off with the controls an orchestrator already uses for every layer, select, mask, hiding and `--layers`, so a job that should not see memories leaves them out the way it leaves out any layer, and no switch of its own is needed. A memory carries no provenance because its value is being cheap to add and to fix; a provenance record and a history would make every memory heavy. Who wrote a join or an observation is kept on it as `by`, STORE-020, and that is not provenance: it is filled by the serving process, never asked of the writer, and keeps no history, so a memory stays as cheap to add; it lets a dispatcher tell whether the session it started recorded at its nodes, which nothing else shows, and lets the page show who recorded a memory, 2026-10-11. A memory's number at its node, its short title and its why, MCP-037 and BASE-040, are not provenance either: the number is taken from the address's counter, and the title and why are one line each, asked of the writer because only it holds the reason, and kept with the memory with no history, so a memory stays cheap to add while a later reader can cite it and tell whether it still holds. Seen at the node where agents read, a memory corrects a small wrong inference in place.
- How it shows: An agent creates an entity at an element, with its title and why, and the next agent reading that element with `map where` is told `1 memory · 1 new` there with the call that reads it, reads it by its number at `metaform://<address>#<n>`, and receives it under `memory` with `contents=true`, MCP-039. After `map mask <address> memory`, or with `--layers` leaving memory out, the read of a node at or below that address shows and counts no memories, and `memory read_graph node=...` there returns an empty graph.
- Build: The memory layer is created per metaform, MAP-045, by the first memory write when the project has a metaform, with name `memory`, kind memory, module `memory`, mutable true, hideable true, and the variable `What agents have noted at this node.`. It has no provenance record, and LAYER-010's refusal does not apply to it, because it is recognized by its kind. Memory shows at an address when the memory layer is in the effective selection there, `store.effective_selection(address)`; with no memory layer, or no metaform, it shows unless the toggled layers leave out `memory`. An entity joined to no node shows in the whole graph while memory reaches the root. What the memory layer held before the memory graph, observations, relations and the person's notes, is carried into the graph and the notes once, STORE-020, and stays in the layer. In the web GUI the memory layer is a row of the Layers list, VIEW-007, turned off as any layer is; the memories drawn are those whose joins `memory graph` says show, VIEW-031.
- Acceptance: A memory at an element is counted in `map where` of the element and shows with `contents=true`; after a mask of the memory layer at a prefix of its address it does neither, and after the mask is cleared it does. With `--layers` naming only the intake layer it does not show.
- Relates to: LAYER-013, LAYER-007, LAYER-010, STORE-018, STORE-020.
- Status: confirmed, 2026-10-02: memory is a layer with no provenance, turned off through layer selection, and memories keep no time and have no maximum age.

### LAYER-013 Memory is a graph of its own, presented at each node exactly as the MCP reference memory server

- Requirement: Memory is a separate graph, the MCP reference memory server's, accessed explicitly. At a node of the map it presents itself exactly like the reference memory service, scoped to that node. Its memories are tied to the map's nodes by joins of type memory, are addressed by the namespace and never as another segment of it, and are kept when the intake is cleared.
- What this means: The graph has entities with a name, an entityType and observations, and relations with a from, a to and a relationType, as the reference server defines them and keeps them, in the order they were made. Each node also holds one note, VIEW-034, which is not a memory.

Kept a separate graph, reached explicitly, memories stay out of the map's types: a memory never becomes an element or a namespace segment and never changes the map. ### LAYER-014 Blind spot analysis over the one Inference Metaform comes in two types, each its own layer

- Requirement: There is one metaform, the Inference Metaform. Blind spot analysis over it finds gaps in the design, functions and encounters the system should have and does not; it comes in two types, metaform-only and metaform plus code, and each run produces its own layer with its own provenance record.
- What this means: The intake agent builds the Inference Metaform from the artifact. In metaform-only analysis, an agent blind to the implementation receives everything the intake agent built, the elements, descriptions, joins and operative purposes, and reasons from outside the intake agent's frame. It can agree with what it sees, question it, or infer missing and different relationships. Like a critic of a specification, it validates intent and finds omissions, because the metaform records the purpose that code does not; some of its concerns will be ones the implementation already handles. In metaform-plus-code analysis, a critic reads the metaform together with the code; its findings are precise and actionable, and the code anchors its view. A critic that reads the code also finds code issues, and writes them as work records, MAP-046, so one pass does both jobs. Either output is its own layer, and both analyses are kept.
- Why: The two see different things. Seeing the code adds blind spots, because the code anchors the critic's view; being embroiled in the code makes bias; a critic is objective because it is not the responsible party. The blind analysis notices what should exist because of what the artifact is, and is expected to raise more, with a lower rate of success, including what a code critic does not see; the sighted analysis notices what the artifact already does that the map never named, LAYER-015, and is expected to be almost always right because it reads the code. Testing shows the value of each. Separate layers keep them from blending with the intake and with each other, and selecting both puts them side by side when a reader wants to compare. The answers of LAYER-015 settle each finding: C for a concern already handled elsewhere, B for a real omission, A for one that adds nothing.
- How it shows: A metaform-only layer's provenance is blinded, and a metaform-plus-code layer's is sighted. A view selecting both shows where they differ.
- Build: Each run creates a new layer with blinded set by its type, writing its items against the metaform's nodes and creating new elements and joins in its own layer where it infers them. `metaform map critic` is one run. Fast mode, metaform-only, is the default; `--critic` is critic mode, metaform plus code, and the critic writes the code issues it finds as tickets. A run creates the layer, named `blind_spot_fast_<UTC time>` or `blind_spot_critic_<UTC time>` in lowercase, LAYER-028's form so the name can be an address root, with provenance module `map`, role `critic`, prompt `blind_spot_challenge`, and blinded true, or false with `--critic`. The mode is a switch rather than a noun so the default needs no word and the other mode is one flag. Built 2026-10-04, the switch and the owner's prompt 2026-10-05.
- Acceptance: A blind spot run of either type leaves the intake layer unchanged and adds exactly one new layer with its own provenance, blinded true for metaform-only and false for metaform plus code.

### LAYER-015 The blind-spot challenge workflow

- Requirement: A blind-spot challenge runs in two passes and one approval: a critic writes blind-spot entries in its blind-spot layer, a project agent answers each A, B or C through the MCP server, and the user, who holds the final veto over every B and every A answer, approves the entries that become part of the metaform.
- What this means:
  - Pass one, the critic. An unembroiled critic, working blind from the metaform or with the artifact's context, traverses the metaform and writes a blind-spot entry wherever something looks like an oversight, or like something neither the user nor any agent thought of that serves a real purpose. Blind, sighted or both is an option of the run, and each critic run builds its own blind-spot layer with its own provenance. An entry is shaped like the intake's records, with more attached: a challenge that proposes new functionality carries the new element and its join, joined to the metaform on either side, MAP-044, and a critic that knows what an entry needs writes its task too, MAP-046. An entry is drawn as a red node at 70% opacity, because it does not exist, VIEW-020. The critic defines the blind spots and answers none of them.
  - Pass two, the answer. A project agent reviews each entry through the MCP server and gives one of three answers, each an equal choice. A: not useful, with the reason; it was considered and is not an oversight, and the node turns yellow. B: useful, it should be taken up, and the node turns green. C: already handled by X, where X is a link to the existing element or join that handles it, which the answer names and marks.
  - Approval. The user has the final veto over every green and every yellow answer. An approved entry becomes a permanent record of the metaform, with provenance; how it enters the metaform, and whether it arrives with an open `missing` work record carrying its task, drawn at partial opacity until it is built, is open, D89. A and C stay recorded as answered, so no later agent raises them again as if they had been missed.
  - States. An entry is open, answered A, answered B, answered C, or approved, stored as `plan`. Only a blind spot needs approval. A plan an agent adds directly is pre-accepted and needs no approval.
- Why: Bias does not come from seeing the code; seeing it adds blind spots, LAYER-014. Bias comes from being embroiled in the role: an agent that sees a problem as its own to deal with defends the current work or reaches for the answer that closes its task, and gaming is part of that. So the blind spots are defined by a critic that owns nothing it judges, and the project agent, which knows the project, answers them. The blind critic notices what should exist because of what the artifact is; the sighted critic notices what the artifact already does that the map never named. The final word stays with the user because what becomes part of the metaform, and what is set aside, is the owner's decision, and an agent's green or yellow is a judgment the owner can overturn. Drawing an entry as not existing yet shows the proposed shape beside the real one.
- How it shows: After pass one, a blind-spot layer holds entries, all open, each a red node at 70% opacity. After pass two, every entry shows its answer next to its layer name, green for B and yellow for A. After `metaform map approve <challenge>`, the B entry reads as plan, and any element and join it carries read as plan.
- Build:
  - The workflow is module work; the chassis supplies the layers, items, links, provenance and challenge states it uses. A challenge is an item in the critic's blind-spot layer, STORE-015, attached to the element or join where the blind spot is seen, or to the new element it proposes. The blind-spot layer is built and locked by the critic like any knowledge layer, LAYER-018.
  - Answers and approvals are recorded as challenge state, STORE-040, not as edits to the critic's blind-spot layer.
  - `answer` is a map verb and MCP tool: challenge, A, B or C, and for C a link to an existing element or join. A C answer without that link is stored as given, with a notice asking for the link, BASE-044.
  - `approve` is a map verb declared for the CLI only, `surfaces=('cli',)`, BASE-035, so it is never an MCP tool and an agent working through MCP cannot approve its own answers. It is the one place a person acts. It accepts a challenge answered B. How the user's veto of a green or a yellow answer is recorded, and what approval writes into the metaform, wait on D89; until then approval records the plan as STORE-040 states.
  - A plan an agent adds directly is recorded as a plan with no challenge, STORE-040.
  - Every read that returns a challenge, or an element or join a challenge carries, shows its state next to its layer name.
  - The critic prompt gives the metaform and asks for blind spots; the answer prompt gives each challenge and the three answers as equals. The provenance of each blind-spot layer records the critic's role and whether it was blinded.
  - Built 2026-10-04: `metaform map critic [--critic]` serves the critic prompt, LAYER-014, and `metaform map challenges <layer>` serves `answer_challenges` with one line per challenge: its id, its state, the node it is attached to and its text. The prompts are in the map module's `resources/prompts.xml`, MCP-031. The critic prompt is the owner's, 2026-10-05; `answer_challenges` is as committed. An entry's task is an item at the same node with `task=true`, LAYER-021. Open: `answer` and `challenge_states` have no place for the reason an A answer gives.
- Acceptance:
  - A C answer without a link to an existing element or join is stored, and the result carries a notice.
  - `approve` is absent from the MCP tool list, and on the CLI it refuses a challenge that is open or answered A or C.
  - After `approve` on a B challenge, reads show that challenge and the element and join it carries as plan; the blind-spot layer's items are unchanged.
  - A plan added directly by an agent reads as plan without any approval.

### LAYER-016 Knowledge layers carry whatever their prompt asks for

- Requirement: A knowledge layer is freeform: it holds whatever its prompt asks to be placed there and may create new namespace objects of any kind, and every item in it attaches to the metaform, at an element or join or at a new object the layer creates that is itself linked to the metaform.
- What this means: The functional map holds only functional types. A knowledge layer is not bound by that. Its content is whatever the prompt that builds it asks for: imperatives, best practices, foresight, a specification at each node after ingesting a paper, or anything else. Those are examples, not a closed list, and the layer's one variable is what its prompt defines, LAYER-002. A knowledge layer carries new namespace objects related to whatever it concerns, and those objects can be pure encounter, medium, encoding, or whatever the prompt asks for; the functional map's address rules, MAP-013, do not apply to them. Every knowledge layer attaches to the metaform: each item links to an element or join of the metaform, or to a new object the layer creates, and that new object is itself linked to the metaform. What a layer holds, and how its agent was prompted, is up to the prompt. For example, a prompt can have an agent apply the intake's reasoning to find blind spots and create new encounter-function objects in its layer, each linked to the part of the metaform it concerns. A knowledge layer is often produced by one prompt applied at every element and every join. How completely it covers the map depends on the prompt: an open-ended prompt gives open-ended coverage, and a prompt that asks for at least one item per join gives one per join. It is built by an agent following its prompt, freely edited until the task is done, then locked and toggled on when needed through select and mask, LAYER-018. A knowledge layer can add new function joins that extend the metaform. Such a join is a normal function join: its receiver owns it, a provider serves it, and it is stored with the id of the layer that added it. It extends the metaform wherever that layer is toggled on, subject to select and mask; when the layer is off, or masked at the join's receiver, the join is absent from every read in context. Every join is noted with where it is from: every read that returns a join shows the name of the layer it comes from, so an agent always sees whether a join belongs to the intake map or to a knowledge layer, and to which one. A knowledge layer sits on top of the metaform as the correction stack leaves it, LAYER-011. If a correction removes what one of its items or joins attaches to, and nothing is left to attach to, that item or join is orphaned: stored, but not shown in context.
- Why: Keeping non-functional knowledge out of the map keeps the map's types clean, while layers put that knowledge exactly where an agent reads. A layer's joins extend the map only where the layer is chosen, and naming their layer on every read keeps the intake map and every extension distinguishable, so an agent weighs a join knowing what produced it. Leaving the content to the prompt is what makes a layer useful for any job, and generating a layer node by node reuses the map's structure as the plan for the work.
- How it shows: A layer built from a prompt asking for porting concerns returns them at each element it covers; an element under `code` can carry a knowledge object for the language in use, which the functional map would never hold. Without the layer selected, the same element shows none of it.
- Build: A knowledge item is either a property, transitive and attached to an element, including an element the knowledge layer created and linked to the metaform, STORE-039, or a function, a join in the layer, STORE-010, MAP-022. Each knowledge layer is an ordinary layer, LAYER-001 to LAYER-004, with one provenance record, LAYER-010, built and locked as LAYER-018. An item attaches at an element or join of the metaform, a subtype join included, or at an element or join the same layer created, LAYER-003; an element the layer creates that carries a function or a purpose is linked to the metaform by a join in the same layer, on either side, MAP-044, and never by the namespace tree, because functions are not transitive; only an element created at a namespace prefix to hold properties is linked by the namespace tree itself, MAP-022. The chassis supplies no kind-specific behavior and does not check the content or the addresses of the objects a knowledge layer creates beyond address form, MAP-010. Whether an element a knowledge layer creates carries an intake role is D48; carrying none is recommended.
- Acceptance:
  - A layer written with one item at every join of a map returns, for each join, exactly the item written there.
  - A knowledge layer creates an element at a medium address, such as one naming a programming language, linked to an element of the metaform, and it is stored and readable in that layer, while the intake map is unchanged.
  - A finished knowledge layer adds a function join between two elements of the intake map. With the layer toggled on, the receiver's `joins` read in context returns that join with the knowledge layer's name, and returns the intake map's joins with the intake layer's name. With the layer toggled off, or masked at the receiver's address, the same read does not return the join, and a raw read still returns it with its layer name.

### LAYER-018 Knowledge layers are written through one read-write tool

- Requirement: Knowledge layers are created, read, changed and removed through one read-write tool, the only tool that makes a new layer; every call names the layer it works on, and an agent with the tool can edit any knowledge layer at any time.
- What this means: Building a knowledge layer is a different path from intake. The intake is recorded through the intake module's own tools, BASE-039. A knowledge layer is assembled object by object: the agent creates the layer, attaches items, properties, elements and joins, reads back what it wrote, and changes or removes any of them, one at a time, with calls that take named arguments. That is why objects are individual and a knowledge layer is never submitted all at once. Every call names the layer being built or edited. Agents are not assigned a layer and there is no ownership check: an agent is trusted to work on the layer it was told to work on. An agent that has the tool can go back to an existing layer and edit it, on its own judgment or because it was prompted to. Who can write is decided only by who has the tool, through tool permissions and the command surface, never by the layer's state. When the agent's task is done it marks the layer finished; a finished layer is listed as ready and can be toggled on, LAYER-019, and it stays editable through the tool. The layer's one provenance record, module and workflow, prompt, model, role, blinded, describes how the layer was created. Function joins the layer adds extend the metaform wherever the layer is toggled on, each shown with the layer it comes from, LAYER-016. Correction layers never change a knowledge layer, and anything in it left with nothing to attach to after a correction is orphaned, LAYER-011. Correction layers keep their own rules, LAYER-011, and memory keeps its own interface, LAYER-012 and LAYER-013.
- Why: The model builds incrementally against its prompt and fixes its own work as it goes, so it needs to add, change and remove single objects. Returning to a layer later, by the same agent or another one prompted to, is how knowledge improves. Controlling access by the tool keeps one rule that holds for every agent and every harness, and trusting the agent to name its layer avoids assignment machinery the design does not have.
- How it shows: An agent with the tool creates layer `practices-cpp`, adds a property at an element, reads the layer by name, changes the property, removes a join it created, and marks the layer finished. It appears as ready in `metaform map layers` and can be toggled on. Later another agent with the tool edits one of its items, and the next in-context read shows the change. An agent without the tool has no way to create or change a knowledge layer.
- Build: One map verb, `knowledge`, served as the single MCP tool `map_knowledge`, BASE-038, with an operation noun: `create`, `add-element`, `add-join`, `add-subtype`, `add-property`, `add-item`, `add-ref`, `edit`, `remove`, `finish`, `tag`, `untag` and `discard`. Every operation names the layer. The store operations are STORE-024 and STORE-032. Nothing the tool is sent is refused for its content, BASE-044: a field that is missing is stored empty and named in a notice, and only a field its record cannot be stored without at all stops a call; BASE-038 lists those fields and why. The tool is granted or withheld like any tool, through the command surface, CLI-022, and harness permissions.
- Acceptance:
  - A layer built with an add, an edit and a removal, then finished, reads back exactly the final state.
  - Before `finish`, the layer's items are absent from another agent's node read in context; after `finish` they are present when the layer is toggled on and absent when it is off or masked.

The layer root gives that content an address, read the same way as every other address, and the same address is what lets a ticket send an agent straight to the work. The name rules follow from the address: a name that is not a valid segment cannot be part of one, and a name that matches a root would collide with the map. Keeping the layer address as a view of the metaform element, never a copy, keeps the element's name, name_length and role defined in one place, so a layer cannot drift from the map. A language is not a function and never appears in the metaform's namespace, MAP-011, so a port's language knowledge belongs in a layer, and the layer address is where the port's work is directed.

### LAYER-029 A work claim reserves the part of the map a chosen proposal touches until its work has landed

- Requirement: When the person chooses a sentinel's proposal, the part of the map it touches is reserved for that work: a work claim naming the elements it reserves and the tickets it covers. The claim is active from the first of its tickets being taken until the last has landed. While it is active no other ticket on its elements starts, by autostart, by the orchestrator or by hand, an issue raised on them waits, and no worker can release or step around it.
- What this means:
  - Separate worktrees stop agents overwriting each other's files, but two pieces of work on the same behavior still collide: two branches edit one file, or different files that change one behavior and break together, and the map and the tickets live in the store, where worktrees isolate nothing. The claim moves that isolation to the map, where the work is understood.
  - Each proposal names its reach, the addresses it would reserve, and its disruption is that reach: how much of the map it blocks and what relies on it. A tactical correction usually reserves little and a strategic one a region, so the person sees the cost of each before choosing, VIEW-045.
  - One claim per chosen proposal, covering all its tickets. It starts when the first is taken, not when the proposal is chosen, so accepted work not started blocks nothing; it ends when every ticket is done and nothing of it waits to merge.
  - While the work runs, the box beside its agent shows the reserved part in white and, unchecked, hides it, so the rest of the map can be reviewed; reviewing a proposal shows its reach the same way.
  - Deciding the reach is the sentinel's job, not a fixed rule; a claim checker that reports a claim drawn too wide is planned and not built.
- Why: Conflicting work should run in sequence by itself rather than be found at merge time, and the person choosing between proposals needs to see what each one blocks for everyone else while it is built. A lock on the map, where purposes and their dependencies are recorded, catches the collisions file locks cannot.
- How it shows: A sentinel's chosen proposal becomes held tickets and a claim; once a worker takes the first, another ticket on a reserved element is refused when started, naming the claim, and autostart passes over it; an issue raised there is queued; when the last ticket lands the claim ends and they start.
- Build: dispatch's own tables, layout 7: `claims` (name, the reserved addresses as a JSON list, the issue it answers) and `claim_work` (each ticket's claim), with the state derived from the tickets: proposed until one is taken, active, ended when all are done and none waits in `merges`. `metaform dispatch claim "<name>" nodes=<addresses> work=<work ids> issue=<work id>` records one and `metaform dispatch claims` reads them with the sentinels' proposals; `startable` refuses a ticket inside another's active claim, which autostart's start meets as well; `in_use` counts an active claim, so `raise` queues an issue on it. The page reads `/api/dispatch-claims` and paints a claimed agent's reserved elements with `paintInUse`. Recorded as a dispatch table rather than a layer in the layer list for now; the layer form, a temporary mask over base nodes, is open.
- Acceptance: `test_a_work_claim_holds_its_part_of_the_map_from_its_first_ticket_taken_until_its_work_has_landed`.
- Relates to: VIEW-045, VIEW-044, BASE-052, LAYER-006, LAYER-007.
- Status: decided 2026-10-08, design notes section 2 and change order 4.1; built 2026-10-09. Open: the claim as a layer in the layer list; the claim checker, whether it also reports claims drawn too narrow, whether it narrows a claim or brings the person a finding, and when it runs.
