# 06 MCP, installer and agent instructions

This section specifies the MCP module that serves Metaform to AI tools, the `metaform install` setup that registers it and writes the skill, and the instructions an agent receives.
It also defines the first working test, which exercises all three end to end.

## MCP module

### MCP-001 MCP is a module

- Requirement: The MCP server is provided by a module named `mcp`, built on the common base like every other module.
- What this means: The chassis runs completely without MCP. The `mcp` module adds the verb `metaform mcp serve`, which starts the server. The verb is declared for the CLI only, so it is never itself a tool, BASE-035. It uses the same chassis resources as any module: the module registry, the settings, the command surface and the verb declarations. It gets no private access. MCP's library dependencies belong to the module, not the chassis.
- Why: The chassis must stay usable on its own, and every surface stands on the same base. Keeping MCP a module also keeps its compiled dependencies out of the chassis, so a wheel without the MCP module runs anywhere.
- How it shows: `metaform list modules` lists `mcp`. With it disabled, `metaform mcp serve` fails with one next step, `metaform enable mcp`. Everything else in the chassis still works.
- Build: Move `src/metaform/mcp_server.py` into `src/metaform/modules/mcp/`, following the template's shape. Remove `mcp` from `VERBS` and `ALWAYS` in `src/metaform/cli.py` and from `RESERVED` in `src/metaform/loader.py`, and remove the `mcp` command page from the chassis docs. Move the `mcp>=1.10` dependency out of the chassis requirements and into the module's `DEPENDENCIES`, BASE-035 and BASE-041. The module ships enabled.
- Acceptance: With the `mcp` module disabled, `metaform mcp serve` exits 2 with a `Next: metaform enable mcp` line, and the chassis command tests still pass. Importing the chassis package with the `mcp` library absent succeeds.
- Relates to: BASE-003, BASE-026, CLI-001, MCP-002, MCP-003.
- Status: confirmed.

### MCP-002 The server speaks MCP over stdio or Streamable HTTP through the official SDK's low-level server

- Requirement: `metaform mcp serve` serves the Model Context Protocol over stdin and stdout, and `metaform mcp serve --http` over Streamable HTTP on 127.0.0.1, both with the low-level `Server` class of the official `mcp` Python SDK and one code path: the transport is the only difference.
- What this means: Over stdio one process serves one host connection, the host starting it in the folder it opens. Over HTTP one process, started by the person, serves the folder it was started in to every client that connects at `http://127.0.0.1:<mcp_port>/mcp`. Tools and instructions are computed on each request from the live module declarations, not registered once.
- Why: Tools come from module verb declarations and change with the folder's command surface. A server that lists tools per request fits that directly. The SDK's high-level `MCPServer`, the former FastMCP, registers each tool once on the server object from a Python function's signature, validates arguments with pydantic before the verb sees them, and holds one tool set for every connection; Metaform's tools differ by folder and change while a session runs, and its arguments are read by the command line's rules, which keep a text argument sent another JSON type with a notice where pydantic would refuse it, MCP-005. The low-level server takes the JSON schemas as built and hands each call over unchanged, so it is kept, and no FastMCP dependency is added. HTTP is offered because a host that cannot start a process, or a person who wants one server for several AI tools, reaches Metaform by address; stdio stays the default because it serves each folder as itself, MCP-010.
- How it shows: A host that launches `metaform mcp serve` completes initialization and receives the tool list and the instructions. `metaform mcp serve --http --port 7434` prints the address it serves, and `claude mcp add --transport http --scope user metaform http://127.0.0.1:7434/mcp` registers it.
- Build: The MCP module declares `DEPENDENCIES = ('mcp>=2.2,<3',)`, pinned below 3 on 2026-10-02 because the server relies on the 2.x middleware list. In the 2.x SDK the low-level server takes its handlers as constructor arguments: `Server('metaform', version=<chassis version>, on_list_tools=..., on_call_tool=..., on_list_prompts=..., on_get_prompt=..., on_list_resources=..., on_list_resource_templates=..., on_read_resource=..., on_subscriptions_listen=ListenHandler(bus), cache_hints=...)`, built once in `serve` of `src/metaform/modules/mcp/server.py`. Over stdio it runs with `stdio_server()` under `anyio.run`, through the relay below. Over HTTP the same server's `streamable_http_app(host='127.0.0.1')` runs under uvicorn, both shipped with the SDK; for a loopback host the SDK turns on DNS rebinding protection, which refuses a request whose Host is not `127.0.0.1`, `localhost` or `[::1]` with any port, answering 421, and one whose Origin is not one of those, answering 403, so a web page in the person's browser cannot drive the server. The SDK serves both wires on both transports, the `initialize` handshake hosts use today and MCP 2026-07-28, whose `server/discover` it answers; the client's first message decides which. The instructions are not given to the constructor: a middleware puts them, composed at that moment, into every `initialize` and `server/discover` answer, MCP-007. `list_tools` returns one `Tool` per command, MCP-003. `call_tool` builds a new `Context` for the call, BASE-028: a verb whose `run` is a coroutine function is awaited in the server's loop, so the host's cancellation reaches it, BASE-031; a plain function runs in a worker thread through `anyio.to_thread.run_sync`. The result follows BASE-036. The `mcp_http` setting, switch `--http`, chooses the transport for the run, and `mcp_port`, global, 7434 by default, switch `--mcp-port` or `--port`, the port; both are declared by the mcp module and read by `serve` as its switches, CLI-012. `mcp_http` is meant for the command line: stored, it would make every `metaform mcp serve` in its scope serve HTTP, the stdio servers AI tools and dispatch start included. The folder is the server's working folder at start, until D37 is answered, MCP-011.
- Recovery amendment, 2026-10-05, work 6efd6c19724541bcb0b77c16ff43e38d and answer A to question 4c706ba21ecc471fb310a3721074f92b: when a long-running server refuses a store upgraded under it and the package code on disk changed since startup, keep the host's stdio connection and relay it to a child running `python -m metaform mcp serve` with the same interpreter, folder and environment. Replay the host's initialize and initialized messages internally before retrying the refused call, suppressing the duplicate initialization answer. The July wire has no initialization to replay. Schema compatibility is checked before dispatch, because a schema failure during an announcement or a module's execution may follow a committed write and cannot safely be replayed. Other active calls finish before replacement, and cancellation notifications and host responses still reach those calls. July subscription streams close gracefully so hosts can reopen them. Unchanged code retains the ordinary schema error, preventing restart loops and preserving the requirement to select newer package code for a pinned old wheel. Failed replacement returns the schema error and keeps the old session usable. The module declares `mcp_recovery`, `relay` by default and `manual` as the alternative, read at server startup. Relay keeps agents working across an upgrade without a host reconnect, while manual lets a host retain control of process replacement. Both surfaces use the public chassis `code_print` service to detect changed package source metadata, so this decision is independent of the web module. Over HTTP there is no relay: an HTTP client opens a connection per request and reconnects to a restarted server on its own, so `mcp_recovery` applies to stdio only.
- Acceptance: An MCP client test starts `metaform mcp serve` as a subprocess, initializes, lists tools and calls one. It protects MCP-003 and MCP-004 through real protocol traffic. The isolated-package upgrade tests replace source and upgrade a copied store while connected, require the refused write to succeed exactly once and a subsequent read on the same connection, and retain refusal with unchanged source or manual recovery. Checked by hand on 2026-10-11 over HTTP: the SDK's Streamable HTTP client listed the 123 tools and called `map_where`, `map_knowledge` and an error case; `server/discover` answered over plain HTTP; a request with a foreign Origin was answered 403 and one with a foreign Host 421.
- Relates to: MCP-001, MCP-003, MCP-010, MCP-012.
- Status: recommended. The context flow was reorganized 2026-10-02 at the owner's request, without changing any prompt's meaning, from baseline commit 4c84d7c. Streamable HTTP was added on 2026-10-11 at the owner's request that the server be usable over HTTP as well as stdio, with the standard SDK's own support.

### MCP-003 Each command is one tool, built from the same declaration as its CLI command

- Requirement: Every verb of every module on the folder's command surface is served as a tool of its own, `<module>_<verb>`, built from the same declaration that builds its CLI command; the chassis's own commands are tools named `metaform_<command>`. A tool is described once, where it is listed: its description, its typed and described arguments, and annotations saying what it does.
- What this means: The tool's description is the verb's summary, with its caution after it. Its input schema comes from the verb's nouns and switches, each property typed and carrying its help as its description. Its annotations come from what the verb declares it does, BASE-006. A module author declares a verb once and gets the CLI command, its help and its tool. Names must match `^[a-zA-Z0-9_-]{1,64}$` and contain no double underscore. A verb whose name would break that rule is refused when the module loads, with the reason. It is not silently skipped.
- Why: One declaration for both surfaces means CLI and MCP never disagree, and an agent without MCP loses nothing. A host plans a call from `tools/list`: a command that is a tool of its own is found by name, its arguments are validated by the host and shown to the model as typed fields, and its annotations let the host tell a read from a write and a removal, for its permission prompts. The module tool that held its commands behind a `command` and an `arguments` object, built 2026-09-28, made an agent call once to see a module's commands and again with `help` to see one command's arguments, so every first use cost two extra turns, and the host could validate nothing because `arguments` was an untyped object. Because every capability is its own tool, a host can also grant one command, such as importing prompts or creating memory layers, to one permitted agent and withhold it from others. What it costs: every command's schema is in the tool list, which a host such as Claude Code defers behind tool search, loading a tool's schema when the model looks for it, CLI-037.
- How it shows: The hello module's `greet` verb appears as the tool `hello_greet`, with the same summary as `metaform help hello greet`; `map_where` is annotated read-only, `memory_delete_entities` destructive, and `dispatch_start` open-world.
- Build: `listing` and `answer` in `src/metaform/modules/mcp/server.py`. For each surfaced verb whose `surfaces` include `mcp`: name `<module>_<verb>`; description the verb's summary, followed by ` Caution: <caution>` for a caution verb; input schema `{"type": "object", "properties": {...}, "required": [...], "additionalProperties": false}` built by `verb_schema`, with one property per noun, typed by BASE-035, which gives the schema for each noun kind including `bool` and `json`, a many noun as an array, required nouns listed in `required`; one property per switch the verb reads, keyed by the setting key, typed by CLI-027, except a `person_only` setting, which only the person writes, so neither this schema nor `metaform_set`'s offers it and a call that sends one is refused, CLI-011; each noun and switch property carries the noun's or the setting's help as its `description`, as does every property of the chassis's own tools, so an agent reads over MCP what `metaform help` says, such as the values `map_knowledge`'s `op` takes; `confirm` of type boolean for a caution verb; and on every module tool, an optional `project`, MCP-025, and `layers`, CLI-033, each with a short description, since it is paid once for each tool listed. Annotations, each of the four set explicitly from the verb's `effect` and `open_world`, BASE-006, so a host never falls back on the protocol's defaults, which take an undeclared tool to be a destructive write that reaches the open world: `readOnlyHint` and `idempotentHint` true for `read`, `destructiveHint` true for `remove`, `openWorldHint` true for `open_world`. The chassis's own tools, `metaform_set`, `metaform_feedback`, `metaform_list_reports`, `metaform_read_report`, `metaform_instructions` and `metaform_register`, and the history, prompt and clear tools of MCP-004, are declared in `CHASSIS`, `SURFACED` and `CHASSIS_EFFECTS` of the same file with their schemas and effects. A call goes to the same run path for every tool, `run_tool`, which checks the arguments as the command line does, MCP-005. A tool's result is the verb's result, BASE-036, so every tool result that holds a join carries the join's `layer`, the name of the layer it comes from, exactly as the CLI shows it, STORE-025, LAYER-016. A result that is a JSON object is also returned as `structuredContent`, for a host that reads tool output as data; no tool declares an `outputSchema`, because no verb declares the shape of its result, and a schema the server invented would be checked by clients against results it does not govern. An invalid tool name is refused at load, BASE-037. Measured on this project on 2026-10-11 with the seven modules that ship enabled: before, 8 module tools whose `tools/list` entries were 7,542 bytes, with every schema behind a second call, or 108,285 bytes with `mcp_schemas` inline; after, 123 tools of 114,095 bytes, each with its schema, so an agent makes no call to learn a command.
- Acceptance: A verb added to a test module appears as a tool with no MCP code written for it. A module declaring an invalid verb name fails to load and says why. In the mcp module's tests: every command is a tool named for it, the list is sorted and the same on two connections, every property is described, every tool carries the four annotations, and an object result is also structured content.
- Relates to: BASE-006, CLI-001, CLI-037, MCP-004, MCP-005.
- Status: confirmed. Built again on 2026-10-11 at the owner's request that each command be its own tool, described once where it is listed, with typed arguments, encoded properly in MCP; it replaces the one tool per module of 2026-09-28.

### MCP-004 The tool list follows the folder's command surface

- Requirement: A tool exists on the MCP server exactly when its command is on the folder's command surface: it is listed only then, and it runs only then.
- What this means: The `modules` setting and the module enabled state decide the surface. `metaform mcp serve` itself is never cut off by narrowing: it is the transport, not a command an agent runs, so it starts whatever `--modules` says, and `--modules` narrows the tools it lists and runs. The chassis tools that always run, `metaform_set`, `metaform_feedback`, `metaform_list_reports`, `metaform_read_report`, `metaform_instructions` and `metaform_register`, stay listed, CLI-022; the history, prompt and clear tools, `metaform_add_origin`, `metaform_list_origins`, `metaform_add_variant`, `metaform_list_variants`, `metaform_extract`, `metaform_prompts`, `metaform_prompt`, `metaform_save_prompt` and `metaform_clear_project`, are listed while the chassis is on the surface. A command outside the surface is neither listed nor callable. A call to it returns an error with one next step. Harness tool permissions can narrow the surface further, but never widen it. The list is sorted by name, so it is the same on every connection to the folder while the surface is.
- Why: The command surface governs what exists, so the narrowing holds even when a host grants every tool. The orchestrator that narrowed the surface holds the way back; a subagent meets only what is on the surface. A list in a fixed order lets a client cache it and compare it, as the 2026-07-28 revision asks of servers whose catalog has not changed.
- How it shows: `metaform set --modules hello` in a folder. `metaform mcp serve` still starts there, and a new MCP connection from that folder lists only `hello_*` tools and the always-run chassis tools. A call to `map_where` returns `Error: No tool map_where on this surface.` followed by `Next: list the tools`.
- Build: The surface is the loaded modules whose ids pass the `modules` check of CLI-022 for the server's folder, and within them the verbs whose `surfaces` include `mcp` and whose `supported_os` includes this system, BASE-016. `listing` in `src/metaform/modules/mcp/server.py` lists exactly those and the chassis tools, sorted. `run_tool` for any other name returns `is_error` true with `Error: No tool <name> on this surface.` and `Next: list the tools`. A change to the surface reaches a running session: the server declares `listChanged` for tools, prompts and resources; after each `tools/call` and `prompts/get` it compares the names it lists with what the session was last shown, whichever process changed them, and when they differ it sends `notifications/tools/list_changed`, or the prompt or resource one, once, on the connection to a client that connected with `initialize`, and on each `subscriptions/listen` stream of a 2026-07-28 client, the only place that revision allows them. A change is heard at the session's next request to Metaform; nothing polls. An alias, CLI-039, changes no tool, so defining one announces nothing. On the 2026-07-28 wire `tools/list`, `prompts/list`, `resources/list` and `resources/templates/list` carry the cache hints `ttlMs` 60000 and `cacheScope` private, set once with the SDK's `cache_hints`: the lists change only when a person enables, disables or narrows modules, each change is announced, and a minute bounds what a client that does not listen keeps; private because what is listed is this folder's. `server/discover` and `resources/read` carry none, since they answer live state.
- Acceptance: With the surface narrowed to a module other than `mcp`, `metaform mcp serve` starts and serves; the narrowed-out tool is absent from `tools/list`, and calling it by name returns `is_error` true. With the surface restored, both work. A running session narrowed hears one `notifications/tools/list_changed`; one that defines an alias hears none.
- Relates to: CLI-022, CLI-039, BASE-016, MCP-003.
- Status: confirmed. The context flow was reorganized 2026-10-02 at the owner's request, without changing any prompt's meaning, from baseline commit 4c84d7c, when the list-change announcements were built. Tool names, ordering and cache hints follow the one tool per command of 2026-10-11, MCP-003.

### MCP-005 Tool arguments follow the command grammar, and booleans appear once

- Requirement: A tool takes each of the verb's nouns and each switch as a named argument. A boolean setting appears once, as a boolean named after the setting, and is left out when not given.
- What this means: Each noun is a named property, the name from its declaration. A switch that takes a value has the JSON type of its setting kind, CLI-027. A boolean appears as `tmux: true | false`. Leaving it out means not given, so the stored or default value applies. The no-form exists for people typing on a command line. An agent never sees it and never has to resolve a double negative. `confirm` is a per-call boolean, present only on caution verbs, and never a setting.
- Why: The CLI grammar is verbs, nouns and switches, and MCP carries the same grammar in JSON. A boolean has three parsing cases: on, off and not given. Absent is how JSON says not given. One argument per setting keeps the tool schema free of contradictions such as `tmux: true, no_tmux: true`.
- How it shows: The schema for a verb with a boolean setting `tmux` shows one property, `tmux`, of type boolean. Calling it with `tmux: false` runs that call with tmux off, even when `--tmux` is glued on. Calling it without `tmux` uses the stored value.
- Build: Switch properties come from the module's settings declarations, not a separate adverb list, CLI-012. A call's switch arguments become `Context.switches` for that call only; `false` is passed through as off. Today the code drops `False`, which makes off impossible over MCP; that changes. A noun's value is read by BASE-035's rule: a `str` noun sent a JSON value that is not a string reaches the verb as that value's JSON text, with a notice in the result and no error; an `int` or `bool` noun sent a value that is not its kind stops the call with the command line's next step. A switch is read by its kind the same way, CLI-027: a `str` or `select` switch, and a `list` member, sent another type is read as its JSON text with the same notice; an `int` or `bool` switch sent another type stops the call. The chassis's own tools, `feedback`, `list_reports` and `read_report`, BASE-045, and the history, prompt and clear tools of MCP-004, read their arguments by the same rule, so every tool on the MCP surface reads a call one way: a text argument sent another JSON type is read as its JSON text, with the notice `<key> is text; what was sent was kept as its JSON text.` as a `Notice: <key>: <message>` line in the block before the result, where a module verb's notices appear; an integer or boolean argument sent another type, and an array argument sent no array, stop the call with the command line's next step.
- Acceptance: A glued-on boolean called with `false` runs off for that call, and the stored value remains on afterward. A call without the argument uses the stored value.
- Relates to: CLI-011, CLI-012, CLI-015, CLI-018, MCP-003.
- Status: recommended.

### MCP-006 Every tool error ends with one next step

- Requirement: A tool error returns `is_error` true with text ending in exactly one `Next:` line, the same line the CLI prints for the same failure, and errors are kept to calls that cannot be read at all; everything else is a notice, BASE-044.
- What this means: Errors from `Stop` carry the message and one next command. A caution verb called without `confirm` explains what it would do and names the call with `confirm` true as the next step.
- Why: An error that names the next command keeps an agent on the surface instead of sending it into the source code, where it starts guessing at the design.
- How it shows: `hello_forget` without `confirm` returns the caution text and `Next: If you are sure: call hello_forget with confirm true`.
- Build: A `Stop` raised by the verb, or by the dispatch checks, becomes a result with `is_error` true whose text is `Error: <message>` and `Next: <next_step>`. A caution verb called without `confirm: true` raises `Stop(caution, 'If you are sure: call <tool name> with confirm true')` before it runs. An unexpected exception becomes `Error: <type>: <message>` and `Next: call metaform_feedback and say what you called`.
- Acceptance: For each error path of the hello module's tools, the text has exactly one `Next:` line, and it matches the CLI's next step for the same failure.
- Relates to: CLI-009, CLI-018, BASE-013, BASE-044.
- Status: confirmed.

### MCP-007 Server instructions are composed live from the base text and each module's instructions

- Requirement: The server's instructions are the chassis base text followed by each surfaced module's concise instructions, in module id order, composed when a connection starts.
- What this means: The base text says what Metaform is, how tools are named, how arguments work, and that errors end with a next step. Each module on the surface adds a section headed by its id. Nothing is cached in files, so enabling, disabling or narrowing takes effect on the next connection. The same composed text is available on the CLI, so an agent without MCP reads the same instructions. The command name for that is open.
- Why: Live instructions have one source. A module's instructions are never copied anywhere that could go stale.

### MCP-008 Each module adds concise instructions that defer to help

- Why: Agents start with little context. The details stay in help, where they are current and cost nothing until needed.
- How it shows: `metaform help hello` opens with `hello: <summary>`, then the module's `purpose`, a few sentences, then its verbs. Over MCP, the hello tool's description is its `summary`, followed by where its instructions are and its commands. ### MCP-017 Setup proves each tool can start the server

### MCP-037 What an agent needs is served as resources, every address resolves, and every command's arguments are in its tool

- Requirement: The server serves MCP resources: the glossary at `metaform://glossary`, the composed instructions at `metaform://instructions`, each surfaced module's full instructions at `metaform://instructions/{module}`, the stored prompts at `metaform://prompts/{name}`, the report files at `metaform://reports/{name}`, whatever a module declares, and every address of the map: `metaform://{address}` is that node's brief, and `metaform://{address}/items/{n}` the one item numbered n there, the fragment form `metaform://{address}#{n}` read too. ### MCP-038 A next step read over MCP names the tool call or resource, never a command line

- Requirement: When a tool call or a resource read fails, the `Next:` line of its error names an action the agent can take over MCP: a call to a tool with a command, a read of a resource, or a listing. A module writes its next steps for the command line, BASE-011; the server translates the forms that name a module's command, `metaform <module> <verb>`, as `call <module>_<verb>`; a command's help, `metaform help <module> <verb>` or `metaform <module> <verb> --help`, as `call <module>_<verb> with the arguments its input schema lists`; a module's help, `metaform help <module>`, and the agents' instructions, `metaform help agents [<module>]`, as a read of `metaform://instructions[/<module>]`; `metaform help commands` as `list the tools`; `metaform help switches` as the `metaform_set` tool's schema; and `metaform add project <id> <path>` as `call metaform_register`. A chassis command line it does not know stays as written.
- What this means: Every error an agent reads over MCP ends with one next step it can act on where it is. The translation only touches a module and verb the loaded modules declare, so a word that happens to follow `metaform` in a sentence is left alone.
- Why: An agent holding tools that is told to run a shell command either has no shell, or leaves the tools to use one; both lose the call. The audit of 2026-10-07 found every server-written next step, and every module's, phrased for the shell.
- How it shows: A missing argument over MCP ends `Next: call <tool> with the arguments its input schema lists`; a wrong address in `map element` ends `Next: call map_where ...`; a tool not on the surface ends `Next: list the tools`; a caution tool without `confirm` ends `Next: If you are sure: call <tool> with confirm true`.
- Build: `mcp_next` in `src/metaform/modules/mcp/server.py`, applied by `_error` and by the resource reader.
- Acceptance: Protected by `src/metaform/modules/mcp/tests/test_mcp.py::test_tool_errors_end_with_the_one_next_step_the_cli_gives` and `test_tool_arguments_are_checked_by_kind_with_the_clis_next_step`.
- Relates to: BASE-011, STORE-026, MCP-006, MCP-037.
- Status: built 2026-10-07, with MCP-037. The next steps name each command's own tool since 2026-10-11, MCP-003.

### MCP-039 An agent is told what is at its node as counts with the calls that read them, once per agent session

- Requirement: Wherever Metaform hands an agent context about the part of the map it works on, it says how much is held there and where to read it, never what it holds, and it says it once in the agent's session. What it holds is read only when the agent asks for exactly that read.
- What this means:
  - The node is the element the agent orients on, its Address. Around it stand the elements that rely on it directly, the receivers of the joins it provides for, and the elements it relies on directly, the providers of the joins it receives. Nothing further away is counted, and nothing of the whole map.
  - For each of those nodes the modules count what they hold there through `Module.node_count`, BASE-035: memory counts the memories joined to it and whether the person left a note. At the node itself the map also counts its open work, its open questions and unread messages, its layer items other than the sources layer's, its earlier runs, the completed tickets there, and the properties that apply there. A part with none is not said.
  - A memory is new when the last agent session that wrote at that node wrote it, a join or an observation, and it is not the reading session's own. The memory module keeps on each observation and memory join the session that wrote it and when, in the columns `session` and `at`, added in memory tables version 4 and kept in version 5, which adds each memory's number, title and why, MCP-037, `compatible_from` 2: every one of them may be empty, so older code still reads and writes the tables, and a row written before has no session and is never new.
  - The counts are drawn as a small tree, in monospace: the elements that rely on the node under the map module's `around_above` heading, then the node marked `▶` with its short name, then the elements it relies on under `around_below`. Each neighbour is a line with its address and its counts; the counts stand in one column; a neighbour holding nothing shows its address alone; each side draws at most eight, those holding most first, and then `around_more`, how many more and the call that lists them all. Under the tree come each module's legend line, memory's `counts` and `note_counts`, which say what new means and name the call that reads them, and the map's `around_read`, the call that reads each kind counted at the node itself. Every word of it is in the map and memory modules' `resources/prompts.xml`; an empty element leaves its part out.
  - The tree is told the first time a session reads the node, in `map where`, in the ticket read `map work id=<id>`, in `dispatch handoff` and in the first turn dispatch sends a worker, BASE-050. What it counted is recorded as shown to the session. A later read in the session that finds the same counts says nothing of them; one that finds a count changed says that one, `around_new`, such as `1 new memory at data.store.sqlite`, or `around_fewer`. What the session wrote itself is never news to it.
  - Calls are named as the surface calls them: over MCP the tool, `memory_read_graph node=<address>`, MCP-038; on the command line the command, `metaform memory read_graph node=<address>`. `Context.calls` renders them, so a module writes command lines once.
  - An agent session is the session its runner names in `METAFORM_SESSION`, for an agent dispatch started and every process it starts, BASE-052; otherwise the MCP server process over stdio, with the client that called it. `Context.session` carries it to every verb, and `Context.seen(key, value)` returns what the session was last shown under a key while recording the new value. A process session's record lives in the process; a named session's is kept in the home's chassis database, table `shown`, so the agent's MCP server and the commands it runs in its shell share one record, and a row older than a week is dropped when another is written. A command line with neither has no session, and every read draws the tree, as a person at a terminal expects.
  - Notices that would repeat on every call are told when their state changes. The first-run provisioning notice, D96, is told once in an agent session. The reminder the installer adds to Claude Code and Gemini CLI, MCP-036, is printed once per host session, which the host names on the hook's standard input; a call that names no session still gets it.
- Why: Metaform exists to give an agent focused awareness of the part it works on. Bulk text pushed at an agent costs its context on every turn whether it needs the text or not, and the same text sent twice costs twice and says nothing new; measured 2026-10-11 on this project's own map, the hand-off at its busiest node was 18,231 bytes, mostly the JSON of what the layers and memories held at the ticket's node, and the where read there 12,106. Told what exists and where, an agent reads what its work needs, once, and keeps its context for the work. Counting only the node and its direct neighbours keeps the awareness local: what relies on the part and what it relies on are the parts a change there touches. New is the last session's work because that is what an agent arriving after it has not seen. A session record that outlives one process is needed because a dispatched agent reaches Metaform through its MCP server and through commands in its shell, two processes that are one session.
- How it shows: `map where code.dispatcher.task` the first time in a session returns the element, its joins as addresses with their purpose and the sources layer's refs, and `around`:
  ```
  Relied on by
    ├ code.web.gui              3 memories
    └ code.workflow.run        12 memories · 2 new
  ▶ code.dispatcher.task  Work queue   32 memories · 5 new · 2 open work · 1 message
  Relies on
    ├ data.store.sqlite          4 memories
    └ code.agent.harness         7 memories
  New = recorded by the last session here. Read them: memory_read_graph node=<address>
  Read here: open work: map_work node=code.dispatcher.task · messages: map_messages node=code.dispatcher.task
  ```
  The same read again returns the element and joins alone; after another session records a memory at `data.store.sqlite`, it returns `changed: ["1 new memory at data.store.sqlite"]`. `contents=true` returns what is held there in full, as the read did before, and `full=true` keeps ids too.
- Build: `src/metaform/shown.py` keeps what each session was shown; `Context.session`, `Context.seen`, `Context.calls`, `Count`, `Module.node_count` and `node_counts` in `src/metaform/module.py`; `serve_session` marks the MCP server over stdio a session of its own. `src/metaform/modules/map/around.py` draws and compares the counts, and the map module's `where` and ticket read use it. The memory module's `node_count`, and its tables, version 5. Dispatch's `handoff_text` composes the hand-off and the runner sends it as the first turn. `agent_setup.ONCE` is the hook's program.
- Acceptance: Protected by `src/metaform/modules/map/tests/test_map.py::test_the_counts_at_a_node_are_told_once_per_session_and_then_only_what_changed`, `test_the_counts_tree_aligns_its_counts_and_caps_each_side`, and `src/metaform/modules/dispatch/tests/test_dispatch.py::test_the_handoff_is_the_brief_the_ticket_its_node_and_counts_under_three_kilobytes`.
- Relates to: BASE-035, BASE-050, BASE-052, MAP-048, STORE-025, LAYER-012, LAYER-013, MCP-029, MCP-036, MCP-038.

### MCP-040 Metaform talks to the A2A peers the person names, and to no other

- Requirement: Metaform keeps a list of A2A peers, each named by its Agent Card URL and the environment variable that holds its token, and sends A2A messages only to the peers on that list. The person adds and removes peers; an agent cannot.
- What this means:
  - The list is the mcp module's `person_only` setting `mcp_a2a_peers`, global. Each entry is a short name, a card URL and a token variable. A token is never stored, only the name of the variable that holds it, as `paperclip_token_env` does.
  - When a peer is added, Metaform reads its Agent Card once and keeps the skills and interfaces the card lists. It reads the card again when a send fails with a version or interface error.

Which outside agents may receive this project's work, and spend from whose budget, is the person's decision, as it is for Paperclip and for every setting that decides which agents run, CLI-011. A list of named peers keeps that decision in one place that every surface reads.
- How it shows: `metaform config --show` lists each peer with its name, card URL and token variable, and whether that variable is set.
- Build: `settings.items('mcp_a2a_peers', ..., scope='global', person_only=True)` declared in `src/metaform/modules/mcp/__init__.py`, each item `<name> <card URL> <token variable>`. ### MCP-041 An agent sends a peer a message about an Address, and follows it to its end

- Requirement: An agent working in Metaform sends an A2A message to a peer on the list, MCP-040, about an Address, and follows the task the peer opens until it ends; the peer's replies, state changes and artifacts come back to that Address.
- What this means:
  - The verb `mcp a2a_send peer=<name> address=<Address> text=<text>`, the tool `mcp_a2a_send`, sends one message with the Address as its `contextId`, the Address extension Metaform already reads inbound. It returns the exchange id and the peer's task id.
  - Metaform follows the task by the peer's streaming or push, whichever its card offers, else by reading the task again. Each change is recorded at the Address: a state change as an update of the exchange, an artifact as an item, MCP-037, and a question the peer asks as an open question at the Address, MAP-050, which the agent or the person answers.
  - A cancel from the sender cancels the peer's task.
- Why: Metaform only receives today. Agents working together means an agent can hand part of its work to another and get the result back where the work lives. Attaching every reply to the Address keeps the Join rule: what was learned attaches to the receiving element.
- Build: the verb in `src/metaform/modules/mcp/__init__.py`, open world, BASE-006; the send and the following through the official `a2a-sdk` client, its streaming, push and task reads; the exchange recorded as MCP-043 says; the items and questions written through the map module's own operations, so they are numbered and titled at the Address like every other.
- Acceptance: with a stubbed peer, a send carries the Address as its `contextId` and returns the exchange id and the peer's task id; a state change, an artifact and a question from the peer each land at the Address as an update, an item and an open question; a cancel from the sender reaches the peer as a cancel of its task.
- Relates to: MCP-037, MCP-038, MCP-040, MCP-042, MCP-043, MAP-050, VIEW-050, BASE-066.
- Built 2026-10-14: `mcp a2a_send`, `a2a_exchanges` and `a2a_cancel` in `src/metaform/modules/mcp/a2a_out.py`; followed by the peer's stream, else by reading the task again; an artifact is a message at the Address, a question an open question there. The answer given to that question goes back on the peer's task once, `answered`, from the map change that closed it, the follower and a listing; while it waits, the follower reads the task only every 10 × 20 seconds. Push from the peer is not built. Acceptance test as MCP-040's, which checks that the answer reaches the peer.

### MCP-042 Every A2A message says which agent sent it, and Metaform checks it

- Requirement: Every message Metaform sends carries the identity of the agent instance that sent it, not of the session that started that agent, and every message Metaform receives from a known peer is checked against that peer's token before its sender is trusted.
- What this means:

- Acceptance: a send from a child agent carries the child's session, not its parent's; an inbound message claiming a peer's identity with a wrong token is not credited to that peer; a call through the gateway with `x-paperclip-agent-id` is credited to that agent.
