# 06 MCP, installer and agent instructions

This section specifies the MCP module that serves Metaform to AI tools, the `metaform install` setup that registers it and writes the skill, and the instructions an agent receives.
It also defines the first working test, which exercises all three end to end.

## MCP module

### MCP-001 MCP is a module

- Requirement: The MCP server is provided by a module named `mcp`, built on the common base like every other module.
- What this means: The chassis runs completely without MCP. The `mcp` module adds the verb `metaform mcp serve`, which starts the server. The verb is declared for the CLI only, so it is never itself a tool, BASE-035. It uses the same chassis resources as any module: the module registry, the settings, the command surface and the verb declarations. It gets no private access. MCP's library dependencies belong to the module, not the chassis.
- Why: The chassis must stay usable on its own, and every surface stands on the same base. Keeping MCP a module also keeps its compiled dependencies out of the chassis, so a wheel without the MCP module runs anywhere.
- How it shows: `metaform list modules` lists `mcp`. With it disabled, `metaform mcp serve` fails with one next step, `metaform enable mcp`. Everything else in the chassis still works.
- Build: Move `src/metaform/mcp_server.py` into `src/metaform/modules/mcp/`, following the template's shape. Remove `mcp` from `VERBS` and `ALWAYS` in `src/metaform/cli.py` and from `RESERVED` in `src/metaform/loader.py`, and remove the `mcp` command page from the chassis docs. Move the `mcp>=1.10` dependency out of the chassis requirements and into the module's `DEPENDENCIES`, BASE-035 and BASE-041. The module ships enabled.
- Acceptance: With the `mcp` module disabled, `metaform mcp serve` exits 2 with a `Next: metaform enable mcp` line, and the chassis command tests still pass. Importing the chassis package with the `mcp` library absent succeeds.
- Relates to: BASE-003, BASE-026, CLI-001, MCP-002, MCP-003.
- Status: confirmed.

### MCP-002 The server speaks MCP over stdio through the official SDK's low-level server

- Requirement: `metaform mcp serve` serves the Model Context Protocol over stdin and stdout, using the low-level `Server` class of the official `mcp` Python SDK.
- What this means: One process serves one host connection. Tools and instructions are computed on each request from the live module declarations, not registered once with decorators.
- Why: Tools come from module verb declarations and change with the folder's command surface. A server that lists tools per request fits that directly. A decorator-based framework would sit between the declaration and the server and add dependencies without adding anything used.
- How it shows: A host that launches `metaform mcp serve` completes initialization and receives the tool list and the instructions.
- Build: The MCP module declares `DEPENDENCIES = ('mcp>=2.2,<3',)`, pinned below 3 on 2026-10-02 because the server relies on the 2.x middleware list. In the 2.x SDK the low-level server takes its handlers as constructor arguments: `Server('metaform', version=<chassis version>, on_list_tools=list_tools, on_call_tool=call_tool, on_list_prompts=list_prompts, on_get_prompt=get_prompt, on_subscriptions_listen=ListenHandler(bus))`, run with `stdio_server()` under `anyio.run`. The instructions are not given to the constructor: a middleware puts them, composed at that moment, into every `initialize` and `server/discover` answer, MCP-007. The SDK serves both wires on stdio, the `initialize` handshake hosts use today and MCP 2026-07-28, whose `server/discover` it answers; the client's first message decides which. The decorator registration of the 1.x SDK is not used; the minimum version is what makes this constructor available, and the current chassis code runs on it with mcp 2.2.0. `list_tools` returns one `Tool` per surfaced verb, MCP-003. `call_tool` builds a new `Context` for the call, BASE-028: a verb whose `run` is a coroutine function is awaited in the server's loop, so the host's cancellation reaches it, BASE-031; a plain function runs in a worker thread through `anyio.to_thread.run_sync`. The result follows BASE-036. The folder is the server's working folder at start, until D37 is answered, MCP-011.
- Recovery amendment, 2026-10-05, work 6efd6c19724541bcb0b77c16ff43e38d and answer A to question 4c706ba21ecc471fb310a3721074f92b: when a long-running server refuses a store upgraded under it and the package code on disk changed since startup, keep the host's stdio connection and relay it to a child running `python -m metaform mcp serve` with the same interpreter, folder and environment. Replay the host's initialize and initialized messages internally before retrying the refused call, suppressing the duplicate initialization answer. The July wire has no initialization to replay. Schema compatibility is checked before dispatch, because a schema failure during an announcement or a module's execution may follow a committed write and cannot safely be replayed. Other active calls finish before replacement, and cancellation notifications and host responses still reach those calls. July subscription streams close gracefully so hosts can reopen them. Unchanged code retains the ordinary schema error, preventing restart loops and preserving the requirement to select newer package code for a pinned old wheel. Failed replacement returns the schema error and keeps the old session usable. The module declares `mcp_recovery`, `relay` by default and `manual` as the alternative, read at server startup. Relay keeps agents working across an upgrade without a host reconnect, while manual lets a host retain control of process replacement. Both surfaces use the public chassis `code_print` service to detect changed package source metadata, so this decision is independent of the web module.
- Acceptance: An MCP client test starts `metaform mcp serve` as a subprocess, initializes, lists tools and calls one. It protects MCP-003 and MCP-004 through real protocol traffic. The isolated-package upgrade tests replace source and upgrade a copied store while connected, require the refused write to succeed exactly once and a subsequent read on the same connection, and retain refusal with unchanged source or manual recovery.
- Relates to: MCP-001, MCP-003.
- Status: recommended. The context flow was reorganized 2026-10-02 at Rich's request, without changing any prompt's meaning, from baseline commit 4c84d7c. Built that day: the July wire's `server/discover` answered fresh, the SDK pinned `mcp>=2.2,<3`, and list changes announced, MCP-004.

### MCP-003 Each module verb is one tool, built from the same declaration as its CLI command

- Requirement: Every verb of every module on the folder's command surface is served as a command of the module's tool, built from the same declaration that builds its CLI command. Corrected 2026-09-28 by CLI-037: a module is one tool, and a verb is reached inside it; before, every verb was a tool of its own named `<module>_<verb>`.
- What this means: The tool's description is the verb's summary. Its input schema comes from the verb's nouns and switches. A module author declares a verb once and gets the CLI command, its help and its tool. Names must match `^[a-zA-Z0-9_-]{1,64}$` and contain no double underscore. A verb whose name would break that rule is refused when the module loads, with the reason. It is not silently skipped.
- Why: One declaration for both surfaces means CLI and MCP never disagree, and an agent without MCP loses nothing. Because every capability is its own tool, a host can grant a capability such as importing prompts or creating memory layers to one permitted agent, and ordinary agents never need that tool.
- How it shows: The hello module's `greet` verb appears as the tool `hello_greet`, with the same summary as `metaform help hello greet`.
- Build: For each surfaced verb whose `surfaces` include `mcp`: name `<module>_<verb>`; description the verb's summary, followed by ` Caution: <caution>` for a caution verb; input schema `{"type": "object", "properties": {...}, "required": [...], "additionalProperties": false}` with one property per noun, typed by BASE-035, which gives the schema for each noun kind including `bool` and `json`, a many noun as an array, required nouns listed in `required`; one property per switch the verb reads, keyed by the setting key, typed by CLI-027; each noun and switch property carries the noun's or the setting's help as its `description`, as does every property of the chassis's own tools, `set`, `feedback`, `list_reports` and `read_report`, so an agent reads over MCP what `metaform help` says, such as the values `map_knowledge`'s `op` takes; `confirm` of type boolean for a caution verb; and on every tool, an optional `project` property of type string, MCP-025. An invalid tool name is refused at load, BASE-037. A tool's result is the verb's result, BASE-036, so every tool result that holds a join carries the join's `layer`, the name of the layer it comes from, exactly as the CLI shows it, STORE-025, LAYER-016. The current code puts all nouns in one `nouns` array and silently skips invalid names; both change.
- Acceptance: A verb added to a test module appears as a tool with no MCP code written for it. A module declaring an invalid verb name fails to load and says why.
- Relates to: BASE-006, CLI-001, MCP-004, MCP-005.
- Status: confirmed. Corrected 2026-09-27 by CLI-037: one tool for each verb of every module is not the design; the record stands for building a command and its tool from one declaration. ### MCP-004 The tool list follows the folder's command surface

- Requirement: A tool exists on the MCP server exactly when its command is on the folder's command surface: it is listed only then, and it runs only then.
- What this means: The `modules` setting and the module enabled state decide the surface. `metaform mcp serve` itself is never cut off by narrowing: it is the transport, not a command an agent runs, so it starts whatever `--modules` says, and `--modules` narrows the tools it lists and runs. The chassis tools that always run, `set`, `feedback`, `list_reports` and `read_report`, stay listed, CLI-022. A command outside the surface is neither listed nor callable. A call to it returns an error with one next step. Harness tool permissions can narrow the surface further, but never widen it.
- Why: The command surface governs what exists, so the narrowing holds even when a host grants every tool. The orchestrator that narrowed the surface holds the way back; a subagent meets only what is on the surface.
- How it shows: `metaform set --modules hello` in a folder. `metaform mcp serve` still starts there, and a new MCP connection from that folder lists only `hello_*` tools and the always-run chassis tools. A call to `map_where` returns `Error: No tool map_where on this surface.` followed by one `Next:` line.
- Build: The surface is the loaded modules whose ids pass the `modules` check of CLI-022 for the server's folder, and within them the verbs whose `surfaces` include `mcp` and whose `supported_os` includes this system, BASE-016. `list_tools` lists exactly those. `call_tool` for any other name returns `is_error` true with `Error: No tool <name> on this surface.` and `Next: metaform help commands`.
- Acceptance: With the surface narrowed to a module other than `mcp`, `metaform mcp serve` starts and serves; the narrowed-out tool is absent from `tools/list`, and calling it by name returns `is_error` true. With the surface restored, both work.
- Relates to: CLI-022, BASE-016, MCP-003.
- Status: confirmed. Corrected 2026-09-27 by CLI-037 and CLI-038: what an agent receives is the top menu and what its folder is given. The context flow was reorganized 2026-10-02 at Rich's request, without changing any prompt's meaning, from baseline commit 4c84d7c. Built that day: a change to the surface reaches a running session. The server declares `listChanged` for tools and prompts; after each `tools/call` and `prompts/get` it compares the tool and prompt lists with what the session was last shown, whichever process changed them, and when they differ it sends `notifications/tools/list_changed` or `notifications/prompts/list_changed` once, on the connection to a client that connected with `initialize`, and on each `subscriptions/listen` stream of a 2026-07-28 client, the only place that revision allows them. A change is heard at the session's next request to Metaform; nothing polls.

### MCP-005 Tool arguments follow the command grammar, and booleans appear once

- Requirement: A tool takes each of the verb's nouns and each switch as a named argument. A boolean setting appears once, as a boolean named after the setting, and is left out when not given.
- What this means: Each noun is a named property, the name from its declaration. A switch that takes a value has the JSON type of its setting kind, CLI-027. A boolean appears as `tmux: true | false`. Leaving it out means not given, so the stored or default value applies. The no-form exists for people typing on a command line. An agent never sees it and never has to resolve a double negative. `confirm` is a per-call boolean, present only on caution verbs, and never a setting.
- Why: The CLI grammar is verbs, nouns and switches, and MCP carries the same grammar in JSON. A boolean has three parsing cases: on, off and not given. Absent is how JSON says not given. One argument per setting keeps the tool schema free of contradictions such as `tmux: true, no_tmux: true`.
- How it shows: The schema for a verb with a boolean setting `tmux` shows one property, `tmux`, of type boolean. Calling it with `tmux: false` runs that call with tmux off, even when `--tmux` is glued on. Calling it without `tmux` uses the stored value.
- Build: Switch properties come from the module's settings declarations, not a separate adverb list, CLI-012. A call's switch arguments become `Context.switches` for that call only; `false` is passed through as off. Today the code drops `False`, which makes off impossible over MCP; that changes. A noun's value is read by BASE-035's rule: a `str` noun sent a JSON value that is not a string reaches the verb as that value's JSON text, with a notice in the result and no error; an `int` or `bool` noun sent a value that is not its kind stops the call with the command line's next step. A switch is read by its kind the same way, CLI-027: a `str` or `select` switch, and a `list` member, sent another type is read as its JSON text with the same notice; an `int` or `bool` switch sent another type stops the call. The chassis's own tools, `feedback`, `list_reports` and `read_report`, BASE-045, and the history, prompt and clear tools of MCP-004, read their arguments by the same rule, so every tool on the MCP surface reads a call one way: a text argument sent another JSON type is read as its JSON text, with the notice `<key> is text; what was sent was kept as its JSON text.` as a `Notice: <key>: <message>` line in the block before the result, where a module verb's notices appear; an integer or boolean argument sent another type, and an array argument sent no array, stop the call with the command line's next step.
- Acceptance: A glued-on boolean called with `false` runs off for that call, and the stored value remains on afterward. A call without the argument uses the stored value.
- Relates to: CLI-011, CLI-012, CLI-015, CLI-018, MCP-003.
- Status: recommended.

### MCP-006 Every tool error ends with one next step

- Requirement: A tool error returns `is_error` true with text ending in exactly one `Next:` line, the same line the CLI prints for the same failure, and errors are kept to calls that cannot be read at all; everything else is a notice, BASE-044.
- What this means: Errors from `Stop` carry the message and one next command. A caution verb called without `confirm` explains what it would do and names the call with `confirm` true as the next step.
- Why: An error that names the next command keeps an agent on the surface instead of sending it into the source code, where it starts guessing at the design.
- How it shows: `hello_forget` without `confirm` returns the caution text and `Next: If you are sure: call hello_forget with confirm true`.
- Build: A `Stop` raised by the verb, or by the dispatch checks, becomes a result with `is_error` true whose text is `Error: <message>` and `Next: <next_step>`. A caution verb called without `confirm: true` raises `Stop(caution, 'If you are sure: call <tool name> with confirm true')` before it runs. An unexpected exception becomes `Error: <type>: <message>` and `Next: metaform list modules`.
- Acceptance: For each error path of the hello module's tools, the text has exactly one `Next:` line, and it matches the CLI's next step for the same failure.
- Relates to: CLI-009, CLI-018, BASE-013, BASE-044.
- Status: confirmed.

The same composed text is available on the CLI, so an agent without MCP reads the same instructions. The command name for that is open.

### MCP-017 Setup proves each tool can start the server

- Requirement: After registering, the installer launches the server with the exact command it registered for each tool, initializes it and lists its tools, and reports pass or fail per tool with the reason.
- What this means: The installer proves that the entry it wrote starts a working server. It does not prove that the host tool applies the server's instructions; each host decides that.
- Why: A written entry is not a working setup. This check turns installed into working.
- How it shows: The report lists each tool with `server starts, N tools` or the failure and one next step.
- Build: The chassis carries a small standard-library client for this, `metaform.probe`, because the chassis must not depend on the `mcp` SDK, BASE-026. It starts the registered command and arguments with `subprocess.Popen`, working folder the user's home, so the surface is every enabled module's; writes newline-delimited JSON-RPC 2.0 to its standard input in MCP 2026-07-28, which has no handshake: `server/discover`, then `tools/list`, each request carrying in `params._meta` the keys `io.modelcontextprotocol/protocolVersion` `2026-07-28`, `io.modelcontextprotocol/clientCapabilities` `{}` and `io.modelcontextprotocol/clientInfo` `metaform-install`; reads standard output line by line, where every line must be one JSON object: a line with an `id` matching a request is that request's response; a line with a `method` and no `id` is a notification and is kept, not answered; a line with a `method` and an `id` is a server request and is answered with a JSON-RPC error `-32601`; a line that is not JSON fails the proof, because standard output carries only protocol messages. Standard error is read and kept only to show in a failure. Then it closes standard input and stops the process. The whole exchange has a 30 second limit per tool, which covers uvx preparing its environment on first run. Pass means a `server/discover` result whose `supportedVersions` holds `2026-07-28`, and a `tools/list` result whose `resultType` is `complete`, or absent, with at least one tool; the report shows `server starts, N tools`, and the proof keeps the discovered instructions.
- Acceptance: A registration with a wrong source path reports fail for that tool and exits 1. A fake server script that answers only the 2026-07-28 wire reports pass with its tool count, and every request it read carries the three `_meta` keys. The real `metaform mcp serve` passes the same proof.
- Relates to: MCP-002, MCP-010, MCP-018.
- Status: recommended. The context flow was reorganized 2026-10-02 at Rich's request, without changing any prompt's meaning, from baseline commit 4c84d7c. Moved to MCP 2026-07-28 that day: the probe had sent the `initialize` handshake the July revision removed. Hosts that still connect with `initialize` are served by the same server, MCP-002.

### MCP-019 Running setup again is safe

- Requirement: Running `metaform install` again shows the current state and offers to repair, update or add tools, and never duplicates an entry.

### MCP-024 The first working test runs installer, instructions and delegation end to end

- Requirement: A fresh machine goes from installing Metaform to an agent that sees each module's concise instructions and the no-intake notice, delegates the intake by name, and then shares memory at map nodes whose visibility follows layer select and mask.

### MCP-037 What an agent needs before its first call is served as resources, and every command's arguments are in its tool

- Requirement: The server serves MCP resources: the composed instructions at `metaform://instructions`, each surfaced module's full instructions at `metaform://instructions/{module}`, each command's argument schema at `metaform://tools/{tool}/{command}`, the stored prompts at `metaform://prompts/{name}`, the report files at `metaform://reports/{name}`, and whatever a module declares. Each tool's input schema lists its commands and nothing beneath them, and its description names the resource that holds its instructions; a command's argument schema is read with `help` or at its resource when the command is used. The server declares `listChanged` for resources and announces a change as it does for tools and prompts, MCP-004.
- What this means: An agent that connects crawls tools and resources before it acts, and plans its calls from what it finds there. Before this record, nothing was a resource: the instructions were reachable only through `initialize`, which some hosts never show the model, or by calling a tool with no command, which no host validator and no agent planning from `tools/list` knows to do; and every command's arguments were behind a second call, `help`, so `arguments` was an untyped object on the wire and a host could validate nothing. Now an agent reads a procedure or a command's schema by URI the moment it needs it and not before, and the `help` command and entering a tool still work as before for an agent that uses them.
- The setting: `mcp_schemas` takes `on_demand`, the default, or `inline`. `on_demand` serves the command names only: the whole menu is about 2,000 tokens, and an agent reads a command's schema when it uses the command. `inline` serves every command's argument schema inside its tool, under `arguments` as an `anyOf` with one branch titled by its command, about 28,000 tokens for every agent whatever its role. Why: this server will carry many roles, skills, prompts and instructions, and an agent in one role touches a fraction of them; what every agent is handed at connect must stay the menu, with everything else read on demand. The builder shipped `inline` as the default on 2026-10-07 and Rich refused it the same day for that reason. The branches sit under `arguments` and not at the top of the schema because Claude Code reduces a top-level `oneOf` to a sentence and drops what the branches held.
- A module's resources: a module declares `resources` on its `Module`, each a `Resource` with a URI, a name, a description and the name of one of its verbs. Reading the resource runs that verb with no arguments and serves its result, so a module serves nothing over MCP that it cannot also give on the command line, MCP-003. A resource naming a verb the module does not declare refuses to load. The intake module declares `metaform://intake/procedure`, its `prompt` verb, and `metaform://intake/schema`, its `schema` verb.
- Every json noun declares its schema: a `Noun` of kind `json` without a schema refuses to load, since an argument served as an untyped object leaves an agent guessing its shape. The nouns that were untyped were given their schemas with this record: workflow's `provenance`, `variables`, `selected`, `addresses` and `calls`; map's `eligible`, `suggestions`, `fields`, `sources`, `tags` and `value`. The nouns whose legal values were listed in prose alone were given an `enum`: map work's `op`, `condition`, `column`, `agent` and `eligible`; map knowledge's and messages' `op`; intake's `condition`.
- Why: An MCP server that hides its procedure in a connect-time string and its argument schemas behind a second call fails the host's discovery: the agent cannot locate its instructions, invents argument shapes, and when told to run `metaform help` from inside a tool result reasons about a shell it may not hold. The audit of 2026-10-07 measured this on the live server: `resources/list` answered `Method not found`, all 120 commands across 8 tools shared one untyped `arguments` object, and the next steps of errors named command lines. Rich's direction the same day was that the server working completely and properly takes priority over the earlier decisions that shaped it, the compact tool list of CLI-037 stays the default.
- How it shows: `resources/list` lists the instructions and each module's declared resources with a description each; `resources/templates/list` lists the four templates; `resources/read` of `metaform://instructions` is what `metaform help agents` prints, and of `metaform://tools/map/joins` is what `help` returns for that command. A tool's description says to read `metaform://instructions/<tool>` before the first call. A URI nothing serves is refused with a next step that says to list the resources. The chassis's `more` prompt and the intake module's instructions prompt name the resources.
- Build: `resource_list`, `read_resource_text`, `TEMPLATES` and `entry_schema` in `src/metaform/modules/mcp/server.py`; `Resource` and the `json` noun check in `src/metaform/module.py`; the setting in `src/metaform/modules/mcp/__init__.py`.
- Acceptance: Protected by `src/metaform/modules/mcp/tests/test_mcp.py::test_resources_serve_the_instructions_each_commands_schema_and_what_a_module_declares` and `test_the_server_lists_one_tool_for_each_module_and_a_module_is_entered_for_its_commands`.
- Relates to: MCP-003, MCP-004, MCP-007, MCP-029, MCP-031, CLI-037, MCP-038.
- Status: built 2026-10-07 at Rich's direction that the server work completely and properly over the earlier decisions on its shape. The resource URIs and the setting's name are the builder's choices, open to his review. The on-demand default is Rich's decision of 2026-10-07.

### MCP-038 A next step read over MCP names the tool call or resource, never a command line

- Requirement: When a tool call or a resource read fails, the `Next:` line of its error names an action the agent can take over MCP: a call to a tool with a command, a read of a resource, or a listing. A module writes its next steps for the command line, BASE-011; the server translates the forms that name a module's command, `metaform <module> <verb>`, a command's help, `metaform help <module> <verb>` or `metaform <module> <verb> --help`, a module's help, `metaform help <module>`, the agents' instructions, `metaform help agents [<module>]`, and `metaform help commands` and `metaform help switches`. A chassis command line it does not know stays as written.
- What this means: Every error an agent reads over MCP ends with one next step it can act on where it is. The translation only touches a module and verb the loaded modules declare, so a word that happens to follow `metaform` in a sentence is left alone.
- Why: An agent holding tools that is told to run a shell command either has no shell, or leaves the tools to use one; both lose the call. The audit of 2026-10-07 found every server-written next step, and every module's, phrased for the shell.
- How it shows: A missing argument over MCP ends `Next: read resource metaform://tools/<tool>/<command>`; a wrong address in `map element` ends `Next: call map with command where ...`; a tool not on the surface ends `Next: list the tools`.

- Acceptance: Protected by `src/metaform/modules/mcp/tests/test_mcp.py::test_tool_errors_end_with_the_one_next_step_the_cli_gives` and `test_tool_arguments_are_checked_by_kind_with_the_clis_next_step`.
