# Web GUI and viewer

This section specifies Metaform's one web GUI, user global, and its first view, the viewer: a floating 3D graph of the metaform and its layers, and a 2D drill-in view of one object and its joins.
The GUI is built after the intake and debug system is stable and the fix pass is complete.

### VIEW-001 Metaform has one web GUI, and the viewer is its first view
- Requirement: One module, `web`, holds Metaform's single web GUI for the user: one server and one app that serve every project registered in the home. The viewer, the floating 3D graph of a project's active metaform and the 2D graph of one object in the left window, is the GUI's first view. Every view a person uses in a browser is part of this one GUI; no module runs a web server of its own.
- What this means: The GUI is user global, not per project: it lists every registered project and switches between them and their metaforms. It owns no data. Three things stay outside it. Web variants of a user's artifact are the artifact running, not Metaform's GUI, so each is served on its own port, PROJ-019; the GUI can list and launch them. MCP stays on stdio, one server per AI tool, MCP-002, since agents, not people, use it. The terminal settings screen stays for people in a terminal, CLI-026; the GUI reads and writes the same settings through the same settings module. The deferral of the workflow editor, the rulebook and the browser terminal under D44 still stands; when they come, they are views of this GUI. How a module adds a view to it is open, question 3.
- Why: One GUI gives one address for everything Metaform shows a person, one process to start and stop, and one place to move between projects and between the map, its layers, its provenance and its prompts. Separate servers per module or per project would each need their own port, token and start, and could not show two projects side by side.
- How it shows: `metaform list modules` lists `web`. `metaform help web` gives its man page. The page opens on the 3D view of a project's active metaform, with a project switcher that lists every registered project.
- Build: The module lives at `src/metaform/modules/web/` with `__init__.py`, `server.py`, `page/` for the HTML, CSS and scripts of the app and its views, `vendor/` for the bundled libraries, and `README.md`. It declares `SUPPORTED_OS = ('linux', 'macos', 'windows')`. It ships enabled. Its verbs are in VIEW-002. Until question 3 is answered, the map views, the provenance view and the prompt editor are the web module's own.
- Acceptance: With the web module disabled, every chassis verb and every other module works. `metaform web` then stops with `Next: metaform enable web`.
- Relates to: BASE-017, BASE-019, BASE-035, CLI-026, MCP-002, PROJ-019, VIEW-002, D44.
- Status: confirmed for one unified web GUI, user global, serving every project, with the viewer as its first view, Rich 2026-09-25. The module name `web` and shipping enabled are recommended.

### VIEW-002 The web GUI is one server for the user, on one fixed port, started with `metaform web`
- Requirement: One server per Metaform home serves the web GUI for every registered project on one fixed port, at a bind address that is loopback by default. `metaform web` starts it when it is not running and prints its address; when it is already running, it prints the address it runs at. `metaform web stop` stops it.
- What this means: The home is the user's Metaform data folder, so in practice this is one server per user; a second home, such as a test's, has its own server and needs another port. Starting from any folder, or for any project, finds the running server and starts no second one. The page lists every registered project and switches between them; the folder `metaform web` ran in chooses only which project the page shows first. The port is fixed, so the address stays the same across restarts and a bookmark keeps working. Before an intake, agents start it and tell the user the address, VIEW-015. Which folder's settings, such as `--layers`, the GUI shows and changes is open, question 5.
- Why: A local server keeps all data on the machine and needs no account. Bound to loopback, as it is by default, nothing on the network can reach the GUI, and the only pages that could try are other sites open in the same browser, which the `Host` and `Origin` checks stop, so no token is needed. A person who sets another bind address opens the GUI to that network, and then a token guards every request. A fixed address lets a person keep the GUI open while agents work.
- How it shows: `metaform web` prints `state: started` and `address: http://127.0.0.1:<port>/`. Run again, from any folder, it prints `state: running` and the same address. With another bind address, the address ends with `?t=<token>` and a `token:` line follows. `metaform web stop` prints `state: stopped`, or `state: not running`. With `--json`, and over MCP, the same fields come back as data.
- Build:
  - The module's verbs are `start`, its default, BASE-035, so `metaform web` runs it and over MCP it is the tool `web_start`, and `stop`, the tool `web_stop`. `start` returns the address and whether it started the server or found it running.
  - `start` launches the server as a process detached from the terminal, so it runs until `metaform web stop`, logout or restart: on POSIX in a new session, on Windows as a detached process, with no console. It returns once the server says it is ready: the server inherits a pipe from `start`, writes its record to it once it listens, and then points that end of itself at the log; `start` reads that one line and is told, and reads end of file when the server ended before it could listen. The read is bounded by `WAIT`, 15 seconds, so `metaform web` never hangs on a server that neither answers nor ends; the bound is a limit on one wait for a message, not a repeated check, and nothing runs while it stands. Pipes are inherited by a detached child on Linux, macOS and Windows alike, QUAL-015.
  - The server uses the standard library, `http.server` with a threading server, so the GUI adds no compiled dependency.
  - Every request is answered only when its `Host` header is the server's own address and port, so a page that rebinds a domain to the machine cannot read the GUI. On a loopback bind address, `127.0.0.1`, `localhost` and `[::1]` with the port are all its own address. Every write, the four POSTs of VIEW-011, is accepted only when its `Origin` header is the server's own address and its body is JSON, so a page from another site cannot send one. On a loopback bind address these checks are all, and the address carries no token.
  - On any other bind address, the home's token is also required: made on the first start that needs it and stored in the home, carried in the page URL, and every request without it refused with 403. `start` returns the token with the address, so the agent that started the server can give it to the user, VIEW-015.
  - The server records its address and process id under `~/.metaform/run/web.json`. `start` reads that file first and reuses a live server: one whose `/api/server` answers with the recorded process id and this home. `stop` signals that process to end, since a stop request would be a write beyond VIEW-011's four, and removes the file. It is told the server has gone by the operating system: before the signal it opens the server's events stream, VIEW-018, which the server holds open until it ends, and then reads the stream to its end; the system closes every socket of a process that ends, on Linux, macOS and Windows alike, so the read returns when the process is gone and not before. The read is bounded by `WAIT` so `metaform web stop` never hangs on a process that will not end; a limit on one wait, not a poll. The server's own loop waits in the system's `select` with no timeout, so it wakes only for a connection; nothing checks for shutdown, because the stop signal ends the process itself, the default of `SIGTERM` on POSIX and what `os.kill` does on Windows. What goes wrong in the server is written to `run/web.log`, and `start` names its last line when a server does not come up.
  - On a wildcard bind address, `0.0.0.0` or `::`, every name of the machine is the server's own, so the `Host` check compares only the port, and the token guards every request. The printed address uses the machine's host name, question 7.
  - The token is accepted as `?t=` on the page URL, which also sets it as an `HttpOnly`, `SameSite=Strict` cookie so the page's own requests carry it, as that cookie, or as the `X-Metaform-Token` header. It is kept in `run/web-token`, readable only by the user.
  - Besides the reads of VIEW-004, three GETs serve the GUI itself: `/api/server`, the server's process id and home; `/api/projects`, every registered project for the project switcher, VIEW-001; and `/api/clear-preview`, what clearing a project would remove and keep, VIEW-019.
  - `--web-port` is a chassis-schema setting declared by the module, an integer, for the whole home, since one server serves the home. Its default is 7433 until question 6 is answered. When the port is held by another program, `start` stops with the port named and `Next: metaform set --web-port <port>`.
  - `--web-bind` is a chassis-schema setting declared by the module, text, default `127.0.0.1`, for the whole home: the address the server binds to. When the server cannot bind there, `start` stops with the address named and `Next: metaform set --web-bind <address>`.
- Acceptance:
  - `metaform web` starts the server and prints its address; run again, it reports the same address as running and no second process exists; `metaform web stop` ends it and removes the run file.
  - `web` run from the folders of two projects leaves one server running, serving both projects.
  - A request whose `Host` is not the server's own address is refused, and so is a write whose `Origin` is not the server's own address or whose body is not JSON. On the default bind address no token is asked for.
  - With `--web-bind` at its default, the server accepts no connection on a non-loopback address; set to another address, it listens there and still refuses a request without the token.
- Relates to: BASE-035, CLI-011, PROJ-003, PROJ-019, VIEW-001, VIEW-004, VIEW-015.
- Status: confirmed for one server for the user serving every project on one fixed port, for `metaform web` to start it and `metaform web stop` to stop it, and for a locally served GUI, Rich 2026-09-25. A bind address setting, loopback by default, is confirmed; so is no token on loopback, with the token required on any other bind address and given to the user by the agent that started the server, Rich 2026-09-25. The `Host` and `Origin` checks, the default verb, the output lines and the setting names are recommended.

### VIEW-003 The viewer works offline with every script bundled
- Requirement: The viewer loads nothing from the network: every script, style and font it uses is bundled in the module with its license.
- What this means: The page references only files served by the viewer's own server. The bundled libraries are `3d-force-graph`, the force-graph library for three.js the approved prototype used, with three.js and its layout engine inside it, Mermaid, the version already vetted on the earlier branch, 12.0.0, and CodeMirror 5.65.16 for the prompt editor, VIEW-013. Each is an unchanged release file with its license file next to it and a `vendor/README.md` naming the version, source and SHA-256.
- Why: Metaform runs offline and in restricted environments. A page that needs a CDN breaks there and sends the user's browsing to a third party.
- How it shows: With the network disconnected, the viewer opens and draws the graph.
- Build: `vendor/` holds `3d-force-graph.min.js`, 3d-force-graph 1.73.4 as the approved prototype loaded it, with three.js r168 and its force layout bundled in, and the licenses of both; `mermaid.min.js`, Mermaid 12.0.0 as vetted on the earlier branch; the IBM Plex fonts the page uses, as `woff2`; and each one's license. `vendor/README.md` names each file's version, source and SHA-256. CodeMirror 5.65.16's editor, its XML and Markdown modes and its search and dialog files are under `codemirror/`, for the prompt editor, VIEW-013. The page has a Content Security Policy of `default-src 'self'`, with inline styles allowed, since Mermaid writes its styles into the SVG, so any accidental remote reference fails visibly. The server sends each file's type from a fixed table, since Windows's registry can map `.js` to a type browsers refuse to run. The wheel build carries the vendor files as package data.
- Acceptance: The served page and every file it loads come from the viewer server; a check of every `src` and `href` in the page and its scripts finds no remote URL. The wheel contains the vendor files and their licenses.
- Relates to: BASE-041, QUAL-002, VIEW-001, VIEW-013.
- Status: confirmed for offline with nothing from a CDN. The library choice is recommended.

### VIEW-004 The viewer reads only through the data access object and follows every visibility rule
- Requirement: Everything the viewer shows comes from data access object reads, under the same rules that govern what agents see.
- What this means: The server calls the store reads of STORE-025 and nothing else. It never opens a database file and never parses an intake document. What is shown is the metaform with the correction stack applied, LAYER-011, plus the knowledge layers the folder's `--layers` setting turns on, CLI-033, with select and mask applied at each address, LAYER-007. Hidden layers do not appear, LAYER-006. Orphaned items do not appear unless the viewer's raw toggle is on, and then they are marked orphaned, STORE-017. Every edge and every item shows the name of the layer it comes from. Every object shows the conditions of its open work records, `open_work`, MAP-046, and every challenge shows its state, LAYER-015.
- Why: A viewer that shows something agents cannot see, or hides something they can, misleads the person checking the map. One source of truth for visibility keeps the picture honest.
- How it shows: Turning a layer off with `metaform set --layers` and refreshing the viewer removes that layer's joins and items from both views. A masked layer at `code.engine` is absent under `code.engine` in the viewer as it is in `map context`.
- Build: The server exposes read-only JSON endpoints that map one to one onto store reads: `/api/<read>` for every read of `metaform query`, STORE-028, such as `/api/roots`, `/api/children`, `/api/node`, `/api/joins`, `/api/layers`, `/api/work`, `/api/search`, `/api/layer-items`, `/api/stack` and `/api/provenance`, with the read's arguments as query parameters by their names, `raw=true` and the paging of STORE-005 among them. Three parameters pick the store and are never a read's argument: `project`, `metaform` and `layers`. `layers` is the view's layer choice, VIEW-007; without it, the read starts from the `--layers` of the project's registered folder, question 5. A read that finds nothing, or names a project that is not registered, answers 404; one that cannot be read answers 400; both carry the error and its next step. `/api/intake-recording` and `/api/layer-graph` are the store reads `intake_recording` and `layer_graph`, STORE-025, the two that show a building intake, BASE-039. `/api/graph` is the store read `graph`, STORE-025: a page of the map in address order, each element in context with its nearest parent element and each join it receives with its subtypes, in one read, VIEW-005 and VIEW-010. The page never computes visibility itself.
- Acceptance:
  - For a store with a hidden layer, a masked layer at one address, an orphaned knowledge item and a flagged element, each endpoint returns exactly what the matching store read returns, raw and in context.
  - The page's data for a node equals `metaform map node` for that node.
- Relates to: LAYER-006, LAYER-007, LAYER-011, LAYER-015, MAP-046, STORE-005, STORE-017, STORE-025, CLI-033.
- Status: confirmed.

### VIEW-005 The 3D view floats the metaform in space in its tripartite form and untangles it
- Requirement: The main view is a 3D graph floating in space that shows every join in its tripartite form and settles itself into the metaform's actual mesh shape through a force layout.
- What this means: Joins are not collapsed in the 3D view. Each join is drawn as the tripartite unit it is, one path, MAP-002: the receiver, a purpose vertex of the join's own, and the encounter, drawn as the link from the purpose vertex on to the provider element that serves it. Nothing is drawn from the purpose or the encounter back to the receiver. Joins that share a receiver or a provider share that element, so the joins form the mesh the metaform is. Because every join has its own purpose vertex, two elements that each receive from the other appear as two separate joins with their own purposes, never as a loop. The namespace tree, along which properties travel, is drawn as its own kind of edge from each element to its nearest parent element, and no namespace branch is collapsed. Subtypes sit inside their join as small vertices attached to the join's purpose vertex. The layout starts from the roots and lets the forces pull connected parts together and push unconnected ones apart, so the tangle opens up into the mesh's shape and settles. The camera orbits, zooms and pans. Hovering a vertex names it. The layout can be paused and resumed while it settles.
- Looks: the 3D mesh reads like a synaptic map in 3D. Elements are glowing nodes against a dark space, joins are fiber-like connections in their tripartite form, and layers are colors, so the whole shape reads like a neural map of the project.
- Why: The receiver, purpose and encounter structure is a shape. Collapsing a join into one edge hides the purpose and the encounter and turns two-way pairs into apparent loops. Drawing each join in full shows the real mesh: where the load-bearing parts are, which branches are thin, and what sits apart from the rest.
- How it shows: Opening the viewer on a real project's metaform shows the VE and DE near the center with the paths of joins arranged around them, settling within seconds. Two elements that each serve the other show two paths between them, each through its own purpose vertex.
- Build:
  - Vertices: one per element, and for each join one purpose vertex. Purpose link: receiver element to purpose vertex. Encounter link: purpose vertex to provider element. Namespace edge: element to nearest parent element. Subtype link: purpose vertex to subtype vertex.
  - The drawing is the approved prototype's, `viewer-prototype.html`, drawn with 3d-force-graph and the prototype's settings. The force simulation holds purpose and encounter links at 34, shorter than namespace edges at 60, and subtype links at 8, and pushes elements apart harder than purpose and subtype vertices, so function structure dominates the shape.
  - Positions of drawn vertices are kept when more of the graph arrives, so the picture does not jump. A reset control re-runs the layout, and a pause control stops and resumes it.
  - While an intake is being recorded, BASE-039, the page follows it live, Rich 2026-09-26: told by the push of VIEW-018 that the intake's layer changed, it switches to that intake's metaform, says so in a toast and in the count line, `intake being recorded`, and draws the building layer from `/api/layer-graph`, redrawing both views, positions kept. When the intake finishes it says `The intake <layer> finished.` and shows the finished map through the usual reads; when the recording disappears because the project was cleared, VIEW-019, it says `The intake <layer> stopped: <project> was cleared.`. While it follows, the Object panel shows the selected element as the building layer records it, from the same `layer-graph` page; it does not read `node` for it, because an intake being recorded is in no reading context until it finishes, LAYER-007, so that read could only find nothing, and a read that is expected to find nothing is not made. The panel's other reads, `context` among them, are made as always. `window.metaform.live()` returns the layer followed, or null.
  - Motion respects the browser's reduced-motion setting.
  - Condition, MAP-046, Rich 2026-09-27: a node with an open `tbd` work record keeps its own color and its full opacity and has circles around it, a glow in its own color; the circles are steady while the part waits, pulsate once an agent has taken its task and the record is `in-progress`, and go when the task is done; a broken part whose task is taken, `fixing`, is steady red with pulsating circles; a join with an open `tbd` record has the circles around its purpose node in 3D and a glow around its edge in 2D. The pulse shows where work is happening now, apart from where work only waits, so a person sees at a glance which parts have an agent on them. The bloom that spreads light across the map is kept for a property's reach, VIEW-022, so the two marks are never mistaken for each other: the circles are a fact about one part, the bloom a fact about a path. The reason: a part not built yet is still that part, so its color, which says its role and its layer, stays readable, and the bloom adds the one fact that it is waiting to be built. Lowering its opacity did not show on the real map of this repository, and giving it a color of its own took away the color it has; a node with an open `broken` record flashes red until it is resolved; an object with an open `cruft` record is drawn in the cruft color and pulses between that color and its own, steady in the cruft color with reduced motion.   - Synaptic look: element vertices are spheres, the DE largest and white, the VE next in the signal color, other elements in their layer's color; purpose vertices are small and light, subtype vertices smaller in their layer's color. Purpose and encounter links are curved fibers with two particles flowing along each toward the provider; namespace edges are thin and dim. ### VIEW-025 One entry of the themes list is a rendered scene that obeys reality

- Requirement: The themes list has one entry that is not a color scheme. ### VIEW-026 A property's reach travels as a wave

- Requirement: A highlighted property's reach is shown as a wave that starts at the element the property is linked to. A dot travels each edge away from that element, toward the leaves where the property applies and toward the trunk where it is visible. A node pulses when a dot arrives, holds the dot, and sends it on along its next edges. With no property highlighted the map is drawn as it is without one.
- What this means:
  - The dots carry the property's color and the glow; the edge keeps its own look.
  - A dot crosses an edge in a time that is set, the same for every edge.
  - A node's pulse lasts exactly as long as the node holds the dot.
  - Each timer, how often a wave leaves, how long a dot takes to cross an edge and how long a node holds a dot, can be multiplied by `rnd() + rnd()` each time it is used. That factor runs from 0 to 2 and is 1 on average, so the timer averages the time set and never repeats.
  - The pulse through a node has a depth, 0 as the dot enters, 1 at the node's center and 0 as it leaves. The node tints the pulse as colored glass tints light: each channel of the pulse's color is multiplied by `1 - opacity + opacity * node`, where the node's opacity is for the light alone and the node is drawn solid whatever it is. The node's body moves from its own color toward that tinted color by the depth, and the glow is the body's color and brightness at that moment.
  - Each property highlighted is its own wave in its own color.
- Why: Dots that all arrive together say only that the elements are related. A wave shows cause in order: the property reaches the near elements first and the far ones last, and it can only move away from where it began, so it shows its direction and the element it is linked to without a label. A node lit only while it holds the dot keeps its own color the rest of the time, so its role and layer stay readable, and the light means one thing, that the dot is here; a pulse that outlasted the hold would show the property in two places at once. A fixed time to cross is used because the map's layout comes from a force simulation, so the length of an edge on screen carries no meaning. The factor from `rnd() + rnd()` keeps any two timers from falling into step, however many waves run. A glow made from the node's own body cannot clash with it, because light coming off a thing has that thing's color. With the dots carrying the property's color, each part has one job: the dots say which property is traveling and which way, the pulse says it has reached this node now, and the glow says what the node is.
- How it shows: Highlighting a property linked at one element sends dots out along its branches and back along the path to the trunk; each node they reach lights as the dot arrives and returns to its own color as the dot leaves.
- Build: Open. The values are chosen by eye on the demonstration page and are not settled: a wave about every 3 seconds, a dot crossing an edge in 1 second, a node holding a dot for about a quarter of a second, and an opacity of 0.6. The bloom and the wave are the same in every theme. In the rendered scene, VIEW-025, the node is made of a material and changes color in reaction to the light, drawn by the renderer, in place of the tinting rule above. The graph library makes a shape for every dot it sends and never lets it go, which fills the graphics card's memory, so every dot shares one shape and one material for each color. What is built today, VIEW-022, lights the whole reach at once with a steady stream of dots; its bloom pass is in the right place, since the bloom belongs to every theme.
- Acceptance: Open with the build. It will hold that a node is lit only while it holds a dot, that the count of shapes and textures the graphics card holds does not grow while waves run for a minute, and that selecting anything else puts every node and edge back.
- Relates to: VIEW-005, VIEW-022, VIEW-025, LAYER-005, LAYER-020.
- Status: confirmed as design, 2026-09-28. The values are open.
