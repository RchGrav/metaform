# Web GUI and viewer

This section specifies Metaform's one web GUI, user global, and its first view, the viewer: a floating 3D graph of the metaform and its layers, and a 2D drill-in view of one object and its joins.
The GUI is built after the intake and debug system is stable and the fix pass is complete.

### VIEW-001 Metaform has one web GUI, and the viewer is its first view
- Requirement: One module, `web`, holds Metaform's single web GUI for the user: one server and one app that serve every project registered in the home. The viewer, the floating 3D graph of a project's active metaform and the 2D graph of one object in the left window, is the GUI's first view. Every view a person uses in a browser is part of this one GUI; no module runs a web server of its own.
- What this means: The GUI is user global, not per project: it lists every registered project and switches between them and their metaforms. It owns no data. Three things stay outside it. Web variants of a user's artifact are the artifact running, not Metaform's GUI, so each is served on its own port, PROJ-019; the GUI can list and launch them. MCP stays on stdio, one server per AI tool, MCP-002, since agents, not people, use it. The terminal settings screen stays for people in a terminal, CLI-026; the GUI reads and writes the same settings through the same settings module. The deferral of the workflow editor, the rulebook and the browser terminal under D44 still stands; when they come, they are views of this GUI. How a module adds a view to it is open, question 3.
- Why: One GUI gives one address for everything Metaform shows a person, one process to start and stop, and one place to move between projects and between the map, its layers, its provenance and its prompts. Separate servers per module or per project would each need their own port, token and start, and could not show two projects side by side.
- How it shows: `metaform list modules` lists `web`. `metaform help web` gives its man page. The page opens on the 3D view of a project's active metaform, with a project switcher that lists every registered project.
- Build: The module lives at `src/metaform/modules/web/` with `__init__.py`, `server.py`, `page/` for the HTML, CSS and scripts of the app and its views, `vendor/` for the bundled libraries, and `README.md`. It declares `SUPPORTED_OS = ('linux', 'macos', 'windows')`. It ships enabled. Its verbs are in VIEW-002. Until question 3 is answered, the map views, the provenance view and the prompt editor are the web module's own.
- Acceptance: With the web module disabled, every chassis verb and every other module works. `metaform web` then stops with `Next: metaform enable web`.
- Relates to: BASE-017, BASE-019, BASE-035, CLI-026, MCP-002, PROJ-019, VIEW-002, D44.
- Status: confirmed for one unified web GUI, user global, serving every project, with the viewer as its first view, Rich 2026-09-25. The module name `web` and shipping enabled are recommended.

### VIEW-002 The web GUI is one server for the user, on one fixed port, started with `metaform web`
- Requirement: One server per Metaform home serves the web GUI for every registered project on one fixed port, at a bind address that is loopback by default. `metaform web` starts it when it is not running and prints its address; when it is already running, it prints the address it runs at. `metaform web stop` stops it.
- What this means: The home is the user's Metaform data folder, so in practice this is one server per user; a second home, such as a test's, has its own server and needs another port. Starting from any folder, or for any project, finds the running server and starts no second one. The page lists every registered project and switches between them; the folder `metaform web` ran in chooses only which project the page shows first. The port is fixed, so the address stays the same across restarts and a bookmark keeps working. Before an intake, agents start it and tell the user the address, VIEW-015. Which folder's settings, such as `--layers`, the GUI shows and changes is open, question 5.
- Why: A local server keeps all data on the machine and needs no account. Bound to loopback, as it is by default, nothing on the network can reach the GUI, and the only pages that could try are other sites open in the same browser, which the `Host` and `Origin` checks stop, so no token is needed. A person who sets another bind address opens the GUI to that network, and then a token guards every request. A fixed address lets a person keep the GUI open while agents work.
- How it shows: `metaform web` prints `state: started` and `address: http://127.0.0.1:<port>/`. Run again, from any folder, it prints `state: running` and the same address. With another bind address, the address ends with `?t=<token>` and a `token:` line follows. `metaform web stop` prints `state: stopped`, or `state: not running`. With `--json`, and over MCP, the same fields come back as data.
- Build:
  - The module's verbs are `start`, its default, BASE-035, so `metaform web` runs it and over MCP it is the tool `web_start`, and `stop`, the tool `web_stop`. `start` returns the address and whether it started the server or found it running.
  - `start` launches the server as a process detached from the terminal, so it runs until `metaform web stop`, logout or restart: on POSIX in a new session, on Windows as a detached process, with no console. It returns once the server says it is ready: the server inherits a pipe from `start`, writes its record to it once it listens, and then points that end of itself at the log; `start` reads that one line and is told, and reads end of file when the server ended before it could listen. The read is bounded by `WAIT`, 15 seconds, so `metaform web` never hangs on a server that neither answers nor ends; the bound is a limit on one wait for a message, not a repeated check, and nothing runs while it stands. Pipes are inherited by a detached child on Linux, macOS and Windows alike, QUAL-015.
  - The server uses the standard library, `http.server` with a threading server, so the GUI adds no compiled dependency.
  - Every request is answered only when its `Host` header is the server's own address and port, so a page that rebinds a domain to the machine cannot read the GUI. On a loopback bind address, `127.0.0.1`, `localhost` and `[::1]` with the port are all its own address. Every write, the four POSTs of VIEW-011, is accepted only when its `Origin` header is the server's own address and its body is JSON, so a page from another site cannot send one. On a loopback bind address these checks are all, and the address carries no token.
  - On any other bind address, the home's token is also required: made on the first start that needs it and stored in the home, carried in the page URL, and every request without it refused with 403. `start` returns the token with the address, so the agent that started the server can give it to the user, VIEW-015.
  - The server records its address and process id under `~/.metaform/run/web.json`. `start` reads that file first and reuses a live server: one whose `/api/server` answers with the recorded process id and this home. `stop` signals that process to end, since a stop request would be a write beyond VIEW-011's four, and removes the file. It is told the server has gone by the operating system: before the signal it opens the server's events stream, VIEW-018, which the server holds open until it ends, and then reads the stream to its end; the system closes every socket of a process that ends, on Linux, macOS and Windows alike, so the read returns when the process is gone and not before. The read is bounded by `WAIT` so `metaform web stop` never hangs on a process that will not end; a limit on one wait, not a poll. The server's own loop waits in the system's `select` with no timeout, so it wakes only for a connection; nothing checks for shutdown, because the stop signal ends the process itself: on POSIX a `SIGTERM` handler writes the stop to the log and ends the process at once, and on Windows `os.kill` ends it before any handler runs. What goes wrong in the server is written to `run/web.log`, and `start` names its last line when a server does not come up. Each line carries its UTC time, and the log has one line when the server starts, with its process id, port, code print and schema version, one when it stops, by `shutdown` or by the signal, one when it hands over to newer code, and one with the traceback when an unhandled error ends it. A page that closes while it is answered is not an error of the server, so a reset or broken connection writes nothing; anything else that fails a request is written with its traceback. An automatic-dispatch error is written once for a project until its text changes or dispatch succeeds, not once for each change heard. Why: the log alone must say when the server died and why; without times and start and stop lines, and with every closed page leaving a traceback, the one fatal error could only be dated from the file's time and an agent's transcript.
  - On a wildcard bind address, `0.0.0.0` or `::`, every name of the machine is the server's own, so the `Host` check compares only the port, and the token guards every request. The printed address uses the machine's host name, question 7.
  - The token is accepted as `?t=` on the page URL, which also sets it as an `HttpOnly`, `SameSite=Strict` cookie so the page's own requests carry it, as that cookie, or as the `X-Metaform-Token` header. It is kept in `run/web-token`, readable only by the user.
  - Besides the reads of VIEW-004, three GETs serve the GUI itself: `/api/server`, the server's process id and home; `/api/projects`, every registered project for the project switcher, VIEW-001; and `/api/clear-preview`, what clearing a project would remove and keep, VIEW-019.
  - `--web-port` is a chassis-schema setting declared by the module, an integer, for the whole home, since one server serves the home. Its default is 7433 until question 6 is answered. When the port is held by another program, `start` stops with the port named and `Next: metaform set --web-port <port>`.
  - `--web-bind` is a chassis-schema setting declared by the module, text, default `127.0.0.1`, for the whole home: the address the server binds to. When the server cannot bind there, `start` stops with the address named and `Next: metaform set --web-bind <address>`.
- Acceptance:
  - `metaform web` starts the server and prints its address; run again, it reports the same address as running and no second process exists; `metaform web stop` ends it and removes the run file.
  - `web` run from the folders of two projects leaves one server running, serving both projects.
  - A request whose `Host` is not the server's own address is refused, and so is a write whose `Origin` is not the server's own address or whose body is not JSON. On the default bind address no token is asked for.
  - With `--web-bind` at its default, the server accepts no connection on a non-loopback address; set to another address, it listens there and still refuses a request without the token.
- Relates to: BASE-035, CLI-011, PROJ-003, PROJ-019, VIEW-001, VIEW-004, VIEW-015.
- Status: confirmed for one server for the user serving every project on one fixed port, for `metaform web` to start it and `metaform web stop` to stop it, and for a locally served GUI, Rich 2026-09-25. A bind address setting, loopback by default, is confirmed; so is no token on loopback, with the token required on any other bind address and given to the user by the agent that started the server, Rich 2026-09-25. The `Host` and `Origin` checks, the default verb, the output lines and the setting names are recommended.

### VIEW-003 The viewer works offline with every script bundled
- Requirement: The viewer loads nothing from the network: every script, style and font it uses is bundled in the module with its license.
- What this means: The page references only files served by the viewer's own server. The bundled libraries are `3d-force-graph`, the force-graph library for three.js the approved prototype used, with its layout dependencies and one shared three.js module, Mermaid, the version already vetted on the earlier branch, 12.0.0, and CodeMirror 5.65.16 for the prompt editor, VIEW-013. Each is an unchanged release file with its license file next to it and a `vendor/README.md` naming the version, source and SHA-256.
- Why: Metaform runs offline and in restricted environments. A page that needs a CDN breaks there and sends the user's browsing to a third party.
- How it shows: With the network disconnected, the viewer opens and draws the graph.
- Build: `vendor/` holds the ES-module release `3d-force-graph/dist/3d-force-graph.mjs`, 3d-force-graph 1.73.4, with its locally vendored layout and rendering dependencies and their licenses. The graph, its dependencies, glass, bloom and agent figures import the same three.js r168 module through the page’s import map, so their objects share runtime identity. The pinned ngraph packages publish UMD only: small adapters in `page/` expose their unchanged local releases as module factories; these contain no three.js. `vendor/graph-modules.json`, linked from the README, names each dependency’s version, tarball source, release paths and file SHA-256. The folder also holds `mermaid.min.js`, Mermaid 12.0.0 as vetted on the earlier branch; the IBM Plex fonts the page uses, as `woff2`; and each one's license. `vendor/README.md` names each file's version, source and SHA-256. CodeMirror 5.65.16's editor, its XML and Markdown modes and its search and dialog files are under `codemirror/`, for the prompt editor, VIEW-013. `three.module.min.js` is three.js 0.168.0, the release shared by the graph and page, and `drei-vanilla/MeshTransmissionMaterial.js` is drei's transmission material from `@pmndrs/vanilla` 1.25.0, for the glass of VIEW-025. The page has a Content Security Policy of `default-src 'self'`, with inline styles allowed, since Mermaid writes its styles into the SVG, so any accidental remote reference fails visibly. The page's one inline script is its import map, which names the copy of three.js for the modules that import it as `three`; the policy allows that script by its SHA-256, which the server reads from the page it sends, and no other. The server sends each file's type from a fixed table, since Windows's registry can map `.js` to a type browsers refuse to run. The wheel build carries the vendor files as package data.
- Acceptance: The served page and every file it loads come from the viewer server; a check of every `src` and `href` in the page and its scripts finds no remote URL. The page's policy allows its import map by its hash and no other inline script. The wheel contains the vendor files and their licenses.
- Relates to: BASE-041, QUAL-002, VIEW-001, VIEW-013.
- Status: confirmed for offline with nothing from a CDN. The library choice is recommended.

### VIEW-004 The viewer reads only through the data access object and follows every visibility rule
- Requirement: Everything the viewer shows comes from data access object reads, under the same rules that govern what agents see.
- What this means: The server calls the store reads of STORE-025 and nothing else. It never opens a database file and never parses an intake document. What is shown is the metaform with the correction stack applied, LAYER-011, plus the knowledge layers the folder's `--layers` setting turns on, CLI-033, with select and mask applied at each address, LAYER-007. Hidden layers do not appear, LAYER-006. Orphaned items do not appear unless the viewer's raw toggle is on, and then they are marked orphaned, STORE-017. Every edge and every item shows the name of the layer it comes from. Every object shows the conditions of its open work records, `open_work`, MAP-046, and every challenge shows its state, LAYER-015.
- Why: A viewer that shows something agents cannot see, or hides something they can, misleads the person checking the map. One source of truth for visibility keeps the picture honest.
- How it shows: Turning a layer off with `metaform set --layers` and refreshing the viewer removes that layer's joins and items from both views. A masked layer at `code.engine` is absent under `code.engine` in the viewer as it is in `map context`.
- Build: The server exposes read-only JSON endpoints that map one to one onto store reads: `/api/<read>` for every read of `metaform query`, STORE-028, such as `/api/roots`, `/api/children`, `/api/node`, `/api/joins`, `/api/layers`, `/api/work`, `/api/search`, `/api/layer-items`, `/api/stack` and `/api/provenance`, with the read's arguments as query parameters by their names, `raw=true` and the paging of STORE-005 among them. Three parameters pick the store and are never a read's argument: `project`, `metaform` and `layers`. `layers` is the view's layer choice, VIEW-007; without it, the read starts from the `--layers` of the project's registered folder, question 5. A read that finds nothing, or names a project that is not registered, answers 404; one that cannot be read answers 400; both carry the error and its next step. `/api/intake-recording` and `/api/layer-graph` are the store reads `intake_recording` and `layer_graph`, STORE-025, the two that show a building intake, BASE-039. `/api/graph` is the store read `graph`, STORE-025: a page of the map in address order, each element in context with its nearest parent element and each join it receives with its subtypes, in one read, VIEW-005 and VIEW-010. The page never computes visibility itself.
- Acceptance:
  - For a store with a hidden layer, a masked layer at one address, an orphaned knowledge item and a flagged element, each endpoint returns exactly what the matching store read returns, raw and in context.
  - The page's data for a node equals `metaform map node` for that node.
- Relates to: LAYER-006, LAYER-007, LAYER-011, LAYER-015, MAP-046, STORE-005, STORE-017, STORE-025, CLI-033.
- Status: confirmed.

### VIEW-005 The 3D view floats the metaform in space in its tripartite form and untangles it
- Requirement: The main view is a 3D graph floating in space that shows every join in its tripartite form and settles itself into the metaform's actual mesh shape through a force layout.
- What this means: Joins are not collapsed in the 3D view. Each join is drawn as the tripartite unit it is, one path, MAP-002: the receiver, a purpose vertex of the join's own, and the encounter, drawn as the link from the purpose vertex on to the provider element that serves it. Nothing is drawn from the purpose or the encounter back to the receiver. Joins that share a receiver or a provider share that element, so the joins form the mesh the metaform is. Because every join has its own purpose vertex, two elements that each receive from the other appear as two separate joins with their own purposes, never as a loop. The namespace tree, along which properties travel, is drawn as its own kind of edge from each element to its nearest parent element, and no namespace branch is collapsed. Subtypes sit inside their join as small vertices attached to the join's purpose vertex. The layout starts from the roots and lets the forces pull connected parts together and push unconnected ones apart, so the tangle opens up into the mesh's shape and settles. The camera orbits, zooms and pans. Hovering a vertex names it. The layout can be paused and resumed while it settles.
- Looks: the 3D mesh reads like a synaptic map in 3D. Elements are glowing nodes against a dark space, joins are fiber-like connections in their tripartite form, and layers are colors, so the whole shape reads like a neural map of the project.
- Why: The receiver, purpose and encounter structure is a shape. Collapsing a join into one edge hides the purpose and the encounter and turns two-way pairs into apparent loops. Drawing each join in full shows the real mesh: where the load-bearing parts are, which branches are thin, and what sits apart from the rest.
- How it shows: Opening the viewer on a real project's metaform shows the CQU and DE near the center with the paths of joins arranged around them, settling within seconds. Two elements that each serve the other show two paths between them, each through its own purpose vertex.
- Build:
  - Vertices: one per element, and for each join one purpose vertex. Purpose link: receiver element to purpose vertex. Encounter link: purpose vertex to provider element. Namespace edge: element to nearest parent element. Subtype link: purpose vertex to subtype vertex.
  - The drawing is the approved prototype's, `viewer-prototype.html`, drawn with 3d-force-graph and the prototype's settings. The force simulation holds purpose and encounter links at 34, shorter than namespace edges at 60, and subtype links at 8, and pushes elements apart harder than purpose and subtype vertices, so function structure dominates the shape.
  - Positions of drawn vertices are kept when more of the graph arrives, so the picture does not jump. A reset control re-runs the layout, and a pause control stops and resumes it.
  - While an intake is being recorded, BASE-039, the page follows it live: told by the push of VIEW-018 that the intake's layer changed, it switches to that intake's metaform, says so in a toast and in the count line, `intake being recorded`, and draws the building layer from `/api/layer-graph`, redrawing both views, positions kept. When the intake finishes it says `The intake <layer> finished.` and shows the finished map through the usual reads; when the recording disappears because the project was cleared, VIEW-019, it says `The intake <layer> stopped: <project> was cleared.`. While it follows, the Object panel shows the selected element as the building layer records it, from the same `layer-graph` page; it does not read `node` for it, because an intake being recorded is in no reading context until it finishes, LAYER-007, so that read could only find nothing, and a read that is expected to find nothing is not made. The panel's other reads, `context` among them, are made as always. `window.metaform.live()` returns the layer followed, or null.
  - Motion respects the browser's reduced-motion setting.
  - Condition, MAP-046: a node with an open `missing` work record keeps its own color and is drawn in characters, VIEW-027; the characters change slowly while the part waits, quicken once an agent has taken its task and the record is `in-progress`, and give way to the node when the task is done; a broken part whose task is taken, `fixing`, is steady red and gives off red light that swells and fades, VIEW-029; a join with an open `missing` record has its purpose node drawn in characters in 3D and a glow around its edge in 2D. The quickening shows where work is happening now, apart from where work only waits, so a person sees at a glance which parts have an agent on them. The light of a node that needs attention and the light of a property's reach are both spread by the bloom, VIEW-022 and VIEW-029, and are not mistaken for each other: one is a single part lit where it stands, the other a wave of dots traveling a path, VIEW-026. The reason: a part not built yet is still that part, so its color, which says its role and its layer, stays readable, and its mark adds the one fact that it is waiting to be built. Lowering its opacity did not show on the real map of this repository, and giving it a color of its own took away the color it has; a node with an open `broken` record flashes red until it is resolved; an object with an open `exclude` record is drawn in the exclude color and pulses between that color and its own, steady in the exclude color with reduced motion. This holds for an element, for a join and for a subtype join alike: the join's purpose node and its edges take the condition as an element's node does. The exclude color is used by no layer, role or kind of edge in any theme, so it is never mistaken for one. The reason: `exclude` identifies material whose inclusion needs review, so a person needs to see and examine the finding, and a record drawn like every other join is a judgment about the project that no one reviews. Both views draw it so, read from each object's `open_work`, and the legend names each condition on the map. With reduced motion the broken node is steady red. In 3D the sphere of a node with a record takes its own material, so no other node of its color changes; the page repaints those nodes each frame. `window.metaform.look(id)` returns how a node is drawn for its condition, so a browser check can read it.
  - Synaptic look: element vertices are spheres, the DE largest and white, the CQU next in the signal color, other elements in their layer's color; purpose vertices are small and light, subtype vertices smaller in their layer's color. Purpose and encounter links are straight fibers with two particles flowing along each toward the provider; namespace edges are thin and dim. Every element carries its short name as a floating label, its address read through name_length, MAP-012. The background is dark space. Selection brightens a node and its joined elements and dims the rest, and the camera flies to it. A click on any vertex selects that object itself, an element, a join's purpose vertex or a subtype, never its parent, Rich 2026-09-26. Hovering a vertex shows an element's short name and address, a subtype's short name and its subtype join's name, or a purpose vertex's join name and purpose, above the vertex and clear of its sphere, so the pointer never covers the text; it goes below the vertex only where it would leave the top of the view, Rich 2026-09-26.
  - The page's graph data is readable as `window.metaform.graph()`, and the counts of drawn vertices and links as `window.metaform.drawn()`, so a browser check can count them.
- Acceptance: Manual: on each operating system, a real project's metaform opens, settles into its mesh, reads as a glowing neural-like map, orbits and zooms. Automated: the page's graph data holds one vertex per visible element; for each visible join one purpose vertex, one link from its receiver to it, one encounter link from it to its provider, and nothing back to the receiver; and one namespace edge per element with a parent element; no join is represented as a single element-to-element edge. ### VIEW-006 Edges and nodes are colored by layer and by kind
- Requirement: Edge color and style show which layer an edge comes from and what kind of encounter it is, and node style shows each object's condition and state.
- What this means:

The edges of the 3D map are smoothed, four samples a pixel in the buffers the scene is drawn into, since the smoothing the screen has does not reach a scene drawn into a buffer, and without it a link thinner than a pixel, as every link is with the whole map in view, breaks into dots, Rich 2026-09-29. Where the processor draws and not a graphics card the samples are left out: measured there they took the page from 10 frames a second to 6 and changed nothing that could be seen. Every link of the 3D map is a straight line, since a straight line shows at a glance which two nodes it joins, where a curve leads the eye around and curves that cross are hard to tell apart, Rich 2026-09-28; a link's kind is told by its width, its color and its particles. A namespace edge, the path properties travel, is a thin straight line in the namespace color. An object or join that a correction layer added or relocated is outlined in that correction layer's color.

### VIEW-007 Viewing never changes settings; a separate control applies the layer choice
- Requirement: The viewer lists the metaform's layers with their tags and lets the person choose which knowledge layers are shown; active viewing never changes any setting, and a separate control applies the viewer's layer choice to the folder's `--layers`.
- What this means: The layer panel is a Layers button at the top right of the header, which names how many layers are on, `Layers · 3 of 5`, and opens a checklist right under it, Rich 2026-09-26, who asked for layers to be chosen by checking them: one row per layer with a checkbox, its color, its name, kind and tags, and whether it is building or hidden, the same fields as `list layers`, LAYER-019; the apply control sits at the list's foot. ### VIEW-025 The nodes are drawn as a material that obeys reality, in every theme

- Requirement: In every theme the elements of the 3D map are drawn as glass, a material that obeys what a person experiences in reality: light passes through it, is tinted by it and reflects from it. The glass is drei's transmission material, which also splits the light passing through it into its colors, bends it as uneven glass does, and shows the far wall of the glass. It is always on. There is no mode to choose, no level to set and no check of the machine.
- What this means: A node is made of something, so it changes color in reaction to the light that reaches it, where a node with only a color had to be recolored by a rule. The glass shows what is behind it, so each theme's background comes through the node by itself and no theme is tuned apart from the others. A node keeps its theme's color as the tint of its glass, and gives off a little of that color as light of its own, so its role and its layer are read on a dark background and on a light one. The bloom, the dots and the wave of VIEW-022 and VIEW-026 are as they are; the material is what reacts to them.
- Why: One way of drawing is built, tested and kept working once. A second mode, a level or a check of the machine is each a place where the page guesses about someone's machine and guesses wrong, and any modern browser draws this, with a graphics card or without one. Reality is what makes the drawing agree with itself: a pulse painted onto a node clashes with the node's color, where light passing through a node of glass is one light, so the body and the glow cannot differ. Glass needs something behind it to be seen, and clear glass on a black background with nothing to reflect shows as black, which is why a node gives off light of its own. And a map that looks well made is one people want to look at.
- How it shows: In each of the themes the elements are glass beads in the theme's colors, and the background shows through them.
- Build: The material is drei's `MeshTransmissionMaterial` in its vanilla form, from `@pmndrs/vanilla` 1.25.0, pmndrs's MIT-licensed release of drei's materials for three.js without React. It is three.js's own physical material with the light passing through it reworked: the light behind the glass is read several times, each color at its own index of refraction, so the colors part at the edges as they do in a lens; the surface bends the light by a noise that drifts slowly, which is the distortion; and the reads are spread along the ray, which blurs it as frosted glass does. The page draws what is behind the glass as drei's own component does each frame, once for every node, in the graph's render chain before the frame: the scene with the glass hidden, into one picture; then the scene with the far wall of every node, which reads the first picture, into a second; and the near wall of every node reads the second in the frame itself. So a node shows its own far wall and the glass nodes behind it, which is drei's backside. Both pictures are half the size of the view, drei's `resolution` and `backsideResolution`. The far wall is a material of its own, since three.js keeps a material's program when only the side it draws changes. It takes the node's tint and gives off no light toward the eye: a node's light leaves its glass outward, so the light of its far wall goes away from the eye, and a node is as bright as its near wall makes it. three.js's own picture of what is behind transmitting objects, which it draws at the full size of the view, is not used: three.js was asked to add the far walls to it at first, which halved the frame rate, since it then finishes that full-size picture twice a frame. The physical values are as they were: transmission 0.7, thickness 9, roughness 0.3, an index of refraction of 1.35, the node's color as its color and as the color light takes on inside it over a distance of 7, a clear coat of 0.6 with a roughness of 0.25, and the node's color given off as light at 0.45. The drei values are a start and are not settled: a chromatic aberration of 0.06, a distortion of 0.25 at a scale of 0.35 drifting at 0.1, and, as drei has them by default, a blur along the ray of 0.1 and 6 reads. They could not be judged by eye: with the frosting and the absorption above, what is behind a node is blurred and tinted almost to the node's own color, so the parting of the colors and the bending hardly show; they show when the roughness is 0 and the absorption is off. With reduced motion the distortion is still. The graph library holds three.js and does not give its classes out, so a copy of the same release, 0.168.0, is in `vendor/` with its license and hash, VIEW-003, and the page imports it; the drei file is beside it unchanged, and imports three.js by the name `three`, which the page's import map gives as that copy, so the material and the page share one three.js. Elements and the nodes of subtype joins are glass; the small nodes of purposes and items keep the basic rendering. Every node of one size shares one shape, of 16 segments as the graph draws its own nodes. `window.metaform.look(id)` returns the node's material, its transmission, its chromatic aberration, its distortion and whether it draws its far wall, and `window.metaform.glass(on, options, segments)` turns the glass off and on with other values, to measure what it costs. Measured 2026-09-28 with three.js's physical material, on this repository's map of 104 nodes at 1600 by 900, with a software renderer and no graphics card: 24 frames a second without glass, 11 with it, and 6 with shapes of 32 segments. The cost is the light passing through, for which the scene is drawn a second time each frame; the clear coat and the frosting cost nothing that can be measured. Measured 2026-09-29 on the same repository's map, now 107 nodes, the same way, with the bloom of VIEW-029 on: no glass, about 15; three.js's physical material, about 8.5; drei's material with its far wall drawn as above, about 11.7, and about 10.2 with both pictures at the full size of the view; with three.js adding the far walls to its own picture, about 4. The number of reads and the distortion change nothing that can be measured. It has not been measured with a graphics card. Open: something for the glass to reflect. drei's `MeshRefractionMaterial`, its diamond, has no vanilla form in `@pmndrs/vanilla` 1.25.0 and needs `three-mesh-bvh`; its `MeshReflectorMaterial` reflects on a flat surface, and the map has none. Neither is built.
- Acceptance: In every theme an element is drawn with drei's transmission material and lets light through, parts its colors, bends it and draws its far wall. With the frosting and the absorption off, what is set behind a node shows through it, and moving it away changes the node. The count of shapes the graphics card holds does not grow with the count of nodes of one size. The page loads nothing from outside itself. ### VIEW-026 A property's reach travels as a wave

- Requirement: A highlighted property's reach is shown as a wave that starts at the element the property is linked to. A dot travels each edge away from that element, toward the leaves where the property applies and toward the trunk where it is visible. A node pulses when a dot arrives, holds the dot, and sends it on along its next edges. With no property highlighted the map is drawn as it is without one.
- What this means:
  - The dots carry the property's color and the glow; the edge keeps its own look.
  - A dot crosses an edge in a time that is set, the same for every edge.
  - A node's pulse lasts exactly as long as the node holds the dot.
  - Each timer, how often a wave leaves, how long a dot takes to cross an edge and how long a node holds a dot, can be multiplied by `rnd() + rnd()` each time it is used. That factor runs from 0 to 2 and is 1 on average, so the timer averages the time set and never repeats.
  - The pulse through a node has a depth, 0 as the dot enters, 1 at the node's center and 0 as it leaves. The node tints the pulse as colored glass tints light: each channel of the pulse's color is multiplied by `1 - opacity + opacity * node`, where the node's opacity is for the light alone and the node is drawn solid whatever it is. The node's body moves from its own color toward that tinted color by the depth, and the glow is the body's color and brightness at that moment.
  - Each property highlighted is its own wave in its own color.
- Why: Dots that all arrive together say only that the elements are related. A wave shows cause in order: the property reaches the near elements first and the far ones last, and it can only move away from where it began, so it shows its direction and the element it is linked to without a label. A node lit only while it holds the dot keeps its own color the rest of the time, so its role and layer stay readable, and the light means one thing, that the dot is here; a pulse that outlasted the hold would show the property in two places at once. A fixed time to cross is used because the map's layout comes from a force simulation, so the length of an edge on screen carries no meaning. The factor from `rnd() + rnd()` keeps any two timers from falling into step, however many waves run. A glow made from the node's own body cannot clash with it, because light coming off a thing has that thing's color. With the dots carrying the property's color, each part has one job: the dots say which property is traveling and which way, the pulse says it has reached this node now, and the glow says what the node is.
- How it shows: Highlighting a property linked at one element sends dots out along its branches and back along the path to the trunk; each node they reach lights as the dot arrives and returns to its own color as the dot leaves.
- Build: The wave is built in `app.js`, in every theme: `wave3d` runs it each frame, and `TIMES` holds its values. The page moves each dot itself along its edge, so a dot travels toward the trunk as well as toward the leaves and each dot has its own time. The values are chosen by eye on the demonstration page and are not settled: a wave about every 3 seconds, a dot crossing an edge in 1 second, a node holding a dot for about a quarter of a second, and an opacity of 0.6. With reduced motion there is no wave and the reach is shown lit and still. `window.metaform.wave()` returns the count of dots, the nodes lit and the count of shapes the graphics card holds, and `window.metaform.waveTimes()` sets the times, so a browser check can read and steer it. The node is glass in every theme, VIEW-025, and its body is tinted by the rule above. The glow is the light the glass gives off: its emission takes the body's color and rises with the depth, from the glass's own 0.45 to 2.6, and the bloom spreads it, VIEW-029; nothing is drawn around the node. The graph library makes a shape for every dot it sends and never lets it go, which fills the graphics card's memory, so every dot shares one shape and one material for each color. What is built today, VIEW-022, lights the whole reach at once with a steady stream of dots; its bloom pass is in the right place, since the bloom belongs to every theme.
- Acceptance: Every element of the reach lights and no other does. The element the property is linked to lights first, and an element a hop further lights later. The elements are never all lit at once. The namespace edges keep their one color. The count of shapes the graphics card holds does not grow while waves run. Selecting anything else leaves no dot and no node lit.
- Relates to: VIEW-005, VIEW-022, VIEW-025, LAYER-005, LAYER-020.

### VIEW-043 Consensus mode: when every open ticket is frozen on a question, voting agents settle what they agree on, and only a write-in, a comment or a tie waits for the person

- D120 amendment, 2026-10-05: the confirmed removal of question-based blocking in VIEW-042 supersedes the automatic trigger below that equated every unanswered question with a frozen ticket. Autostart dispatches those tickets as ordinary work and ends any previous consensus mode. The timing setting `dispatch_consensus` and its Vote on questions now control are removed because they select only variants of that superseded trigger. The authored voter and coordinator logic, vote storage, results and vote command are preserved. A new automatic trigger is not specified by this decision. Why: an unanswered question alone cannot establish that no useful work remains, and starting voting in place of the ticket's worker would retain the dispatch gate that D120 removes. Coordinator and voter tests continue to exercise voting directly, while starter tests prove that unanswered questions receive workers.

- Requirement: While Autostart agents is checked, dispatch's agent starter first starts agents on every open ticket that has no unanswered question. In consensus mode, voting agents each choose one answer for each frozen ticket's question, or write in their own. The coordinator's rule closes a ticket as soon as its votes meet one of its conditions. A winning choice is written as the question's answer at once, and the ticket goes back to work. A write-in, a comment or a tie goes to the person through the web. The voter and the coordinator are Rich's logic, below, carried exactly as he wrote them.

- Rich's logic, the coordinator, authored content used as written. It is not a prompt. It is carried into Python in `src/metaform/modules/dispatch/consensus.py`, whose docstring quotes it:
  ```
  #! AXIOM/2.0 name=coordinator
  @STATE_INIT: {Tickets} := <<DATA: [tickets]>>   {Cap} := min(|voters|, 8)
  @CONSTRAINT:
    !> Max 5 agents open. One vote per agent per ticket. No fabricated votes. Late votes discarded.
    +> Refill free slots at once with open, unblocked tickets. Voters never see counts.
  @CONDITION (TICKET):
    ?IF ( blocked ) -> BLOCKED
    :ELSE ?IF ( comment ) -> HALTED
    :ELSE ?IF ( write-in ) -> CLOSED
    :ELSE ?IF ( votes>=3 AND leader*100 > 66*votes ) -> CLOSED
    :ELSE ?IF ( votes>=4 AND leader*2 > votes ) -> CLOSED
    :ELSE ?IF ( votes>={Cap} ) -> CLOSED, most votes wins (tie -> TIE_REVIEW)
    :ELSE -> OPEN
  @ROUTER: @MATCH ( any OPEN ticket ) -> [TRUE] Run | [*] YIELD results
  @EXECUTE_PIPELINE (Run): @LOOP (max=|Tickets|*8): fill slots, oldest OPEN first -> record votes -> re-run TICKET -> refill. YIELD results + counts.
  @VERIFY: Agents <= 5? No duplicate or fabricated votes? Each CLOSED meets its rule? Else RECURSE(max=3), then HALT.
  ```
- What this means:
  - The order of the work. While Autostart agents is checked, the starter starts agents on open tickets that have no unanswered question. Held tickets without a question are still started, after the others, as before. Consensus mode starts only when no such ticket is left and every open ticket is frozen. It ends as soon as a ticket can be worked again, or when Autostart agents is unchecked.
  - How the coordinator's rule plays out with the default of five voters, so the cap is 5. The checks run in order, and a comment comes before every vote count, so a comment halts the ticket even when one answer already leads.
    - Two matching votes of three close the ticket, since 200 is more than 198.
    - Three of four close it.
    - Two of four do not.
    - Three of five close it as a majority.
    - At five votes the answer with the most votes wins. A tie goes to the person.
  - A write-in ends voting on that ticket and counts as completed for voting. Its words go to the person to read, because a voter that writes its own answer saw something the offered answers miss.
  - A ticket closed for the person's review is seen only through the web from then on, and never again by the consensus system, so the agents never vote twice on a question the person now holds.
  - Voters never see the counts or each other's votes, and a vote that arrives after its ticket closed is discarded. Each vote is then the voter's own judgement, not a follow of the leader.
  - Interpretations made in the build. These are not Rich's decisions and stay open to his correction:
    - Blocked means a frozen ticket an agent has taken.
    - |voters| is the `dispatch_agents` setting, default 5, so the cap is 5.
    - A comment is any other line a voter writes that names a queued ticket.
    - A write-in is an id line whose answer is none of the choices, by words or by number.
    - A ticket is voted on by its oldest unanswered question.
    - Each pass of the coordinator's loop is one run of the agent starter, which the server makes after every change, and a voter's recorded votes are a change.
    - The loop's cap counts the voters started in the round against |Tickets|×8.
    - Results are told at the ticket's node as a message by `consensus`: the answer applied with its tally, or the write-in, comment or tie for the person to read.
    - A voter may read, and every other permission it asks for is rejected.
- Why: Work must never stop. When every open ticket waits on the person, idle agents can still settle the questions they clearly agree on, so only real disagreement or new input waits for the person. Starting agents on any ticket without a question first keeps consensus mode a last resort, used only when nothing else can move. The thresholds close a ticket as soon as agreement is plain, so work resumes without waiting for every voter, and a hard cap ends the vote when agreement never becomes plain. A comment or a write-in is new input, and a tie is real disagreement, so those reach the person instead of being decided by count. Hiding the counts and discarding late votes keeps the votes independent, which is what makes agreement meaningful. Writing the winning answer at once and returning the ticket to work is the point of the mode: the ticket was frozen only for want of that answer.
