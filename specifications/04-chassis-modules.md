# 04 Chassis, common base and modules

Scope: what the chassis is and owns, the common base every module builds on, how modules are found, loaded, enabled and retired, and how Metaform is versioned, packaged and delivered as wheels.
Out of scope here: the map and layer data model (MAP, LAYER), storage internals (STORE), the command grammar and settings semantics in detail (CLI), the MCP module's tools (MCP), and quality checks (QUAL).

Current code referenced below is the `chassis` branch: `src/metaform/module.py`, `loader.py`, `module_metadata.py`, `events.py`, `settings.py`, `cli.py`, `mcp_server.py` and `modules/template/`.

## Chassis

### BASE-001 The chassis runs completely on its own as a CLI
- Requirement: The chassis is a complete, working Metaform with every feature module disabled or physically absent.
- What this means: With no modules, `metaform` still shows status, registers projects, reads and changes settings, gives help, and holds, imports, exports and queries the project data. Feature modules add capabilities; their absence removes only those capabilities. This holds for an installed Metaform and for a directly run wheel.
- Why: The data must stay usable without any module, and every module must stand on the same working base. A chassis that needs a module to function makes that module privileged and makes the data hostage to it.
- How it shows: With the modules folder empty and every system module disabled, `metaform`, `metaform help`, `metaform set`, `metaform unset`, `metaform config --show`, `metaform export` and `metaform import` all work and exit 0.
- Build: The chassis package contains no import of any module package. Chassis verbs live in `cli.py` and never branch on a module id; module state reaches chassis output only through the generic status hook of BASE-035, which the chassis calls for every enabled module alike. `loader.discover()` returning an empty list is a normal state, not an error.
- Acceptance: Run the chassis verbs above in a home with all modules disabled; each succeeds. Run them with `src/metaform/modules/` removed from a built wheel; each succeeds. Import `metaform` with every module package unimportable; import succeeds.
- Relates to: BASE-002, BASE-003, STORE, CLI.
- Status: confirmed.

### BASE-002 The chassis owns the data, the settings and the CLI
- Requirement: The chassis is the only owner of Metaform data, settings and the command line, and it provides import, export, query and wheel building for them.
- What this means: All persistent Metaform state is written and read by chassis code. Settings are declared by modules but stored, validated and presented by the chassis. Every command, including module commands, is parsed, dispatched and documented by the chassis. Import, export and query operate on the whole of the data, so they are chassis verbs, not module verbs.
- Why: One owner means one format, one set of rules and one place to fix a fault. Data that a module keeps privately cannot be exported, imported or queried whole, and a command surface parsed in several places drifts apart.
- How it shows: `metaform export all file=backup.json` writes every project's data, including what modules stored, and `metaform export` writes the folder's project. `metaform import backup.json` restores it. `metaform query` reads it. `metaform build` produces a wheel. No module needs its own storage code.
- Build: New chassis verbs `import`, `export`, `query` and `build`, added to `cli.VERBS` and to `loader.RESERVED`. The grammar and document of export and import are STORE-027, query is STORE-028, and build is BASE-042. The chassis dependencies stay limited per BASE-026.
- Acceptance: A module writes layer data through the data access object; `export` then `import` into an empty home reproduces it, read back through the same object. A module that writes a file into the home outside the data access object is reported by a test over the home folder after the template's verbs run.
- Relates to: BASE-004, STORE-022, STORE-027, CLI.
- Status: confirmed.

### BASE-003 The chassis does not run workflows, and MCP is a module
- Requirement: Workflows and the MCP server are modules built on the common base; the chassis contains neither.
- What this means: The chassis never starts a model, a subagent or a workflow. A workflow is module work. The MCP server is the `mcp` module: it serves the tools and instructions that come from module declarations through the same base every other module uses.
- Why: Workflows are agent work that modules provide. Keeping MCP a module puts it on the same footing as every other module and keeps its compiled dependencies out of the chassis, so a wheel without MCP runs anywhere.
- How it shows: `metaform disable mcp` leaves every chassis verb working. A wheel built without the `mcp` module carries no `mcp` package dependency.
- Build: The chassis contains no workflow runner and no model launcher. Moving the MCP server into the `mcp` module, its verb, its dependency and its disabled behavior are specified in MCP-001.
- Acceptance: With `mcp` disabled, every chassis verb works. The rest is MCP-001's acceptance.
- Relates to: MCP-001, MCP-007, CLI.
- Status: confirmed.

## Common base

### BASE-004 One common base that every module builds on
- Requirement: Modules reach every Metaform resource through one public base, and a module may use everything that base offers.
- What this means: The public base is a small set of stable imports: `metaform.module` for the declaration types and the verb context, `metaform.settings` for declaring settings, `metaform.data` for the data access object, `metaform.events` for publishing and subscribing, `metaform.prompt_files` for reading the module's own `resources/prompts.xml`, MCP-031, `metaform.axiom` for the structural check of a prompt before it is stored or sent, MCP-035 and BASE-057, and `metaform.home` for the home and its registered projects, with their clear, backups, restore and removal, PROJ-025, PROJ-030 and PROJ-031, `metaform.outline` for the map Markdown writer, MAP-052, and `metaform.finish_xml` for the map XML writer, MAP-059. A module may use all of it. There is no prohibition on what a module does beyond that. If modules need a Metaform resource that the base lacks, the resource is added to the chassis base, not built inside a module.
- Why: One implementation of each resource means every module behaves the same way and no module rebuilds what another has. Shared resources in the chassis are what let modules compose.
- How it shows: The hello and template modules import only from these public names. A resource that two modules need appears in the base, and both use it.
- Build: Public names are `metaform.module` (Module, Verb, Subscription, Stop, Context, call), `metaform.settings`, `metaform.data`, `metaform.events`, `metaform.prompt_files` (text, required), `metaform.axiom` (incomplete, notices, SIGNAL), `metaform.home` (home, projects, project, Project, to_clear, clear_project, Cleared, backups, restore_project, Backup, Restored, not_empty, removal_caution, remove_project), `metaform.outline` (markdown), `metaform.finish_xml` (xml). `metaform.module` also offers `refresh_modules`, which loads or drops the modules enabled or disabled since a long-running process started, BASE-037. `metaform.settings` also offers `toggled_layers(folder)`, the folder's chosen layers, CLI-033. `metaform.events` also offers `listen(module, handler)` and `announce(folder, surface)`, BASE-053. `metaform.data` also offers `NewerStore`, the error for a store newer than this Metaform, `plain`, a record as plain JSON data, and `query_reads` and `query_read`, the store's named reads, STORE-028. The map module and the web module import the same public writers, `metaform.outline.markdown` and `metaform.finish_xml.xml`, so the command and the page export one document for each format, MAP-052, MAP-059 and VIEW-024. Everything else in the package is private. Importing a public name creates no database, process or project state; services resolve the active context when called.
- Shared recovery service, 2026-10-05, work 6efd6c19724541bcb0b77c16ff43e38d: `metaform.module.code_print()` hashes the package source paths, sizes and modification times without creating state. The web GUI and MCP relay use the same fingerprint to distinguish changed code from an unchanged release that cannot read a newer store, STORE-029. Shared ownership prevents either surface from depending on the other's module.
- Acceptance: A test lists the imports of hello and template and fails if any is outside the public names. Importing each public name into a fresh interpreter with a missing home creates no files.
- Relates to: BASE-006, BASE-009, BASE-010, STORE-023, CLI-010, MCP-031.
- Status: confirmed. `metaform.prompt_files` joined the public names 2026-10-03: MCP-031 has a module read its own prompts with it, and dispatch, held to the five names before it, carried its own copy of the reader. `metaform.axiom` joined 2026-10-05: the workflow and dispatch modules both run the structural prompt check of MCP-035, so it lives once in the base instead of in either module. `metaform.home` joined 2026-10-05 from work d7838bba, with the names above added to settings, events, data and module: the web GUI, the MCP server and the map module reached privately into the home's projects, the cross-process map changes, the module reload, the chosen layers, the named reads and record conversion, so each joined the base import it belongs to, and the three modules now use only public names. `metaform.outline` and `metaform.finish_xml` joined the public base on 2026-10-05, work `b48c1de250c2456b9bc7eddfc0728d29`, following the approved answer to question `b26c825699eb47cc9ba7ad634f7f1412`: both the map command and web export need these writers, so shared chassis ownership keeps one implementation per format and allows either module to use it without importing another module.

### BASE-005 The data access object is the only way modules keep data
Specified in STORE-022, STORE-023 and STORE-045: everything a module keeps is written through the data access object, as a layer or in tables the module declares, and a verb reaches it as `ctx.store`.

### BASE-006 Modules declare verbs with nouns, switches and their effect

- Requirement: A module declares each verb once, with the nouns it acts on, the switches that change how it runs, and what it does to what it acts on, and that one declaration drives the CLI, help and MCP.
- What this means: Commands are verbs, arguments are the nouns a verb acts on, and switches are adverbs that change how it runs. A verb runs as `metaform <module> <verb> <nouns> [switches]`. Its summary, details, usage and examples come from the declaration. MCP exposes the same verb as its own tool, `<module>_<verb>`, MCP-003. The verb also declares its `effect`: `read` changes nothing; `write`, the default, adds or changes and keeps what was there, as a new version, a history or a backup; `remove` deletes or replaces what cannot be had back from the store. And `open_world=True` when it reaches past the Metaform home and the project's map, to agents it starts or steers or to services on the network.
- Why: A consistent grammar makes every command predictable. One declaration means the CLI, help and MCP can never disagree. The effect is declared because it cannot be read from the code: a verb such as `map work` lists, reads and writes by its `op`, and only its author knows whether any of its calls removes. A host uses it to tell a read from a write and a removal, for its permission prompts and for running reads in parallel; left undeclared, the protocol's defaults take every tool to be a destructive write that reaches the open world. `write` is the default because a verb that changes something and is called a read would be trusted to run unasked, which is the costly mistake; a read declared as a write only asks once more.
- How it shows: `metaform help <module> <verb>` shows the page, `metaform <module> <verb> --help` shows the syntax, and the MCP tool list carries the same verb with its annotations: `map_where` read-only, `memory_delete_entities` destructive, `dispatch_start` open-world.
- Build: The full declaration is BASE-035. `Verb.effect`, one of `read`, `write` and `remove`, and `Verb.open_world`, in `src/metaform/module.py`; a verb with another effect refuses to load. The shipped modules declare them on each verb, the template and its changelog describe them, and hello's verbs show each. The MCP server maps them to the tool's four annotations, MCP-003. The web module's `start` and `stop` keep the default, `write` and not open world, since its folder was not changed with this record.
- Acceptance: Declaring a verb in a scratch module makes it appear in `metaform help commands`, in `metaform help <module>` and in the MCP tool list with the same summary and with annotations from its effect.
- Relates to: CLI-012, CLI, MCP, MCP-003, BASE-035.
- Status: confirmed. The effect was added on 2026-10-11 with one tool per command, MCP-003, for the tool annotations the owner asked for; its three values and the `write` default are the builder's choices, open to his review.

### BASE-007 Module switches are settings
Specified in CLI-011, CLI-012, CLI-015 and CLI-018: every long switch a module declares is a setting declared once, booleans have two forms, and `--confirm` is never a setting.

### BASE-008 Modules declare their settings in code
Specified in CLI-010, CLI-019 and CLI-020: a module declares its settings in its own code through `metaform.settings`, one schema drives every surface, selects take choices from a list or the module's data, and the defaults work with zero configuration.

### BASE-009 Verbs run sync or async the same way
- Requirement: A verb or a subscriber may be a plain function or a coroutine, and the chassis runs both the same way.
- What this means: The chassis awaits a coroutine and calls a function; the author does not manage an event loop. Long work can be async without blocking other work the chassis runs in the same loop.
- Why: Module work includes waiting on processes, networks and agents. Authors should not choose between blocking the chassis and writing loop code.
- How it shows: The hello module's `wait` verb is async and behaves like any other verb on the CLI and over MCP.
- Build: `module.call(function, *args)` calls the function; when the result is awaitable and no event loop is running in the current thread, it runs it with `asyncio.run`. The MCP module does not use `call` for coroutine verbs: it awaits a coroutine verb in the server's own loop, so the host's cancellation reaches it, and it runs a plain function in a worker thread, MCP-002. Nothing ever calls `asyncio.run` inside a running loop: when a loop is running in the current thread, `call` refuses an awaitable with a `RuntimeError` saying to await it, so no caller blocks the loop without knowing. The settings screen runs discovery, enable and disable in a worker thread, so a module's async `start` and `stop` run there on a loop of their own. Cancellation is BASE-018 and BASE-031.
- Acceptance: An async verb called from the CLI and through the MCP module both complete and return the same result.
- Relates to: BASE-018, MCP.
- Status: confirmed.

### BASE-010 Events connect modules
- Requirement: A module publishes a topic and every enabled module subscribed to it receives the payload, and one subscriber's failure never hides the others.
- What this means: Modules cooperate through events without importing each other. Each delivery reports completed or failed for each subscriber.
- Why: Modules must compose without knowing each other's code; an event names what happened, not who handles it.
- How it shows: The hello module's `greet` publishes `hello.greeted`, and its subscriber records the name.
- Build: `ctx.publish(topic, payload)` calls `events.publish(topic, payload, ctx)`. For each loaded module in discovery order, BASE-037, and each of its subscriptions whose topic equals the topic exactly, the chassis builds a new `Context` for the subscriber's module with the publisher's folder and project, BASE-028, and calls `handler(copy of payload, context)` through `call`. It returns a list with one entry per delivery: `{"module": id, "status": "completed", "result": value}` or `{"module": id, "status": "failed", "error": message}`, and `cancelled` per BASE-032. A subscriber's exception is caught and reported, never raised to the publisher. Subscribers write through the data access object per STORE-022. From an async verb a module publishes with `await ctx.publish_async(topic, payload)`, which awaits an async subscriber in the running loop and runs a plain one in a worker thread, with the same deliveries, BASE-009; `ctx.publish` called while a loop is running raises a `RuntimeError` naming `publish_async`.
  - The chassis itself fires `map.changed` after any command that changed a project's map, VIEW-018, and the web GUI's server fires it the same way after each of the page's writes that changed the map: a topic every module can subscribe to, with no module announcing its own writes. A subscriber's `Context.surface` is `cli`, `mcp` or `web`, where the change was made. The bus also hands `map.changed` to each listener of another process of the home, BASE-053.
- Acceptance: Two subscribers, one raising; publish returns one completed and one failed delivery, and the completed one's effect is stored.
- Relates to: STORE-022, BASE-053.
- Status: confirmed.

### BASE-013 Destructive verbs act only with --confirm
- Requirement: A verb declared with a caution does nothing until called with `--confirm`, and without it prints the caution and the exact confirming command.
- What this means: The caution text says what will be lost. The confirming command is the same command plus `--confirm`.
- Why: The main agent that holds the confirming command acts with confidence; a subagent meeting only the caution hesitates. The wording steers, and nothing gates inference.
- How it shows: `metaform hello forget` prints the caution and `Next: If you are sure: metaform hello forget --confirm`.
- Build: `Verb.caution`, BASE-035, checked by the dispatcher as in CLI-018 and by the MCP module as in MCP-006.
- Acceptance: Without `--confirm` the data is unchanged; with it, the data is removed.
- Relates to: CLI-018, CLI.
- Status: confirmed.
- Amendment, 2026-10-17, UX review round 1, fix group person-consent (fresh-start-intake F4, agent-identity-handoff F2): `Verb.person_says` marks a verb that is the person's decision. It runs only on the person's own `--confirm`, the page, or their answer to their AI tool's form; a command an agent runs (`metaform.module.agent_caller`) is refused whatever it confirms, with the caution and `Next: the person runs: <command> --confirm`. `Verb.cautioned(ctx)` gives the caution for one call, naming what it would take; `caution` stays the fixed text of the tool's description. Here the wording does gate: the person's decision is not left to an agent's inference.

## Module contract and discovery

### BASE-014 Modules load from the system place, the user place, entry points and the project place
- Requirement: Metaform finds modules in the system place shipped with Metaform, the user place `~/.metaform/modules`, installed packages that declare a `metaform.modules` entry point, and the project place, whose modules load only for the active selected project.
- What this means: A module is a folder with an `__init__.py`, or a package named by an entry point. Its id is its folder or entry point name and must equal `MODULE.id`. The system place holds the modules bundled in and installed from a wheel. The user place holds modules any project can use. The project place holds modules that load only for the active selected project, PROJ-003. The project place is in the project folder, as `.metaform/modules/`, which the person creates; Metaform only reads it, so it still writes nothing there, D93. The places are ranked, system, then user, then project: a module whose id a module of an earlier place already holds does not enable, so an installed module always wins, and the chassis can disable any module, BASE-017. A directly run wheel is not a higher place but a separate authority of its own, BASE-023. Two modules with one id, or a module named like a chassis verb, are not loaded, and `metaform list modules` says why.
- Why: Community extensibility means a module can be dropped into the user place or installed like any Python package. A module made for one project's own work loads only where that project is selected, so it never adds its commands and tools to every other project. Ranking the places means a module installed with Metaform, or by the user for every project, is never displaced by a same-name copy of a later place. Metaform writes nothing into a project folder, because all data is global; the project place is one the person creates and Metaform only reads, D93.
- How it shows: `metaform list modules` shows each module with its place and state, and the reason for any that is not loaded. In a folder of project `notes`, a module in `<notes folder>/.metaform/modules/` is listed with the place `project`; in a folder of another project it is not listed.
- Build: Discovery and loading in full are BASE-037. `RESERVED` is every chassis verb plus `chassis`: `help`, `add`, `list`, `set`, `unset`, `config`, `enable`, `disable`, `activate`, `import`, `export`, `query`, `build`, `install`, `uninstall`, `feedback`, `read`, `extract`, `prompts`, `prompt`, `clear`, `chassis`. It loses `mcp`, which is a module. The project place is found after the entry points, at `.metaform/modules/` in the folder of the project selected for the folder the process runs in, PROJ-003. Its modules and their submodules are imported through a loader that never writes bytecode, so the project folder stays byte for byte unchanged, STORE-001.
- Acceptance: A user-place module and an entry-point module with the same id: the second is reported with the reason and not loaded. A module named `export` is refused with the reason. A project-place module loads in a folder of its project and in a folder that selects that project, and not in a folder of another project or outside every project. A project-place module with the id of a user-place or entry-point module is refused, naming that place. Listing the modules and running a project-place verb that imports submodules leave the project folder byte for byte unchanged.
- Relates to: BASE-015, BASE-017, BASE-023, BASE-037, PROJ-003, STORE-001, CLI.
- Status: confirmed for the system and user places, 2026-09-19, and for entry points. The project place, the ranking of the places, a same-name module of a later place never enabling, and the wheel as a separate authority are confirmed as design, 2026-09-19. Where the project place lives is answered, 2026-10-03, D93, and built.

### BASE-015 Compatibility is read before any module code runs
- Requirement: The chassis reads a module's compatibility and dependencies without importing it, and skips an incompatible module without affecting the chassis or other modules.
- What this means: `SUPPORTED_OS` is a literal tuple of `linux`, `macos`, `windows`. The chassis parses it from source. A module without it is not loaded.
- Why: Importing incompatible code can fail in ways that take the chassis down. Reading literals first keeps every failure contained and reportable.
- How it shows: A module declaring only `linux` is listed on Windows as not loaded, with the reason.
- Build: The module's `__init__.py`, or the entry point package's `__init__.py`, is parsed with `ast` and never executed. Each declaration is one top-level assignment of a literal: `SUPPORTED_OS` and `DEPENDENCIES` a tuple or list of strings, `SHIPS_DISABLED` a boolean, and from 1.0 `REQUIRES_CHASSIS` a string. A name assigned more than once, assigned a non-literal, or defined any other way is an error naming the declaration. A `manifest.py` beside `__init__.py` may hold the same declarations; when both hold one, they must be equal. `SUPPORTED_OS` values are `linux`, `macos` and `windows`, compared with `platform.system()` lowercased, with `darwin` read as `macos`. A missing `SUPPORTED_OS` makes the module incompatible with the reason `SUPPORTED_OS is required`. Each `DEPENDENCIES` requirement is checked against the installed distributions, by name and version, still without importing the module; a module whose requirement is not installed is not imported, and its reason names the requirement, so `list modules` says what to install instead of showing an import error.
- Acceptance: A module whose `__init__.py` raises on import but declares an unsupported OS is reported as incompatible and its code never runs.
- Relates to: BASE-016, BASE-022.
- Status: confirmed.

### BASE-016 A verb may narrow its own compatibility
- Requirement: A verb may declare the systems it runs on, narrower than its module, and on other systems it is filtered out like a command outside the folder's command setting, while help says where it runs.
- What this means: The module still loads everywhere it declares. The verb is not shown and does not run on a system outside its list. `metaform help <module> <verb>` on that system states the systems it runs on and gives one next step. A small OS-specific piece may instead be its own module.
- Why: One piece that cannot run on a system should not make a whole module unusable there. Filtering through the existing command check adds no second mechanism.
- How it shows: On Windows, a linux-only verb is missing from `metaform help <module>` and from the MCP tool list, and its help page explains why.
- Build: `Verb.supported_os`, a subset of the module's `SUPPORTED_OS`, default the module's. The dispatcher and the MCP tool list apply the same filter as the command setting. `metaform help <module>` lists such a verb after the others under the heading `Not on this system`, with the systems it runs on. `metaform help <module> <verb>` and running the verb both print `<module> <verb> runs on <systems>.` with the next step `metaform help <module>`.
- Acceptance: Simulating the current OS outside a verb's list hides it from help commands and MCP, running it gives the explanation with one next step, and the module's other verbs still work.
- Relates to: BASE-015, CLI, MCP.
- Status: per-verb compatibility is confirmed as acceptable; the mechanism is recommended.

### BASE-017 Modules are enabled and disabled by name, and hello and template ship disabled
- Requirement: Modules are the only thing Metaform enables or disables, by name, and a module's declaration states whether it ships disabled; hello and template ship disabled.
- What this means: `metaform enable <module>` and `metaform disable <module>` take the module's name directly, because nothing else in the design is enabled or disabled. A module's state is its declared shipping state until the user enables or disables it. The user's choice is stored and wins. A copy of the template starts disabled, and its author enables it.
- Why: Every module adds commands, so many modules clutter help and the menus; enabling and disabling keeps the surface to the modules in use. A fresh install runs only real work, so the two example modules ship disabled. Declaring the shipping state in the module means the chassis keeps no list of names.
- How it shows: On a fresh home, `metaform list modules` shows `hello` and `template` off. `metaform enable hello` turns it on.
- Build: A literal `SHIPS_DISABLED = True` in the module source, read per BASE-015. The base db stores explicit choices in the `module_state` table of STORE-002. The current `disabled_modules` table records only disables, so every module loads on by default, including the current demo; that changes.
- Acceptance: Fresh home: hello off, template off, map on. Enable hello, restart: on. Disable map, restart: off.
- Relates to: BASE-014, BASE-019, STORE-002.
- Status: confirmed; declaring the shipping state in the module is recommended.

### BASE-018 Module lifecycle is owned and reversible
- Requirement: Loading a module registers its contributions as one owned unit, and unloading, reloading, shutdown and async cancellation withdraw them completely while durable data stays.
- What this means: A failed load withdraws whatever it registered. Unload removes its verbs, settings from the schema, help, subscriptions and running tasks. Reload does not accumulate duplicates. Shutdown ends the module's running tasks cleanly. Cancelling an async verb stops it and leaves stored data consistent. Stored settings values, layers and history are never removed by unload.
- Why: The quality standard requires explicit lifecycle and no resource leakage or state corruption across load, unload, reload and shutdown. Without owned contributions, disabling a module leaves behind ghost commands and subscribers.
- How it shows: `metaform disable hello` removes its verbs and settings from help at once; enabling it again shows them once.
- Build: The loader records every contribution by owner. Existing: failed import restores the settings schema; `loader.reset()` removes settings by owner. Added:
  - `Module(start=None, stop=None)`. Each is a function or coroutine taking one argument, the module's `Context` with no nouns. `start` runs once per process, after the module's verbs, settings and subscriptions are registered and before its first verb, subscriber or tool call runs. `stop` runs once, at process exit or unload, after its running tasks are cancelled. A `start` that raises unloads the module and reports the error as its load problem. A `stop` that raises is reported as the module's problem in `list modules`, and its withdrawal completes all the same: settings, verbs and code are removed whatever `stop` did.
  - `ctx.spawn(coroutine)` starts a task owned by the context's module and returns it. The chassis keeps each module's tasks. Unload, reload and shutdown cancel them, wait for them to finish, then call `stop`.
  - Withdrawal of subscriptions and tasks on unload.
- Acceptance: Load, unload, load: each verb, setting and subscription appears exactly once. A module whose import fails leaves no settings behind. Cancelling a running async verb leaves no partial write.
- Relates to: BASE-009, QUAL.
- Status: confirmed; the hook names are recommended.

## Template

### BASE-019 Two example modules: hello shows the features, template is the empty start of every module
- Requirement: Metaform ships exactly two example modules: `hello`, a demo that shows each chassis feature working, and `template`, the same module completely empty but scaffolded; every module and every non-chassis feature starts from `template`, which is kept current with its changelog.
- What this means: `hello` is hello-world style code that exercises the current contract once each: verbs with nouns and switches, sync and async, events, settings declared in code including a select from its own data, data kept as a layer through the data access object, instructions for agents, the status hook, MCP tools, per-verb compatibility and a caution verb with `--confirm`. `template` has every file and declaration `hello` has, in the same places, with nothing in them, ready to copy. Its changelog records each contract change so forks can follow. The chassis is developed against both. Other modules are added only when a need exists.

### BASE-020 Versioning and compatibility
- Requirement: Before 1.0 the module contract changes freely; from 1.0 a module declares the lowest chassis version it needs and checks capabilities, breaks come only in a major release, and a frozen suite enforces this.
- What this means: The chassis publishes its version and a set of named capabilities. A module declares its minimum chassis version as a literal read before import. At runtime it asks whether a capability exists instead of comparing versions. The frozen suite is a set of modules written against earlier releases that must keep working. Compatibility runs one way: at the official release, a chassis runs the modules written for an earlier chassis of the same major version; an older chassis running a module written for a newer one is not promised. During development the version is CalVer, never SemVer; its format is open, D94. 1.0 in this spec names the first official release.
- Why: Community modules must keep working across chassis updates, or nobody builds on the chassis. Capability checks let a module use new features where they exist without breaking on an older chassis. Until the first release the design is still settling, so compatibility machinery would only slow it, and a SemVer number would promise a compatibility the contract does not yet keep; a CalVer version says only when a build was made. A module states the lowest chassis it needs, so the promise can only run toward newer chassis: an older chassis cannot know features that did not exist when it shipped.
- How it shows: A module needing a newer chassis is listed as not loaded with the version it needs.
- Build: From 1.0: `metaform.CHASSIS_VERSION`, `metaform.capabilities` with `has(name)`, a literal `REQUIRES_CHASSIS` in the module source. Before 1.0 none of this is required. During development the version is `YYYY.M.D.N`, written with no leading zeros as packaging writes a version: the date of the update and its place among the updates of that day, counted from 1. `python -m scripts.calver` stamps it into `pyproject.toml` and `src/metaform/__init__.py` before a commit, counting the commits already made that day. It says when a build was made and which of that day it is, and asks for no decision when it is set.
- Acceptance: From 1.0 only: the frozen suite loads and runs on each release.
- Relates to: BASE-015, BASE-047.
- Status: confirmed. CalVer during development, 2026-09-19. Its format, 2026-09-28 at `code.builder.package`: the date and the count of updates made that day, `YYYY.M.D.N`, where N counts the commits of that day, from 1. Compatibility within a major version at the official release, running one way toward newer chassis, 2026-09-19.

### BASE-028 Context travels with each operation

- Requirement: Every verb, event delivery and tool call receives its full context explicitly, and no operation reads another operation's context.
- What this means: The chassis builds one context object for each operation and passes it in. It holds the module, the folder, the project, the nouns and switches of this call, and the way to reach the data access object and settings. A module never keeps the current project or folder in a module-level variable. Two operations running at once, such as two MCP tool calls, each have their own context and cannot see each other's changes to it.
- Why: Metaform serves many folders and agents at once through the CLI and MCP. Context held anywhere but the operation leaks from one call into the next, and a write lands in the wrong project with no error at all.
- How it shows: A tool call for one project and a tool call for another, running together, each read and write only their own project.
- Build: `Context` gains `project`, the project the folder resolves to or the one named by the call, and `store`, the data access object bound to that project. Events build a new context for each subscriber from the publisher's folder and project. The server builds a new context for every tool call; a call names its project with the optional `project` argument every tool takes, MCP-025, as `--project <id>` does on the CLI, CLI-021, and otherwise uses the folder's project. Module code receives context only as the argument to its verb or handler.
- Acceptance:
  1. Two concurrent tool calls for two different projects each write one element; each element lands only in its own project's store.
- Relates to: BASE-004, BASE-009, BASE-010, STORE-023, MCP-003, MCP-011, MCP-025, CLI-021.
- Status: confirmed. The per-call project argument is recommended, MCP-025, see D37.

Every layer's provenance names the module that created it. The chassis's own commands are listed as chassis. Module commands are not flattened into the chassis's root.

### BASE-030 Work state never depends on the client that started it

- Requirement: Anything an operation needs later is written through the data access object before the operation returns, so no state depends on the lifetime of the process that started it.
- What this means: A CLI call or MCP session can end at any moment. Whatever a later call must continue from is already stored when the call returns: layers, items, provenance, settings. Long-running agent work runs in the host, as subagents the host starts, not inside Metaform, so the chassis itself holds no running jobs. The workflow module, when specified, owns receipts for work it tracks and keeps them as layers through the same store.
- Why: Agents come and go, sessions end and hosts restart. A workflow that only lives in one process is lost the moment that process ends.
- How it shows: Killing the MCP server or the CLI right after a write returns loses nothing that the write reported as done.
- Build: Every write operation commits before it returns success, per STORE-006. The chassis keeps no in-memory job table. Whether any chassis verb runs long enough to return a receipt is open.
- Acceptance:
  1. A write reported as successful is readable by a new process started after the first is killed.
- Relates to: BASE-003, STORE-006, STORE-024.
- Status: confirmed for durability; open for receipts.

### BASE-031 Cancellation is reported truthfully

- Requirement: Success, failure, cancellation requested, cancellation completed and interruption are always told apart.
- What this means: Asking an operation to stop is not the same as it having stopped. An async verb that is asked to cancel reports that the request was received, and reports cancelled only once it has actually stopped and cleaned up. A CLI call stopped by the user reports interruption, not failure. Over MCP, a cancelled tool call reports cancellation, not an error.
- Why: An agent that believes work stopped when it did not will start a second copy, and one that believes work failed when it was cancelled will retry work nobody wants.
- How it shows: Pressing Ctrl+C during an async verb prints that the verb was interrupted, and the exit code differs from a failure's.
- Build: A verb's outcome is one of completed, failed, cancel requested, cancelled, interrupted. The CLI exit codes: 0 completed; 1 failed with an unexpected error; 2 a user error, a `Stop` with its Next line, CLI-009; 3 cancelled; 130 interrupted by the user. On the CLI, the first Ctrl+C during an async verb requests cancellation and prints `Cancelling <module> <verb>...` to standard error; the verb then reports cancelled when it has stopped. A second Ctrl+C interrupts at once with exit 130. Over MCP, the host's `notifications/cancelled` for a running tool call cancels its task; per the protocol no result is sent for a cancelled request, and the task's stored writes follow BASE-030.
- Acceptance:
  1. Cancelling an async verb mid-wait yields cancelled, never completed or failed, and its partial writes are either committed whole or absent.
- Relates to: BASE-009, BASE-018, MCP-006.
- Status: confirmed for the distinction; recommended for the exit codes and the display. Exit 2 for user errors follows CLI-009, confirmed.

## Records added by the cold build check

### BASE-035 The module and verb declarations in full
- Requirement: A module is declared with fixed records, `Module`, `Verb`, `Noun` and `Subscription`, and a verb receives a fixed `Context`, all from `metaform.module`.
- What this means: These records are the whole contract between a module and the chassis. Everything the CLI, help, MCP and the settings screen show about a module comes from them.
- Why: A builder with only this spec must be able to write the chassis and a module against the same contract without reading earlier code.
- How it shows: The hello module's declaration uses every field below.
- Build:
  - `Stop(message: str, next_step: str)`: an exception for a user error. `next_step` is required and is one command, CLI-009. The CLI prints `Error: <message>` and `Next: <next_step>` to standard error and exits 2; MCP returns the same two lines with `is_error` true.
  - `Noun(name: str, help: str, kind: str = 'str', required: bool = True, many: bool = False, schema: dict | None = None)`. `kind` is `str`, `int`, `bool` or `json`. Only the last noun of a verb may have `many`.
    - On the CLI: a `str` noun is the word; an `int` noun is decimal digits with an optional leading minus; a `bool` noun is `true` or `false`, and nothing else; a `json` noun is JSON text, parsed with the standard `json` module. A value that does not parse for its kind is an error naming the noun and its kind.
    - Over MCP, each noun is one input schema property: `str` is `{"type": "string"}`, `int` is `{"type": "integer"}`, `bool` is `{"type": "boolean"}`, and `json` is the noun's `schema` when given, else `{}`, which accepts any JSON value. A `many` noun is `{"type": "array", "items": <the kind's schema>}`. A JSON value sent for a `str` noun that is not a string is not refused, BASE-044: the chassis grammar hands the verb that value's JSON text, `json.dumps(value, ensure_ascii=False)`, and adds a notice to the call's result, `<noun> is text; what was sent was kept as its JSON text.`, each member of a many `str` noun the same way. This is the grammar's job, not each verb's: the grammar owns the reading of a call on both surfaces, it already carries a notice for a name it does not know, BASE-043, and a verb declared with a `str` noun then always receives text, whoever wrote the module. An `int` or `bool` noun sent a value that is not its kind cannot be read as that kind, so it stops the call as the command line does, with the same next step, MCP-005. A switch is read by its setting kind under the same rule, CLI-027. Usage renders a required noun as `<name>`, an optional one as `[name]`, and a many noun as `<name>...` or `[name...]`.
  - `Verb(name, run, summary, nouns: tuple[Noun, ...] = (), switches: tuple[str, ...] = (), details='', examples: tuple[tuple[str, str], ...] = (), caution='', supported_os: tuple[str, ...] | None = None, surfaces: tuple[str, ...] = ('cli', 'mcp'))`. `name` matches `^[a-z][a-z0-9_-]*$`; an underscore is allowed so the memory module's commands carry the MCP reference memory server's names, such as `create_entities`, 2026-10-02, LAYER-013. `switches` names setting keys the verb reads, CLI-012. `caution` makes it a `--confirm` verb, BASE-013. `surfaces` says where it is offered; a verb with only `cli` is never an MCP tool, such as `mcp serve`, MCP-001. Usage is generated: `metaform <module> <verb> <nouns> [switches]`, plus `[--confirm]` for a caution verb.

### BASE-039 The intake module
- Requirement: A shipped module named `intake` serves the intake instructions by name, records the intake one object per call as the agent reasons it, in the owner's shape, lets the agent read back and correct what it recorded before it finishes, and reports intake state.
- What this means: The intake module owns everything specific to the intake and nothing general. An intake run is: a subagent reads `intake prompt`, which returns the stored intake text with its prompt slot filled; it starts the intake with `intake_start`; as it works the method it records each element with `intake_element` and each purpose record with `intake_purpose`; once everything is recorded it reads the map back with `intake_show`, corrects it by recording again and with `intake_remove`, and ends with `intake_finish`. The intake schema: an element is its `namespace_address`, `name_length`, `name` and `role`; a purpose record is its type, `purpose`, `ef` and `ifd`, held by its receiver, holding the elements that serve it. An element's refs go in the sources layer while `intake_sources` is on, MAP-021.
- Why: The purpose name tells the agent what the record means without treating the database operation called a join as a separate object type. The intake schema repeats ordinary elements and purpose records at every depth, with no special subtype record. The orchestrator passes only the name of the instructions, and the subagent reads them itself, MCP-009. Tools that take the general data pattern mean an intake text change that keeps the pattern never breaks recording. An intake is long, so the agent records the map as it builds it and the web GUI shows each object as it arrives; once everything is recorded, the agent proofs it. ### BASE-043 Optional nouns are written as name=value
- Requirement: A verb's optional nouns are passed on the CLI as `name=value` words, in any order after its required nouns, and over MCP as named arguments.

A word containing `=` whose part before `=` is an optional noun of the verb is that noun; so is one whose part before `=` is a required noun not yet given, and the remaining positional words fill the remaining required nouns in order. After `--`, no word is read this way, CLI-003. Why the required nouns too, 2026-10-11: `map citing key=path value=<file>`, the form the connect text taught, read `key=path` as the key and answered nothing, a wrong answer with no notice against BASE-044; a named required noun now means what it says.
- Why: The grammar keeps data as nouns and behavior as switches, and switches are settings, CLI-011. Record fields are data, and storing a join's purpose as a setting would be meaningless. Named optional nouns keep the grammar and stay readable.
- How it shows: `metaform map add-join intake-20260924T220000Z code.daemon code.failsafe "catch a dead gateway" "probes the gateway" "The failsafe probes the gateway." "One probe every 5 s." non_goal="balance load"`.

### BASE-044 Agent submissions are never blocked
- Requirement: No agent submission is refused for its content; what does not fit is stored as given and noted in the result as a notice, never an error; and an agent that cannot continue stops, submits a trouble report and ends, never looping.
- What this means: This covers every write an agent makes: the intake tools, the knowledge-layer tool, memory, challenge answers, feedback, and settings an agent sets. When part of a submission does not fit the pattern, it is stored as given, and the result names each part and what happened to it, once. An operation that cannot apply, such as an in-place edit of an intake layer's item, writes nothing and says which operation does it; the call still succeeds. Only a call that cannot be read at all, or a failure that would damage the store itself, is an error, and its message tells the agent once what to do, never to try again. When an agent cannot submit its shape at all, it saves what it has with its report, BASE-045, so a person can review and fix it. An agent that cannot continue for any reason stops: it submits a trouble report through `feedback` and ends. It never keeps looping.
- Why: An agent must never loop and spend inference retrying, especially during testing. A rejecting check once turned a five-minute intake into 456 minutes and $750. The shape enforces itself; what does not fit is kept, seen and fixed later by a correction layer or a reviewer, not bounced back to the agent.
- How it shows: `intake_add_purpose` without a purpose returns its receiver and provider and `notices: [{"where": "purpose", "message": "purpose is missing; stored empty."}]`, with no error.
- Build:
  - A result that has notices carries them under `notices`: a list of objects with `where`, the path or id of the part, and `message`, one sentence. The CLI prints each as `Notice: <where>: <message>` after the result; MCP returns them in the JSON block with `is_error` false. BASE-036.
  - The data access object's rules for what is stored and what is noted are STORE-026. Module verbs follow the same rule: a verb raises `Stop` only when its call cannot be read or the store would be damaged.
  - A field that is missing is stored empty, and the result names it in a notice, `<field> is missing; stored empty.`. A call stops only when a field is missing that its record cannot be stored without at all, because nothing else in the call can stand for it: the field that says what the record is, where it attaches, or which layer holds it. For the map's write tools, `map_knowledge` and `map_work`, BASE-038 lists those fields and why.
  - The exit code of a CLI call that stored with notices is 0.
  - The stop rule is delivered in the words agents read: the base instructions, MCP-007 and MCP-029, say to stop and submit a trouble report instead of retrying. It applies whatever the settings are. Whether the trouble report is written when `--debug` is off is open, question 12 of this section; until it is answered, it is written.
  - `approve`, which only a person runs on the CLI, LAYER-015, and module loading, BASE-037, are not agent submissions and keep their stated checks.
- Acceptance:
  - For every refusal condition that STORE-026 and BASE-039 turn into a notice, the call returns `is_error` false over MCP and exit 0 on the CLI, the notice names the part, and the part is readable raw afterwards.
  - An MCP client that sends a malformed `elements` receives exactly one notice and no request to retry; no row is written and the server keeps serving.

- Relates to: STORE-026, BASE-038, BASE-039, BASE-045, LAYER-015, LAYER-018, MCP-006.

### BASE-047 Installing a wheel goes through an install stage that never downgrades
- Requirement: A wheel becomes the installed Metaform through an install stage, the front door, which never downgrades an installed Metaform without force, and a first-run check, the backstage, protects a home last run by a newer Metaform when an install went around the front door.
- What this means: Running a wheel directly never changes an installed Metaform, BASE-023. The front door is `python metaform.whl install`: from a wheel, `install` runs the stage and then the AI tool setup, MCP-013. The stage reads the installed copy's version with `metaform --version`, compares it with the wheel's version and the home's installed and last-run versions, and installs the wheel with `uv tool install --force <wheel>` if it is not a downgrade or `force=true` was given. The stage records the version it installed in the main home. An installed copy's `install` runs only the setup. On the first installed run of a version with no matching stage record, a home last run by a newer Metaform causes a stop naming the downgrade and `install force=true` as the next step. Otherwise the run records its version and continues. An installed `install force=true` explicitly permits that downgrade and continues to setup.
- Why: An installed Metaform's data is written at its own schema versions, and an older chassis refuses a store written by a newer one, STORE-029, so forcing a downgrade must be a deliberate act. Checking the installed executable and the home's installed and last-run versions protects a home even when a raw package install has already replaced the executable, or a newer version was staged but has not run yet. The stage record carries that deliberate permission to the installed copy, while the backstage catches installs that bypassed it. Version probing stays read-only so the stage can discover even an installed version the backstage would refuse. A directly run wheel stays outside this installed-version check because BASE-023 permits it to run independently of the installed code.
- How it shows:
  - A wheel older than the installed copy or either recorded home version stops before installation or tool setup, names the versions being compared, and gives `python <wheel> install force=true` as the next step.
  - A permitted wheel install runs the uv install before tool setup and records its installed version in the shared home, BASE-025. Installing it moves no data.
  - A raw downgrade stops on its first installed run and gives `metaform install force=true` as the next step. A permitted first run records its version and proceeds normally.
- Build:
  - The chassis `install` verb takes optional boolean noun `force`, default false, written as `force=true`, BASE-043. It runs the stage before setup when `METAFORM_WHEEL` is set, BASE-042, and only setup otherwise. The stage uses that environment variable's absolute wheel path.
  - The stage finds the installed `metaform` executable on PATH and reads its version with `--version`. With no installed executable there is no installed-copy comparison. Compare development versions as the four numeric parts of `YYYY.M.D.N`, BASE-020, rather than as strings.
  - The stage compares the wheel version with the discovered installed version and both home records, `installed_version` and `last_run_version`. Without force, an older wheel stops before `uv tool install --force <wheel>` runs. That uv option replaces the tool installation, while the Metaform `force` noun expresses the user's downgrade decision. If uv installation fails, stop without recording success or running setup. Record the installed version only after uv succeeds.
  - Use the existing chassis database's `meta` table in the resolved Metaform home, STORE-001 and STORE-002. `installed_version` records the version approved by the stage or by an installed `install force=true`. `last_run_version` records the version of a permitted installed run. These records are chassis data and belong to no project.
  - On installed startup, a matching `installed_version` permits the version, including a forced downgrade. Otherwise compare the running version with `last_run_version`, stop a downgrade unless this is `install force=true`, and record the version on a permitted run. A blocked run changes neither version record. Skip the backstage for direct wheel runs and for the read-only `--version` probe, so neither changes the installed-run record. A forced installed setup records its approval before the next installed run.
- Acceptance:
  1. With an executable version, recorded installed version or last-run version newer than the wheel, an unforced wheel install runs neither uv installation nor setup, changes neither version record, names the downgrade and offers `force=true`.
  2. With no installed copy, or an installed copy no newer than the wheel and no newer home history, the wheel install invokes `uv tool install --force <wheel>` with the wheel's absolute path, records its version after success and then runs setup. A failed uv install records no success and runs no setup.
  3. With `force=true`, an older wheel installs and records its approval. Its first installed run proceeds even when the previous last-run version was newer.
  4. With no matching stage record and a newer `last_run_version`, an installed run stops before command execution, leaves both version records unchanged and gives `metaform install force=true`. That command permits the downgrade and the next installed run proceeds.
  5. With no matching stage record and no newer last-run version, an installed run records its running version and executes its command. No project, map or settings data is created by that startup record, STORE-002.
  6. An installed copy's `install` runs setup without invoking uv tool installation. A direct wheel run and `metaform --version` neither run the backstage nor change its records. The stage can therefore probe the actual executable version after a raw downgrade, and still refuses an unforced wheel older than either recorded home version.
  7. Numeric comparison treats `2026.10.1.1` as newer than `2026.9.30.9` and update `10` as newer than update `9` of the same day.
- Relates to: BASE-020, BASE-023, BASE-025, BASE-027, BASE-041, BASE-042, BASE-043, MCP-013, STORE-001, STORE-002, STORE-029.

### BASE-051 A workflow is reusable procedure stored as callable logic, made by ingest or authoring and run by one executor

- Requirement: A workflow is reusable procedure stored as callable logic, outside any project's metaform. Each step is a subroutine: a logic requirement written in Axiom, called by address and name with parameters, and returning values, MAP-056. Two prompts produce workflows in the same shape, so one executor runs both.
- What this means:
  - A workflow is a procedure written once and run on any project. Its logic names no project's elements; the elements it works on reach it as parameters, MAP-056, and logic added on an element passes that element with `element=this`. It lives under the `workflow` root, MAP-055, and is recorded in a workflow layer, LAYER-027.
  - Workflow ingest starts from an existing prompt or workflow. It first replaces each element the prompt mentions with a lettered placeholder, `{Element_A}`, `{Element_B}`, the same element always the same letter, so the procedure no longer depends on the project it was written for. Each step becomes a subroutine holding that step's text unchanged; each placeholder a step uses becomes one of its parameters; what the prompt leaves unstated, such as when a step is done or how many attempts it gets, becomes a parameter the caller passes. Ingest adds no step, condition, loop or route the prompt does not state.
  - Workflow authoring starts from a goal and writes the subroutines itself, each with its parameters, its acceptance, its control flow, its retries and its error routes, then hands the executor the first call.
  - Both produce the same shape, so one executor runs both.
  - Inside a subroutine, control flow uses the terms of Amazon States Language, which agents already know: `Choice` branches; `Parallel` runs independent work at once; `Map` with `MaxConcurrency: 1` works through several things one at a time, each until its acceptance holds; `Retry` repeats work that can fail, with a maximum number of attempts; `Catch` routes an error to the subroutine that handles it; a subroutine ends with `RETURN` or a call to the next one. Every loop has a maximum number of attempts. An error no `Catch` handles fails the subroutine and goes up to its caller, as an exception does, and at the top of the calls to the orchestrator.
  - A call that needs independence from the work before it, such as a review with fresh eyes, is a handoff: it runs on a fresh agent. The call is registered as a run of its own, with its caller as its parent, and its run id is what the fresh agent is given, BASE-050, which works as a Step Functions task token does. The run id goes straight to a fresh agent where the host supports handing work from agent to agent, and through the orchestrator otherwise. The fresh agent resumes the run and receives that subroutine alone, with complete instructions, since it has no earlier context; its `RETURN` is delivered to the caller's run, and the caller goes on. Every handoff states the data it accepts and the data it passes back.
  - A run's state is its run record, one row of the workflow module's `runs` table at project level, STORE-045, keyed by its run id: its kind, `call` or `assign`; its state, `running`, `waiting` on its children, then `completed` or `failed`; its parent run; its call frames, each with its frozen logic, arguments, `this` and saved variables; its caller's scope; the children it waits on and, for `Parallel`, each branch's result; and once it returns, its result. A run that returned keeps its row and accepts nothing more. A clear of the project's metaforms and a change of the active metaform keep it.
  - The worked example, the code quality workflow with `improve`, `review`, `fix` and `diagnose`, is the one under How it shows.
- Why: A prompt that holds several steps is followed loosely, and differently on each run. Compiled into subroutines, its routing, acceptance and handoffs are reasoned once, when the workflow is made, and every run starts from them instead of reasoning them again: inference amortization applied to procedure. The earlier design kept the prompt as tagged text for agents to follow; the Axiom compiler turns a prompt into logic an executor runs, which is why that design is superseded. Ingest and authoring produce one shape so that one executor runs both. Delexicalizing an ingested prompt frees it from the project it was written for, so it runs anywhere. A step that needs independence is handed to a fresh agent by its run id, so the agent sees only its subroutine, and the run record brings its return back to the caller. The record is the module's own table because the executor's state belongs to the workflow module, and a project-level table outlives both the session that made a run and a change of metaform.
- How it shows: `( {ok}, {issues} ) := workflow.quality.code.improve( target=code.engine.game )` starts a run; `review` runs on a fresh agent by its run id; while issues remain, `fix` works through them one at a time until each is accepted, an error goes to `diagnose`, and `review` runs again; with none left, `improve` returns `( ok, issues )` to the caller.

### BASE-056 The loop controller in the workflow module owns every loop: code counts the attempts, opens each pass as a ticket and ends the run

- Requirement: The workflow module holds a loop controller that runs every loop of a workflow run. ### BASE-062 Editors mount Metaform as their ACP agent

- Requirement: `metaform dispatch serve` speaks ACP v1 as an agent over standard input and output, so Zed, JetBrains IDEs and any ACP client start Metaform as their agent. With an agent behind it, the conversation passes through to that agent with Metaform's MCP server added and is recorded, so the page shows and steers it; with none, Metaform answers its own commands and starts no model.
- What this means:
  - The agent behind it is the adapter command after `--`, else `agent=<name>`, else the person-only setting `dispatch_serve_agent`: `default` follows `dispatch_agent`, `none` serves Metaform alone. When the agent the setting names is not found, Metaform serves alone and says why, so the editor is never left with nothing.
  - With an agent, Metaform is a transparent proxy in the stdio pipe. Every message passes through as the JSON it was, with its own id, so the editor's client capabilities and the agent's requests of the editor (files, terminals, permission, elicitation) reach the other side unchanged. Metaform changes only this: `session/new`, `session/load`, `session/resume` and `session/fork` gain Metaform's MCP server, run by Metaform's interpreter with the session's `METAFORM_SESSION`, unless the editor already names a server `metaform`, and when it cannot be added the editor is told by a Session Notice, or a message where the editor takes no notices; `initialize` advertises `sessionCapabilities.list` only when the agent can open a listed session (`loadSession` or `sessionCapabilities.resume`), and `session/list` follows the agent's own pages with Metaform's (cursors `metaform:<n>`) of the dispatch sessions of the same agent it did not list itself, each with the title and last activity its agent gave by `session_info_update`, else its ticket and its last turn, and its `additionalDirectories`; `session/delete` goes to the agent and keeps the session out of Metaform's pages too, and of a session the agent does not know is answered by Metaform; the agent's `available_commands_update` gains Metaform's commands; a session a dispatch runner, or another editor through Metaform, is running is refused to `session/load`, since two processes would each prompt it; and each `terminal` auth method has its `args` moved into its `env` as `METAFORM_SERVE_LOGIN`, a JSON list.
  - ACP's terminal authentication has the editor run the agent program it is configured with plus the method's `args` and `env`; that program is `metaform dispatch serve`, which would refuse the adapter's own arguments, or take them for part of an adapter command after `--`. Started with `METAFORM_SERVE_LOGIN` set, serve speaks no ACP: it replaces itself with the resolved adapter command plus those arguments, in the editor's terminal, and the editor reads its exit status.
  - Metaform keeps the agent's order: a response Metaform takes in, to change it or to answer from it, holds what the agent writes after it until Metaform has passed it on, so the editor learns a session's id before any update of that session. Updates of a session that arrive before its record is made are recorded once it is.
  - Metaform forwards before it records: an update of the agent's reaches the editor at once, and its record is written by one task per session in order, so the store, a subscriber or the relay never holds back a permission request or a response queued behind it. A failed write is said on standard error and the session goes on.
  - ACP's turns are sequential, so every turn the agent is given, the editor's and the page's, holds the session's lock from prompt to answer: an editor prompt sent during the page's turn waits for it, and the editor's `session/cancel` cancels the turn in flight and answers a prompt still waiting `cancelled`, unsent. `$/cancel_request` for a request Metaform answers itself stops it and is answered -32800 (a prompt `cancelled`); for one at the agent it goes on to the agent. Every message Metaform writes in a session carries a `messageId` of its own.
  - Metaform's slash commands are its MCP tools, `<module>_<verb>`, with their summaries and their arguments as the input hint, from the declarations of the folder's command surface. A prompt that is one of them runs that command line as the person in the session's folder and shows what it prints, with no turn of the agent; `session/cancel` stops it. A name the agent's own commands use stays the agent's. The person-only setting `dispatch_serve_commands` turns them off.
  - Each session an agent runs is recorded in dispatch's tables on a held ticket, "Sessions from editors", made at the DE, or before the intake at the first node of the map: its row, its thread as the runner keeps one, and a control port. `runner_of` names a `dispatch serve` process, so the session reads as running while it is. Editor sessions share that ticket, so the page addresses each by its session: `dispatch message` and `dispatch interrupt` take `session=<id>`, checked live, and the page sends the session of the thread on view; without one, the latest session of the ticket that is running still, checked live, so a row a killed process left is passed over; a session that stops answering in between is a failure naming `dispatch sessions`, never a traceback. A late status reply never ends an editor session, since a serve's pid answers for each session it holds. The page's message goes into the turn in flight by the agent's `_session/steering` when it advertises it, `dispatch_steering` is on and nothing waits before it, as the runner's does, and its answer says `steered`; otherwise it reaches the agent as a `session/prompt` in its own turn, and the editor is shown it as the person's message, or one another agent sent as `From the <role> agent: …`, never as the person's, BASE-052; `interrupt` sends `session/cancel`; permission and the session's end stay the editor's, and `dispatch stop` says so and fails, and the dock shows "In your editor" in place of Stop. An editor session is the person's own agent, never one of dispatch's: it takes no `dispatch_agents` slot in autostart or in summoning. Its state line keeps the agent's own slash commands, as the runner's does. The person-only setting `dispatch_serve_record` turns recording off.
  - With no agent, `initialize` offers `loadSession` and `sessionCapabilities.list`, `close` and `delete`, ACP v1 as published (no draft keys); `session/list` lists the dispatch sessions whose recorded folder is the `cwd` asked, or with none those of every project the home knows, and `session/load` replays one's thread; free text is answered with the `serve_free_text` prompt, which names how to put an agent behind it and, while the commands are offered, that `/` lists them. When the agent the setting names is not found, a Session Notice says so as the session opens. Every word serve shows the person is a prompt in dispatch's prompts.xml (`serve_free_text`, `serve_commands`, `serve_alone_title`, `serve_alone_notice`, `serve_server_title`), except the `From the <role> agent:` prefix the thread and the runner share.
  - `metaform install zed` and `metaform install jetbrains` register `uvx --from <wheel> metaform dispatch serve` as a custom agent named `metaform`, in Zed's `agent_servers` (`type: custom`) and JetBrains' `~/.jetbrains/acp.json` `agent_servers`, the formats each editor documents. Zed's settings.json (`~/.config/zed`, under `XDG_CONFIG_HOME`, or `%APPDATA%\Zed` on Windows) is JSON with comments and trailing commas, so only Metaform's member is written into or removed from its text, on lines of its own, keeping the rest: a comment stays on its line, and an `agent_servers` left empty goes with it, so an uninstall gives back the file as it was. A JetBrains IDE is found by `~/.jetbrains` or by the configuration folder every JetBrains IDE keeps, and `acp.json` is made when there is none. A config Metaform cannot read fails that tool alone, an MCP client's as an editor's; the others are still set up and proven. The proof starts it with `agent=none`, checks it answers `initialize`, and names the agent the registration reaches with the settings as they are, and whether it is installed. VS Code has no ACP standard of its own, so it is not offered.
- Why: An editor's agent is where most of the person's work happens, and none of it reached the map: the dock could not show it, the page could not steer it, and its agent did not have Metaform's server unless the person configured one. Mounting Metaform as the agent puts every editor session in the same set as the page's, with the same server and identity, without the editor or the agent changing. The Proxy Chains RFD's `proxy/initialize` and `proxy/successor` and the MCP-over-ACP transport would be the standard way, but both are drafts the installed SDK (agent-client-protocol, schema 1.19) and the adapters do not implement, and the MCP-over-ACP draft has already replaced the `mcp/connect` form the SDK carries; a transparent proxy in the pipe needs neither and works with every ACP agent today. Metaform alone starts no model, BASE-003, yet is still useful in an editor: its commands, and the sessions it holds.

### BASE-063 Refactoring intake prepares reusable knowledge before implementation

- Requirement: An optional `refactor` module serves an Axiom intake procedure that prepares refactoring knowledge in a `refactor` CEL on the existing functional map.
- What this means: `metaform refactor intake`, exposed as `refactor_intake`, returns the procedure. Optional `text` supplies the target, intended outcome or task context as JSON text after the procedure. Reading it is read-only. The agent following it connects existing RE-owned purposes to exact implementation symbols, examines their dependencies and records the inference needed by subsequent editing agents. Ordinary elements and purpose records retain the intake schema's recursive form.
- Why: Symbol and call lookup supplies structural evidence but does not resolve which functionality the code serves, what a proposed boundary must preserve, or why one extraction depends on another. Recording that reasoning once at its RE lets later agents use and reexamine it without reconstructing the same understanding.
- How it shows: An agent reads `refactor_intake`, prepares the requested scope, then records and reads items at the receiving Addresses in the `refactor` layer. An editing agent reads `<address>@refactor` and the code context for that Address. The procedure is Axiom, although the module's normal prompt store is XML.
- Build: Reuse the existing layer, item and code-link operations. The procedure creates the mutable, hideable `refactor` knowledge layer if absent and otherwise resumes its contents. It uses Cypher to retrieve bounded functional-map and code-graph evidence, and NetworkX to examine dependency groups, cycles, boundary crossings and reachability. These results inform inference; they do not determine functional ownership or IFD. Code links retain exact file-qualified symbols and their reasons in the code layer. Refactoring items retain intended boundaries, behavior, state/lifecycle and callback dependencies, verification and unresolved evidence at the RE, with source freshness information. Existing code-link proposals retain their existing lifecycle. The module can be enabled or disabled through the normal module interface. BASE-065 extends it to ship enabled and follow completed code intakes when the required services are available.
- Acceptance:
  1. CLI and MCP return the authored Axiom procedure; optional task text survives as separate JSON data.
  2. Repeated reads of the procedure leave the existing base, source records and populated knowledge layers unchanged.
  3. MCP declares `refactor_intake` as a read-only tool, available when the module is enabled.

### BASE-064 Optional bulk provider classification during refactor preparation

- Requirement: Refactor preparation offers an optional Jev pass that selects a provider category for each code item from the full provider list, using a configurable confidence threshold.
- Why: A complete category choice lets the model compare the intended functional alternatives directly. Reusing the same category definitions for independent code items amortizes discovery while leaving uncertain placements visible for source analysis.
- Build: `refactor intake association=jev confidence=83` adds the optional procedure. `refactor associate` receives named code evidence and defaults to all eligible providers in the current base, with eligibility refined in BASE-065. Explicit categories carry provider namespace and verbatim EF text. Category labels reverse namespace segments and render code as Program Code, with the EF beneath. Distinct descriptions for the same provider are retained in one category. Shared Choice criteria include the complete list. One question asks which category each named code item belongs to. Batching splits items, never alternatives. Results retain the choice, confidence, probability distribution, category identity, usage and timing. The intake agent records associations through existing map operations. Reading the procedure sends nothing; sending private source requires authorization.
- Acceptance: Each code item gets one Choice with all provider categories. Category text preserves the namespace reading and EF. Named items retain identity across batches. Low confidence produces review. Invalid or incomplete service answers cannot become accepted classifications. Oversized full-list questions fail before network submission. CLI and MCP expose the optional pass and declare its external service access.
- Status: Confirmed full-category Choice design, superseding pairwise purpose judgments, 2026-10-12.


### BASE-065 Code intake places indexed functions upfront and delegates the remainder

- Requirement: Completing a code intake automatically follows it with provider classification when the configured code graph MCP and a working Jev/OpenRouter API key are available. Without those services, the ordinary intake still completes. The same extension is callable for an existing intake through `metaform refactor extend` and `refactor_extend`.
- Why: Structural discovery and confident classifications can be performed once before editing agents begin their work. A reasoning agent should spend its inference on the remaining placements, using the completed map and source evidence. Service availability must not prevent the map itself from being recorded, and an existing intake should receive the same benefit without being repeated.
- What this means:
  - The refactor module ships enabled. A completed code intake publishes `intake.finished` after its layer is ready and its base is active, identifying its project, base and layer. The optional extension runs in a detached process, retaining the completed intake if a service is absent or fails.
  - The extension checks for the key and code inventory capability. The configured MCP supplies code evidence. The first useful Jev batch verifies a responding API and model before the remaining batches run. An unavailable service is reported as such, not as a completed classification.
  - The refactor module owns the Tree-sitter runtime and JavaScript grammar dependencies and provides its source parser through `code.functions`. Map consumes that capability through the public module interface and declares no parser dependency. Missing refactor dependencies must not withdraw map, intake or dispatch: optional source analysis cannot disable the project's map or work controls.
  - Every code item receives one Choice question against all eligible provider categories selected for that run. The literal `code` root and namespaces rooted at `upstream` or `downstream` are excluded because the code root organizes the implementation and external elements are not implementation files in this project. All other providers remain eligible unless explicitly excluded. Category labels reverse the provider namespace, render `code` as `Program Code`, and retain the EF text verbatim. There is no synthetic `none` category. Explicit provider exclusions are supported. Only named function names and source bodies are sent as implementation evidence; source identities and freshness evidence remain local.
  - Placements at or above the configured threshold, 83 percent by default, are recorded in the existing `refactor` knowledge layer directly at the selected provider element acting as RE, never at a purpose/join record. The implementation belongs to that element, independently of the purposes it serves for other receiving elements. Lower-confidence items remain for a reasoning agent. Their durable ordinary work ticket starts a session that reads source, resolves category selections and records the evidence for each decision. If a session cannot start, the work remains available.
  - Each run remains bound to its intake base. Local artifacts under `.metaform/refactor/` preserve inputs, completed batches and decisions so retries reuse completed work. Source changes are detected before saved evidence is used to record placements. `status`, `pending` and `resolve` expose progress and the remaining work through the normal CLI and MCP surfaces.
- Acceptance:
  1. Finishing a code intake with working services starts the extension against the finished base. No-building and noncode finishes do not start it.
  2. Missing keys, unavailable code MCP and failed API responses leave the ordinary intake complete and report the extension's outcome.
  3. An existing intake can run and resume the same extension without rebuilding its functional map.
  4. Requests contain the full eligible provider category list after explicit exclusions, reversed namespace labels and verbatim EF descriptions, with no `none` option and only the required function evidence. The literal code root and upstream/downstream namespaces are never placement choices, and every other provider remains eligible unless explicitly excluded.
  5. Confident placements are persisted directly at the selected provider element acting as RE, not at its purpose records, and all remaining items are exposed as durable ordinary work for source-supported resolution. Repeating a completed batch or run does not duplicate placements.
  6. Saved run identity and source checks prevent placements from silently applying to a different intake base or changed source.
