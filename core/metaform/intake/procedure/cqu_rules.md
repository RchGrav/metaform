Rules:

- We call the explicit party for whose benefit a piece of property or work is held, modified, and managed the CQU (Cestui Que Use) a term that specifically highlights their role as the "receiver of consideration" who drives the value-adding work.
- Assume an artifact is converted into a metaform to improve it. The CQUs that matter are the ones whose purpose drives changes or improvements to the artifact. Enumerate each of them.
- The CQU that drives the most improvement gives the best inference.
- Never the person who asked for the intake, and never the simply the end user, the term is too general.
- The CQU is especially important because it forms the tripartite root dependency that makes the map artifact specific: the CQU as receiver, its Operative Purpose as the why, and the Providing Element's Encounter Function as the how. Every other dependency in the map traces back to a root dependency through its receivers.
- Elements are types, so the CQU is a type: the type of party that holds an objective purpose for this type of object, named at its most specific reusable type level.
- When one person can hold several roles, name the role that changes the artifact, by the title that role carries.
- Identify the CQU by asking who drives the most improvement in an artifact of this type.
- Deciding on the CQU takes deep consideration because it is not a present element in what you are examining. Infer it from what the artifact is; do not look for it in the artifact.
- The CQU is not the developer, the user, or anyone performing the operation. That could be said of every artifact, so it identifies nothing about this one, and it is the wrong way to be reasoning.

Examples of a CQU:

- artifact type `media.photo`, CQU `downstream.seller`: valid. the seller goes out of its way to present the photo in the best possible way to facilitate a sale.
- artifact type `media.photo`, CQU `downstream.operator`: invalid. the party performing the operation could be named for every artifact, so it identifies nothing about this one.
- artifact type `code.[not a programming tool]`, CQU `downstream.developer`: invalid. Never state the user or the developer sitting on the other side of the screen; it's not the answer we are looking for, because it doesn't present unique reasoning.
- artifact type `code.ide`, CQU `downstream.developer`: valid. The developer is the party who the project is targetting, so this is valid.
- artifact type `code.sdk`, CQU `downstream.code.*`: valid. The downstream project type that this project is targetting, so this is valid.
- artifact type `*`, CQU `downstream.user`: invalid. This is a non answer, it says nothing worthwhile to reason about.
- artifact type `document.story`, CQU `downstream.reader`: valid. The reader is true because they are vested in reading a good story; they will be spending their time to read the story, and they want it to be good. Vested does not always mean money.
- artifact type `media.photo`, CQU `downstream.buyer`: invalid. the buyer judges the photo; judging does not change or improve it
- artifact type `media.photo`, CQU `downstream.company.insurance`: invalid. the insurance company records the photo and does not want it changed
- artifact type `media.photo`, CQU `downstream.influencer.media.social`: valid. a social media post drives changes or improvements to the photo
- artifact type `media.photo`, CQU `downstream.blogger`: valid. a blogger drives changes or improvements to the photo
