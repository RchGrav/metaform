Act as a senior product designer and frontend engineer. Design and, if code generation is available, implement a polished desktop-first GUI for Metaform: a developer system that analyzes a software repository and maps its functional design. The graph is a way to explore the repository’s functional specification—not a generic workspace or an end in itself. Users inspect how capabilities, modules, APIs, data, dependencies, and tests relate; agents can propose refinements to the project specification; and the GUI can generate the specification as a Markdown document that accurately matches the specification currently shown on screen.

## Product principles
- Make the repository and its functional design the primary context. Keep project identity, analysis scope, graph location, and specification status clear.
- Treat the graph, structured specification, and Markdown output as synchronized views of the same canonical specification state. Changes shown in the GUI must be reflected in the generated Markdown; do not export a separate, stale, or hidden representation.
- Separate repository evidence from interpretation. Identify claims as source-backed, inferred, agent-proposed, accepted, rejected, or unverified, and provide source paths or other available evidence where possible. Do not invent repository behavior or imply analysis occurred when it did not.
- Prefer a coherent, working repository-analysis and specification workflow over decorative breadth. Do not leave primary controls inert. If a behavior is simulated, label it clearly.

## First: inspect and plan
If a repository is available, inspect its framework, existing UI, run instructions, and any available repository-analysis or agent integrations before changing files. Reuse conventions where practical. If the product repository is not available, build a standalone React + TypeScript prototype with realistic sample repository data and clearly isolated interfaces for analysis, agent, and export integrations. Use an appropriate interactive SVG or canvas graph approach.

Before implementation, briefly state the proposed architecture and distinguish real integrations from simulated behavior. Use a single canonical, typed specification model as the source of truth for the graph, specification views, and Markdown export. Keep transient UI state, analysis activity, and agent conversation separate from saved specification content.

## Phase 1: repository analysis and functional map
Build a dark-first, accessible, desktop-first GUI with a large graph canvas and compact repository context: repository/project name, analysis status, current graph or scope, breadcrumbs, selected entity, and specification status. Keep persistent chrome minimal; provide a compact menu that can be hidden and deliberately reopened.

Use believable sample data for a repository, preferably a Rust service, including functional capabilities, modules, API endpoints, data stores or models, external dependencies, tests, and deployment/runtime components. Model meaningful relationships between these entities. Clearly distinguish repository structure from functional concepts, and show cross-module relationships without obscuring boundaries.

Implement graph, selected-entity detail, and presentation/read-only modes while preserving graph context and selection. Support pan, zoom, visible zoom level, recenter, and fit-to-view, including fit graph, fit selection, fit branch, and fit visible scope. Double-click navigable entities to inspect nested functional areas; provide breadcrumbs and a clear return action. Support pivoting to related context and returning to the prior context or repository overview. Include concise discoverable hints for non-obvious navigation.

Provide useful graph controls for expanding and collapsing branches, depth, or the whole map; include collapse all, expand all, collapse to depth, expand one level, and undo/restore where practical. Communicate collapsed state and hidden descendant counts. Support layer/category visibility, isolate, toggle all, and restore all, with clear active, hidden, and isolated states. Preserve positions and selection where practical.

## Phase 2: specification review and agent refinement
Provide configurable surfaces for entity details, evidence/source references, analysis findings, specification outline, agent activity, and review history. Panels should be addable/removable, dockable to understandable zones, detachable or floating, resizable, and reattachable. Include a default-layout restore action without forcing every panel open. Persist reasonable local UI preferences, including workspace and panel text size, and avoid clipping at supported sizes. Adapt docking and floating behavior for narrower screens.

Let users inspect and refine the project’s functional specification. Support editing relevant specification fields and relationships, with clear distinctions between repository-derived facts and user-authored content. When agents are available, let users ask them to refine a selected project, functional area, or entity. Show each proposed change with rationale and available evidence; allow review, accept, reject, or edit before applying. Make accepted changes visible in the same canonical specification state used by the graph and export. Do not silently overwrite user work or present agent suggestions as verified facts.

If agent services are unavailable, provide clearly labeled simulated proposals that demonstrate this workflow. Do not claim simulated agents or analysis are connected to real services.

Provide a focused analysis/activity stream for repository findings, source changes, test/build results, dependency changes, runtime issues, and agent proposals when appropriate. Each item should include type, timestamp, status, relevant repository scope, and affected specification entity when available. Selecting an item should show concise details, highlight the related entity, and offer a return to the previous view. Include useful filters and clear simulated/connected, paused, empty, and disconnected states. Incoming activity must not unexpectedly change the user’s current view.

## Phase 3: Markdown generation and export
Provide a prominent action to generate or preview the project specification as Markdown from the current canonical specification state. The rendered Markdown must match what the GUI currently shows, including accepted edits and the currently included scope. Define and communicate what is included, such as project overview, functional capabilities, components, relationships or flows, APIs, dependencies, tests, evidence, and unresolved or unverified items. Respect user-visible inclusion and scope choices. Exclude transient events, private secrets, and unaccepted agent proposals unless the user explicitly chooses to include proposals in a clearly marked section.

Show an in-app Markdown preview before export. Ensure the preview and downloaded file are generated from the same state and update when the specification changes. Support browser download when filesystem writing is unavailable, explain this in the UI, and provide success/failure feedback. If practical, let users copy the Markdown and inspect the generated content. Do not describe this as exporting the GUI layout; it is exporting the project’s functional specification represented by the current GUI state.

## Visual, accessibility, and interaction standards
Use crisp typography, balanced contrast, precise spacing, subtle depth, and purposeful graph styling. Avoid decorative gradients or glow as substitutes for hierarchy. Differentiate entity types, selection, evidence status, agent proposals, and analysis state using accessible signals beyond color alone. Support keyboard focus, readable labels, concise tooltips for non-obvious controls, reduced motion, and fast, purposeful transitions. Maintain orientation cues such as repository, breadcrumbs, selected entity, scope, and zoom.

## Completion and verification
After implementation, run the prototype where possible and verify the main flows: explore and navigate the repository map; expand/collapse and restore graph structure; filter or isolate entity categories; inspect evidence and findings; edit specification content; review and accept/reject a simulated or connected agent proposal; confirm accepted changes update the graph and specification view; generate a Markdown preview that matches the visible specification; and download or copy that Markdown. Fix obvious errors and report unverified behavior and limitations.

Deliver either the working prototype or, if code generation is unavailable, a directly implementable screen specification and interaction map covering these phases. End with a concise summary of how to run it, key interactions, the canonical specification model and Markdown sections, accessibility support, and which repository analysis, agent actions, and exports are simulated versus connected through real integrations. Be explicit about limitations.
