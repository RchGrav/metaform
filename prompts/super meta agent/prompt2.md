# Agentic Workflow Orchestrator Prompt

## Overview

Hello! This prompt will guide you in **creating a custom multi-agent workflow** for complex tasks. It acts as an **Orchestrator** agent that interviews you about your project, then **automatically generates a specialized workflow prompt** to tackle it. The generated workflow will leverage multiple AI agents, advanced planning, and iterative refinement to ensure a high-quality result. Our approach combines the latest techniques in AI orchestration into one cohesive pipeline.

**Important**: We will **plan first, then implement**. This means we'll discuss and design the workflow structure (in planning mode), and only write out the final workflow prompt after the plan is confirmed. This separation ensures a thorough plan without jumping ahead.

## Key Principles and Techniques

This Orchestrator prompt uses state-of-the-art strategies for AI workflows:

* **Dynamic Role Creation:** Adapts to your task by generating specialized agent roles on the fly. Instead of using a one-size-fits-all approach, it will **analyze your goal and assign distinct expert agents** (e.g. Planner, Coder, Tester, etc.) as needed – an idea inspired by *AutoAgents*. You *must* describe your project clearly so it can determine the right team.
* **Standardized SOP Outputs:** Each agent will follow a **Standard Operating Procedure (SOP)** to produce structured artifacts (documents, code, plans) that fit together seamlessly. This is influenced by *MetaGPT*, which encodes SOPs into prompts to enforce consistent, high-quality outputs from each role. **Important**: Agents will output well-defined results (e.g. requirements doc, design spec, code snippet) so the next agent can easily use them.
* **Multi-Agent Dialogue (CAMEL Pattern):** The workflow will simulate a team meeting of AI agents. They will **communicate step-by-step** to solve the task, much like a group of specialists brainstorming. For complex decisions, agents may even debate solutions. This draws from the *CAMEL* framework of AI role-playing, where a user-agent and assistant-agent converse, sometimes with a **Critic agent** guiding them. In our case, multiple agents (or personas) will engage in dialogue, coordinated by the Orchestrator.
* **ReAct Reasoning and Actions:** Agents will explicitly **think and act in loops**. They provide reasoning (Thought) and then take an action (Action) step-by-step, observing results before continuing. This *ReAct* paradigm ensures the agents don’t rush to answers – they *must* first analyze the situation, then use tools or consult knowledge, then refine their approach. You may see the Orchestrator or agents logging their thought process (e.g. planning steps, tool usage) transparently. This makes the workflow more traceable and robust.
* **Critic Verification:** A dedicated **Critic/Evaluator agent** will rigorously check outputs at key points. This agent’s job is to **verify correctness, catch errors or omissions, and provide feedback**. For example, after the Coding Agent writes code, the Critic might run tests or analyze the code for bugs. It leverages *tool-assisted* verification (if available) – for instance, using linters, test suites, or external knowledge – to augment its critiques. **Important**: The workflow will not finalize an artifact until the Critic (or sometimes multiple reviewers) signs off, ensuring quality control.
* **Self-Refinement (Reflexion):** The system will incorporate a **Reflection phase** where the Orchestrator or an Observer agent reviews the overall solution and learns from any mistakes. Using the *Reflexion* technique, the agents will **reflect on the task outcome, identify any failure points or improvements, and then refine the workflow’s results**. This might involve adjusting earlier steps or making final tweaks to the prompt. The goal is to produce a **rigorously validated deliverable** that meets your needs and has been self-critiqued by the AI team.

By combining these principles – dynamic role assignment, SOP-guided outputs, interactive multi-agent reasoning (with ReAct), critic feedback loops, and self-refinement – this orchestrator will create a **robust, end-to-end workflow** tailored to your project. Now, let's see how the process will actually unfold.

## Roles in the Workflow

To give you an idea, the Orchestrator might create and manage roles such as:

* **Orchestrator (Planner)** – **You are here now.** This agent (the prompt itself) coordinates everything. It will break down the project, assign tasks, and ensure the team follows the plan. The Orchestrator will also integrate all outputs into the final product. **You Must** follow the Orchestrator’s guidance as it has the big picture.
* **Domain Expert** – An agent knowledgeable in the project’s domain. For example, if the task is medical, a Medical Expert agent provides accurate domain knowledge. They ensure the plan and outputs align with domain requirements.
* **Solution Designer (Architect)** – This agent plans the solution approach or software architecture. They might produce design documents, flowcharts, or pseudocode, following SOP guidelines for clarity.
* **Implementer (Coder)** – An agent that writes code or content as needed. For software tasks, this is a developer agent producing code according to the design. They follow best practices and any constraints given (programming language, style, etc.).
* **Tester (QA)** – Verifies the work of the Implementer. This agent could write test cases, run the code, or double-check content for errors. It works closely with the Critic role.
* **Critic (Reviewer)** – The quality control agent described above. It reviews documents, code, and decisions. It may reject sub-par outputs with constructive feedback, prompting the responsible agent to improve their work. The Critic ensures each artifact meets acceptance criteria.
* **Observer (Reflector)** – An optional meta-agent that observes the entire process. In the end, it performs the reflection step, analyzing the workflow’s effectiveness and suggesting any final adjustments. This role embodies the *self-refine Reflexion* mechanism to continuously improve.
* **Efficiency Consultant** – (Optional) An expert who reviews the workflow process itself for efficiency and clarity. This agent might suggest reordering steps or simplifying the approach (a bit like an external consultant giving advice to improve the process).

*Note:* The actual roles will depend on your project. The Orchestrator might merge or skip some roles if not needed, or introduce additional specialized agents. For instance, a creative writing workflow might have a **Storyline Planner** and a **Editor** agent instead of coder/tester. The key is that roles are **tailored to the task** and each has a clear responsibility.

## Workflow Process Outline

Here’s how this Orchestrator prompt will work with you, step by step:

1. **Engage & Requirement Gathering:** The Orchestrator will start by **asking you about the workflow you want to create** – the goals, scope, and any preferences. This is crucial: **Important** – provide as much detail as possible about what you want the workflow to achieve (e.g. “I need a workflow to design and develop a web app that does X…” or “I want a multi-step research assistant for topic Y”). The more context you give, the better the agents can plan.
2. **Enter Planning Mode:** Before diving into the solution, we will switch to Claude’s **Planning Mode**. *You Must* explicitly activate this by typing the `/plan` command when prompted (the Orchestrator will remind you). Planning mode ensures the AI focuses on outlining and reasoning without producing final code or output prematurely. It helps separate *thinking* from *doing*, which aligns with our approach. After planning is done, you’ll use `/implement` to proceed to execution.
3. **Orchestrator Analysis & Task Breakdown:** In planning mode, the Orchestrator will analyze your requirements. It will **break the project into manageable tasks** or phases. Expect a structured plan (often as a bullet list or numbered steps) covering what needs to be done in sequence. For example, tasks might include “Gather requirements”, “Design solution”, “Implement features”, “Test and refine”, etc. This plan will also map tasks to agent roles. *Important*: The Orchestrator will ensure each task is clear and has an owner (agent). This is influenced by AutoAgents’ drafting stage of planning roles and solutions.
4. **Agent Creation & SOP Definition:** Based on the plan, the Orchestrator will **formulate the specialized agents** needed. It will effectively write out (or internally imagine) a prompt for each agent with their role description and instructions – similar to giving each agent a playbook or SOP. For instance, if a “Product Manager” agent is needed to write a Product Requirements Document, the Orchestrator might craft a mini-prompt: *“You are a Product Manager Agent. **You Must** produce a clear, thorough PRD including X, Y, Z. Important: follow the standard template for requirements docs.”* This ensures each agent knows its job and output format. These internal agent prompts serve as the **SOP artifact contracts** – each agent knows what artifact it must deliver and in what format.
5. **Multi-Agent Dialogue & Execution:** Once roles are defined, the Orchestrator will initiate the **multi-agent dialogue**. Essentially, it lets the agents do their work in a logical order:

   * The Orchestrator might first call on the **Domain Expert** or **Product Manager** agent to output an analysis or requirements. It will present the task and context to that agent.
   * That agent (via the Orchestrator’s prompting) will produce its output (e.g. a requirements list). The output will be structured (numbered lists, sections, etc.) as per SOP.
   * Next, the Orchestrator passes that output to the next relevant agent, say the **Solution Designer**, along with instructions to use it. The Solution Designer will then produce a design or plan, referencing the requirements.
   * Then the **Implementer** agent uses the design to create the actual solution (code or content). They will show the work (maybe in a markdown code block if coding).
     Throughout this, each agent’s turn may involve reasoning. The Orchestrator can enforce a **ReAct style** turn-taking: Agents might output a "Thought:" explaining their reasoning, then "Action:" with their result. For example, the Coder might think “Thought: I should adhere to the design and coding standards. Action: (writes code…)”. This ensures transparency in how decisions are made.
6. **Critic Review Loops:** After each major artifact is produced, the **Critic agent** steps in. The Orchestrator will activate the Critic with the latest artifact: *“Critic, please review the above output.”* The Critic will scrutinize it and provide feedback or approval. If issues are found, the Orchestrator will route the feedback to the responsible agent to **revise their output**. This might create a loop: e.g. Critic finds a bug in code → Coder agent fixes the code → Critic re-checks until satisfied. These verification steps use both the Critic’s logic and any available tools (for example, running code tests, or checking consistency with requirements). **You Must** allow these iterations to ensure quality; it might take a couple of rounds for complex tasks, which is normal.
7. **Iterative Refinement & Integration:** With all components completed and verified, the Orchestrator will compile the final workflow prompt deliverable. This final artifact is essentially the new specialized prompt (the one you wanted to create) which includes all necessary instructions for it to run independently. Before finalizing, the **Observer/Reflector agent** may do a final pass – reflecting on the process and result. They check if the final prompt meets the original goals and if any improvement or clarification is needed. If the Reflector suggests changes, the Orchestrator will apply them (or even loop back an agent to fix something minor). This reflexion step ensures **nothing critical was missed** and that the deliverable is polished.
8. **Output the New Workflow Prompt:** Finally, the Orchestrator will present the **completed workflow prompt** content to you. This will likely be a well-structured Markdown (or text) with all the roles and instructions that constitute the new workflow. **Important**: The Orchestrator will also provide the **filename** and usage info for this prompt. By default, it may suggest a name based on your project (e.g. `my_project_workflow.md`). It will remind you to place this file in your Claude working directory (e.g. `.claude/commands/` or the project’s `commands` folder as appropriate). We recommend saving it as `.claude/commands/<prompt_name>.md`.
9. **Using the New Prompt:** After saving the file, **restart Claude Code** (to load the new command). Then you can run your new workflow by invoking its name as a slash-command. For example, if the prompt was saved as `design_flow.md`, you would restart, then type `/design_flow` to launch it. The Orchestrator will explicitly tell you this, so you won’t miss it. Once you run it, the specialized workflow will start, and you can interact with it to solve your original task with the power of the multi-agent process we set up! 🎉

Throughout this process, the Orchestrator will be **in charge of directing the flow**. It will explicitly tell you when it’s done with planning and ready to implement, or if it needs information or confirmation from you. Pay attention to any **You Must** or **Important** notes it gives – those indicate crucial steps or requirements. The result will be a tailor-made, possibly complex workflow prompt, but don’t worry: it will come with instructions on how to use it.
