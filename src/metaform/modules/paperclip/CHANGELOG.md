# Changelog

Each change to the paperclip module, newest first.

## Unreleased

- 2026-11-17, kickoff Phase 3, decision t-legacy-keep: a project held in the project store has its Paperclip tickets and messages there (`stored.py`). An issue's ticket is a record of its `tickets` overlay, the one the board reads: `link` writes it taken by the issue, `send` claims it by the revision it read and gives it back when the issue cannot be made, `heartbeat` writes it in To do, and `sync` closes it with the resolution in its own paragraph of the note, as `map work done` writes it, and reads that paragraph back to report a ticket's end. A comment that crosses in is a message of the `questions` overlay, written by map's `project_messages.tell`; the questions that cross out are that overlay's questions naming the ticket, and their answers come back through `map reply` as before. The brief, in `brief`, in the issue document's `brief:` line and in `links`, is the project tool's read of the element, since `map where` has nothing of that map. An issue cancelled in Paperclip stops a running session with dispatch's `stop` and the ticket is closed here, because dispatch's `cancel` closes a ticket of the old store only. Jev's candidate Addresses come from the project store's elements and the wants they hold. `watch` counts a `project.map` commit only, and syncs only the links whose ticket or questions changed revision since the last sync read them, so its own writes and memory commits cost no Paperclip read. The `links` and `bridged` tables stay in this module's own tables. Projects not held there take the old path unchanged.
- 2026-10-25, the owner's decision that nothing chooses an agent, model or thinking level for the person: `send` no longer asks Jev to pick a Paperclip agent for a ticket with no `assignee` and an empty `paperclip_assignee`; the issue goes to Paperclip's backlog unassigned, and `send` shows no `assignee_chosen`. The chassis's `choose_agent` decision point is gone.
- 2026-10-15, ticket 2ede3067 (code.system.management.knowledge#32), no polling: `watch` follows Paperclip's live events WebSocket and `map.changed` instead of syncing every `paperclip_check_minutes`, which now times syncs only for a server with no such stream; whether a watcher runs is the lock it holds on `run/paperclip/<project>.lock`, not a beat written every 20 seconds. `DEPENDENCIES` gains `websockets>=13`.
- Settings cleanup, 2026-10-15, ticket 0d9e3882: `paperclip_jev_route` folds into the chassis's `jev_decisions` as the decision point `paperclip.route`, which `jev.pick_one` is now asked under. Where the setting was off, paperclip's start carries it once (`carry_route`, marked `carried:paperclip-jev-route`): `jev_decisions` at that folder names every other decision.
- A ticket sent while the web GUI already runs, or in a project other than where `web start` ran, now closes by itself (round 5, ce3791fd). `send` starts the project's watcher when none runs; `web.started` starts one for every registered project with paperclip on and issues to follow, wherever the GUI started; `watch` ends, state `idle`, after a sync that leaves no link to follow or once paperclip is disabled, and writes each log line as it is said.
- Tests, the module's first (wave2-integrations F4): `tests/test_paperclip.py` runs each verb against a Paperclip server simulated in memory, reached through the new module-level `OPENER`, the opener every `Client` the module makes is given (urlopen when None). Covered: send and its rollback, sync closing done and cancelled issues with and without dispatch, a person's cancel crossing to the issue, heartbeat checkout, release and the one `unrouted` note, monitor re-arming, question cards out and answers back through `map reply`, the failed ticket's card and its retry or close, and the F3 comment and resolution checks.
- A ticket sent to Paperclip follows its issue by itself, and what the Paperclip agent did reaches the Address (wave2-integrations F3). `sync` writes each new comment on an issue a Paperclip agent works as a message at the Address while its ticket is open, and resolves a ticket whose issue is done with the assignee's last comment, up to 2,000 characters. New verb `watch` runs `sync` every `paperclip_check_minutes`; the module subscribes to `web.started` and starts it detached when such issues are open, recording it in `run/paperclip/<project>.json`. `send` returns a `next` saying how the ticket follows the issue. `Client.comments` takes `order`.
- `brief` resolves an explicit `issue=` first, then the HTTP gateway issue in `ctx.identity`, then `PAPERCLIP_TASK_ID`. A shared gateway call can read its linked Address without repeating the issue argument or inheriting another run's process context.
- Second review, 2026-10-12. An issue cancelled in Paperclip cancels its ticket through dispatch's `cancel`, which cancels the agent's turn; one done in Paperclip stops a running session with dispatch's `stop` first. A failed ticket is reported `in_review` with a question card only a person answers, try again or close it, instead of `blocked`. The ticket's questions, a dispatched agent's permission requests among them, go out as question cards and their answers come back through `map reply`; plain messages no longer cross out, since no verb writes them at a node (map tell is gone), and only the ticket's own questions cross. What was said crosses before the end is reported. `heartbeat` reads `inbox-lite`, leaves one `unrouted` comment on an issue it cannot place, and runs dispatch's `autostart` itself when Autostart is on. The monitor states its bounds, one attempt and a timeout. `status` names this install's own entry point. Jev's candidate Addresses are ranked by how rare the shared words are. New prompts `taken_state`, `unrouted`, `failed`; `message` removed. The chassis's `harness.IDENTITY` now strips the `PAPERCLIP_*` names from every process Metaform starts.
- Review fixes, 2026-10-12, each checked against Paperclip's server code at 4611d6e. `status` prints the process-adapter configuration with the command and its arguments apart, since Paperclip spawns without a shell. `heartbeat` posts a comment on each issue it takes and sets an `external_service` monitor, so Paperclip wakes the agent to check rather than reading the run as stuck; `sync` sets it again while the ticket is open. Comments on an issue and messages at its Address cross both ways while a Metaform agent works it (table `bridged`, column `comments_seen`; tables version 2). Paperclip's states are shown in the one status vocabulary. `send` takes the ticket before making the issue and gives it back on failure, resolves an assignee's short name to its id, lets Jev choose an agent when none is set, repairs a missing issue document on a repeat, and is offered over MCP behind `paperclip_agents_may_send`. `heartbeat` lets Jev choose the Address of an issue that names none (`paperclip_jev_route`) and says whether dispatch will start the ticket. A ticket the person cancels on an issue a Paperclip agent works cancels the issue. One link's failure in `sync` is listed, never raised. The issue document's brief line names the `map_where` call. New settings: `paperclip_check_minutes`, `paperclip_jev_route`, `paperclip_agents_may_send`. New prompts: `taken`, `ended`, `message`, `comment`, `jev_route`.
- The module, started from template 0.2.0: `status`, `brief`, `links`, `link`, `send`, `sync` and `heartbeat` over Paperclip's REST API, the `links` table tying each issue to a ticket at an Address, the issue document keyed `metaform` naming that Address, and five person-only settings. Ships disabled. Design and sources: `artifacts/swarm-2026-10-11/PAPERCLIP-INTEGRATION.md`.
