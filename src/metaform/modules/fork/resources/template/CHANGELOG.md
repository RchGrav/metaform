# Changelog

Each change to the module contract, newest first, so a module copied from the template can follow it.

## Unreleased

- `metaform.module.module_registry()` exposes discovered module states, sources, summaries and load problems.
  `metaform.data` exports the existing `sources_index`, `relative` and `placed` helpers for linked source references.
  Modules use these public services instead of private loader or data imports.

- MCP requires current tool instructions before execution. Ordinary verb guides are generated from declarations;
  optional `Provides('agent.tool.instructions', callable)` components supplement them. The callable receives
  `(ctx: Context, tool: str, op: str | None)` and returns exact named/versioned components. Canonical reads use
  `metaform://tools/<tool>/instructions[/<op>]`, with `metaform_instructions tool=<tool>` as an alias. Readers queue
  components through `ctx.queue_context`; only complete delivered bodies receive receipts. Changed effective
  content becomes due again. Catalog and instruction retrieval remain available. Tool usage stays with its
  declarations and module-owned prompts, without full startup catalogs or repetition in role duties. The template
  documents the provider contract without registering an inactive provider.

- Optional `agent.context.changes` providers supply compact changed-reference notices through `pending(ctx, session)`
  and acknowledge exact accepted revisions through `delivered(ctx, session, notices)`. Dispatch attaches notices to
  the next scheduled turn. Providers retain consumed identities and tombstones, coalesce relevant external changes,
  suppress own/unrelated writes, and leave newer concurrent revisions pending. No extra turn, polling or body
  broadcast is introduced. The template documents the contract without registering an inactive provider.

- `DataTx.cleanup(kind, identity)` applies recorded removal rules in the current transaction, including absent owners.

- `TableTx.rows_in(table, column, values, *, where=None, by=())` reads selected rows in index order as a tuple. The selected column and equal `where` columns must form a declared index's prefix. Repeated values are read once. Queries use at most 900 bindings, including `where`, and retain global index order across batches. Empty selections issue no SQL. This lets modules read children for selected records without scanning every child.

- A module's prompts.xml may hold `<rules>`, MCP-031: `<rule why="the reason">One sentence.</rule>`, each a rule an agent keeps while it works with the module. A rule without a why, or with no sentence, is a faulty declaration: the loader refuses the module and names the rule. `prompt_files.rules(folder)` reads them, as `(rule, why)` pairs in the order written, and `prompt_files.module_rules(id)` a loaded module's. The MCP server gathers the rules of every enabled module on the folder's surface into one block at the end of `metaform://glossary`, after the tool index, each line `[<module>] <rule> Why: <why>` under mcp's `rules_heading`, so an agent reads each once with the glossary. The template carries an empty `<rules></rules>` with the form in its comment; memory's rule shows one.
- A verb that can take long declares `task=True`, BASE-030: over MCP a client that declares the tasks extension, `io.modelcontextprotocol/tasks`, is answered at once with a task, in the one status vocabulary of `metaform.data.status`, while the verb runs on in the server, and polls it with `tasks/get` for the verb's result, or stops it with `tasks/cancel`; every other client and the command line wait for the result as for any verb. Hello's `wait` shows it. `tasks/cancel` is a request: it stops an `async` verb at its next `await`, and the task then reads cancelled; a verb run in a thread finishes, and its task completes with its result. A verb that returns `{'run': <run id>}`, a workflow run record the server itself advances to its end, such as an agent Metaform starts and steers, declares `task='run'`: the verb runs as ever, the run is the task, followed until it completes, fails or the person cancels it, and a run paused on the person asks its question in their AI tool. A task only for work the server advances by itself: a host gives the model a task's result only once it ends, so a verb whose result the calling agent must act on, such as workflow's `assign`, declares neither. A tool-call task is kept in the project for a day, so it outlives the server that ran it.
- A verb's `caution`, and a person-only setting an agent asks to change, are confirmed by the person in their AI tool where it can show a form (MCP elicitation, by multi round-trip requests on the 2026-07-28 wire) and `mcp_consent` is `ask`; elsewhere `confirm=true` and the refusal stand as before. A module declares nothing new for it.

- A module adds tools to the web GUI's toolbar and panes to its workspace: `Module` gains `toolbar`, a tuple of `ToolbarItem`, and `panes`, a tuple of `Pane`, both of `metaform.module`. A `ToolbarItem(id, title, description, icon='tool', verb=, arguments=, pane=, page=, link=, selection=, group='', placement='toolbar', order=100, shortcut='')` does exactly one of: run a verb of the module with fixed arguments, never an `open_world` one; show a pane; run a command of the page; open a link. A `Pane(id, title, description, icon='box', page=, verb=, arguments=, resource=, selection=, area='right', group='', visible=False, order=100, min_width=240, min_height=160)` shows exactly one of: a view the page draws, a `read` verb's result, a `.md`, `.txt` or `.html` file under `resources/`. `selection` names the noun that receives the selected node's address. The description is the tooltip: one line saying why a person uses it, not the title again. The icon is a name from `ICONS` or an SVG under `resources/`. `Module` refuses duplicate ids, an undeclared verb or noun, a pane verb that writes, a tool's undeclared own pane; the loader refuses a named file the module does not carry. `metaform.module.contributions(folder)` gives the chassis's and each surfaced module's, and `module_files(id)` a loaded module's package files. They are defaults: the web module lays the person's arrangement and workspaces over them, `web_toolbar`, `web_layout`, `web_workspaces` and `web_workspace`. The template declares an `about` tool showing its `about` pane, `resources/pane.md`; map, memory, dispatch, intake, web and the chassis declare theirs.

- A module numbers each item it writes at an address, and reads it back by that number, MCP-037: `Module` gains `item_read`, `item_read(ctx, address, number) -> Any`, a function or coroutine returning plain data with `kind`, `title`, `why`, `body` and `links`, or None. `metaform://<address>#<n>` and `map item <address>#<n>` call `item_read` of `metaform.module`, which asks each module on the folder's command surface in module id order and returns the first item found with its `item` reference and `module`. An item takes its number with `store.number(address)`, `DataTx.number(address)` inside an operation, or `TableTx.number(address)` inside `store.tables()` and a module's upgrade: one counter per address in the project's own database, counting up from 1, never reused, so a deleted item leaves a gap and an item moved to another address takes the next number there. `store.latest_number(address)` and `metaform.module.latest_item` give the last number taken. `metaform.data` gains `reference(address, n)`, `<address>#<n>` in lowercase hex, `parse_reference(text)`, which reads upper case too, and `shown_number(n)`. A write that makes an item carries a short title, and one that records knowledge or a decision a short why: `metaform.module.titled(ctx, what, title, why, why_needed=, title_needed=, why_step=)` refuses it with the one next step that names what is missing, on every surface but the page, the person's, where the title is the text's first line; `first_line(text)` gives a short single-line text as its own title. The template declares `item_read=None`; memory's `item_read` and map's `map_item_read` show it.

- A module tells an agent how much it holds at a node, never what, MCP-039: `Module` gains `node_count`, `node_count(ctx, addresses) -> Count | None`, a function or coroutine, where `addresses` are element addresses, the node an agent orients on and its direct neighbours. It returns `Count(one, many, at, legend)` of `metaform.module`: the word for one and for several, at each address `(how many, how many the last session there wrote, how many this session wrote)`, and `legend`, the line from the module's `counts` prompt naming the command that reads them, with `<address>` for the agent to fill. The map module draws the counts in `map where`, the ticket read and the hand-off once per agent session, and after that says only what changed; a hook that raises is left out. `Context` gains `session`, the agent session a call is made in, `seen(key, value)`, what that session was last shown under a key, and `calls(text)`, command lines named as the surface calls them, a tool over MCP. The template declares `node_count=None` and an empty `counts` prompt; memory's `node_count` shows it.

- `metaform.nonce` leaves the public base, BASE-008 and BASE-050: `request`, `read`, `update`, `close`, `reached` and `current` are gone, and `metaform <nonce>` runs nothing. A module hands work to an agent by the standard ways: dispatch starts the agent over ACP and sends the hand-off as its first prompt, with its identity in `METAFORM_ROLE`, `METAFORM_SESSION`, `METAFORM_WORK` and `METAFORM_NODE`; an agent not started over ACP reaches its work by its ticket id. State a module's work needs between agents is kept in a table the module declares, STORE-045, keyed by an id of its own, as the workflow module's `runs` keeps each run. hello's `noncedemo` is gone.

- A verb declares its effect, BASE-006 and MCP-003: `Verb(..., effect='read' | 'write' | 'remove', open_world=False)`. `read` changes nothing; `write`, the default, adds or changes and keeps what was there, as a new version, a history or a backup; `remove` deletes or replaces what cannot be had back. `open_world=True` marks a verb that reaches past the Metaform home and the project's map, to agents it starts or steers or to services on the network. Over MCP every verb is its own tool, `<module>_<verb>`, and these become its `readOnlyHint`, `destructiveHint`, `idempotentHint` and `openWorldHint`, each set explicitly. Hello's verbs show each effect.

- A module declares `REMOTE_AGENT`, a literal boolean read without running the module, BASE-060: True when an agent working on an already-mapped project from a hosted code-execution sandbox, through the CLI, has use for it; a module that needs a screen, local agents or compiled packages a direct run of a wheel does not carry declares False. An undeclared module counts as False. The Remote agent shape of `metaform build` and of the web GUI's build panel is the modules that declare True. The template declares False; a copy declares its own.

- Shipped and user modules share the public chassis services, BASE-004 and QUAL-016: `metaform.module` exposes home/project lookup, layer selection, command surfaces and aliases, module refresh and change announcement, version and command summaries, and project clear, removal, backup and restore services. `metaform.data` exposes Markdown/XML rendering, named reads with their text conversions, `Record`, `plain` and `NewerStore`. `prompt_files.module_commands` reads loaded modules' slash commands. These services keep extensions on the same implementation as shipped modules without private imports. Hello's `basedemo`, `base-restore`, `base-remove` and existing `follow` demonstrate them.

- Public module-owned DAO operations: `Module.data` declares `Data` with named `Operation` handlers, record contributions and item-write contributions. `DataTx.tables()` joins an operation's metaform tables to its current transaction. Hello's existing `visit` uses `count_visit`; the template includes `data=`. `Table.from_sql` adopts an existing table layout, with persisted `on_remove` rules and module-owned historical upgrade callbacks.

- A module's long-running process hears `map.changed` published in other processes, BASE-053: `ctx.listen(handler)` returns a `Listener`, a loopback port recorded under the home's `run/listeners`, and the bus hands each `map.changed` to every listener of another process, one more entry each in the deliveries. The handler runs in the listener's thread; close the listener when the process is done. The web module's `/api/notify` and its subscriber, and dispatch's subscriber and `changed` request, are gone. hello's `follow` shows it.
- A module keeps its own fields on a work record, BASE-035: `Module` gains `work_read`, `work_read(ctx, record) -> Any`, a function or coroutine, where `record` is the `WorkRecord`. The module keeps the fields in a table of its own keyed by the work id, STORE-045, so the work table's layout never changes for them. The map module's `work` with an id and no op calls `work_reads` of `metaform.module`, which calls the hook of each module on the folder's command surface with a context of its own module and the call's project, and puts each result that is not None under the module's id; a field the read holds already is never replaced, and a hook that raises adds `{"failed": ...}` under its id. The template declares `work_read=None`; hello's `todo` and `work_read` show it.
- A module's upgrade reads what a dropped column held, STORE-045: `upgrade(tx, found)` reads `tx.found_rows(table, limit=, after=)`, the rows as the version found held them, every column it declared included, in that version's key order, so it can carry a dropped column's values into a new column before the column goes. Outside an upgrade it is refused.
- A module adds to the read of a node, BASE-035: `Module` gains `node_read`, `node_read(ctx, node) -> Any`, a function or coroutine. The map module's `where` and `node` call `node_reads` of `metaform.module`, which calls the hook of each module on the folder's command surface with a context of its own module, the call's project and toggled layers, and puts each result that is not None under the module's id; a field the read holds already is never replaced, and a hook that raises adds `{"failed": ...}` under its id. hello's `node_read` adds `{"greeted": <count>}` at its own element; memory's adds a node's note and memories.
- A verb name may hold an underscore, `^[a-z][a-z0-9_-]*$`, so the memory module's commands carry the MCP reference memory server's names, such as `create_entities`, LAYER-013.
- A module's own tables, STORE-045: `Module` gains `tables`, a `Tables(version, tables, upgrade=None)` from `metaform.data`, each `Table(name, columns, key, indexes=(), place='metaform')` of `Column(name, kind='text', required=False, default=None)` and `Index(columns, unique=False)`. `place='metaform'` keeps the table in the metaform's store beside the map, removed and backed up with the metaform; `place='project'` keeps it in the project's store for the module, which a clear of the project's metaforms keeps. A verb reads and writes them in `with ctx.require_store().tables() as tx:`, one transaction on the store of the first table it touches, with `tx.insert`, `tx.update`, `tx.delete`, `tx.get` and `tx.rows(table, where, by=, limit=, after=)`; every read goes through the key or a declared index, and one that no index answers is refused. The chassis creates the tables, versions them with the module's own version, upgrades them when the version is raised, running `upgrade(tx, found)` in each store, and carries them through export and import. A module's data is no longer only a layer, STORE-022 corrected. hello's `visit`, `note` and `notes` show it.
- `Status` gains `instruction`, MCP-031: a message for the instructions agents read, put after the module's instructions prompt on its line under "modules available." when the status hook returns it. Its words come from the module's prompt file. web's autostart message, VIEW-015, shows it.
- Prompts, MCP-031: every prompt an agent reads is an element of the module's `resources/prompts.xml`, named for the prompt, and served as what is between its tags; no prompt's words are written in Python. A module reads its own with `prompt_files.text(resources.files(__name__), name)`, or `prompt_files.required` when a missing prompt is a defect. Its `instructions` prompt is listed in the instructions agents read under "modules available."; the default is `<instructions>Module name is active.</instructions>`, with the module's name. A status notice comes from the module's `notice` prompt and is shown by `metaform status`, and is no longer added to the instructions.
- The words after a nonce, BASE-050: words that name none of the module's commands reach the nonce's function as its words, so `metaform <nonce> next` runs the function as `metaform <module> <function> next` would, with the nonce reached. The function takes them through a noun, `Noun('step', ..., required=False, many=True)`; a function that declares no nouns still refuses them and names `metaform <nonce> help`. hello's `noncedemo` shows it, and replaces `task`, `brief` and `finish`.
- Nonces, BASE-050: a nonce is seven digits, the first never zero. `nonce.reached()` returns the nonce the running command came through, or `None` when it did not come through one, so one verb can be the module's entry and also its nonce's function. A closed nonce and one never issued print exactly `Error: Invalid or Unknown Nonce`. A closed nonce's record is kept, so its number is never issued again.
- The nonce service, BASE-050: a module imports `metaform.nonce` and requests a nonce with `nonce.request(module, function, value)`, where the function is one of the module's verbs. An agent runs `metaform <nonce>` for what that verb returns, `metaform <nonce> help` for the module's commands, and `metaform <nonce> <command>` for one of them; inside the verb `nonce.current()` is the record, `nonce.update` changes the value or the function the next run is sent, and `nonce.close` ends it. hello's `noncedemo` shows it.
- Work records, MAP-046 and STORE-042: the condition of an element or a join, a subtype join included, is its own record, apart from the map, written by any module through `store.add_work`, `store.edit_work` and `store.finish_work` and read with `store.work`; every element and join read carries `open_work`. The `flag` and `flag_note` fields of elements, joins and subtypes are gone. helloworld's `todo` and `done` show it.
- An element is its address, `name_length` and role, MAP-012 and STORE-009: `store.add_element(layer, address, name_length=, role=, refs=, extra=)` writes no name and no descriptor item, `Element` has no `name` and no `descriptors`, and every element read returns `reading` and `short_name`. The project's name for a functionality is the join's `name`: `store.add_join(..., name=)`, and `store.add_subtype(..., name=)` for the subtype join, MAP-020. An element recorded again at an address it held before is the same element, with everything attached to it, STORE-009.
- A subtype is a join of type `subtype`, MAP-030 and STORE-011: `store.add_subtype(layer, join, address, ...)` writes a join inside its parent join that holds the element at `address`, an ordinary element record. Its node is `Node('join', join_id)`; the `subtype:` node form is gone. `store.edit` and `store.correct` move a join with `receiver`, `provider` or `parent`, and never move an element, MAP-003 and MAP-015.
- `store.where(address, full=False)` is one read of an address: the element, what relies on it, what it relies on, the subtype joins inside those joins and the one holding it, its open work records and the layers in context at it; its plain data leaves out ids and empty fields unless `full`, STORE-025.
- Nothing a module sends is refused for its content, BASE-044: a ref whose key or value is not text is kept in the record's `extra` under `refs` with a notice, STORE-012; over MCP a `str` noun or a text setting sent another JSON value reaches the verb as its JSON text with a notice, BASE-035 and MCP-005.
- The topic `map.changed`, `{project, base_id}`: the chassis fires it after any command that changes a project's map, and the web server after the page's own writes, so a module does nothing to announce its writes and any module can subscribe; the web module passes it to its server, which pushes it to each open page, VIEW-018. The chassis fires it when the command ends, so a module publishes it itself, after each write, for work done outside a command, in a spawned task, and for writes made inside a verb that runs on for a long time, such as `dispatch run` or a server run in the foreground, so an open web GUI shows them while the verb runs; dispatch's runner shows it. helloworld's greeting shows it.
- Nothing polls for a change and nothing a person or an agent waits on blocks behind slow work, QUAL-015; what happened is published.

## 0.3.0

- `Verb` gains `transport`: a transport verb, such as `mcp serve`, runs whatever the folder's command surface, CLI-022 and MCP-004.
- The common base gains `tool_arguments` and `setting_value`, which check a tool call's arguments as the command line does, MCP-005; `on_this_system`, BASE-016; and `feedback`, `save_report`, `list_reports` and `read_report`, BASE-045.
- A write that does not fit is stored as given and its result carries `notices`, each with `where` and `message`; only a call that cannot be read raises `Stop`, BASE-044 and STORE-026.
- Elements, joins and subtypes carry `flag` and `flag_note`, MAP-046 and STORE-042.

## 0.2.0

- `Verb` takes `nouns` as `Noun` records and `switches` as setting keys; `Adverb` is gone, CLI-012 and BASE-035.
- `Context` carries `project`, `store`, `nouns` as a dict, `switches`, `surface`; `Context.data` is gone, keep data as a layer through `ctx.store`, STORE-022.
- `Module` gains `start`, `stop` and `status`; `Status` adds status lines and one notice, BASE-018 and BASE-035.
- A module declares `SHIPS_DISABLED` and `DEPENDENCIES` as literals, read before import, BASE-015 and BASE-017.
- A verb may declare `supported_os` and `surfaces`, BASE-016 and BASE-035.
- A verb returns its result; the CLI and MCP show the same data, BASE-036.
