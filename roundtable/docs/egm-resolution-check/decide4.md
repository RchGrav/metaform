1. **Shell commands from the OpenRouter adapter are approved automatically and are not confined** (adapter row 4). The adapter's permission request for `run_command` names only the session folder, so Roundtable's policy approves it every time. The command can reach anything the user account can, and it sees every environment variable except the three Roundtable secrets. This matches the residual risk recorded with the owner's permission decision of 2026-11-05, so it is a known, accepted risk, not a new fault. What is wrong is that the adapter's description says its tools stay inside the session folder. Other credentials in the user's environment (cloud keys, Git hosting tokens) reach every harness this way, not only this adapter. Removing more variables would be a change to the permission design and needs the owner. Check: run a table with a test variable set in the host environment and confirm that `run_command` can print it.
2. **The registry environment filter misses variables that change what code is loaded** (launcher row 5). A remote registry entry can set PYTHONHOME, uv and pip package-index variables, or certificate overrides. The risk added is limited, because the registry already names the package to run, but the code's own comment promises more than it delivers. Check: add the names, then run the existing test `registry_cannot_set_loader_or_path_variables` extended with them.
3. **Registry package entries are marked available without checking that npx or uvx is installed.** This is outside my rows but sits next to launcher row 15: `parse_registry_with` sets `available` from whether a launch exists, which overrides the PATH check that `entry` made. On a machine without npx, such an entry looks launchable and fails only at start. This is not a safety issue, but it is a "do not get stuck" issue. Fix: keep the PATH check for the npx and uvx branches.
