## Findings that conflict with sources

### F1. `goto` delivers context

L-10 and P4 state: "`goto` stays a read and does not deliver."
R-5.30 states that `goto` "returns what is directly linked there" and "delivers this once per context".
The owner's words in R-5.30: "goto only dumps new info IF the info changes its once per context".

The accurate statement is narrower. `goto` delivers layer names, skill frontmatter and record counts at the address. It delivers no records from other addresses.

**Consequence:** the specification puts once-per-context delivery tracking on `goto`. R-5.31 says a ticket "does for the agent what goto does". A delivery design that excludes `goto` omits the only delivery path the specification defines.

### F2. The resolver is outside the specification

P4 places device CEL delivery on the resolver path (L-10).
`TOPOGEE-SPEC.md:556` lists "The context resolver, Composer, Facilitator and ACP harness in `TOPOGEE.md`" under "Not in this document yet".
The L-60 report records the resolver as "not built". The more exact status is "not specified".

**Consequence:** a build cannot verify L-10. The owner must first specify the resolver and its relation to `goto` and tickets.

### F3. C-5 treats a decided store as open

Topic 03 asks P7 to "Rule on C-5". The ledger asks the owner to weigh "§9 'JSON store, SQLite log' against Ladybug in world-ideas".
The map store is already decided:

- `DECISIONS.md`, Settled requirements, owner 2026-11-03: the map, layers, settings and registry are JSON files under `~/.metaform`, written only by the map server. This "replaces 'LadybugDB is selected'".
- R-4.1 is Decided: JSON by default, SQLite where tabular data fits better, Ladybug where it fits better.
- `docs/world-ideas.md` does not propose Ladybug for the map. Its Tested table (`:122`–`:130`) measures Ladybug databases only.

L-20 has two further errors:

- "The map stays JSON." The map is built on Ladybug today (`mcp-server/src/store.ts:10`; R-4.1 status "Built on Ladybug, not yet on JSON"). The accurate verb is "moves to".
- "Ladybug databases are per world." I found no owner source for this. World-ideas `:125` tests 200 databases in one process, not a per-world layout. Metaform roundtable 7 (A02) proposes "One active writer per world", and that file is a record of past proposals.

**Consequence:** the open storage question covers world storage only. P7 should not re-rule the map store.

### F4. L-3 decides an item the owner left open

L-3 states: "Bevy never stores wants."
R-2.11 is Decided: with a chassis present, a module uses the chassis "as its data source for the parts that matter for deep integration". It adds: "Which parts move to the chassis is decided when the chassis is specified."
`DECISIONS.md:124` says the chassis uses Bevy, and the map server "passes control of its integrated data to the chassis".

L-3 therefore excludes, in advance, wants from the data the chassis might control.

**Recommendation:** scope L-3 to the world server. Leave chassis data control to R-2.11.

## Design gaps in the ratified rows

### G1. The link CEL stores runtime state

L-7 stores `status` (`bound`, `stale`, `unbound`) in the link CEL.
L-3 says the map never stores runtime component state. R-4.4 makes the map server the only writer under the home.

Inference: each world restart or despawn becomes a map write on the project's write queue (R-4.7).

Stale-ID test 2 requires `unbound` "within the L-6 budget". L-6 measures from map commit to world application, which is the opposite direction. No method measures the world-to-map direction.

**Option (`judgment`):** hold `status` in the link runtime beside the boot token. The CEL keeps `world` and `instance_id`, which both persist.

### G2. "Common interface" might reuse an owner term

Topic 03 asks P7 to define "the common interface between map server and world server".
`TOPOGEE-SPEC.md:558` lists "The three topologies and the common navigation interface" as unsettled owner material.

Inference: P7 might apply the owner's term to a narrower boundary. L-2 already names that boundary "the world link". P7 should use "world link" (TASTE rule 7).

### G3. Success criterion 8 targets the method

Draft criterion 8 ends: "No gain is claimed without it."
`docs/countermeasures.md:94`: "A poor result implicates the build first." `docs/pushback.md` T2 aims every test at the build.

**Recommendation:** state criterion 8 as a measure of what the build delivers, so a poor result implicates slicing, delivery or the store.
