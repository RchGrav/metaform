# Inference Metaform
## Advance Inference Amortization through Functional Understanding

**Rich · Independent developer**  
Original preprint: September 26, 2026. Revision manuscript: October 27, 2026.

## Abstract

The Inference Metaform develops substantive understanding before work and makes that understanding available for subsequent inference. It represents an artifact under examination through functional types, receiving purposes, and Encounter Functions rather than identifying it with its current implementation arrangement. Meaningful namespace Addresses engage a model's primordial type understanding; receiver-owned purpose records connect that orientation to the particular artifact. The resulting functional topology supplies locations for memory, specifications, tasks, skills, documentation, and further inference. Contextual layers preserve these contributions separately and disclose them where they bear on the work. A graph realization using LadybugDB and Cypher selects and presents context from this functional topology, independently of any entity-component runtime. Where Bevy is used for simulation, it supplies an ordinary Entity-Component-System (ECS) runtime with shared Resources; it does not define the Metaform graph. The same contextual arrangement accommodates functional Address navigation, simulated spatial encounters, and physical sensor zones without equating their distance measures or sensing fidelity. High-rate local execution remains separate from model reasoning: an edge reflex changes device behavior, an event records that change, and an agent harness delivers the relevant context through a subsequent agent turn. Loaded skills remain with their context as the agent moves; handoff establishes a new context with a concise continuation and references to retained understanding. The paper distinguishes these delivery mechanisms from the inference that produces the functional account. Historical project records and a supplied intake with indivisibly coupled elements provide inspectable examples; performance improvements remain empirical questions. The contribution is a continuing process in which prepared understanding becomes reusable material for further reasoning while unnecessary context delivery and repeated inferential work are reduced.

**Keywords:** inference amortization; functional understanding; contextual topology; progressive disclosure; addressable memory; knowledge layers; agent systems; embodied interfaces.

## 1. Conception and independent origin

The Inference Metaform is organized around a practical question: **what reasoning can be performed in advance to offset reasoning that an agent would otherwise have to perform while doing the work?** The answer includes understanding what a workpiece is, distinguishing its functional parts, establishing who receives their effects and why, and preserving those relationships for later implementation, examination, and synthesis.

An agent can possess extensive information about a project while still lacking this orientation. Knowing a file does not establish its contribution. Recognizing a dependency does not preserve the reason it exists. Remembering a conversation does not necessarily identify which of its conclusions applies to the next task. Reconstructing these relationships repeatedly is an inferential obligation, not merely a retrieval operation.

Metaform develops useful portions of that understanding in advance. Its principal subject is the amortization of inferential effort. Context efficiency is a complementary objective: prepared understanding should be delivered without repeatedly loading irrelevant material or reproducing bodies already present in the working context. These objectives are related but distinct. A larger prepared input can contain more completed semantic work than a shorter input that leaves the executing agent to originate the same relationships.

The author's account describes six years of independent work with AI models, including self-authored context-management and semantic procedures predating GPT-3's completions API and six months refining the expression presented in the original preprint. The research comparisons in Section 14 are subsequent connections, not a claimed derivation of the method. The account of origin is attributed to the author; the supplied material is not an independently collected historical study.

The name is singular: **Inference Metaform**. Generalized type understanding and artifact-specific understanding participate in the same representation. They are not mandatory separate systems with different Metaform names.

## 2. What preparation produces

Preparation produces conclusions about what an artifact is doing, not only descriptions of its contents. An intake of a plugin system can identify the module author as a receiving element, the ability to add a capability as that receiver's purpose, and the declaration-and-loading arrangement as the Encounter Function serving it. Later work can reason from this relationship instead of rediscovering it from scattered source files.

The canonical intake establishes the **Base Functional Map**. Its input can be a specification, an implemented artifact, or their combination. In a greenfield project it captures intended functional relationships. In a brownfield project it examines the implementation and the requirements it appears to serve. Disagreement between intended and observed behavior becomes an addressed finding rather than being silently resolved in favor of either source.

The map is not a transcription of directories, classes, or packages. A functional element can span several implementation locations, and one file can realize several contributions. References connect functional understanding to those locations without making the locations its identity.

Preparation continues as the artifact evolves. New functionality can introduce an element or a Join; revised understanding can refine an existing record. A task that introduces a capability therefore carries the corresponding map work as part of its functional description. The base is persistent, but it is not complete for all future versions of the artifact.

Additional operations use the map as the subject of further inference. They can develop implementation knowledge, identify a missing contribution, construct a task-specific skill, or explain a changed user journey. Their results become contextual layers and addressed records. This is a connected process, not a mandatory sequence that every task traverses in full.

## 3. Primordial type understanding and prompting surfaces

### 3.1 Meaningful Addresses engage existing understanding

A model enters a task with understanding of kinds of things: code, engines, interfaces, documents, photographs, queues, and their characteristic relationships. Metaform calls this **primordial type understanding**. The term concerns the orientation engaged by meaningful types; it does not claim that an Address selects particular neurons or internal activations.

The author's address-only example uses prompts of the form `write 10 best practices for [address]` at four scopes:

```text
code
code.engine
code.engine.game
code.engine.game.fps
```

The recorded examples distinguish general code practices, engine concerns, game-engine responsibilities, and first-person game-engine concerns. The ancestry establishes the domain in which the final distinction is interpreted. These examples illustrate the Address as an input for inference, not merely a retrieval key. Their generated practices are example content rather than universal requirements for all instances of those types.

### 3.2 Every prefix provides a perspective

An **Address** narrows semantically from trunk to leaf. Reversing its segments yields an intelligible functional name. Every prefix is itself a usable type and a perspective from which further inference can proceed.

General knowledge belongs where it remains applicable. A concern that applies to engines generally need not be copied beneath every engine specialization. A first-person targeting concern does not become a concern of all code because it is visible from a broader perspective. Ancestral application and broader visibility are different relationships.

The **artifact type (AT)** groups artifacts by shared functional characteristics. **Namespace scope (NS)** establishes the scope of the AT. The artifact roots are `code`, `document`, `media`, `data`, and `collection`; `upstream` and `downstream` locate external supplying and receiving perspectives. These are functional naming conventions, not a fixed directory layout or prescribed number of segments.

### 3.3 Functional and project names have different jobs

The Address supplies a functional proper noun; the `name` field preserves the canonical project name. In the original project example, `code.system.plugin` provides functional orientation while **module contract and loader** identifies the project's realization. The `name_length` value specifies the short-name lookback within the Address.

A dotted path is not an arbitrary property container. Encoding, medium, and implementation language belong in contextual descriptions when they condition the work. They do not automatically create a new functional element. A named encoder can be a function; a file extension appended to an unrelated functional Address is a different matter.

## 4. Functional relationships and the shape of the workpiece

### 4.1 Entity, element, and receiving perspective

The **artifact under examination (AUE)** is the thing or collection being examined, created, modified, or used. Whether it serves as an asset depends on the current relationship. The method applies to software, specifications, documents, narratives, photographs, and other artifacts.

An **entity** is a whole at the scope of examination. An **element** is a nameable part considered as a type. Examining an element's internal composition makes it an entity for that examination; this perspectival change does not create another identity record.

A **receiving element (RE)** bears an **Operative Purpose (OP)**: the active goal recorded in its purpose record. A **providing element (PE)** supplies the **Encounter Function (EF)** through which that OP is served. The same element can provide outwardly and receive internally. RE and PE describe participation in a relationship, not fixed classes of agents or components.

The **cestui que use (CQU)** is the vested receiving party whose purpose drives improvement in that type of artifact. Identifying the CQU requires reasoning about the artifact's contribution. Substituting the operator or a generic end user would omit that reasoning. Purpose traces connect internal requirements to the external receiving purposes they ultimately serve.

### 4.2 A Join retains the reason

A **Join** reifies a receiving relationship. Its purpose record is held by the RE and records the OP, the PE's EF for that encounter, the information flow direction, and the contributing elements. Knowledge about that relationship is kept at the Join. The EF is not a global provider property or a layer independently defining every use of that provider.

Reification makes the relationship itself addressable. A discovery can concern the way two elements serve a purpose rather than either endpoint generally. A message can be kept at their Join so later participants find the discussion where it matters. Any agent can read that addressed message or contact another agent; its location determines contextual presentation, not a private channel between endpoints.

The original module-author example records why the module contract and loader are needed: a capability should be declared once and exposed through the system's shared facilities. The Join retains this reason together with the relevant contribution. It is more than an edge indicating that an author and a module system are connected.

### 4.3 Convergence preserves load-bearing structure

A **defining element (DE)** supplies the functionality whose loss would prevent the AUE from remaining the same type. A **substantial element (SE)** contributes to the DE's service of the CQU's OP, including contributions that are weak, replaceable, or candidates for improvement. A **notable element (NE)** identifies an essential demand or requirement on the environment. A **parametric** quality is tunable without becoming an independently named functional element at the represented scope.

Intake surveys the artifact, traces receiving purposes and their providers, then anneals the representation. A subpart absorbed into a load-bearing parent remains represented through the appropriate purpose record. Its contribution is not discarded, nor does it acquire an unnecessary independent copy of the parent's OP.

### 4.4 Indivisible coupling preserves the work unit

**Indivisibly coupled elements (ICE)** are parts whose separation would break their functionality, meaning, or operation. A **Block** is their numbered grouping, such as `BLOCK_001`. Membership is established by the functional trace and its evidence; containment, a shared file, or an ordinary dependency does not establish it by itself.

The practical consequence is work composition. When an assignment changes a Block's coupled contract, its participating elements are kept in one work unit and one worktree. Several people or agents can contribute to that unit. The grouping keeps the interdependent change together; it does not assign exclusive ownership of the elements.

The supplied Hermes correction demonstrates this distinction with explicit groups for transcript settlement, an RPC client and server, task-graph publication, sprite-atlas production and interpretation, and plugin/environment publication and recovery. These groups concern shared functional contracts, not arbitrary file neighborhoods.

## 5. Function, Encounter, and scoped propagation

### 5.1 The deliberate Unloaded Definition

**Function** concerns operative capability. **Encounter** concerns the form through which something is expressed, realized, used, or experienced. **Encounter Function** accommodates both the encounter of a functionality and the functionality of an encounter. This **Unloaded Definition** lets the receiving relationship determine the appropriate sense without reducing the term to a programming callable, a graphical widget, or an instantaneous event.

A timer's countdown and the audible encounter that gains a cook's attention illustrate the distinction. A declaration can likewise be an encounter through which a module author adds a capability. The appropriate EF is the active account of how the particular receiver's OP is served.

### 5.2 Realization conditions reasoning without replacing the type

A disk utility can retain its functional Address while a contextual record describes a C realization. That realization affects reasoning about memory, interfaces, dependencies, and error behavior. The consequences apply at the relevant attachment scope and its descendants. A broader view can reveal the realization without making unrelated sibling branches C implementations.

This account keeps language-specific knowledge in a realization description rather than requiring a language suffix in the base namespace. It preserves the intake's functional naming and the original example's distinction between backward visibility and forward application.

Preparing realization-specific understanding is another amortization opportunity. A later implementation task can receive the relevant consequences without originating every consequence in the same episode as the change.

### 5.3 Spatial observations are specialized Encounters

A spatial receiver can need an account of nearby surfaces. A virtual provider can supply that account through a calibrated grid of 64 raycasts. A physical provider can supply it through an 8×8 ToF sensor and its driver. These are distinct realizations of an observation interface serving a recorded OP.

Their shared contract specifies the meaning of the observation: zone arrangement, coordinate frame, units, capture time, source identity, quality, and calibration. A shared array shape alone is insufficient. In the selected VL53L5CX profile, reported depth is perpendicular to the sensor plane; a simulated ray's slant length therefore needs conversion to axial depth before it supplies the same field [10, 11].

The provider's origin remains explicit. An ideal raycast does not reproduce a physical zone's footprint, multiple returns, optical effects, or uncertainty merely by returning the same JSON fields. Interface compatibility supports reuse of reasoning and tooling; it does not establish physical equivalence.

### 5.4 Observation and semantic interpretation remain distinguishable

A range matrix records observations. An assertion that it depicts a person, an opening, or a moving object requires another inferential or computational contribution. That contribution records its inputs and method separately.

The spatial interface can expose structured observations without making imagery the primary input. Camera resources remain available where the work requires them. Neither the functional map nor the spatial observation contract presupposes that every agent has a body, a camera, or a rendered scene.

## 6. Exact relational identity and change

For a Type T, the semantic identity is the exact set:

**C(T) = { (r_i ∧ p_i ∧ e) }**

Each conjunction binds a receiving element r_i, its Operative Purpose p_i, and the Type's single Encounter Function e at the represented resolution. It identifies who or what receives the effect, why that receiver needs it, and how the effect is realized or encountered.

The set is exact. It is not a lower bound, partial signature, similarity score, or confidence estimate. A materially different Encounter yields a different Type or variant through an additional typological distinction. It does not add another EF to the same exact Type.

This distinguishes **mutation** from **transformation**. Mutation changes a realization while preserving the relevant semantic identity. Transformation changes the represented thing in that relational sense. The distinction concerns semantic reasoning rather than preservation of particular files, classes, or implementation text.

A broad provider record can participate in several receiver-owned Joins. Those records provide evidence for reasoning at the appropriate resolution; they do not automatically prove that every Join describes the same exact T. Likewise, a shared interface between physical and virtual observations does not establish identical Encounter-specific Types at every level of description.

A refactor can preserve receiving relationships while changing arrangement. A port can preserve a broader contribution while introducing another realization-specific Encounter. Keeping the same broad Address is useful orientation, not by itself a proof of semantic equivalence.

## 7. Addressable memory, layers, and contextual projection

### 7.1 Understanding has a functional location

A finding can concern an element or a Join. Those objects provide locations for memory, documentation, specifications, and later work. A general note about a plugin system belongs at the element; an explanation of why a particular receiver needs its contribution belongs at that receiving relationship.

Location contributes meaning without requiring every available record to be delivered immediately. A participant can encounter a short description and follow a reference for the full material. The retained record remains available when another task reaches the same location.

### 7.2 Composed element layers preserve distinct questions

A **composed element layer (CEL)** is a knowledge layer over the tripartite, non-manifold functional graph through which agents index and understand an AUE. As the cel-animation analogy suggests, layers can be taken out of the current view and restored without removing the underlying representation.

A layer's variable identifies the question or perspective it addresses. Skills, tickets, specifications, documentation, memories, and implementation references are possible contents, not an exhaustive layer taxonomy. Payloads can be kept locally or referenced at the tool or service that owns their native format.

**Objective Purpose** belongs to the specification layer. It states the outcome a particular specification seeks to realize. **Operative Purpose** remains the active goal of the intake's RE-owned purpose record. A specification can elaborate an OP without replacing the intake term. EF remains the recorded how of the receiving relationship.

Informational knowledge supplies observations, explanations, and decisions. Imperative knowledge supplies instructions or acceptance criteria when selected for that role. Delivery preserves the distinction rather than silently converting an observation into a requirement.

### 7.3 Selection is separate from retention

The original local-selection expression is retained:

```text
outgoing = (incoming & mask) | select
```

The starting selection is established separately. A missing local rule leaves it unchanged. A local mask removes a layer from the projected view; a local selection restores or adds it. Restoring a layer on one branch does not restore it on a sibling branch. An explicitly empty selection differs from an unspecified selection.

Hidden layers remain stored. Recorded derivation dependencies explain when a derived layer leaves the same view as its source. Direct addressed reads remain available. The intake is the base map, not another selectable overlay, and refinements preserve its earlier forms.

Selection controls the next delivery. It does not erase a skill or observation already incorporated into an agent's current context.

### 7.4 The graph realization supplies place-based context

The selected realization stores the Base Functional Map, RE-owned Joins, and contextual layer attachments in LadybugDB. Cypher reads their relationships and assembles place-specific context for an agent [8]. This **context projection** is a selection and delivery operation, not a new entity-component architecture. A Metaform element is a functional type whose entity/element role depends on the scope of examination. Its Address is not an engine-local entity identifier, and LadybugDB is not an ECS runtime.

A virtual implementation may use Bevy's established **Entity-Component-System (ECS)** architecture: entities identify runtime objects, components hold associated data, systems process that data, and **Resources** hold shared data used by systems [9]. A virtual sensor system or physical-data adapter can provide normalized observations for the same MCP contract without changing Metaform's semantic model. Bevy is a possible execution adapter, not a requirement for functional Address navigation or the physical sensor bridge. The commonality across the three paradigms is contextual delivery at a functional or spatial place, not a common ECS or ECR data model.

A place's task harness is composed from its functional relationships and contextual records. The facilitator examines the PE's EF in the RE-owned Join together with the receiver's specification-layer Objective Purpose. It creates or reuses a skill and records the specification, tool, and source relationships that explain its use. Cypher subsequently retrieves those prepared bindings. The query assembles already reasoned context; it does not infer a semantic intersection from arbitrary prose on every visit.

Ancestry supplies general context. Joins supply receiving relationships. Spatial geometry supplies observed neighborhoods. These three relations are distinct even when they contribute to the same projection. An agent can go to any Address and receive the tools and context attached there and through its applicable lineage.

## 8. Context-efficient delivery and continuing work

### 8.1 Progressive disclosure is a delivery contract

Arrival supplies orientation: the target Address, relevant receiving purposes and Encounters, current work, and descriptions of the attached material. Larger specifications, documents, memory bodies, and skill files are read when needed. A descriptor identifies its source and version so that a subsequent read resolves the same material or explicitly identifies a newer one.

The objective is minimal unnecessary delivery, not minimal understanding. Repeated unchanged bodies can be omitted when the host has already delivered them to the same context. Large collections are paginated with explicit continuation. A response distinguishes a complete result, an empty result, and a partial result; absence from one page does not become absence from the system.

MCP supplies tools with typed input schemas and descriptive annotations, addressable resources, and change notifications. Its official skills extension serves skill files through resources and carries their manifests [5, 6]. Metaform's contribution is the functional selection and lifecycle of the material presented through those primitives.

### 8.2 Availability, loading, and retention are different events

A new place can disclose an unfamiliar skill. A notice of that availability is not the skill body and does not establish that the model has received its instructions. The host records resource delivery and skill loading separately from discovery.

Once loaded, a skill stays with that agent context as the agent moves. The next place changes the discoverable local material, not the accumulated knowledge already supplied. Handoff ends that accumulation for the predecessor's context and starts the successor with the work's continuation and source references. The successor acquires the skills required at its own place.

Compaction requires explicit integration with the host. A reference implementation preserves loaded skill bodies in a host-managed retained segment or reconstructs that segment after an observed compaction. When a harness does not expose its retained context, the record can establish delivery but cannot establish what the model still has. This is a boundary of observability, not evidence that an instruction survived.

### 8.3 The edge reflex and the agent wake-up operate on different clocks

The local controller consumes sensor observations and executes physical reflexes independently of model turns. If a configured zone closes in, the controller can stop the motor and record the resulting event without waiting for graph traversal, MCP transport, or an agent response.

The bridge publishes the observation and event as resources. A resource-update notification reaches the host; the host reads the event and schedules a turn in the target context. In the ACP realization, that turn is initiated with `session/prompt` [7]. MCP notification delivery and model execution are separate operations. The event preserves its physical origin rather than masquerading as a new user request.

The latest matrix and the event history serve different purposes. A matrix reports current state. A journal preserves a threshold crossing even if the state clears again before the host reads it. Arrival, discovery, and incident events can therefore share context-delivery machinery without turning each sensor frame into an agent turn.

Sensor rate, local controller rate, transport latency, and model-turn latency must be reported separately. For example, an 8×8 VL53L5CX profile operating at 15 Hz does not supply fresh observations at the rate of a faster controller loop [10]. No claim of instantaneous reasoning follows from a hardware interrupt.

### 8.4 Shared understanding supports independent participants

The functional map is shared infrastructure rather than one agent's workspace. Multiple humans and agents can participate simultaneously, use the same addressed understanding, and contribute findings to it. Equivalent place queries have equivalent results regardless of the participant's identity.

Identity, context, and embodiment are separate records. An agent can continue through several contexts; a person can interact through several clients; a body can be associated with a participant without becoming that participant's identity. Each participant has its own position, view, and delivery history. Shared knowledge does not imply a single shared model context.

These foundations accommodate interactive work without prescribing its presentation. A 3D environment, a conventional interface, or a screen-sharing experience can refer to the same functional locations and interaction records.

### 8.5 Efficiency is measured across the lifecycle

The relevant accounting includes preparation, maintenance, context resolution, and execution. A useful comparison is the accumulated cost of preparing and reusing understanding against the cost of repeatedly reconstructing it during otherwise comparable tasks.

Input tokens, repeated bytes, loaded skill bodies, model calls, resolution latency, and task outcomes are separate measures. A lower token count alone does not establish better reasoning; a longer prepared input alone does not establish useful amortization. The evaluation should also distinguish retained knowledge from newly generated explanations and state the source revisions used.

### 8.6 Secondary, deferred processing: project-grounded lexicalization

Project-grounded prompt lexicalization is an optional additional producer. It resolves a request's referents to canonical project names and Addresses while preserving the requested operation. “Review error handling in the plugin system” can be grounded as a review of the **module contract and loader** at `code.system.plugin`, without diagnosing a defect or inventing an execution plan.

This processing is secondary to the functional map and its context-delivery contract. It can use the same relationships, layers, and memory, but ordinary navigation and work do not depend on it.

## 9. Perspectival reasoning and blindspot challenges

Functional grounding and implementation inspection cooperate. A critic can examine the Metaform alone or inspect the artifact with its Metaform. The represented purposes supply a perspective separable from the present implementation arrangement; they do not require source code to be withheld.

A **blindspot challenge** identifies a function or Encounter the design appears to lack and asks for a substantive project response. Three responses distinguish useful situations: the concern was considered and adds no benefit, with the reason; it has not been considered and has relevant consequences; or it is already handled elsewhere, with the location and functional relationship that fulfill it.

These responses are explanations, not merely labels. A function can be fulfilled through several elements even when a critic does not see a local implementation. Conversely, the existence of a node does not establish that its consequences were considered. The exchange is not reducible to counting unvisited nodes or missing edges.

In a derived module-development example, a question about separate settings persistence can be answered by identifying the chassis's existing settings facility and the declaration through which the module uses it. Retaining that rationale at the receiving relationship prevents later work from repeating the same investigation or creating a duplicate mechanism.

The method keeps the criticism, response, evidence, and subsequent work distinguishable. A recorded state is not a substitute for the reasoning that supports it. The supplied materials do not establish that every such exchange has an integrated automated producer.

## 10. Provenance and the lifecycles of understanding

Understanding becomes more reusable when its origin and participation remain inspectable. A produced layer can name its source records, generating operation, prompt version, model, role, and artifact revision. A reference can identify the exact implementation or document passage supporting a claim.

Different records retain different lifecycles. Intake establishes a base and subsequent refinements. Knowledge layers retain their own question, state, and source associations. Mutable project memory records current understanding. Prompt history records authored instructions and their versions. Artifact origins and variants record realizations. Event and interaction histories record what occurred. These records can be connected without asserting that they all share one versioning mechanism.

For reproducible composition, a named snapshot freezes the particular source records used by that operation. This does not require every live memory write to become an immutable project-wide revision. It requires the producer to retain the evidence it actually consumed.

Provenance identifies a contribution's origin, not superior standing for its author. When participants contribute different accounts, the representation retains the accounts and their supporting evidence at the relevant place so the difference can be examined.

## 11. A modular realization and its boundaries

### 11.1 Existing facilities are implementation references

The repository supplies a modular realization with declared operations, shared context and data facilities, MCP surfaces, agent sessions, addressed memory, and user-facing views. Its agent and workflow documentation also describes instruction delivery, versioned responsibilities, and continuations. These are useful implementation references, not a requirement that the new functional specification inherit the repository's complete product surface.

The original preprint described a particular source snapshot. Its observations about modules, storage, and producer boundaries remain observations about that edition. Later source documentation and the target contracts in this revision are identified separately; a design described here is not thereby claimed to be integrated in that snapshot.

### 11.2 Runtime frameworks are adapters, not the functional model

The target architecture separates graph storage, context projection, protocol adaptation, and local execution. A component can use an existing implementation where its behavior matches the contract. The contract specifies data meanings and observable interactions rather than requiring a common programming language.

Bevy is a reference ECS framework for virtual sensor execution and browser-hosted realizations. Its Resources hold shared runtime observations and commands; they do not turn LadybugDB or the Metaform functional map into an ECS. ROS data conventions supply useful spatial interoperability. Other engine-specific MCP services can be examined as adapters, but their project-specific interfaces do not define Metaform's semantic model [9, 12].

### 11.3 A functional description does not invent execution behavior

Naming a graph element “event bus” does not establish ordering, concurrency, durability, or detached delivery. Those behaviors belong to its realized interface. Likewise, a `HAS_SKILL` edge does not load a skill, a notification does not run a model, and a specification reference does not establish implemented behavior.

The technical specification following this paper supplies concrete contracts for these boundaries. Database execution, protocol interoperability, and physical behavior still require implementation evidence. Their specification is distinct from a report that they have been demonstrated.

## 12. Forming the workpiece through intent

### 12.1 A formboard, not a frozen implementation

The author's formboard analogy describes meaningful positions through which work can be organized and findings attached. The representation supplies a functional arrangement for constructing and examining something. It does not freeze the present material or require future realizations to occupy the same files.

User intent can preserve relevant receiving purposes while changing realization, or deliberately transform the relationships that define the artifact. The Metaform makes those relationships available as the subject of the decision.

A composer translates a specification into functional work records. A facilitator prepares the skill context for that work. Both retain the link to the receiving purpose. ICE Blocks preserve indivisible work composition where the functional account establishes it.

### 12.2 Refactoring and porting

A capability spread across several files can retain its functional identity while references locate its present realization. Refactoring can reconsider the arrangement through its receiving purposes. Porting can develop knowledge appropriate to a different realization and attach that knowledge at the relevant scope.

These are uses of prepared understanding, not claims of a universal automatic code transformation. An Address and its Joins orient the work; they do not alone prove behavioral equivalence of generated code.

### 12.3 Documentation and specification recomposition

Documentation recomposition has a narrower, executable scope. A programmatic stage selects the functional and contextual records associated with a named repository commit and assembles an ordered account. A comparison identifies changed files and records. A composition agent interprets the changes against the receiving relationships and updates declarative explanations and user journeys.

The distinction between change detection and interpretation matters. Git identifies source differences; it does not independently establish their functional meaning [13]. The composition agent preserves the distinction between specified behavior, observed implementation, and unresolved correspondence.

The output is a standalone specification or documentation artifact with source references and production provenance. It can reorganize explanations and revise journeys to reflect the selected revision without introducing new features into the underlying artifact. Unchanged, still-supported explanations can be reused rather than regenerated.

### 12.4 Other artifacts retain their particular meaning

In a document, one section can receive evidence from another for the purpose of supporting a claim. In a narrative, a resolution can receive earlier events that make its effect coherent. In a photograph, a defining subject and a substantial setting can contribute differently to the intended encounter. These examples concern the contributions within the particular work, not generic labels substituted for its content.

The same image, document, or code component can become an asset in another AUE. Its receiving relationship then supplies another context of use. The Unloaded Definition keeps that breadth available.

## 14. Connections to other work

These connections locate conceptual neighbors of an independently developed design.

**Structured prompting.** Zhang, Yuan, and Yao's *Meta Prompting for AI Systems* studies formal task structure and typed transformations between tasks and prompts [1]. Metaform's represented subject is the reusable functional understanding of a particular AUE and the contextual contributions through which subsequent work is interpreted.

**Prepared graph understanding.** Edge and colleagues' GraphRAG constructs an entity graph and pregenerated community summaries for query-focused summarization [2]. It already performs inference before query time. Metaform likewise reuses prior inferential work, but organizes it around functional receiving relationships and subsequent implementation, criticism, and formation of an artifact.

**Reflection retained for later action.** Shinn and colleagues' Reflexion retains linguistic reflections on feedback in episodic memory to inform later trials without updating model weights [3]. Metaform situates reusable findings at functional elements and Joins and distinguishes those findings from selected instructions and task-specific skills.

**Provenance.** W3C PROV-DM distinguishes entities, activities, agents, and derivation relationships [4]. These distinctions help explain why a result, its production, and its inputs are different records. This paper does not claim that Metaform's provenance representation implements PROV conformance.

## 15. Conclusion

The Inference Metaform develops functional understanding before work and supplies that understanding to later reasoning. Meaningful Addresses engage type understanding. Operative Purposes and Encounter Functions connect that understanding to the particular artifact. Joins become both subjects of inference and places for retained knowledge. Contextual layers preserve distinct perspectives and disclose their contributions where they bear on the work.

The graph-backed context projection extends this arrangement across functional navigation, virtual spatial encounters, and physical observations. The commonality is contextual delivery, not identical physical behavior. Edge reflexes execute locally; events bring the relevant situation to the agent harness; the agent reasons with the place's prepared context.

Context efficiency concerns the whole lifecycle: useful preparation, selective disclosure, retention within a context, explicit handoff, and reuse of prior work. Multiple humans and agents can participate in that process without merging their identities or contexts. Documentation recomposition supplies a concrete producer that turns revision-bound functional understanding into maintained explanations.

The central contribution is the connection among these mechanisms. Previously inferred understanding becomes usable material for further inference, and the results can become the next preparation. Graphs, memory, skills, protocols, and interfaces participate in that account; none alone replaces it.

# PART 3 — System Architecture & Data Schema Specification

**Inference Metaform · Working specification 1.0 · October 27, 2026**

## 1. Scope and normative meaning

This specification defines a language-independent implementation of functional intake records, contextual layers, place-based context projection, skill delivery and retention, event-driven agent turns, spatial observation adapters, and revision-bound specification/documentation composition. The selected graph database is LadybugDB; Cypher is its query interface. Implementation languages and process packaging remain implementation choices.

“Must” describes an observable contract of the proposed system. “Reference profile” identifies a concrete selected realization. “Design decision” identifies completion of an underspecified point, not a claim that the source already implements it. Source-backed protocol behavior is cited by specification section; unexecuted integration claims are identified in Section 14.

The system supports multiple human and agent participants in a shared project. Participant identity is used for attribution, delivery, and continuity, not context selection. Identical place, view, and revision inputs produce identical available context and tools for every participant. An agent can inspect or navigate to any Address and can address any other agent. Messages at elements and Joins are ordinary addressed records.

The functional core ends at the context, operation, event, and adapter contracts. Existing harnesses retain their own execution behavior. A multiplayer game, screen-sharing application, team-management product, and implementation migration are not defined here.

## 2. Canonical semantics and source normalization

### 2.1 Identity and terminology

An Address identifies an element within a map. The project and map revision disambiguate the same Address in different AUEs or editions. A storage key identifies a stored version; it does not replace the Address's semantic role.

An element can be examined as an entity without duplication. RE and PE are relationship positions. A purpose Join has one RE, an Operative Purpose, an Encounter Function, an information flow direction, and one or more contributing PEs. A combined encounter can include several elements; this does not create several global EFs on one provider.

The specification-layer `objective_purpose` field remains separate from the Join's `purpose` field. The latter is always OP. No field named `objective_purpose` is aliased to OP. Specifications attach to their receiving element or Join; `SPECIFIES` records the Join they elaborate.

A CEL is a contextual knowledge layer, not a new base-map identity system. AT, NS, DE, SE, NE, parametric, ICE, and Block retain the definitions in the supplied Canonical Intake. `SE` means substantial element. The five artifact roots and the two external-reference roots are distinguished rather than repeating the intake's inconsistent numerical phrase “five” before seven names.

### 2.2 Input adapters

The intake adapter flattens repeated XML references by Address while preserving nested contribution relationships. It reads legacy `function` as the source's EF text when that field is the descriptive encounter; it preserves the original field/value in source provenance. It normalizes `send`/`receive` to `sends`/`receives`, with `both` unchanged. Legacy observation, relation, reference, and non-goal fields become source or knowledge items associated with the same receiver-owned Join.

A historical categorical EF marker, such as `Function` or `Encounter`, is retained as source metadata rather than replacing the descriptive EF. Unresolved references are recorded with their source location and shown as unresolved. No additional element is inferred merely to satisfy an importer's missing reference.

New canonical intake and refinement operations record functional meaning directly. Import compatibility does not rewrite the authored intake procedure.

### 2.3 Snapshot and live-state separation

`MapSnapshot` identifies a consistent published set of base records and contextual attachment descriptors. Its `commit_oid` can be null for live work not yet bound to a Git commit. A refinement produces a new snapshot or a storage-equivalent versioned view; earlier referenced snapshots remain readable.

Mutable conversations, current task status, presence, delivery records, and live observations reside in `RuntimeRecord` or the native provider. A graph attachment can point to such a record. Its read response supplies the actual runtime revision. An immutable graph descriptor is not falsely represented as freezing an external live resource.

Every context response records `snapshot_key` and the runtime revisions actually resolved. A commit-bound composition uses only committed exports, unless its request explicitly names an additional runtime cut.

## 4. LadybugDB data schema

### 4.1 Tables and keys

The full DDL is supplied in `contracts/graph.cypher`. The following is the complete table definition, not Neo4j constraint syntax. Ladybug's documented `CREATE NODE TABLE` and `CREATE REL TABLE` support these typed endpoints, including multiple endpoint pairs. Relationship identities are application-maintained because relationship tables do not have user-defined primary keys. [Ladybug: Create table — Primary key; Create a relationship table.]

```cypher
CREATE NODE TABLE MapSnapshot(
  key STRING, project_id STRING, repository_id STRING, commit_oid STRING,
  manifest_digest STRING, parent_key STRING, created_at STRING, state STRING,
  PRIMARY KEY(key));
CREATE NODE TABLE Namespace(
  key STRING, snapshot_key STRING, address STRING, depth INT64,
  PRIMARY KEY(key));
CREATE NODE TABLE Element(
  key STRING, snapshot_key STRING, address STRING, name STRING,
  name_length INT64, role STRING, PRIMARY KEY(key));
CREATE NODE TABLE PurposeJoin(
  key STRING, snapshot_key STRING, stable_id STRING, purpose STRING,
  ef STRING, ifd STRING, PRIMARY KEY(key));
CREATE NODE TABLE IceBlock(
  key STRING, snapshot_key STRING, block_number STRING, explanation STRING,
  PRIMARY KEY(key));
CREATE NODE TABLE Layer(
  key STRING, snapshot_key STRING, stable_id STRING, name STRING,
  variable STRING, kind STRING, state STRING, mutable BOOL, hidden BOOL,
  PRIMARY KEY(key));
CREATE NODE TABLE ContextItem(
  key STRING, snapshot_key STRING, stable_id STRING, revision STRING,
  kind STRING, name STRING, summary STRING, content_role STRING,
  payload_mode STRING, payload_json STRING, payload_uri STRING,
  native_schema_uri STRING, content_digest STRING, byte_length INT64,
  objective_purpose STRING, PRIMARY KEY(key));
CREATE NODE TABLE RuntimeRecord(
  key STRING, project_id STRING, kind STRING, revision INT64,
  payload_json STRING, PRIMARY KEY(key));

CREATE REL TABLE IN_SNAPSHOT(
  FROM Namespace TO MapSnapshot, FROM Element TO MapSnapshot,
  FROM PurposeJoin TO MapSnapshot, FROM IceBlock TO MapSnapshot,
  FROM Layer TO MapSnapshot, FROM ContextItem TO MapSnapshot);
CREATE REL TABLE AT_ADDRESS(FROM Element TO Namespace);
CREATE REL TABLE PARENT(FROM Namespace TO Namespace);
CREATE REL TABLE ANCESTOR(FROM Namespace TO Namespace, hops INT64);
CREATE REL TABLE OWNS(FROM Element TO PurposeJoin);
CREATE REL TABLE PROVIDED_BY(FROM PurposeJoin TO Element);
CREATE REL TABLE CONTAINS(FROM Element TO Element);
CREATE REL TABLE MEMBER_OF(FROM Element TO IceBlock);
CREATE REL TABLE INCIDENT(FROM Namespace TO PurposeJoin, side STRING);
CREATE REL TABLE IN_LAYER(FROM ContextItem TO Layer);
CREATE REL TABLE DERIVED_FROM(FROM Layer TO Layer);
CREATE REL TABLE SPECIFIES(FROM ContextItem TO PurposeJoin);
CREATE REL TABLE SUPPORTS(FROM ContextItem TO ContextItem);
CREATE REL TABLE USES_TOOL(FROM ContextItem TO ContextItem);
CREATE REL TABLE DEPENDS_ON(FROM ContextItem TO ContextItem);
CREATE REL TABLE HAS_SKILL(
  FROM Namespace TO ContextItem, FROM PurposeJoin TO ContextItem,
  attachment_key STRING, scope STRING);
CREATE REL TABLE OFFERS(
  FROM Namespace TO ContextItem, FROM PurposeJoin TO ContextItem,
  attachment_key STRING, scope STRING);
CREATE REL TABLE HAS_TASK(
  FROM Namespace TO ContextItem, FROM PurposeJoin TO ContextItem,
  attachment_key STRING, scope STRING);
CREATE REL TABLE HAS_SPEC(
  FROM Namespace TO ContextItem, FROM PurposeJoin TO ContextItem,
  attachment_key STRING, scope STRING);
CREATE REL TABLE HAS_DOC(
  FROM Namespace TO ContextItem, FROM PurposeJoin TO ContextItem,
  attachment_key STRING, scope STRING);
CREATE REL TABLE HAS_MEMORY(
  FROM Namespace TO ContextItem, FROM PurposeJoin TO ContextItem,
  attachment_key STRING, scope STRING);
CREATE REL TABLE HAS_ITEM(
  FROM Namespace TO ContextItem, FROM PurposeJoin TO ContextItem,
  attachment_key STRING, scope STRING);
```

Storage keys are SHA-256 digests of length-prefixed UTF-8 `(snapshot_key, table_kind, logical_identity)` values. Namespace and element logical identity is the Address; Join, layer, and item logical identities are stable record IDs. Runtime keys include project and record kind. This makes primary-key lookup possible without treating an opaque digest as the element's semantic name.

A `Namespace` prefix can exist for navigation and inherited context without claiming an additional independently significant element in the intake. `Element` contains the actual DE/SE/NE/CQU records. `CONTAINS` records represented composition, not namespace ancestry and not ICE membership.

### 4.2 Record meanings

`Layer.kind` and `ContextItem.kind` identify data kinds, not a closed catalog of future layers. The typed relationships above provide the common projections. `HAS_ITEM` carries additional native layer kinds without changing the base ontology.

`content_role` is `informational` or `imperative`. `payload_mode` is `inline`, `reference`, or `query`. Inline content uses `payload_json`; a reference uses `payload_uri`; a query payload identifies its provider, native operation/query, typed arguments, and returned schema. The adapter preserves the provider's payload rather than translating every format into an invented universal skill or tool body.

For a specification item, the payload contains `objective_purpose`, requirements with stable IDs, inputs, outputs, observable behavior, and supporting references. A task payload contains its goal, target Addresses/Joins, specification revisions, Block IDs, work-unit ID, current state reference, and result references. A documentation payload contains the audience, explanation or journey, and source records. A skill payload uses the official skill representation. A tool payload preserves its native name, input schema, annotations, and provider reference.

Source references identify repository, commit/blob or provider revision, path/URI, and line range or structured pointer. `DEPENDS_ON` records declared item dependencies; `DERIVED_FROM` records layer derivation. They do not assert that all semantic dependencies have been discovered.

### 4.3 Derived topology

`PARENT` links each namespace to its immediate prefix. `ANCESTOR` is a materialized transitive closure containing one self-edge with `hops=0` and one edge to every proper prefix. There is no fixed namespace-depth limit.

`INCIDENT` links each actual endpoint's namespace to a purpose Join with `side='receiver'` or `side='provider'`. It is derived from `OWNS`, `PROVIDED_BY`, and `AT_ADDRESS`. A participant therefore discovers the Join from either endpoint while the Join's purpose record remains receiver-owned.

A refinement updates affected derived relationships in the same publication transaction as the source records. The application maintains one closure edge per `(descendant, ancestor)`, one attachment per `attachment_key`, and consistent snapshot references. These responsibilities preserve a consistent data shape.

Ladybug permits concurrent reads and one write transaction. The reference deployment therefore uses one database service with a write queue and read transactions for multi-query projections. The queue serializes storage changes, not agent reasoning or interactive participation. [Ladybug: Transactions — Important properties; Transaction Statement.]

## 5. Context projection and explicit Cypher

### 5.1 Resolve layers before collecting payloads

Let U be the layer IDs in the selected snapshot. When no starting selection is supplied, begin with its selectable finished nonhidden layers. An explicit empty selection is the empty set. Apply namespace-local rules trunk to leaf:

```text
selection_next = (selection_current − locally_masked) ∪ locally_selected
```

This is the set form of the manuscript's mask/select expression. The mask and selection records are project data. Compute the hidden-source dependency closure from recorded `DERIVED_FROM` relationships. The projection's `excluded_layer_keys` is the complement of the resulting participating selection plus that closure. The rules are stored as `RuntimeRecord` entries of kind `layer_selection`, keyed by project, snapshot, and Address, with `masked_layer_keys` and `selected_layer_keys` arrays. Resolve these entries for the ancestry in the same read transaction before running the projection; absent entries are transparent. Snapshot-qualified rule entries remain unchanged with that snapshot. No list is hardcoded into the query.

Scopes are `local`, `descendants`, and `visible_up`. Local material is delivered at its attachment. Descendant material applies from that attachment toward its descendants. `visible_up` material appears in an explicitly requested broader overview; it does not apply to siblings. A direct named read can retrieve material outside the current projection.

### 5.2 Place-context query

Compute `$leaf_key` from the selected snapshot and target Address, and supply the dynamic `$excluded_layer_keys`. This query returns descriptors, not full payload bodies:

```cypher
MATCH (leaf:Namespace {key: $leaf_key})-[lineage:ANCESTOR]->(at:Namespace)
MATCH (at)-[attachment]->(item:ContextItem)-[:IN_LAYER]->(layer:Layer)
WHERE item.snapshot_key = leaf.snapshot_key
  AND layer.snapshot_key = leaf.snapshot_key
  AND layer.state = 'finished'
  AND NOT (layer.key IN $excluded_layer_keys)
  AND (lineage.hops = 0 OR attachment.scope = 'descendants')
RETURN item.key AS item_key, item.stable_id AS item_id,
       item.revision AS revision, item.kind AS kind,
       item.name AS name, item.summary AS summary,
       item.content_role AS content_role,
       item.payload_mode AS payload_mode, item.payload_uri AS payload_uri,
       item.native_schema_uri AS native_schema_uri,
       item.content_digest AS content_digest, item.byte_length AS byte_length,
       at.address AS via_address, '' AS via_join,
       lineage.hops AS namespace_hops, 0 AS join_hops,
       attachment.attachment_key AS attachment_key, layer.key AS layer_key
UNION ALL
MATCH (leaf:Namespace {key: $leaf_key})-[lineage:ANCESTOR]->(at:Namespace)
MATCH (at)-[incidence:INCIDENT]->(j:PurposeJoin)
MATCH (j)-[attachment]->(item:ContextItem)-[:IN_LAYER]->(layer:Layer)
WHERE item.snapshot_key = leaf.snapshot_key
  AND j.snapshot_key = leaf.snapshot_key
  AND layer.snapshot_key = leaf.snapshot_key
  AND layer.state = 'finished'
  AND NOT (layer.key IN $excluded_layer_keys)
  AND (lineage.hops = 0 OR
       (incidence.side = 'receiver' AND attachment.scope = 'descendants'))
RETURN item.key AS item_key, item.stable_id AS item_id,
       item.revision AS revision, item.kind AS kind,
       item.name AS name, item.summary AS summary,
       item.content_role AS content_role,
       item.payload_mode AS payload_mode, item.payload_uri AS payload_uri,
       item.native_schema_uri AS native_schema_uri,
       item.content_digest AS content_digest, item.byte_length AS byte_length,
       at.address AS via_address, j.stable_id AS via_join,
       lineage.hops AS namespace_hops, 1 AS join_hops,
       attachment.attachment_key AS attachment_key, layer.key AS layer_key;
```

For an attachment, functional proximity is the ordered pair `(namespace_hops, join_hops)`. The host sorts by this pair, then kind, stable item ID, revision, and attachment key. It groups duplicate item/revision references while retaining all attachment reasons. Different revisions or contradictory sources remain distinguishable.

This definition separates ancestry from a Join encounter; it does not pretend that geometric meters and namespace hops are interchangeable. A provider is not assumed to be an ancestor. Provider tools relevant to a receiving task are recorded as `OFFERS` at that receiving Join, retaining their native provider references. Merely reaching a provider does not recursively inject all that provider's other tasks and receivers.

The query avoids independent `OPTIONAL MATCH` branches for skills, tasks, specs, and docs, which would multiply combinations before aggregation. Materialized ancestry also avoids an implicit recursion-depth cutoff: Ladybug documents a default upper bound for recursive patterns without an explicit bound. The optimization is structural—primary-key start, prepared closure, descriptor-only rows—not a measured latency claim. [Ladybug: Match — Recursive relationships.]

A separate namespace lookup distinguishes an unknown Address from a known place with an empty catalog. An overview reads descendant attachments with `scope='visible_up'` and labels them informational visibility; it does not add them to the applying harness.

The next stage resolves selected item bodies by primary key. For the native tool catalog it resolves every offered tool's descriptor, including its input schema and annotations; for ordinary arrival text it resolves only the bodies selected for that delivery. Reference/query payloads are then read through their named native provider.

```cypher
UNWIND $item_keys AS selected_key
MATCH (item:ContextItem {key: selected_key})
RETURN item.key AS item_key, item.stable_id AS item_id,
       item.revision AS revision, item.kind AS kind,
       item.payload_mode AS payload_mode, item.payload_json AS payload_json,
       item.payload_uri AS payload_uri, item.native_schema_uri AS native_schema_uri,
       item.content_digest AS content_digest, item.byte_length AS byte_length;
```

This second stage is how descriptor discovery becomes the concrete tool harness. Large skill, specification, and documentation bodies are not fetched merely to build the tool list.

### 5.3 Functional bindings, not prose matching at every visit

The following inspection query exposes the recorded connection between intake and specification terms:

```cypher
MATCH (receiver:Element {key: $receiver_key})-[:OWNS]->(j:PurposeJoin)
MATCH (j)-[:PROVIDED_BY]->(provider:Element)
MATCH (spec:ContextItem)-[:SPECIFIES]->(j)
MATCH (skill:ContextItem)-[:SUPPORTS]->(spec)
MATCH (skill)-[:USES_TOOL]->(tool:ContextItem)
WHERE j.snapshot_key = receiver.snapshot_key
  AND provider.snapshot_key = receiver.snapshot_key
  AND spec.snapshot_key = receiver.snapshot_key
  AND skill.snapshot_key = receiver.snapshot_key
  AND tool.snapshot_key = receiver.snapshot_key
RETURN receiver.address AS receiver, j.stable_id AS join_id,
       j.purpose AS operative_purpose, j.ef AS encounter_function,
       provider.address AS provider, spec.stable_id AS specification_id,
       spec.objective_purpose AS objective_purpose,
       skill.stable_id AS skill_id, tool.stable_id AS tool_id;
```

The facilitator authors or reuses these bindings from the functional evidence. A skill can have no tool dependency, and a specification can have no prepared skill yet; those records remain visible through the main catalog query. The inspection query is not a completeness condition for work.

### 5.4 Context envelope and cache

A projection returns:

```text
project_id; snapshot_key; address; place_key;
orientation {ancestry, active_join, operative_purpose, encounter_function};
work_refs[]; specification_refs[]; skill_entries[]; tool_descriptors[];
document_refs[]; memory_refs[]; message_refs[];
attachment_reasons[]; resolved_runtime_versions[];
page {complete, next_cursor, returned_count}; findings[]
```

`active_join` is nullable; a place can serve several purposes. Other Joins remain in the catalog. Native objects, such as tool descriptors and skill entries, retain their native fields. The envelope is host data: text already supplied through the native tool catalog is not repeated in the turn text, and a retained skill body is not reinjected on every arrival.

Cache keys include snapshot, target, selection digest, provider/catalog revisions, and requested projection shape. Actual content delivery is deduplicated per context/epoch by source URI and content digest. Cache reuse never means that a different context has received the material.

## 6. Tickets, facilitation, and ICE work composition

A composer receives a specification revision and its receiving relationships. It emits tickets with `ticket_id`, `goal`, `objective_spec_refs`, `target_addresses`, `join_ids`, `block_ids`, `work_unit_id`, `state`, `result_refs`, and source provenance. Dependencies express work ordering where the specification establishes it.

For each target element, expand explicit Block membership. Overlapping established couplings form one composed work unit. The unit records all coupled Addresses, the specification revisions in force, the participating tickets and agents, and one worktree reference for software work. Task decomposition can describe sub-contributions within that unit without splitting its shared contract across worktrees. Work without a filesystem uses the same unit without an invented worktree.

The facilitator consumes that unit's functional context and finds or prepares a skill for its task. Its output is the official skill package or a native server skill reference, the specification bindings, and the tool references. General server instructions can remain at the server. Project-specific procedure belongs at the relevant element or receiving Join. Existing skills are reused when they address the work; no duplicate is created solely because another agent arrived.

When a ticket adds functionality, its result identifies corresponding element/Join refinements and contextual updates. A newly discovered coupling emits `block.changed` with the affected work units and source evidence. Existing contributions remain referenced; the work description records how the coupled changes are brought together. The context system does not silently merge code branches.


The capability fragment belongs in the server's `server/discover` result. A legacy transport binding, when implemented, must have its own version-correct adapter; legacy `resources/subscribe` messages are not mixed into this binding.

### 7.2 Place surfaces and tool presentation

A logical MCP place surface has an endpoint identity determined by project, Address, and shared view. It can be served by the same process as all other places. Its tool/resource catalog depends on the place's published data, not the identity or hidden navigation state of a connection.

This matters because MCP 2026-07-28 Tools and Resources explicitly prohibit catalog variation caused by connection-local state or other requests on that connection. Navigation selects another named place surface; changes to a place's actual tool catalog produce `notifications/tools/list_changed`. [MCP: Tools — Capabilities, List Changed Notification; Resources — Capabilities.]

The harness adapter implements `project_surface(context_id, place_key, catalog_revision)`: it obtains the new place catalog and updates the model-facing tool projection while retaining the context's previously loaded skills. This function is a **Metaform host integration contract**, not an ACP method. ACP alone does not establish live MCP-catalog replacement in every existing harness.

A harness lacking native tool-projection support can use a stable navigation/read/invocation adapter. It receives the native descriptors as context, and the invocation adapter forwards the chosen tool's arguments unchanged to its provider. This preserves reachability and native execution, but is identified as a gateway presentation rather than claiming direct per-tool installation in that harness.

Core operations have typed schemas:

| Tool | Input fields | Result |
|---|---|---|
| `metaform_go` | `project_id`, `context_id`, `address`; optional snapshot/view | Place descriptor and arrival context; updates that context's presence |
| `metaform_inspect` | `project_id`, `address`; optional snapshot/view/cursor | Context projection without moving the participant |

Provider tools retain their typed input schema and annotations. A collision between native tool names is resolved by a stable presentation name recorded with `(provider_id, native_name)`; the reference rule is `mf_` followed by the full SHA-256 hex of the length-prefixed pair. The descriptor title retains the readable native name. Invocation resolves that mapping, not a name guessed from the current place.

Annotations describe effects and risks. The projection adds no read-a-skill receipt prerequisite before invoking a tool. [MCP: Tools — Tool, ToolAnnotations, Calling Tools.]

### 7.3 Official skills transport

## 8. Uniform spatial observation interface

### 8.1 Resource identity

The canonical resource is:

```text
resource://spatial/tof/matrix_8x8
```

At each place endpoint it denotes that place's declared primary ToF source. This binding is shared and stable, not “the sensor most recently selected by a caller.” Additional sensors have explicit source-specific URIs. Both virtual and physical adapters return the same payload schema. The `source.kind` field preserves which realization produced it. The resource describes observation, not a guarantee of clearance or object identity.

### 8.4 Calibration and adapter algorithms

The calibration resource contains source and frame IDs, 64 normalized optical direction vectors, a permutation from native zone order to canonical order, the sensor-to-body rigid transform, native distance convention, sample-model description, and the native quality mapping reference. The permutation contains each integer 0–63 once. Rays have positive z and unit length; the rigid transform uses meters and a normalized quaternion in x/y/z/w order.

For virtual ray direction d_i and hit distance t_i in meters:

```text
axial_depth_mm[i] = 1000 × t_i × d_i.z
point_m[i] = (axial_depth_mm[i] / 1000 / d_i.z) × d_i
```

Thus a perpendicular wall one meter away yields 1000 mm in every valid zone, including oblique rays. Raw slant distances would not satisfy this contract. The reference virtual profile uses the nearest hit along each calibrated center ray. A richer finite-footprint simulator can use another declared sample model without changing the resource schema.

The physical VL53L5CX adapter uses the vendor ULD's decoded measurements, target counts, and status fields over the device's I2C interface. It reorders zones, applies the documented depth convention, and preserves quality. Where multiple targets are reported, the reference reduction selects the nearest measurement classified valid by the native quality interpretation, while exposing full native results through a separate resource when needed. The selected status mapping and driver revision are part of the calibration/profile record, not guessed from an integer buffer. [ST: UM2887 §§1–3; ST employee explanation of perpendicular distance.]

The supplied material does not establish the actual mounting transform, native-to-canonical permutation, or calibrated rays for Rich's hardware. These are deployment data. The profile supplies them from vendor calibration or a measured calibration; their status remains visible until established. A center-and-corner target fixture checks orientation, and a perpendicular-wall fixture checks depth convention.

The reference acquisition profile is 8×8 at 15 Hz. ST's published material distinguishes this from 4×4 at 60 Hz. A faster controller loop may reuse the latest sample but does not claim a new observation on each tick. No fixed model-response frequency is required.

## 9. Edge reflex and wake-up state machine

### 9.1 Separate local reaction from contextual response

The reference incident is a forward-facing zone crossing a configured near boundary. A `BoundaryProfile` contains `profile_id`, sensor source/frame, zone indices, enter depth, exit depth, local reflex operation, target Address, optional Join ID, and source revision. Enter and exit values belong to the device/application profile. An illustrative 200/250 mm pair demonstrates hysteresis; it is not a universal stopping distance.

The controller evaluates fresh source sequences. In state CLEAR, any valid monitored zone at or below the enter depth produces OBSTRUCTED. It runs the local reflex immediately and records the effect. In OBSTRUCTED, further near samples update the current observation without creating another entry event. All monitored zones valid at or above the exit depth produce CLEAR and a clearing event. An unavailable/invalid sample is not interpreted as clear; it produces a quality event when quality state changes. The existing device's behavior for unavailable sensing is recorded in its device profile rather than inferred by Metaform.

The local action does not depend on database persistence, MCP connectivity, or a model turn. Software-derived threshold events retain the exact triggering matrix. A hardware threshold interrupt whose observation time cannot be aligned with a later read records that distinction.

### 9.2 Durable event record

`contracts/event.schema.json` specifies:

```text
event_id; source_id; source_epoch; source_sequence;
journal_id; journal_sequence; kind;
project_id; target_address; join_id;
clock_id; observed_ns; persisted_clock_id; persisted_ns;
cause_id; observation_uri; observation_sequence;
summary; details
```

The event ID is stable across transport retries. The journal sequence orders persistence in the receiving journal; source sequence orders events from one source. Neither asserts synchronized physical time across unrelated sources.

The reference journal uses a head record and sequence-keyed records in `RuntimeRecord`. Appending the next sequence and advancing the head share one transaction. A page after sequence n reads the head and calculates the keys for n+1 through the requested page end; it does not scan JSON payloads to find events. The read transaction fixes that page's head. Messages use the same pattern for each addressed conversation stream.

`details` records affected zones, boundary profile revision, triggering values, reflex requested/applied state, and relevant command ID. The incident frame is retained with the event. Ordinary nonincident frames can replace the latest matrix without entering long-lived project memory.

### 9.3 End-to-end trace

| Step | State transition | Observable action |
|---|---|---|
| 1 | Sensor sequence advances | Driver publishes a new observation with time, quality, source epoch, and calibration reference |
| 2 | CLEAR → OBSTRUCTED | Controller runs its local stop reflex; records actual effect independently of transport |
| 3 | Event created → journaled | Bridge stores event and incident frame, then advances the journal cursor |
| 4 | Resource changed | Bridge emits `notifications/resources/updated` for the event journal |
| 5 | Harness IDLE → WAKE_PENDING | Host reads journal entries after its last cursor, deduplicates event IDs, resolves target Address |
| 6 | Projection prepared | Cypher returns the place's context; host reuses already delivered bodies and offers newly relevant material |
| 7 | WAKE_PENDING → RUNNING | Harness submits the event-originated ACP `session/prompt` |
| 8 | Agent reasoning | Agent reads observation/skill/specification as needed and chooses its response |
| 9 | Native operation queued/applied | Adapter reports motion or other tool status from the actual provider |
| 10 | RUNNING → IDLE | Completed turn and delivered event IDs are recorded; later independent events remain pending |

A busy agent's events join its pending queue and can accompany the next natural turn. Arrival caused by the agent's own navigation is returned in that operation's result rather than forcing an extra model invocation. A state event can wake an idle agent without polling sensor matrices through the model.

### 9.4 Disconnection, duplication, and ordering

`resource://metaform/events` identifies the journal; a resource template with `after` and `limit` identifies subsequent pages. Cursors contain journal identity and sequence. On reconnect, the host reads from the retained cursor. Crossing and clearing events remain distinct even if one resource notification covers both. Matrix update hints can coalesce; event records do not disappear through coalescing.

The host persists delivery states `pending`, `submitted`, `completed`, and `delivery_unknown`, with context and ACP request IDs. A crash after submission but before a result leaves an explicit unknown outcome. Recovery examines available session history and preserves the uncertainty; it does not claim exactly-once model execution. Repeated events carry the same identity.

Native commands likewise distinguish `queued`, `applied`, `completed`, `interrupted`, `failed`, and `unknown`. A lost acknowledgment is not reported as completed motion. Provider-native retry and command-status behavior is described by the tool.

### 9.5 Timing contract

Measure separately:

```text
local reaction = fresh-sample wait + driver read + reflex computation + actuator response
agent response = bridge/journal + notification + context projection + ACP scheduling + model turn
```

The first expression does not contain the second. At 15 Hz, a periodic sample interval is approximately 66.7 ms before readout and actuator effects. A 100 Hz controller cannot remove that sensing interval. Record actual timestamps and p50/p95/p99 for each boundary; no unmeasured end-to-end deadline is asserted.

## 10. Agent contexts, retention, and shared participation

### 10.1 Runtime records

The following payloads use `RuntimeRecord`, each with a project-local revision:

| Kind | Required logical fields |
|---|---|
| Participant | `participant_id`, kind human/agent, display name, genesis reference where applicable |
| Agent context | `context_id`, `agent_id`, harness ID, native session ID, epoch, state, predecessor context |
| Presence | Participant/context ID, project, current Address, optional spatial instance/frame, view reference |
| Layer selection | Snapshot key, Address, `masked_layer_keys`, `selected_layer_keys` |
| Delivery | Context/epoch, source URI, actual digest/revision, delivery channel, time, content reference |
| Message | Message ID, sender and attribution source, target kind/ID, body reference, reply/causation IDs, sequence |
| Work unit | Unit ID, target Addresses/Joins, Block membership revision, ticket IDs, participant IDs, worktree/artifact references |
| Wake delivery | Context/event IDs, ACP request ID, pending/submitted/completed/unknown state |
| Handoff | Predecessor/successor context IDs, same logical agent ID, target, goal, progress, decisions, references, event cursor |

The body used for spatial action is an instance reference with time-bounded participant association. It is not an agent ID. The transport's session is provenance, not an inferred participant identity. Multiple users do not share a process-global “current user,” and multiple contexts do not share a global “current place.”

### 10.2 Identity continuity

The reference choice retains logical agent identity across an explicit handoff and creates a new identity for an independently proceeding fork. Both retain predecessor/parent references. A stopped historical context remains readable from retained records, whether or not its native harness can resume it.

Display names follow the supplied genesis rule: FNV-1a over the first session ID's UTF-8 bytes, XOR-fold to sixteen bits, high/low bytes indexing the fixed adjective/noun tables. The tables' version is retained. Names can collide; stable IDs disambiguate them and no rehash changes an established name. The word tables are referenced from the existing project's naming implementation, not recreated here.

### 10.3 Delivery and retention

The host distinguishes `discovered`, `resource_body_delivered`, `skill_loaded`, and `changed_since_delivery`. The latter is a source-version comparison, not a judgment of understanding. `learned_skills` is the set of versions delivered by the harness's skill-loading path into the current context; it grows through that context and is not reduced when the agent leaves a place.

On observable compaction, the reference host restores the retained skill segment and records the new epoch's delivery. A harness with no retention observability reports that limit; delivery records are not represented as proof of surviving comprehension. The adapter's ability to preserve the segment is an implementation requirement of this retention profile, not an undocumented ACP feature.

A handoff carries the goal, completed/remaining work, decisions, current source revisions, event cursor, work-unit/worktree references, and skill references. It does not copy every prior skill body by default. The successor starts with an empty loaded-skill set and acquires its place's material. `contracts/handoff.schema.json` defines the record.

### 10.4 Budget and page behavior

Use the harness's actual context capacity and tokenizer where exposed. Available input is capacity minus retained context and the requested output reserve. When a configured usage fraction is reached, or the next planned delivery would exceed that capacity, emit a handoff-needed signal and prepare continuation at the next appropriate turn boundary. A goal boundary or explicit handoff can use the same mechanism. Unknown capacity is reported as unknown rather than replaced by an invented universal limit.

Descriptor lists use deterministic ordering and revision-bound cursors. Explicit body reads supply the requested bytes or a declared range with continuation. No summary is substituted for a requested full body without identifying the substitution. Changed versions are announced by references first, then read when relevant. These mechanisms reduce repeated delivery while leaving direct access available.

### 10.5 Concurrent contributions

Shared mutations carry record ID, observed revision, and operation ID. The store transaction retains the contributor's proposed value and publishes the resulting revision. If the observed revision has changed incompatibly, the result includes both versions and a `concurrent_change` finding rather than silently discarding one contribution. This is an observable data interaction, not a participant hierarchy.

Messages and events retain origin and causation. An addressed message is readable by any participant; subscription determines automatic delivery. A user interface can show multiple participant views or shared attention, but Metaform does not prescribe screen-sharing or multiplayer transport.

## 11. Intent-driven documentation recomposition

### 11.1 Frozen inputs

A request names `repository_id`, `target_commit`, optional `base_commit`, document kind, audience, source selection, and prior output reference. Resolve movable branch names once to immutable commit IDs before collecting data.

The versioned repository export contains a manifest and canonical base/layer records. The manifest lists record files and byte digests; it does not contain the hash of the commit that contains itself. After Git creates that commit, the composition run binds `(repository_id, commit_oid, manifest_digest)` to a graph snapshot. This avoids a self-referential commit hash.

A live database state is not silently joined to a past source commit. Missing committed records, changed external native resources, and additional requested runtime cuts remain explicit findings and provenance. A commit-only run resolves external material from committed captures or pinned provider versions; a live fallback is labeled as such.

### 11.2 Programmatic sweep

The composition request's explicit publication selection determines this sweep; it does not inherit whichever leaf a participant last visited. Traverse all selected namespace records, including specification and documentation attachments at Joins. `contracts/document-sweep.cypher` contains the complete two-branch query. Both branches select the requested `snapshot_key`, participating finished layers, and item kinds `specification` and `documentation`; the second obtains the receiver Address through `OWNS`.

```cypher
MATCH (place:Namespace)-[attachment]->(item:ContextItem)-[:IN_LAYER]->(layer:Layer)
WHERE place.snapshot_key = $snapshot_key
  AND item.snapshot_key = $snapshot_key
  AND layer.snapshot_key = $snapshot_key
  AND item.kind IN ['specification', 'documentation']
  AND layer.state = 'finished'
  AND NOT (layer.key IN $excluded_layer_keys)
RETURN place.address AS address, '' AS join_id,
       attachment.attachment_key AS attachment_key,
       item.stable_id AS item_id, item.revision AS revision,
       item.kind AS kind, item.content_digest AS content_digest,
       item.payload_mode AS payload_mode, item.payload_json AS payload_json,
       item.payload_uri AS payload_uri, item.native_schema_uri AS native_schema_uri
UNION ALL
MATCH (receiver:Element)-[:OWNS]->(j:PurposeJoin)
MATCH (j)-[attachment]->(item:ContextItem)-[:IN_LAYER]->(layer:Layer)
WHERE receiver.snapshot_key = $snapshot_key
  AND j.snapshot_key = $snapshot_key
  AND item.snapshot_key = $snapshot_key
  AND layer.snapshot_key = $snapshot_key
  AND item.kind IN ['specification', 'documentation']
  AND layer.state = 'finished'
  AND NOT (layer.key IN $excluded_layer_keys)
RETURN receiver.address AS address, j.stable_id AS join_id,
       attachment.attachment_key AS attachment_key,
       item.stable_id AS item_id, item.revision AS revision,
       item.kind AS kind, item.content_digest AS content_digest,
       item.payload_mode AS payload_mode, item.payload_json AS payload_json,
       item.payload_uri AS payload_uri, item.native_schema_uri AS native_schema_uri;
```

Resolve each body once by `(item ID, revision, digest)`. Sort the structural spine by namespace segment sequence with parents before descendants, then receiver, Join ID, kind, and item ID. Preserve cross-branch Joins as explicit references rather than duplicating the same section. Include the relevant OP, EF, CQU trace, source references, and Block context beside the specification/documentation records.

A native query-backed payload is evaluated against its pinned snapshot when the provider supports that operation. Otherwise the producer records the actual provider revision and its correspondence limit. It does not label an unpinned response as commit-bound.

### 11.3 Detect changed source, then interpret meaning

The programmatic stage executes equivalent argument-array calls to:

```sh
git diff --name-status -z --find-renames "$BASE" "$TARGET" --
git diff --no-ext-diff --unified=0 "$BASE" "$TARGET" --
```

`BASE` and `TARGET` are resolved object IDs, not interpolated user text. The first result supplies zero-delimited path/status records, including rename pairs; the second supplies textual changes. Binary changes retain old/new blob references rather than fabricated text. Git documents these operations as diff formats and options, not as a semantic analysis engine. [Git: git-diff — name-status, -z, find-renames.]

Parse canonical exports by stable record ID. Compare OP, EF, Objective Purpose, attachment scope, native tool schemas, skill digests, documentation, source references, and ICE membership independently. A file rename without a changed functional record is not automatically a functional transformation. A changed implementation reference identifies material to inspect, not proof that the documented behavior changed.

For code-only changes, follow recorded source references to candidate elements and Joins. Unmapped changes are listed explicitly. The composition agent examines their evidence and states the inferred functional consequence with its support or uncertainty. Git detects the change; the agent supplies the interpretation.

### 11.4 Impact and context assembly

Compute affected records from direct changes, declared source/derivation dependencies, changed Join endpoints, and relevant Block membership. Then find document sections whose recorded source dependencies intersect those records. Include the parent outline and cross-references needed to keep the result standalone.

The structural sweep is complete for the selected source set, but the model does not receive the entire repository in every section job. It receives the relevant spine fragment, exact source bodies, changed records, previous section, and references to other fragments. A section is reused only when its source fingerprints, relevant outline context, and cross-references remain unchanged.

### 11.5 Composition-agent contract

Input:

```text
run identity and source cut;
document kind/audience;
section identity and complete outline;
current functional records and native payloads;
changed records and supporting source excerpts;
previous section, if any;
recorded working decisions and unresolved findings.
```

Output:

```text
section text;
claims[] {claim_id, source_refs, status specified|observed|inferred|unknown};
journeys[] {participant, goal, starting_context, interactions, observable_result};
cross_references[];
source_dependencies[];
findings[].
```

The agent rewrites explanations to match the selected sources. User journeys describe actual specified interactions and distinguish intended behavior from implementation evidence. A new requirement is introduced only by an explicit design assignment, as in this working specification; routine documentation refresh explains the selected sources and records unresolved correspondence.

The programmatic stage checks structural completeness, resolvable references, source identifiers, and output formatting. It reports unsupported statements or unresolved correspondence in the generated artifact and run findings. No automatic critic cascade is required.

### 11.6 Publication, failure, and provenance

Write each generated or reused section into a run-specific output directory. Assemble the standalone document with its glossary, interfaces, journeys, and references. Write a manifest containing source cut, selection, producer identity, prompt/version digest, section dependencies, output digests, and findings. `contracts/composition-manifest.schema.json` specifies that manifest.

A completed generation atomically replaces the output pointer. A failed section leaves the previous complete output in place and records which section failed; partial text is retained as partial work, not presented as the completed document. Generated artifacts do not automatically commit, push, or modify source code.

Re-running the same source cut can reuse completed sections with matching dependencies. Re-running a model can produce different prose; retained outputs and manifests provide inspectability rather than a claim of deterministic natural-language generation.

## 12. Compatible ecosystem profiles

### 12.1 Bevy ECS with Resources: optional execution adapter

Bevy uses **Entity-Component-System (ECS)**. Runtime entities identify simulated objects, components hold their per-entity data, and systems process components and shared **Resources**. A Bevy adapter maps stable Metaform functional references to appropriate runtime objects without treating engine-local entity handles as durable Metaform identities. LadybugDB remains the functional graph store; neither its graph nodes nor its CEL attachments become Bevy ECS components by definition.

In a Bevy implementation, Resources may hold the latest normalized observation, motion-command state, and references to context services. Simulation systems can produce ray observations; an adapter for physical observations can populate the same application-level data contract. Command-application systems run at the local execution rate, independently of MCP client timing. A physical bridge outside Bevy implements the same observation contract without needing an ECS runtime. Browser-WASM examples establish one deployment option, not a universal module ABI. [Bevy: Getting Started — ECS; Getting Started — Resources; Examples in WebGL2.]

### 12.2 ROS-compatible data

Use ROS optical-frame conventions for the observation frame and SI units when producing ROS messages. An 8×8 `sensor_msgs/Image` with `32FC1` encoding carries axial depth in meters; valid millimeters divide by 1000. Unknown/invalid values become NaN. The resource's native status can accompany it on a separate diagnostic topic. A no-return observation becomes +Inf only when the source explicitly establishes beyond-range meaning; otherwise it is unknown.

The calibration supports organized `PointCloud2` conversion through the direction-vector formula. A body-frame motion profile can adapt `TwistStamped` values after applying the recorded sensor/body frame relationship. Message types and frame semantics are reused rather than named as newly invented Metaform formats. [ROS: REP 103; REP 118; sensor_msgs/Image; PointCloud2; geometry_msgs/TwistStamped.]

### 12.3 Drone and WebAssembly interfaces

MAVLink is an informative adapter target, not a selected flight controller. Its `OBSTACLE_DISTANCE` message has 72 directional bins in centimeters, not an 8×8 image. An adapter must document the angular projection and lost vertical information; it cannot relabel the 64-zone payload as that message. [MAVLink common.xml: OBSTACLE_DISTANCE.]

A WASM-backed tool is a normal provider with a content digest, declared ABI/version, input/output schema, execution entry point, and outcome resource. A skill can explain its use; a skill manifest is not itself the executable module. Browser presentation, native Bevy execution, and other hosts can share the functional contract while identifying their actual native bindings. This specification does not invent a universal WASM bus or prescribe a permission model.

## 14. Verification, acceptance, and remaining uncertainty

Sixteen local checks were executed against the delivery's application schemas and reference semantics. They cover five well-formed JSON Schemas, a complete 64-zone observation, resource-text round-tripping and required cache fields, incorrect array length, negative depth, status/depth agreement, unknown values, axial conversion of 64 rays, branch-local layer restoration, ancestry beyond thirty hops, skill retention across movement, event replay deduplication, actual skill-file digest, and the supplied Hermes correction's five Blocks/fifteen members. Results are in `verification/results.json`.

These checks do not execute the proposed system. LadybugDB was not installed in the runtime; an installation attempt failed because the package server could not be resolved. The DDL and Cypher are therefore **source-reviewed, engine execution unverified**. MCP/ACP end-to-end interoperability, Bevy integration, physical sensor calibration, and motor behavior were not exercised. No latency, capacity, or inference-amortization benchmark is claimed.

Implementation acceptance is observable:

| Contract | Required demonstration |
|---|---|
| Functional representation | One element serves several receivers without a global EF; nested references preserve Address identity |
| Context projection | Same place/view/revision yields the same catalog for two participants; ancestor context applies correctly; sibling-local context does not |
| Query execution | DDL and supplied queries run on the selected Ladybug release; empty known place differs from unknown Address; deep ancestry is complete |
| Progressive disclosure | Arrival gives descriptors and relevant orientation; explicit reads return bodies; repeated unchanged bodies are not automatically reinjected |
| Retention and handoff | A loaded skill remains after movement; compaction retention is established by the harness profile; successor loading begins from its new context |
| ICE work composition | Coupled elements share the work unit/worktree while multiple participants can contribute |
| MCP | Current request metadata, native tool schemas/annotations, official skill entries, subscription acknowledgment, and update notifications interoperate |
| Spatial compatibility | Physical and simulated adapters validate against one schema; orientation, units, axial convention, and unknown values remain correct |
| Edge independence | Reflex completes with MCP disconnected and the model idle; event and incident frame are delivered after reconnect |
| Event recovery | Enter/clear between reads are both preserved; duplicate transport events keep one identity; unknown ACP outcomes remain explicit |
| Recomposition | A change to an Objective Purpose updates affected explanations/journeys; a mere file rename does not invent a functional change; source cut and citations remain reproducible |
| Shared participation | Two humans and two agents maintain independent positions, contexts, and delivery histories while reading and contributing to the same functional records |

The unverified items are integration work and deployment evidence, not unspecified semantic mechanisms. The specification identifies the data, behavior, and observable result needed to build and test each boundary.
