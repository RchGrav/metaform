# Feature Blueprint Specification

**State:** draft, 2026-11-07. Fills W-1.4: "What a feature blueprint holds and how agents write it are not specified yet."
**Builds on:** W-5.3 (manifest of ports + `description`), W-5.4 (links), W-5.5 (intent records), W-1.1, W-4.1, W-7.4 (handles), W-9.1/9.3/9.4/9.6, W-11.6.
**Synthesis:** LogicalImpala + HunterRanger (subgraph) + SeriousMagni (archetype/slot endpoints, submit→observe→revise loop, hash reconciliation) + AcuteNitrate (agent-owned metaform, slot addressing, derived assertion layer, handle-grant two-phase check, description restoration, intent copy at instantiation).

## 1. Definition

**B-1.1** A feature blueprint is an **agent-owned, design-time metaform**: an addressable map of *intended* entities, ports, links and assertions, authored and owned by the agent (owner 2026-11-06: "build their own metaform map ... give them ownership of their own metaform"). It is the *writer* of the world graph but a distinct artifact from it. It is stored in the world's LadybugDB (W-3.5) in the agent's own namespace — never the functional map's namespace (W-1.1/W-1.4). No document/YAML blob format: duplicating W-5.3 fields would create a second source of truth and break W-5.6.

**B-1.2** Pipeline (three stages, three owners): **agent-owned map → admin-world test (W-9.1) → admin-gated release (W-9.4/W-9.6)**. A blueprint is *met* when its assertions evaluate true against the live world on a fixed simulation step (W-8.3), never by agent prose.

**B-1.3 Addressing (the namespace answer W-1.4 names).** Design-time entities have no minted ids yet (W-4.1) and cannot use functional-map addresses, so the blueprint addresses draft entities by **slots**: `<blueprint-id>/<slot-name>` and `<blueprint-id>/<slot-name>.<port>`. Links (W-5.4) are written between slot addresses and type-checked at write time against the slot's archetype manifest. At instantiation the server mints entity ids and records a `bindings` map keyed **`(blueprintId, slotName, instantiationId) → entityId`**. The third key is required: a design instantiated twice (two doors from one blueprint) yields two entities per slot, and a `parentBlueprint` fork mints a fresh `instantiationId`. Without it, B-4.1/B-4.2 cannot say *which* instance's hashes and handles they pinned. The *world graph* remains entity-id-grounded (W-5.1); only the design-time map is slot-addressed. Slots are stable across forks even though entity ids change on re-instantiation.

## 2. What a blueprint holds

**B-2.1** Blueprint-level fields: `id`, `name`, `version` (semver of the blueprint itself), `author`, `parentBlueprint` (linear history), `description` (written specification of the whole feature, same style as W-5.3; restores W-5.2's decided description requirement), `intentRefs[]` (W-5.5 records; non-empty), `agent_record` (the audit trail of how the agent wrote and tested it — B-3.5). `status` is restricted to `draft|authored|submitted|superseded` (build/test/release state lives on the build, not the blueprint); `assembly` is *not* held — it is produced at release (W-9.4). No `context_budget` field is held: W-11.6's budget is enforced server-side by the bounded context slice (B-3.2) and the outcome digest (B-3.1), not by an author-maintained counter, which would be unverifiable.

**B-2.2** Per slot: `archetype`/`kind` (content key, W-3.5), `manifest` layer referencing W-5.3 (carrying `name`, `intent`, WIT `type`, `goal`, `function`, **and `description`**), scoped W-5.5 intent record, `links[]` (W-5.4 tuples between `slot.port` endpoints), `build_steps[]` (**typed**, below), `limit_request` (a declaration of *need* under W-6.3, clamped by the server at `submit()` — see B-3.1), `precision` (W-7.3 physics precision, a genuine per-entity setting).

`build_steps[]` is typed, because it is the only field that causes entities to exist and the only one that was prose. Every other field carries a WIT or enum type; an untyped construction step lets a blueprint pass all checks and still not instantiate (W-4.2: "the builder chooses where an instance attaches" — a choice, not prose; W-4.4: joints have limits and motors):

```
{ op:"place",     slot, voxel:(i64,i64,i64) }                         -- W-3.4 grid, W-2.2a spawn
{ op:"attach",    slotA, slotB, joint:<WIT record> }                  -- W-4.4; shape per D-W1
{ op:"link",      slotA.port, slotB.port, kind }                      -- W-8.2 enum
{ op:"grant",     slot, handleKind, targetRef }                       -- W-7.4 (= B-3.1 grant)
{ op:"set_param", scope:"world"|"volume"|slot, param:<WIT record> }   -- W-7.3
{ op:"emitter",   slot, particle:<WIT record> }                       -- W-2.4 particles; never saved (W-3.6)
```

A `build_step` whose `slot` is undeclared is rejected, and `place` requires a coordinate, so an agent cannot produce an uninstantiable blueprint while its assertions pass. `joint`/`param`/`particle` are WIT records from the host interface, validated at write time like a port `type`; their exact shape follows D-W1.

**B-2.2a Owned slots vs external roles (integrates MS-3).** A slot is one of two kinds. An **owned slot** is the default: it names an archetype (W-3.5 content key) that the server instantiates, mints an entity id for, and includes in the release unit. An **external role** is a slot bound to an *existing* entity: it names the target's `worldId`/`entityId` only. Its manifest is **read from the live entity, never declared by the agent** — declaring an expected contract would let the agent's claim drift from the entity's actual manifest, the same failure B-2.3 prevents for selectors, so the type-check would validate against a lie. It is never instantiated, minted, or copied into the release unit (MS-3: "referencing an entity never makes it part of the release unit"). Both kinds produce an `entityId.portName` endpoint after binding, so the same W-5.4 link and WIT type-check machinery applies; the difference is the manifest's source — an archetype's manifest (W-5.3) for an owned slot, the entity's live manifest for an external role. Because the target exists, its manifest is available at write time, so the type-check runs identically and survives to the live world. On an external role, `declare_port` and `place` are **illegal** (it already has a manifest and a position; HunterRanger's narrow rule); `attach`, `link`, `grant`, `emitter` are legal. During authoring and testing the external role binds to an **admin-world** entity (W-9.1); at release it is **rebound and revalidated against the destination manifest** (MS-3). This is the boundary that resolves what modification a blueprint can express: a blueprint may **reference and control** an existing entity (link to its ports, grant it handles) but may **not change its manifest or behavior** — that would edit a manifest the blueprint does not own. If the table wants in-place modification, that is a separate, larger capability; otherwise the external role is the ceiling.

**B-2.3 Layers, resolver, and the three-state split of assertions.** Each slot address carries layers — `intent`, `manifest`, `link`, `assertion`, `provenance` — and a resolver selects them per consumer (D-W10 model). **Resolver scope is settled (D-B4):** the resolver is a *separate instance* from any functional-map resolver. W-1.1 (Decided) says the world system never reads or writes the functional map, so composing layers across both graphs would require the world system to read functional-map layers — prohibited. W-5.1 says the world graph is "modeled on" the metaform technique, not the same instance. Field *shapes* are shared (W-5.3's `goal`/`function`/`intent` keep the functional map's meaning R-3.6, so one agent reader parses both); execution is not. Adopting a resolver for the whole world graph changes which layers a consumer sees; it does not change the derived/stored/server-only split, because pass/fail remains a function of the live world at step n (W-8.3), not of the selected layers. D-W10 therefore splits: the world-side selection question is now specification, and only the agent-side context delivery (W-5.6/W-11.7) remains Open. The assertion layer splits into three states, and the split is forced rather than stylistic:

| Data | State | Written by |
|---|---|---|
| **selector set** | **derived (⧗)** — the legal selectors, a function of the slot manifest (W-5.3) + W-7.2 kinds | nobody; not writable |
| **assertions** | **stored (■)** — `{selectorRef, expected: <WIT value>, step}` or `{selectorRef, expected, window:{from,to}}` | `blueprint.assert`, once; immutable |
| **outcomes** | **server-only (●)** — `{assertionRef, observed, step, verdict}` | evaluation only |

Why not "derived, not stored" as a single statement (which an earlier revision said): (a) the *set of legal selectors* is static, so it is derived and an agent that wants a new one must declare a port — that is what prevents assertion drift from the manifest; (b) `expected` is an agent choice, so it must be stored; (c) pass/fail is a function of the **live world at step n** (W-8.3), not of the manifest — a motor that moved and one that did not have identical manifests and identical selectors, and only a recorded `outcome` separates them. Without (c), `status = tested` is unfalsifiable and W-6.4's safety claim has no evidence. Reachability of `sensor`/`voxel`/`worldparam` selectors is *not* derivable at authoring time: W-7.4 makes the builder grant handles, so those are `pending-handle` until B-3.1's grant resolves them. At least one negative assertion is required. **Assertion timing (resolves D-B2):** the default is a single `step` (exact, deterministic, cheap — adequate when the feature's delay is a known constant, as in the lever-door example's `n+2`). An **optional bounded `window:{from,to}`** expresses temporal properties — "the observable equals `expected` at at least one step s, from ≤ s ≤ to" — for features whose delay is variable or depends on physics (W-4.4 joints/motors) and is not a constant the agent can know without running. The window must be finite; and the server records the observed values across the whole window in `outcomes`, not just the verdict, so a pass stays inspectable (which step matched) and falsifiable. This extends the assertion record without touching the derived/stored/server-only split: `window` selects more steps, it does not change what is derived or who writes it.

**B-2.4** Provenance layer: `author`, `intentRef`, `moduleHash`/`assetHash`, `parentBlueprint`. Feeds W-9.4.

**B-2.5 What a blueprint does not hold.** No minted entity ids (W-4.1 — the server mints them; `bindings` records them afterward, B-1.3). No voxel data (W-3.1: chunk data is region data; the assembly carries what release copies, W-9.4). No WASM or asset bytes (W-3.5: content is keyed by hash, so hashes only). No functional-map addresses or namespaces (W-1.1, W-1.4). No duplicate copy of a W-5.3 manifest (ports are references into the manifest; B-2.2 gives the manifest one owner). No authority of its own: the blueprint names the handles it needs, but holding it grants nothing (MS-4; W-7.4, W-9.6). B-3.4 rejects any of these.

**B-2.6 Modification of existing entities — reference/control allowed, in-place change out of scope.** A blueprint may **reference and control** an existing entity through an **external role** (B-2.2a, MS-3): a slot bound to the existing entity's id, type-checked against its actual manifest at write time, linkable, and grantable. What a blueprint may **not** do is change the existing entity's own manifest or behavior in place — that would edit a manifest the blueprint does not own. To change an existing entity's behaviour, the agent writes a new blueprint whose feature is new-instance-and-link: a new code block + granted handle (W-7.4) + link to the existing entity from outside (the builder's choice, W-4.2). Chain: W-5.5's "builds the entity from that intent" is satisfied because the intent attaches to the new code-block entity the blueprint creates, not a mutated target; W-11.2's "possess and program NPCs" runs through the same grant-plus-link path, not blueprint mutation. **Observable:** binding a slot to an existing entity *as an owned archetype* is rejected at `add_node` (no instantiation of something that exists); binding it *as an external role* via `add_external_role` is accepted and type-checks against the entity's manifest. The legal programmatic route to affect an existing entity is a new code block + granted handle + link. Recorded in D-B7.

## 3. How an agent writes it

**B-3.1** MCP verb set over the agent's own metaform (W-1.4 custom server), each verb a validated edit:

| Verb | Server check |
|---|---|
| `blueprint.open(intentRef)` | Intent exists; agent holds right (W-9.6). Returns **context slice** (B-3.2). |
| `blueprint.add_node(archetype)` | Declares an owned slot; archetype resolves in content key (W-3.5). |
| `content.publish_component(componentBytes, manifest, sourceRef, buildInfo)` | Stores new code outside the blueprint under server-computed hashes; validates component structure, WIT declarations and required host-interface versions. Returns `componentHash` and `manifestHash` (B-3.7). Does not create entities or grant authority. |
| `blueprint.bind_component(slot, componentHash, manifestHash)` | Owned code slot only; pins the published component and its manifest. Requires agreement with the slot's planned ports, including names, directions and WIT types; rechecks incident links and invalidates prior build evidence (B-3.7, MS-2). |
| `blueprint.add_external_role(worldId, entityId)` | Declares an external role (B-2.2a): the target entity exists in the admin world (W-9.1); the slot's manifest is read from that entity, never declared, and type-checks against it at write time. |
| `blueprint.declare_port(slot, entry)` | WIT valid (W-7.1); name unique; `description` carried (W-5.3). Legal **only on slots this blueprint owns**: W-5.3 gives the manifest to the module, so a shared archetype must not gain ports from two blueprints — a differing port set needs a derived content key (recorded as a new module hash, W-9.4). |
| `blueprint.link(slotA.port, slotB.port)` | W-5.4 WIT type check **now**, against **each endpoint's manifest resolved from its slot's source** (B-2.2a): the archetype manifest for an owned slot, the live entity's manifest for an external role. For two owned slots the result is permanent — the minted entity carries the same manifest, so a link that passes here passes after minting. For a link touching an **external role** it is *not* permanent: the live entity's manifest can change before `submit()`, which is what MS-2's dependency fingerprint and MS-3's release-time revalidation exist to catch. Link kind (W-8.1) recorded. |
| `blueprint.assert(resolvedSelector, expected)` | Two-phase check: `port` → declared here; `sensor`/`voxel`/`worldparam` → syntax vs W-7.2 WIT, then marked `pending-handle` (a handle is a build-time grant per W-7.4, not an authoring-time fact). |
| `blueprint.grant(handle, slot, target)` | Builder grants W-7.4 handle; pending selectors resolve. |
| `blueprint.step(op)` | Appends one typed `build_step` (B-2.2). Validates the `op` discriminator against the closed set; `slot`/`slotA`/`slotB` must be declared; `voxel` present for `place` and within y ∈ [−64, 319] (W-2.2); `joint`/`param`/`particle` must type-check against the host-interface WIT record it names (W-7.1); `kind` must be a W-8.2 member. **`place` claims the cell** (B-3.6): refused if the cell holds a material (W-3.4) or a claim held by another submission. |
| `blueprint.declare_limit(slot, request)` | Records `limit_request` (W-6.3 fuel/memory/messages) as a declaration of *need*. It is **not** accepted as an actual budget: W-6.3's limits exist to stop content harming the core (W-2.5, W-6.4), and D-W6 says the values are measured from W-12.1 content, not authored per blueprint. At `submit()` the server clamps every request to the world's W-6.3 limits and records the effective values in the build receipt (MS-1). A request that exceeds the cap is clamped, not fatal; the agent cannot raise the cap (W-9.6). |
| `blueprint.declare_precision(slot, precision)` | Sets W-7.3 physics precision (continuous collision detection, substep count) — a genuine per-entity setting, not a resource budget. |
| `blueprint.submit()` | All links type-check; **every *owned* slot has at least one `place` step** (an external role has none and must not — it is already placed, B-2.2a); assertions non-empty with ≥1 **behavioural** negative (a structural negative such as a refused link does not satisfy this, MS-1); **all `pending-handle` assertions have granted handles**; hashes resolve. **Each `limit_request` is clamped to the world's W-6.3 limits** (B-3.1 `declare_limit`); the effective values are recorded in the MS-1 receipt. Lands in agent map, then admin world (W-9.1) for the observe/revise loop (B-3.3). **Returns an outcome digest, not a full dump** (W-11.6): `verdict`, `first_failure` (only on fail), `counts`, and `outcome_ids` — never one row per assertion per step. |
| `blueprint.outcome(outcomeId)` | Returns one recorded `outcome` (B-2.3) — the pull half of W-11.7, so the agent fetches only the observations it needs and W-11.6's per-word cost stays bounded. |
| `blueprint.release()` | Release right (W-9.4/W-9.6); copies assembly. |

**B-3.2 Context slice (concrete W-5.6/D-W10 answer):** on `open`, return only the intent record, resolved manifest/link layers of concerned slots, and the host catalogue at targeted versions — never a traversal, never the whole blueprint (W-11.6).

**B-3.3 Loop.** `submit()` instantiates in the admin world; server evaluates assertions step by step, records each `outcome` (observed value + verdict, B-2.3), and returns the outcome digest (B-3.1: `verdict`, `first_failure`, `counts`, `outcome_ids`), recording `tests`/`faults` on the agent record. A blueprint is met only if every `outcome.verdict = pass`; without recorded outcomes, "tested" is unfalsifiable. The agent revises via `parentBlueprint` and resubmits. First-pass success is the corner case; the loop is the norm (W-11.3/W-11.4). Submitted versions and stored assertions are immutable.

**B-3.4 Rejection (server-enforced):** empty `intentRefs[]`; WIT mismatch on a slot link; port collision; missing handle for a `pending-handle` assertion (error names the selector); positive-only assertions; any B-2.5 content. Errors as `{field, reason, offending value}`. Writes serialised per blueprint id; conflict → rebase on `parentBlueprint`.

**B-3.5 The agent record (what "how an agent wrote it" leaves behind).** The `agent_record` is the audit trail of the writing process. It holds: (a) `task` — the context slice (B-3.2) actually used, so the record shows what the agent read; (b) `cycles[]` — each submit-to-revise iteration: the submitted version, the observed `outcomes` (B-2.3), and the revision made in response, which makes the loop (B-3.3) inspectable rather than asserted; (c) `code` — the full source of each module the agent wrote, not just hashes, so W-6.4's "generated code is not a safety risk" can be inspected; (d) `decisions[]` — the non-obvious choices with their reasons, so a reviewer can question them. The record lives with the blueprint in the agent's namespace; the hashes of the code in (c) are what B-4.1 pins, and the record is what the admin reviews before release (W-9.6). A blueprint whose `cycles[]` is empty or whose `outcomes[]` contradict its `status` is not releaseable.

**B-3.6 Voxel cell claims (makes MS-5's staging well-defined).** MS-5 says a failed submission "removes or leaves explicitly inactive only that submission's staged content, without undoing unrelated world edits." That presumes staged voxels are distinguishable and reserved, which nothing else in this spec provides. W-3.4 allows one cell to hold one material reference or nothing, so two submissions placing at the same coordinate have no defined outcome.

A cell placed by a submission has three states: `staged(submissionId)`, `active(instantiationId)`, `released`. `place` is refused unless the target cell is empty or already `staged` by the same `submissionId`; a successful `submit()` flips this submission's claims to `active`; MS-5 cleanup drops its `staged` claims, returning the cells to empty. `release()` flips the assembly's claims to `released`.

Chain: MS-5 needs staged content to be identifiable and removable → a voxel cell holds one occupant (W-3.4) → removal must not take another submission's occupant → therefore a claim records its owner and `place` must check it. Observable: two blueprints placing at the same coordinate — the second is refused with `{field:"voxel", reason:"cell staged by <submissionId>"}`; after the first fails and is cleaned up, the second succeeds.

**B-3.7 Authoring new behavior, not only assembling existing behavior (ModularShift).** W-5.5 requires an agent to build a solution from user intent. W-5.3 gives that solution's code module a manifest, while W-3.5 stores code by content hash. Consequently an agent needs a way to obtain a hash for newly written code before `add_node` or submission can reference it. The two operations above provide that missing write path:

1. Read the user's intent and write the module source plus its W-5.3 manifest: entity description and each port's name, direction, WIT type, goal and function. Compile the source into a WebAssembly component targeting the world's supported host interfaces (W-7.1). Compiler selection is outside this specification.
2. Call `content.publish_component`. The server computes the executable component hash from the supplied component bytes and separately hashes the associated manifest. It validates the component format, the manifest's WIT declarations and required host imports. It stores their association; supplied manifest metadata must agree with any port metadata embedded in the component. These checks establish a declared interface, not proof of the code's behavior; behavioral assertions still require execution.
3. For a new slot, use the returned component content key with `add_node`. For an owned draft slot whose `declare_port` edits changed its intended interface, publish the revised component and call `bind_component`. Planned port edits alone never modify an existing shared module. A slot with unbound interface edits cannot be submitted.
4. Submit and test the resulting build through the existing loop. A mismatch between the planned manifest and the published manifest is rejected before instantiation, identifying the slot and differing port. A changed component or manifest requires a successor submitted revision and new evidence under MS-2.

The blueprint holds the returned hashes and references, not the uploaded executable bytes (B-2.5). The agent record distinguishes `sourceHash` (source text), `componentHash` (compiled executable), `manifestHash` and `buildInfo` (compiler/version/options and their input/output association). Source text and compiled WASM are different byte sequences: their hashes are not compared for equality. B-4.1 pins the **tested componentHash**, not sourceHash; source is retained or referenced for inspection. This paragraph corrects B-3.5's shorthand that hashes of the recorded source are the hashes release pins.

**Observable acceptance case:** starting with no module that implements the user's requested lever behavior, the agent can publish one, receive its component hash, add a slot referencing it, link its declared ports and submit a test build. Publishing alone creates no world entity. If the slot declares an outbound boolean `open` port but the published manifest declares `open` as a string, `bind_component` or submission is refused with that port identified. Recompiling after tests produces a new component hash and cannot reuse the old build's passing evidence.

## 4. Integrity / reconciliation (SeriousMagni)

**B-4.1 Hash reconciliation.** At release the server pins the hashes of the *tested* admin-world instance. If provenance hashes differ, release is refused until the blueprint is re-submitted with the tested module; the discrepancy is recorded. Observable: a blueprint whose `provenance.moduleHash` differs from the tested instance cannot be released. This anchors W-6.4's safety claim.

**B-4.2 Handle-set pinning.** The tested instance's handle set is pinned into the assembly alongside hashes (W-9.4), so a live-world release cannot run code whose assertions passed only under grants that do not exist there. At release the server checks the pins (hashes + handle set match the tested instance, per B-4.1) and does **not** re-evaluate behavioural assertions: the live world has different entities, adjacencies and steps than the admin-world test, so re-running `outcomes` there would test the destination, not the blueprint. `release()` therefore copies an already-tested build; the evidence for it is the recorded `outcomes` (B-2.3), not a fresh run. Resolving D-B6 on this wording.

**B-4.3 Intent copy.** At instantiation the server copies each slot's intent record onto the minted entity (W-5.5 "stays with the entity"), and the intent record ids ride in the W-9.4 assembly. After the blueprint is superseded or deleted, `resolve(entityId)` still returns a non-empty intent record.

## 5. Worked example

Lever door: intent "lever opens door on use" (W-5.5); slots `bp-7f3/lever` (code-block archetype) and `bp-7f3/door` (imported archetype); `use` inbound port (W-7.5); link `lever.open → door.open` written as `bp-7f3/lever.open → bp-7f3/door.open`, type-checked now against archetype manifests; assertion `{kind:"port", selector:"bp-7f3/door.open", expected:true, step:n+2}` plus a negative assertion; build steps in the typed form of B-2.2 — `{op:"place", slot:"bp-7f3/lever", voxel:[0,-63,0]}`, `{op:"place", slot:"bp-7f3/door", voxel:[1,-63,0]}`, `{op:"attach", slotA:"bp-7f3/lever", slotB:"bp-7f3/door", joint:{kind:"revolute", axis:"x", limits:{..}}}`, `{op:"link", ...}`; submit tests in the admin world; release pins tested hashes + handle set into the assembly (W-9.4). Note the joint is a WIT record, not the word "joint": W-4.2 makes the attachment a builder choice and W-4.4 gives joints limits and motors, so the blueprint must state the kind and axis or the server has to guess.

In-place manifest/behaviour editing is out of scope; effecting change goes through a new code block + granted handle + link (B-2.6). |


## ModularShift addition: build receipts and dependency validity

**Status:** Proposed. These rules refine blueprint submission and release. They add no functional-map namespace or core content kind.

**MS-1 Evidence identifies an exact build.** Submission returns a server-issued build receipt containing the blueprint id/revision, slot-to-entity bindings, instantiated assembly id, world id, module/asset/manifest hashes and relevant world configuration. A test result names that receipt, the acceptance criterion id, fixture/starting state, stimuli, observations and verdict. Merely storing assertions or claiming tests passed does not establish a tested feature. Release requires passing evidence for every required criterion on the same build. A rejected type-mismatched link proves a validation rule, not that a valid machine works.

**MS-2 Dependencies cannot silently change.** Validation records a dependency fingerprint: pinned WIT package definitions, archetype manifests, referenced graph revisions, hashes and relevant world settings. Submission rechecks it. A changed dependency returns a diagnostic identifying the changed references; the agent rereads those records, revises, validates and retests. A module, manifest, binding, assertion or relevant world-setting change invalidates dependent evidence. Historical receipts remain inspectable. An agent cannot replace provenance hashes in an immutable submitted revision; it creates and tests a successor revision.

**MS-3 Local and external ownership are explicit.** A planned slot is either owned content to instantiate or an external role requiring a binding. An external binding records its world/entity id; the **server** additionally records the target's manifest hash as a dependency fingerprint (MS-2) at validation time. The agent declares **no** expected manifest contract: B-2.2a forbids it, because an agent-declared contract could drift from the entity's actual manifest and the W-5.4 type check would then validate against a lie. A server-read snapshot cannot drift, since it is the entity's manifest at that revision, and it is what MS-2's dependency recheck compares against. Missing bindings are permitted in drafts and block building. An assembly copies owned content only. On release, internal endpoints, joint targets and intent attachments are remapped to destination ids; external roles are explicitly rebound and revalidated against destination manifests. Two instantiations receive separate entity-id mappings. Referencing an entity never makes it part of the release unit.

**MS-4 Ownership grants no world authority.** Owning an agent map or blueprint permits editing that artifact. It grants no handle to actuate referenced entities or alter volumes. Required W-7.4 handles are declared dependencies and must be granted within W-9.6. Instantiation and release never serialize or clone authority. Release may be performed by any holder of the release capability, held by the admin by default. Current grants and destination bindings are checked again at release.

**MS-5 Submission is retryable and staged.** Submission accepts a request id; retrying the same request returns the prior receipt rather than creating duplicate entities. The server resolves all slots and links before activating any feature module. Failure returns diagnostics and removes or leaves explicitly inactive only that submission's staged content, without undoing unrelated world edits. The response identifies staged resources requiring cleanup. Build validation respects W-2.3: an admin void without a generator cannot receive chunk writes. Describing voxel data as an entity component cannot bypass this rule.

**MS-6 Intent remains attributable.** Every referenced intent is pinned by record id and revision and retains its author and original text. Agent interpretation and assumptions are attributed additions, never replacements for user intent. Acceptance criteria reference the intent clauses they demonstrate; built entities and released assemblies retain the applicable intent references (W-5.5). An unresolved ambiguity that changes observable behavior or required authority blocks readiness. Routine implementation choices may proceed with a recorded rationale.

These checks belong to the server. The agent's write loop is: preserve intent → declare criteria → draft slots, ports and links → validate → instantiate → exercise and observe criteria → revise/retest as necessary → hand the exact tested build to a release-capability holder. The loop requires no particular MCP implementation and does not settle perception or general context delivery in D-W7/D-W10.

### Inspectable acceptance cases

These are proposed implementation checks, not claims that a server exists or has passed tests.

| Case | Required result |
|---|---|
| Submit a controller/door blueprint twice with the same request id | One staged assembly, same binding map and receipt |
| Instantiate it under a new request id | Distinct entity ids; each link resolves within its own assembly |
| Change its module after door tests pass | Old evidence cannot qualify the changed build for release |
| Change an external target manifest after validation | Build reports the changed dependency fingerprint (MS-2/MS-3) and creates no active partial machine; the agent never declared a contract that could disagree with the entity |
| Release with an unresolved external target | Rejected with that role identified; unrelated entities are not copied |
| Clone a blueprint requesting an actuator handle | The clone has a request, not a grant |
| Write voxels into an admin void without a generator | Rejected under W-2.3 |
| Test only rejection of mismatched port types | Structural negative case passes; door-opening behavior remains unproved |
| Agent refines user intent | Original author/text/revision survives; interpretation is separate |

W-5.4 establishes structural compatibility; W-5.5 supplies behavior to demonstrate. Neither proves that a later module hash or differently bound destination behaves like the tested build.
