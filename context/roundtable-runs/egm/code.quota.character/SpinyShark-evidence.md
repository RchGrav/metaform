# SpinyShark: corrections supported by the supplied code

- **A review can consume recovery.** A busy seat can complete work and become Idle without clearing `recovery_due` (`engine.rs:689`). If fewer than two seats are free, `give_floor` may ask that now-free seat to review (`537–550`). `offer` gives that review the pending recovery limit and clears the flag (`595–605`). The claim in `feralsteel-turn2.md` that this is unreachable confuses being busy when skipped with remaining busy forever. A review is a discussion contribution, so this consumption matches the stated contract.
- **Restoring a line from `seat.limit` would advertise the previous limit.** `offer` computes the new limit at `engine.rs:596`, builds the prompt at 597, and stores `seat.limit` at 604. Pass the computed limit into the builder and use that same value for enforcement; otherwise the first recovery prompt and its successor advertise stale values.
- **Do not silently introduce `max(base, recovery)`.** The current rule specifies the recovery limit once, not a minimum. A base of 5,000 followed by a recovery of 1,024 exposes the difference. My recommendation is the fixed recovery cap, independently of base, with “larger” removed from the description. This is a resolution recommendation, not a new owner quotation.
- **Starting tool work is distinct from a missed later opportunity.** `on_tool` releases a Floor prompt and counts its opportunity as SkippedWorking, but that same prompt still finishes and submits its reply (`engine.rs:670–675, 703–704`). Arming recovery there would grant it even if no subsequent turn is missed. Define the recovery trigger as an actual scheduled busy skip rather than deriving it from an accounting enum.
- **Not every block consumes another opportunity.** `submit` returns Failed, but `resolve_reply(..., true)` does not count another opportunity for Working/Reviewing completions (`turn.rs:94–122`; `engine.rs:703–704`). Document this qualification.
